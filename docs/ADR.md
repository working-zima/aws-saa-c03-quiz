# Architecture Decision Records

## 철학

읽는 시간이 긴 학습 앱이다. 기능을 늘리기보다 **개념 본문이 잘 읽히는 것**을 우선한다.
서버 없이 정적 파일로 끝나는 구조를 유지한다. 외부 의존성은 이유가 있을 때만 추가한다.

---

### ADR-001: Next.js가 아니라 Vite + React SPA
**결정**: Vite 5 + React 18 + TypeScript로 순수 클라이언트 SPA를 만든다.
**이유**: 런타임에 서버가 할 일이 없다 — 데이터는 정적 JSON이고 상태는 localStorage다.
개발 환경 Node가 18.17.1이라 Next.js 15(18.18.0 이상 요구)는 애초에 돌지 않는다.
**트레이드오프**: SSR·SEO·서버 라우트를 포기한다. 학습 앱이라 검색 유입이 목적이 아니므로 손실이 작다.
나중에 서버가 필요해지면 마이그레이션 비용을 그때 낸다.

### ADR-002: 문제 은행은 빌드 전에 확정한 정적 JSON
**결정**: 개념·문제 데이터를 harness step에서 한 번 생성해 `src/data/*.json`으로 커밋한다.
런타임 AI 생성을 하지 않는다.
**이유**: 런타임 생성은 매번 정답 신뢰도가 달라진다. 학습 앱에서 틀린 해설은 안 만드느니만 못하다.
고정된 JSON은 사람이 검수할 수 있고, API 키·비용·지연시간이 전부 사라진다.
**트레이드오프**: 문제가 732개로 고정된다. 다 풀면 새 문제가 없다.
문제를 늘리려면 데이터 파일을 고치고 다시 배포해야 한다.

### ADR-003: 사용자 상태는 localStorage만
**결정**: 진행률·정오답 기록을 localStorage에 저장한다. 계정도 서버도 두지 않는다.
**이유**: 정적 호스팅만으로 배포가 끝난다. 개인 학습 기록이라 공유·동기화 요구가 없다.
**트레이드오프**: 기기 간 동기화가 안 되고, 브라우저 데이터를 지우면 진행률이 사라진다.
시크릿 모드에서는 저장이 실패할 수 있으므로 읽기·쓰기를 전부 try/catch로 감싸고,
저장소가 없어도 앱은 정상 동작해야 한다.

### ADR-007: GitHub Pages 배포 — HashRouter + 상대 경로 base
**결정**: `vite.config.ts`에 `base: './'`를 두고, 라우터는 `HashRouter`를 쓴다.
URL은 `/#/topic/s3-storage-classes` 형태가 된다.
**이유**: GitHub Pages는 정적 파일 서버라 SPA fallback이 없다. `BrowserRouter`로 만들면
`/topic/s3`에 직접 들어가거나 새로고침할 때 404가 난다. 흔한 우회책인 `404.html` 복사 트릭은
브라우저가 404를 한 번 받고 리다이렉트하는 구조라 깜빡임이 생기고, 저장소 이름이 바뀌면
`base` 설정도 따라 고쳐야 한다. `HashRouter` + `base: './'`는 **배포 설정이 0**이고
저장소 이름·서브경로에 무관하게 동작한다.
**트레이드오프**: URL에 `#`이 붙어 보기 나쁘고 검색엔진 색인에 불리하다.
개인 학습 앱이라 둘 다 비용이 작다. 나중에 커스텀 도메인을 붙이면 `BrowserRouter`로 바꿀 수 있다.

### ADR-004: react-router-dom을 쓴다
**결정**: 화면 전환을 `useState`가 아니라 URL 라우팅으로 처리한다.
**이유**: 개념을 읽다가 문제로 갔다가 다시 개념으로 돌아오는 흐름이 핵심이다.
브라우저 뒤로가기가 동작하지 않으면 이 흐름이 깨진다. 주제 URL을 북마크할 수도 있어야 한다.
**트레이드오프**: 의존성이 하나 늘고, 정적 호스팅 시 SPA fallback 설정이 필요하다.
상태 기반 전환보다 초기 코드가 조금 많지만, 뒤로가기를 직접 구현하는 것보다 싸다.

### ADR-005: 4지선다 단일정답으로 고정
**결정**: 모든 문항은 보기 4개, 정답 1개다. 복수정답·순서맞추기 등을 만들지 않는다.
**이유**: 이 앱의 문제는 시험 재현이 아니라 개념 점검 수단이다.
형식이 하나면 채점 로직과 UI가 단순해지고, 문제 은행 품질에 집중할 수 있다.
**트레이드오프**: 실제 SAA-C03에 나오는 복수정답 유형에는 대비되지 않는다.
시험 직전 실전 감각은 다른 자료로 보완해야 한다.

### ADR-006: 원본 텍스트를 유일한 출처로 삼는다
**결정**: 개념 본문과 문제는 `docs/source/concepts-raw.md`에서만 만든다.
모델이 알고 있는 AWS 지식을 끌어와 보강하지 않는다.
**이유**: 원본은 사용자가 고른 학습 자료다. 앱이 원본에 없는 걸 가르치면
"이 자료 한 권으로 끝낸다"는 전제가 깨지고, 검수 기준도 사라진다.
**트레이드오프**: 원본이 다루지 않는 주제는 앱에도 없다. 원본의 오류도 그대로 따라간다.
명백한 오탈자는 추출 단계에서만 교정하고, 내용 보강은 하지 않는다.

### ADR-008: 두 번째 출처로 문제 덤프 해설을 인정한다 (ADR-006 개정)
**결정**: `docs/source/concepts-raw.md`에 더해 `docs/source/exam-gaps.md`를 출처로 인정한다.
후자는 `[pdf] 예상 기출 문제 163문제 & 해설지` 163문항의 해설에서, **개념 원문에는 없는데
정답 근거로 쓰인 것**만 추려 정리한 문서다. 두 출처 밖의 내용은 여전히 만들지 않는다.
**이유**: 개념 원문만으로는 답을 고를 수 없는 문항이 실제로 존재한다.
"CloudFront에 붙일 ACM 인증서는 us-east-1에서 발급한다", "RDS 자동 백업 보존은 최대 35일",
"객체 잠금은 버전 관리가 켜져 있어야 한다" 같은 것들이다. 이걸 앱이 다루지 않으면
"이 자료로 시험을 준비한다"는 전제가 개념 쪽에서만 성립하고 문제 쪽에서 깨진다.
**트레이드오프**: 출처가 둘이 되면서 검수 기준이 하나 늘었다. 대신 exam-gaps.md의 모든 항목에
`[섹션 #문항 pP]` 형식으로 덤프 원문 인용을 붙여, 어느 해설에서 왔는지 되짚을 수 있게 했다.

한 가지 예외를 둔다. **덤프 해설이 실제 AWS 동작과 명백히 어긋나는 항목은 그대로 옮기지 않는다.**
ADR-006은 "원본의 오류도 그대로 따라간다"고 했지만, 개념 원문은 사용자가 고른 학습 자료인 반면
덤프 해설은 정답 판정 근거라서 성격이 다르다. 틀린 사실을 개념으로 가르치면 학습 앱의 목적 자체가 깨진다.
수정하거나 제외한 항목은 `exam-gaps.md`의 "원본 수정 이력" 절에 덤프 원문과 함께 남긴다.
현재 3건이다. 이 예외는 **명백한 사실 오류에만** 적용하고, 모델이 아는 AWS 지식으로
내용을 보강하는 용도로 쓰지 않는다.

### ADR-009: 개념 본문을 직접 쓴 문장으로 재작성한다 (ADR-006 표현 규칙 개정)
**결정**: 0-mvp에서 만든 개념 97개의 `summary`·`paragraphs`를 새로 쓴 문장으로 교체한다.
`id`·`name`·개념 개수·주제 배치는 건드리지 않는다. 1-exam-gaps에서 만든 개념 77개는 대상이 아니다.
**이유**: 원본 `docs/source/concepts-raw.md`는 외부 참고 자료의 추출 전문이고, 0-mvp 개념 본문은
"원본의 표현과 어투를 유지한다"는 당시 규칙 때문에 사실상 그 전사본이다. 저장소를 공개하면
원문이 그대로 공개된다. 1-exam-gaps 개념 77개는 덤프 해설을 읽고 재구성해 쓴 문장이라
성격이 다르고, 그래서 이번 대상에서 빠진다.

**의미는 바꾸지 않는다.** 바꾸는 것은 표현·문장 구조·문단 구성뿐이다. 원본에 있던 사실이
빠져도 안 되고, 모델이 아는 AWS 지식을 끌어와 보태도 안 된다. 출처를 두 파일로 한정한
ADR-006·ADR-008은 그대로 유효하다. 이 ADR이 개정하는 것은 **표현 규칙 하나**다.

**id와 name을 고정하는 이유**: 문항 169개가 `conceptId`로 이 개념들을 참조하고,
`src/data/data.test.ts`가 개념 개수와 주제 메타데이터를 검증한다. 본문만 교체하면
참조 무결성과 기존 테스트 675줄이 그대로 산다. 개념을 쪼개거나 합치면 둘 다 깨진다.

**검증**: `scripts/check-verbatim.mjs`가 공백·문장부호를 지운 뒤 원본과 32자 이상 연속
일치하는 구간을 잡아낸다. 임계값 32자는 1-exam-gaps 개념 77개가 전부 통과하는 최소값으로,
"같은 사실을 한국어로 쓰면 이 정도는 자연히 겹친다"는 실측 하한선이다.
이 검사는 하한선이지 완료 증명이 아니다. 본문이 짧으면 전사여도 통과한다.
**이 검사는 손으로 돌린다** — `npm test`·`npm run build`에 엮여 있지 않다. 비교 대상인
`concepts-raw.md`가 gitignore로 로컬에만 있어서 clone한 환경에는 없기 때문이고, 그래서
원본이 없으면 실패가 아니라 건너뜀(exit 0)으로 끝난다. 원본을 가진 사람이 개념 본문을
고친 뒤 `node scripts/check-verbatim.mjs`를 직접 돌리는 것이 이 검사의 유일한 실행 경로다.
**이 검사가 무엇을 보는지는 ADR-025가 좁혔다** — `name`은 보지 않고, 겹친 구간에 한글이
한 글자도 없으면 넘긴다. 임계값 32자는 그대로다.

**트레이드오프**: 원본의 어투와 암기 요령이 사라진다. 사실은 남기므로 학습 가치는 유지되지만
"원문을 그대로 읽는 느낌"은 없어진다. `sourcePages`는 죽은 필드가 되더라도 유지한다 —
제거하면 타입·테스트·컴포넌트를 함께 고쳐야 해서 재작성 범위를 넘어선다.

### ADR-010: 일반 IT 용어의 한 줄 풀이는 출처 제한의 예외로 둔다 (ADR-006·ADR-008·ADR-009 예외)
**결정**: `MFA`, `NFS`, `FTP`, `DDoS`, `엔드포인트`처럼 **AWS 고유 사실이 아닌 일반 IT 용어**에 한해,
풀네임과 한 줄 풀이를 두 원본 파일에 근거가 없어도 개념 본문에 쓸 수 있다.

**이유**: 개념 182개를 훑어보면 이런 용어 13종이 풀이 없이 쓰인다. 원본 자료는 독자가
이 정도는 안다고 전제하고 쓰였지만, 이 앱은 "개념을 읽고 바로 확인 문제를 푸는" 학습 도구라
`NFS 프로토콜만 지원한다`에서 막히면 그 문단 전체가 읽히지 않는다. 원본을 확인해 보니
`FTP`·`JWT`·`DDoS`가 무엇인지는 두 출처 어디에도 없다. 규칙을 그대로 두면 이 문제를 고칠 방법이 없다.

**이 예외가 ADR-009의 두 가지 금지와 충돌하지 않는 이유**:
- *외부 자료 전사 금지* — 원본에 없는 내용이므로 전사할 원문 자체가 없다.
- *모델이 아는 AWS 지식 보강 금지* — 이 금지는 시험 정답 판정에 영향을 주는 AWS 동작을
  창작하지 말라는 뜻이다. `MFA는 다중 인증이다`는 AWS 동작이 아니라 용어의 뜻이고,
  어떤 문항의 정답도 바꾸지 않는다.

**경계 — 무엇이 예외가 아닌가**: 판정 기준은 **"이 사실이 어떤 문항의 정답 근거가 될 수 있는가"**다.
될 수 있으면 예외가 아니고, 두 출처가 필요하다. `Glacier의 조회 시간`, `ACM 인증서의 리전`,
`ALB가 지원하는 프로토콜`은 전부 예외가 아니다. 서비스의 사양·제약·비교는 AWS 고유 사실이다.
예외는 **서비스 바깥의 일반 용어가 무엇을 가리키는지**에만 적용한다.
`Reader Endpoint`가 이 경계의 예다. **엔드포인트가 접속 주소를 뜻한다**는 것은 예외로 쓸 수 있지만,
**Aurora의 Reader Endpoint가 읽기 전용 복제본에 부하를 분산한다**는 것은 AWS 고유 사실이라 예외가 아니다.
후자를 본문에 쓰는 근거는 이 ADR이 아니라 `docs/source/exam-gaps.md`의 덤프 인용이다.

**형태**: 본문 문장 안에 인라인으로 넣는다. 용어집 페이지나 툴팁을 만들지 않는다.
읽던 자리에서 해결되는 것이 목적인데 페이지를 옮기면 그 목적이 깨지고, 툴팁은 모바일에서
터치 처리가 까다롭다. 한 용어는 **처음 등장하는 개념에서 한 번만** 풀이하고 되풀이하지 않는다.

**개념 구조는 그대로다.** `id`·`name`·개념 개수·주제 배치·`summary`를 바꾸지 않고
`paragraphs`에 문장을 더하기만 한다. `summary`를 제외하는 이유는 UI에서 개념 제목 아래
작은 글씨로 렌더되는 한 줄 요약이라, 괄호 풀이가 들어가면 요약 구실을 못 하기 때문이다.
`scripts/check-structure.mjs`가 이 범위를 강제한다.

**트레이드오프**: 출처 밖 문장이 본문에 들어가므로 "두 파일만 읽으면 검수가 끝난다"는 성질이
깨진다. 대신 대상을 13종으로 한정해 목록을 `phases/13-term-gloss/step0.md`에 남기고,
`src/data/data.test.ts`가 각 풀이의 존재를 개념 단위로 검증한다. 목록을 늘리려면 이 ADR을
다시 손대야 한다 — 슬금슬금 늘어나는 것을 막기 위해서다.
12종이 13종이 된 것은 phase 13을 **실행하기 전에** `엔드포인트`가 빠진 것을 발견해 확정한 결과다.
실행이 끝난 뒤 하나씩 덧붙인 전례가 아니다.

### ADR-011: 문항과 보기의 순서를 열 때마다 섞는다
**결정**: 확인 문제 화면에 들어갈 때 그 주제의 문항 순서와 각 문항의 보기 4개 순서를
무작위로 섞는다. 섞은 결과는 그 화면에 머무는 동안 고정이고, 화면을 다시 열면 다시 섞는다.
순서를 저장하지 않는다.
**이유**: 이 앱은 같은 주제를 여러 번 풀게 되어 있다. 복습 화면이 오답이 가리키는 개념으로
되돌려 보내고, 진행률도 주제 단위로 다시 점검하는 것을 전제한다. 순서가 고정이면 두 번째
풀이부터는 문제를 읽지 않고 "세 번째 문항의 두 번째 보기"라는 자리로 답하게 된다.
그 시점부터 확인 문제는 개념 점검이 아니라 배열 암기가 된다.
**구현 방식 — 새 `Question`을 만든다**: 보기를 섞을 때 `choices`를 재배열하고 `answerIndex`를
그 보기가 옮겨 간 위치로 갱신한 **새 `Question` 객체**를 돌려준다. 원본 인덱스와 화면 인덱스의
매핑을 따로 들고 다니지 않는다. 이유: `Question` 타입과 `isCorrect(question, choiceIndex)`가
그대로 유지되고, 화면은 자기가 받은 문항만 보면 된다. 매핑을 두면 채점·해설 표시·
`answers[questionId]` 기록 세 곳이 각자 변환해야 하고, 한 곳만 빠뜨려도 조용히 틀린다.
**저장 형식은 그대로다**: `Progress`에 남는 것은 `answers[questionId]`의 정오답 boolean이고
questionId는 순서와 무관하다. `version`을 올릴 일도, 기존 저장분을 마이그레이션할 일도 없다.
**트레이드오프**: 새로고침하면 같은 주제라도 다른 순서가 나오므로 "아까 그 3번 문제"로
되짚을 수 없다. 되짚기는 푸는 동안의 이전 문항 화살표로만 가능하고, 그 범위는 ADR 밖
UI 규칙(UI_GUIDE "문항 사이 이동")에 이미 정해져 있다. 순서를 저장하면 되짚을 수 있지만
그러려면 `Progress`를 늘려야 하고, 얻는 것보다 비싸다.
**해설·문제문이 보기 위치를 가리키지 않는 것이 전제다.** `questions.json`의 어떤 문항도
"위의", "1번 보기" 같은 표현을 쓰지 않는다(732문항 확인). 앞으로 문항을 추가할 때도
보기를 위치로 가리키지 마라 — 섞이는 순간 해설이 거짓이 된다.

### ADR-012: 전체 문항에서 뽑는 랜덤 세트를 둔다
**결정**: 주제와 무관하게 **전체 문항을 섞어 앞에서 N개**를 낸 세트를 푸는 화면을 둔다.
N은 시작 화면에서 10 / 20 / 30 중 고른다. 제한시간·합격 기준·점수 저장은 두지 않는다.
문항을 푸는 화면·조작·기록은 주제별 확인 문제와 **완전히 같다.**
**이유**: 주제별 확인 문제에는 "이 주제의 문제"라는 맥락이 항상 힌트로 붙는다.
S3 주제에서 푸는 동안에는 보기에 낯선 서비스가 있어도 답이 S3 계열이라는 것을 이미 안다.
주제 이름 없이 마주해야 서비스를 실제로 구분하는지 드러난다.
PRD가 제외한 것은 **시험 리허설**(제한시간·점수 산출·합격선)이지 주제 경계를 넘는 점검이 아니다.
그 셋을 넣지 않는 것이 이 결정의 경계다.
**뽑기에 가중치를 두지 않는다**: 오답·미풀이를 우선하는 표본을 만들지 않는다. 이유가 둘이다.
`/review`가 이미 오답이 가리키는 개념을 개념 단위로 모아 보여주므로 역할이 겹치고,
진행 상태에 따라 표본이 달라지면 "무작위로 뽑는다"는 화면의 약속이 어긋난다.
**세트를 저장하지 않는다**: ADR-011과 같다. 화면에 머무는 동안 고정이고 다시 열면 다시 뽑는다.
`Progress`에 남는 것은 여전히 `answers[questionId]` 하나뿐이라, 랜덤 세트에서 푼 문항도
그 문항이 속한 주제의 진행률에 그대로 반영된다. **랜덤 세트 전용 기록을 만들지 마라** —
점수 이력을 남기는 순간 이 앱은 모의고사가 되고 `Progress`의 `version`을 올려야 한다.
**문항 수는 URL에 둔다**: `/random/:count`. 새로고침해도 같은 분량으로 다시 뽑히고,
"20문항짜리"를 북마크할 수 있다. 허용값(10·20·30) 밖의 값은 시작 화면으로 되돌린다 —
`/random/999`로 246문항 전부가 나오는 경로를 열어두지 않는다.
**트레이드오프**: 문항 수가 많은 주제가 더 자주 뽑힌다(16문항짜리가 8문항짜리의 두 배).
주제별로 균등 배분하면 이건 사라지지만 10문항을 고를 때 20개 주제 중 절반이 통째로 빠진다.
어느 쪽도 완전히 고르지 않으므로 규칙이 단순한 쪽을 택한다.
세트가 겹칠 수 있는 것도 받아들인다 — 246문항에서 30개를 뽑으므로 연달아 풀면 겹친다.

### ADR-013: 검색은 개념 단위로 연다 (PRD "검색 제외" 개정)
**결정**: 개념과 주제를 찾는 검색 화면(`/search`)을 둔다. 검색 대상은 개념 이름 · 한 줄 요약 ·
개념 본문 · 주제 제목 넷이고, **문항은 대상이 아니다.** 헤더에 진입 링크를 두되 확인 문제
화면에서는 렌더하지 않는다.
**이유 — 제외 사유가 더는 대상을 덮지 못한다**: PRD의 제외 사유는 "20개 주제는 목록으로
훑는 게 더 빠르다"였다. 그 문장이 맞는 대상은 주제 20개다. 그런데 지금 그 20개 안에 개념이
182개 들어 있고, 개념 이름은 목록 어디에도 나오지 않는다. "Aurora가 어느 주제였더라"를
풀려면 주제 제목에서 서비스 이름을 역추적해야 하는데, 제목은 `Aurora·DynamoDB·ElastiCache`
처럼 **대표 서비스만 이어 붙인 것이라 나머지 개념은 제목에 아예 없다.** 훑기가 빠른 것은
주제고 못 찾는 것은 개념이다. 제외 사유의 범위 밖이므로 새로 결정한다.
주제 20개를 목록으로 훑는다는 판단 자체는 그대로다 — 주제 목록에 필터를 붙이지 마라.
**문항을 검색 대상에서 뺀다**: 문제문을 찾을 수 있게 하면 검색 결과가 그 문항의 존재와
문맥을 미리 알려준다. 해설까지 대상에 넣으면 정답이 그대로 노출된다. 확인 문제는 개념을
읽은 직후 스스로 점검하는 자리이고(PRD 핵심 기능 3), 그 앞에 답을 흘리는 경로를 만들면
기능 자체가 무의미해진다. **`questions.json`을 읽는 검색 코드를 넣지 마라.**
**질의는 토큰 AND 매칭이다**: 질의를 공백으로 쪼개 **모든 토큰**이 들어 있는 항목만 낸다.
대소문자는 무시하고, 본문에 든 `**강조**` 마커는 지운 뒤 비교한다. 이유: 통짜 부분 문자열
매칭이면 `s3 암호화`처럼 사이에 다른 말이 낀 질의가 전부 빗나가고, 마커를 남겨두면
`**장기** 보관`이 `장기 보관`에 걸리지 않는다. 형태소 분석기·퍼지 매칭·외부 검색 라이브러리를
쓰지 마라 — 182개 개념을 매번 훑어도 사람이 못 느낄 양이고, 의존성을 늘릴 이유가 없다.
**순위는 필드 우선순위 하나로 정한다**: `개념 이름 → 주제 제목 → 한 줄 요약 → 개념 본문`.
같은 항목이 여러 필드에서 걸리면 가장 앞선 필드 하나로만 센다. 점수 함수(빈도·위치 가중치)를
만들지 마라. 이유: 결과가 왜 그 순서인지 사람이 설명할 수 있어야 하고, 이 규모에서 점수화는
정확도를 올리는 대신 디버깅만 어렵게 한다.
**검색 결과는 주제 상단으로 보낸다**: 개념이 있는 위치로 정확히 점프하지 않는다. 이유:
`Layout`이 라우트 전환마다 맨 위로 되돌리는 계약을 갖고 있고(ARCHITECTURE "화면 전환 시
스크롤", 실측값으로 확정된 규칙이다), 앵커 이동은 그 계약과 정면으로 부딪힌다.
대신 **결과 카드에 개념의 한 줄 요약을 함께 싣는다** — 목록만 보고도 "이게 그거였다"가
확인되면 점프의 값어치가 크게 줄어든다.
**트레이드오프**: 개념이 20개 가까이 든 주제에서는 착지 후 눈으로 찾아 내려가야 한다.
앵커 이동이 정말 필요해지면 스크롤 계약을 다시 재는 별도 결정으로 다룬다.
검색은 진행률·복습과 달리 **아무 상태도 남기지 않는다** — 최근 검색어를 localStorage에
저장하지 마라. `Progress`의 `version`을 올릴 일이 없어야 한다.

### ADR-014: 용어 풀이 목록에 TTL·라운드 로빈을 더한다 (ADR-010 개정)
**결정**: ADR-010이 13종으로 못 박은 일반 IT 용어 풀이 목록에 `TTL`과 `라운드 로빈`을 더해
**15종**으로 한다. 아울러 이미 목록에 있던 `TCP·UDP` 풀이에 **둘의 차이**를 한 문장 덧붙인다.
목록이 ADR-010의 트레이드오프대로 `phases/13-term-gloss/step0.md`에 있었으므로, 늘어난
두 항목은 여기에 적는다.

- `compute-delivery.cloudfront-ttl` 문단 0 앞 — `TTL(Time-to-Live)은 캐싱한 사본을 얼마 동안 그대로 써도 되는지 정해 둔 유효 시간이다.`
- `compute-delivery.sticky-session-tradeoff` 문단 1 — `끄면 요청을 인스턴스에 차례대로 돌아가며 넘기는 라운드 로빈 방식이 되어 부하가 고르게 분산된다.`
- `compute-delivery.elb` 문단 1 뒤 — `TCP는 보낸 데이터가 빠짐없이 도착했는지 확인하고 빠진 것은 다시 보낸다. UDP는 그 확인을 생략해 더 빠른 대신 일부가 유실될 수 있다.`

**이유**: 사용자가 개념만 읽으며 학습하다 이 세 자리에서 막혔다고 알려왔다. ADR-010이 예상한
그대로의 상황이다 — 원본 자료는 독자가 이 정도는 안다고 전제하고 썼지만, 이 앱은 개념을 읽고
바로 확인 문제를 푸는 학습 도구라 여기서 막히면 그 문단이 읽히지 않는다. `TTL`은 개념 이름과
한 줄 요약에까지 풀이 없이 들어가 있었고, `라운드 로빈`은 스티키 세션을 끈 결과를 설명하는
유일한 단어인데 뜻이 없었다. `TCP·UDP`는 풀이가 있었지만 어느 계층의 규약인지까지만 말해
둘의 차이를 알려주지 않았고, 그래서 `NLB가 둘을 모두 다룬다`가 이름표로만 읽혔다.

**ADR-010의 경계를 넘지 않는다**: 판정 기준은 "이 사실이 어떤 문항의 정답 근거가 될 수 있는가"다.
셋 다 서비스 바깥의 일반 용어이고, 관련 문항 `q193`(캐시 무효화) · `q191`(스티키 세션) ·
`q080`(NLB)의 정답은 모두 서비스나 기능 이름이라 용어의 뜻이 답을 바꾸지 않는다.
`형태`도 ADR-010과 같다 — `paragraphs`에만 인라인으로 넣고, 처음 등장하는 개념에서 한 번만
풀이하며, 용어집 페이지나 툴팁을 만들지 않는다.

**목록이 슬금슬금 늘지 않게 하는 장치는 그대로다**: 늘리려면 이 ADR을 또 고쳐야 하고,
`src/data/data.test.ts`의 `termGlosses`가 각 풀이의 존재와 **중복 없음**을 개념 단위로 검증한다.
사용자가 학습 중에 막힌 자리를 짚어준 경우에만 목록을 늘린다 — 미리 훑어 후보를 늘리지 마라.

**함께 고친 것 — 이 ADR의 예외가 아닌 손질**: `compute-delivery.global-accelerator-protocols`의
`둘의 갈림길은 "캐싱할 콘텐츠인가, 가속할 연결인가"다`를 구체적인 기준으로 다시 썼다.
용어 풀이가 아니라 ADR-009가 이미 허용하는 본문 문장 손질이고, 새 사실을 넣지 않았다 —
`이미지나 파일`은 `compute-delivery.cloudfront`에, `연결이 지나는 경로`는 같은 개념 문단 0의
`가장 가까운 AWS 엣지로 진입시켜 지연을 줄이고 ... 트래픽을 정상 리전으로 라우팅한다`에 있다.

### ADR-015: 해설의 약어에 풀네임을 괄호로 붙인다 (ADR-006·ADR-008·ADR-010 개정)
**결정**: 확인 문제 해설(`explanation`)에서 약어가 **처음 나오는 자리**에 `약어(Full Name)` 형태로
풀네임을 붙인다. 대상 약어 62종과 각각의 풀네임은 `src/data/data.test.ts`의 `acronymFullNames`가
유일한 정의이고, 같은 파일의 테스트 4개가 이를 강제한다. 해설 186개가 바뀌었다.

**이유**: 해설은 문제를 푼 직후 읽는 자리인데 약어만 늘어놓으면 무엇을 가리키는지 알 수 없다.
개념 본문에는 ADR-010이 이미 이 문제를 다루고 있었지만 해설은 대상이 아니었다. 그리고
ADR-011·ADR-012 때문에 문항 순서가 열 때마다 섞이고 랜덤 세트는 일부만 뽑으므로,
**앞 해설이 풀어 줬을 것이라고 가정할 수 없다.** 각 해설은 단독으로 읽혀야 한다.

**출처 규칙을 넓힌다**: `VPC`·`ECS`·`OAC`·`SCP`의 영문 풀네임은 두 출처 어디에도 없다.
ADR-006·ADR-008은 두 출처 밖의 내용을 만들지 말라고 하고, ADR-010의 예외는 "서비스 바깥의
일반 용어"로 한정돼 있어 이 넷은 어느 쪽으로도 쓸 수 없었다. **사용자가 판단해 허용했다.**
근거는 이것이 서비스의 사양·제약·비교가 아니라 **이름 표기**라는 점이다. 풀네임은 그 서비스가
무엇을 하는지 한 줄도 보태지 않으므로 어떤 문항의 정답 근거도 되지 않는다. `q083`(정답 `ECS`),
`q152`(정답 `OAC`), `q242`(정답 `SCP`)처럼 약어 자체가 정답인 자리도 있지만, 해설은 답을 고른
뒤에만 보이므로 정답이 새지도 않는다.
**이 예외는 약어의 풀네임에만 적용한다.** 서비스가 무엇을 하고 어떤 제약이 있는지는 여전히
두 출처에서만 가져온다 — ADR-010의 "정답 근거가 될 수 있으면 예외가 아니다"는 기준은 그대로다.

**대상이 아닌 것**:
- `AWS`·`DB`·`CPU`·`MB`·`KB`·`IP` — 상식으로 통한다. 해설 60개에 `AWS(Amazon Web Services)`가
  반복되면 읽는 데 방해만 된다.
- `API`·`URL`·`SSD` — `API Gateway`, `함수 URL`, `프로비저닝된 IOPS SSD`처럼 제품·유형 이름의
  일부로만 나온다. 이름 가운데를 풀이로 가르면 오히려 읽기 어려워진다.
- `NoSQL`·`MySQL`·`PostgreSQL`·`io1`·`io2`·`gp2`·`gp3` — 약어를 펼친 것이 이름이 아니다.

**규칙 셋**: ① 한 해설에서 한 약어는 한 번만 푼다. ② **괄호 안에 든 약어는 대상이 아니다** —
이미 다른 풀이의 일부다. ③ 이름이 서로를 품는 묶음(`HTTP`·`HTTPS`, `FTP`·`SFTP`·`FTPS`)은
먼저 나온 하나만 푼다. 둘 다 풀면 같은 말이 잇달아 두 번 나온다.

**`FSx`는 `File System for Extended use`로 쓴다.** `src/data/topics.json`이 개념 화면에서
그렇게 쓰고 있고, 개념과 해설이 서로 다른 이름을 가르치면 안 되기 때문이다.

**손으로 고친 해설 둘**: `q051`의 `FTP(SFTP, FTPS)`와 `q197`의 `HTTP(S)`는 괄호가 이미 다른
뜻으로 쓰이고 있어 규칙 ②에 걸렸다. 각각 `FTP와 그 통신을 암호화한 SFTP·FTPS`,
`HTTP·HTTPS`로 먼저 풀어 쓴 뒤 규칙을 적용했다. 앞 문장의 근거는
`data-transfer-services.transfer-family` 문단 0이다.

**검증**: `src/data/questions.json`은 `scripts/check-structure.mjs`가 sha256으로 막고 있으므로
`scripts/topics-baseline.json`의 `questionsSha256`을 같은 커밋에서 갱신했다.

**트레이드오프**: 해설이 길어진다(평균 126자, 가장 긴 것은 풀이 7개). `q089`의
`API Gateway HTTP(HyperText Transfer Protocol) API`처럼 제품 이름 가운데 풀이가 끼는 자리가
남는다. 규칙을 기계적으로 지키는 쪽을 택했다 — 자리마다 예외를 두면 표가 정의가 아니게 된다.

### ADR-016: 확인 문제에서 주제의 개념 페이지를 화면 안에서 펼친다 (ADR-013 "헤더 링크" 개정)
**결정**: 확인 문제 화면에서 개념을 볼 때 **개념 읽기 화면으로 이동하지 않는다.**
보기 블록 아래의 토글이 `question.topicId`가 가리키는 **주제의 개념 전체**를 그 자리에 펼친다.
개념 읽기로 내보내던 두 경로 — 헤더의 "근거 개념" 링크와 해설 아래의
"근거 개념으로 돌아가기" 링크 — 를 없앤다. 그 결과 헤더의 "검색" 링크가
**모든 화면에 상시로 있다**: ADR-013의 "확인 문제 화면에서는 렌더하지 않는다"를 개정한다.

**이유 — 나가는 길에는 돌아오는 길을 만들 수 없다**: 문항 진행 상태(`questionIndex`·
`selections`)는 `QuizRunner`의 `useState`다. 라우트를 옮기면 컴포넌트가 언마운트되어 그
상태가 사라지고, 돌아와도 페이지가 세트를 **다시 섞어** 1번 문항부터 시작한다.
ADR-011·ADR-012가 순서를 저장하지 않기로 했고 ARCHITECTURE "확인 문제 안의 문항 이동"이
이 상태를 화면 안 일시 상태로 못 박았으므로, **되돌아가는 버튼을 붙이는 것으로는 해결되지
않는다.** 7번 문항에서 개념을 확인한 대가로 앞의 6문항을 다시 푸는 것이 되기 때문이다.
랜덤 세트는 더 심하다 — 개념 읽기 화면의 하단 바는 그 주제의 확인 문제로만 가므로
**뽑힌 세트로 돌아갈 길이 아예 없다.**

**진행 상태를 화면 밖에 보관하는 안을 택하지 않았다**: 문항 순서·선택·현재 인덱스를
보관해 두고 복원하면 개념 읽기 화면 전체를 그대로 쓸 수 있다. 그러려면 ADR-011·ADR-012의
"순서를 저장하지 않는다"와 ARCHITECTURE의 "화면 안 일시 상태다"를 함께 개정해야 하는데,
그 셋은 각자 이유가 있어서 서 있다(순서 고정은 배열 암기를 부르고, 저장은 `Progress`의
`version`을 건드린다). **얻는 것이 같은데 개정할 것이 셋 더 많으므로 펼치기를 고른다.**

**ADR-013을 어디까지 개정하는가**: 검색 대상 네 필드, 문항 제외, 토큰 AND 매칭, 필드
우선순위, 상태를 남기지 않는다는 조항은 **전부 그대로다.** 바꾸는 것은 헤더 진입 링크의
렌더 조건 한 줄뿐이다. 그 조항의 근거는 검색이 덜 중요해서가 아니라 320px에서 헤더 링크가
세 개가 되면 로고가 눌린다는 실측이었고(UI_GUIDE "헤더 안의 링크"), "근거 개념"이 헤더에서
빠지면서 세 번째 링크가 사라졌다. **링크 두 개가 상한이라는 규칙은 그대로 살아 있다.**

**정답을 고르기 전에도 펼친다**: 헤더 링크가 맡고 있던 "채점을 기다리지 않고 개념을 확인하는
통로"를 그대로 잇는다. 해설 아래에만 두면 답을 고른 뒤에야 열려 그 통로가 사라진다.

**근거 개념 하나가 아니라 주제 전체를 펼친다**: 처음에는 `conceptId`가 가리키는 개념 하나만
펼치기로 정했고, 근거로 "통째로 펼치면 문항과 무관한 본문이 화면을 채운다"를 들었다.
**사용자가 이를 되돌렸다** — 원하는 것은 그 문항이 속한 주제 페이지 전체이고 연관 개념까지였다.
근거는 **개념 하나는 이웃 개념과 대비될 때 이해된다**는 것이다. `q180`("다중 AZ 배포의 대기
인스턴스로 할 수 없는 작업은?")의 근거는 `rds-storage-features.multi-az-standby-limits`
하나지만, 왜 대기 인스턴스가 읽기를 처리하지 않는지는 같은 주제의 `features`(다중 AZ는
고가용성, 읽기 전용 복제본은 읽기 확장)와 함께 읽어야 선다. 근거 개념만 떼어 주면 정답의
출처는 확인되고 **이유는 확인되지 않는다** — 이 앱을 학습 도구로 두기로 한 PRD와 어긋난다.
분량 우려는 실측으로 근거가 없었다: 20개 주제 중 가장 큰 것이 개념 11개·3043자이고,
펼치기는 사용자가 일부러 여는 것이다.

**어느 개념이 근거인지 표시하지 않는다**: 표시하면 펼치기가 다시 "정답의 출처"를 가리키는
장치가 되어 페이지를 읽게 하려던 목적과 어긋난다. 개념 읽기 화면에도 그런 표시는 없고,
두 화면이 같은 본문을 보여주는 것이 이 펼치기의 약속이다. `conceptId`는 계속 필요하다 —
`/review`의 오답노트가 문항마다 근거 개념 링크를 붙이는 데 쓴다.

**트레이드오프**: 펼치기는 주제 하나까지다. 주제를 넘어 앞뒤 주제로 이어 읽으려면
(개념 읽기 화면 하단 바의 `←`·`→`) 세트를 버리고 그 화면으로 가야 한다. 완료 화면의
"개념으로 돌아가기"나 검색·주제 목록이 그 경로다. 지금 풀던 세트를 버리는 선택이므로
실수로 일어나지 않게 명시적인 이동으로만 남긴다.


### ADR-017: 오답노트를 별도 집합으로 영구 보관하고 삭제는 사용자만 한다 (PRD "복습" 개정)
**결정**: `Progress`에 `wrong: Record<string, true>`를 두고, 문항을 틀리면 넣는다.
여기서 빠지는 경로는 **복습 화면의 `지우기` 버튼 하나뿐이다.** 같은 문항을 다시 풀어
맞혀도 빠지지 않는다. 복습 화면(`/review`)은 개념 목록이 아니라 이 오답노트의 문항을
주제별로 보여주고, `/review/quiz`와 `/review/quiz/:topicId`가 그 문항만 다시 낸다.

**이유**: 찍어서 맞힌 것과 익힌 것을 앱이 구분할 수 없다. 자동으로 지우면 한 번 운 좋게
맞힌 문항이 복습 대상에서 영구히 빠진다. 무엇을 충분히 익혔는지는 학습자가 판단하는 편이
낫다는 것이 사용자의 결정이다.

**마지막 채점 결과에서 파생시키지 않는다**: 그전까지 복습 목록은 `answers[id] === false`
에서 파생됐고, `recordAnswer`가 정오답 boolean을 덮어쓰므로 다시 맞히는 순간 항목이
사라졌다. 파생을 유지한 채로는 위 결정을 지킬 수 없어서 별도 집합이 필요하다.
`answers`는 마지막 시도를, `wrong`은 등재 여부를 잰다 — 서로 다른 것을 재므로 갈라진다.

**개념 목록을 문항 목록으로 바꾼다**: PRD는 복습을 "틀린 문제가 속한 개념만 모아 다시
본다. 시험 오답노트가 아니다"로 정의했다. 이 ADR이 그 문장을 개정한다. 개념 목록은
오답에서 파생된 것이라 문항 목록이 그것을 포함하고, 문항마다 근거 개념 링크를 붙이면
잃는 정보가 없다. 두 목록을 함께 두면 한쪽은 자동으로 사라지고 한쪽은 남아 기준이
어긋나 보인다.

**다시 푸는 경로는 `QuizRunner`를 재사용한다**: ADR-016이 확인 문제 화면 안에 주제
개념 페이지 펼치기를 넣었고, 사용자가 오답 다시 풀기를 원한 이유가 그것이다. 별도의
간이 문항 뷰어를 만들면 개념 펼치기가 없는 화면이 하나 더 생긴다. 세트는 ADR-011·012와
같이 저장하지 않지만, **진입 시점에 한 번만 고르고 푸는 동안 고정한다** — 푸는 사이
`wrong`이 바뀌어도 세트가 흔들리면 안 되기 때문이다.

**version 2로 올리고 마이그레이션한다**: `Progress`에 필드를 더하므로 ARCHITECTURE
"확인 문제 안의 문항 이동"이 정한 대로 `version`을 올린다. v1 저장분은 버리지 않고,
그때 `answers`가 `false`인 문항을 `wrong`의 씨앗으로 채워 옮긴다. 이미 쌓인 오답 기록이
스키마 변경 때문에 끊기면 안 되기 때문이다. 마이그레이션은 `src/lib/storage.ts` 한 곳이다.

**트레이드오프**: 오답노트는 사용자가 지우지 않는 한 계속 자란다. 246문항을 다 틀리면
복습 화면이 그만큼 길어지고, 개념 목록이던 때보다 항목당 높이도 크다. 대신 무엇을
틀렸는지가 남고, 지우기가 그 길이를 줄이는 수단이다. 실행 취소는 두지 않는다 —
지운 문항은 다시 틀리면 돌아온다.

### ADR-018: 랜덤 세트에 50·100과 전체를 더한다 (ADR-012 개정)
**결정**: 랜덤 문제 시작 화면의 문항 수를 10 · 20 · 30 · 50 · 100과 **전체**로 늘린다.
전체는 숫자 허용값이 아니라 `/random/all` 세그먼트이고, 문항 수는 문제 은행 크기에서 읽는다.
ADR-012의 나머지는 그대로다 — 가중치 없는 무작위, 세트 미저장, 제한시간·점수 이력 없음.

**이유**: 사용자가 30문항으로는 부족하다고 알려왔다. ADR-012가 10·20·30으로 정한 것은
분량에 대한 설계 판단이 아니라 초기 값 선택이었고, 그 판단을 유지할 근거가 따로 없다.
한 번에 더 많이 푸는 것은 ADR-012가 경계로 삼은 셋(제한시간·점수 산출·합격선)과 무관하다.
**따라서 이 ADR은 "시험 리허설을 만들지 않는다"는 경계를 건드리지 않는다** — 늘어난 것은
한 세트의 분량뿐이고, 다 풀어도 남는 것은 여전히 `answers`의 정오답과 오답노트뿐이다.

**전체를 숫자로 두지 않는 이유**: ADR-012는 `/random/999`로 246문항 전부가 나오는 경로를
열지 않겠다고 했다. 그 취지는 **아무 숫자나 받지 않겠다**는 것이지 전체를 금지한 것이 아니므로,
허용값 목록을 유지한 채 전체를 별도 세그먼트로 더한다. `246`을 허용값에 넣는 방법도 있지만
문항이 늘어나는 순간 그 숫자는 전체를 뜻하지 않게 되고, `/random/246`을 북마크한 사람은
조용히 일부만 받는다. 세그먼트로 두면 은행이 커져도 링크의 뜻이 변하지 않는다.

**트레이드오프**: 전체 세트는 246문항이라 한 번에 끝내기 어렵고, 중간에 나가면 진행이
사라진다 — 세트를 저장하지 않기로 한 ADR-011·012가 그대로 적용되기 때문이다. 이어 풀기를
넣으려면 `Progress`에 세트 상태를 저장해야 하는데, 그것은 ADR-012가 만들지 않기로 한
모의고사 쪽으로 한 걸음 가는 일이다. 푼 문항의 정오답은 그때그때 기록되므로 중간에 나가도
진행률과 오답노트에는 남는다. 지금은 여기까지로 둔다.

### ADR-019: AWS 공식 카테고리를 세 번째 출처로 인정하고 개념 본문에 한 줄로 넣는다 (ADR-006·ADR-008·ADR-009 개정)
**결정**: AWS 백서 *Overview of Amazon Web Services*의 "AWS services by category"에서 뽑은
**카테고리 이름 13종과 서비스 배치**를 세 번째 출처로 인정한다. 추출본은
`docs/source/service-categories.md`이고, 그 파일이 이 내용의 유일한 근거다.
서비스 개념 **75개**의 `paragraphs[0]` 맨 앞에
`{주어}는 AWS 분류로는 {카테고리} 쪽 서비스다.` 한 문장을 넣는다.
`src/data/data.test.ts`의 `serviceCategories`가 75개 전부와 표기를 강제한다.

**이유**: 사용자가 개념만 읽으며 학습하다, 어떤 용어가 무슨 서비스인지·관리 툴인지·분석
플랫폼인지 하는 **큰 갈래를 앱이 알려주지 않는다**고 알려왔다. 개념 182개의 한 줄 요약은
그 서비스가 *무엇을 하는지*는 말하지만 AWS 전체 지형에서 *어디에 속하는지*는 말하지 않는다.
주제 제목도 `EMR·Spark·RedShift·Athena·Kinesis·Glue·X-Ray·CloudWatch`처럼 나열형이라
지도 구실을 하지 못한다. 이 앱은 시험 시뮬레이터가 아니라 학습 도구이므로
(CLAUDE.md), 읽는 것만으로 전제가 서야 한다.

**출처 규칙을 넓히는 이유**: 카테고리 분류는 두 원본 어디에도 없다. 원본 자료는 장 구성으로
서비스를 묶어 두었을 뿐 AWS의 공식 카테고리를 쓰지 않고, `exam-gaps.md`에도 없다.
`관리 도구`·`플랫폼`·`메시징` 같은 말은 두 출처에서 한 번도 나오지 않는다.
ADR-010의 예외는 "서비스 바깥의 일반 용어"로 한정돼 있어 이쪽으로도 쓸 수 없었다.
**사용자가 판단해 허용했다.** ADR-015가 약어 풀네임을 허용한 것과 같은 성격의 개정이다.

**이 예외의 경계 — 카테고리 이름과 배치뿐이다**: ADR-010의 기준("이 사실이 어떤 문항의
정답 근거가 될 수 있는가")은 그대로 살아 있다. 카테고리는 그 서비스가 무엇을 하고 어떤
제약이 있는지 한 줄도 보태지 않으므로 어떤 문항의 정답 근거도 되지 않는다. 반면
`Glacier의 조회 시간`, `ACM 인증서의 리전`처럼 사양·제약·비교는 여전히 예외가 아니고
두 원본에서만 가져온다. 카테고리를 근거로 문항을 만들거나 고치지도 않는다 —
`src/data/questions.json`은 이 개정에서 한 글자도 바뀌지 않았다.

**추출본을 저장소에 커밋하는 이유**: `concepts-raw.md`는 외부 참고 자료 추출본이라 ADR-009에 따라
gitignore로 로컬에만 두지만, 이 파일은 **AWS 공개 문서**에서 뽑은 것이다. 전사해도 외부 자료가
드러나지 않으므로 커밋해서 clone한 환경에서도 근거를 대조할 수 있게 한다. 백서의 카테고리별
목록에 개별 항목이 없던 셋(`STS`, `Billing and Cost Management`, `Cost Anomaly Detection`)은
IAM 사용자 가이드와 AWS Cost Management 사용자 가이드를 보조 출처로 썼고, 어느 것이
보조 출처인지 매핑 표에 표시했다. 모델이 아는 AWS 지식으로 채운 항목은 없다.

**형태는 ADR-010과 같다**: `paragraphs`에만 인라인으로 넣는다. **뱃지·용어집 페이지·툴팁을
만들지 않고 주제 목록도 갈래별로 다시 묶지 않는다.** 읽던 자리에서 해결되는 것이 목적이고,
새 화면을 만들면 그 목적이 깨진다. `id`·`name`·개념 개수·주제 배치·`summary`도 그대로다 —
`summary`를 제외하는 이유는 ADR-010과 같다. `scripts/check-structure.mjs`가 이 범위를 강제한다.

**한 서비스가 두 주제에 있으면 양쪽에 다 넣는다**: `EC2`·`ELB`·`CloudFront`·`Lambda`·`RDS`가
그렇다. ADR-010은 일반 IT 용어를 "처음 등장하는 개념에서 한 번만" 풀라고 했지만, 그것은
용어 풀이라서 되풀이가 군더더기인 경우다. 카테고리는 그 개념이 소개하는 서비스의 성격이고,
주제 페이지는 각각 독립적으로 열리므로 `serverless-containers`만 읽는 사람은
`aws-core-services`의 문장을 볼 일이 없다. ADR-015가 해설마다 약어를 다시 푼 것과 같은 논리다.

**`AWS 분류로는`을 넣는 이유**: 원본에서 온 정의 문장이 다른 갈래의 이름을 쓰는 개념이 있다.
`EMR`의 정의는 `컴퓨팅 서비스다`이고 `RedShift`는 `AWS 데이터베이스 서비스다`인데 백서
카테고리는 둘 다 분석이다. 프레임 없이 붙이면 두 문장이 서로 다투는 것처럼 읽힌다.
이 표현은 카테고리가 AWS가 매긴 분류라는 것도 함께 밝혀, 서비스의 정체를 다시 정의하는
문장이 아님을 분명히 한다.

**주제를 옮기지 않는다**: 백서 카테고리와 이 앱의 주제 배치가 갈리는 자리가 있다.
처음 적을 때는 10곳이었고, phase 26이 주제를 서비스 경계로 재편한(ADR-023) 뒤로는 15곳이다 —
`MSK`는 `kinesis-streaming`으로 옮겨 이웃과 카테고리가 같아져 빠졌고, `Elastic Beanstalk`·
`Amplify`·`Managed Grafana`·`Elastic Disaster Recovery`·`Audit Manager`·
`Resource Access Manager`가 들어왔다. **목록은 여기 복제하지 않는다** —
`service-categories.md`의 "주제 배치와 어긋나는 자리"가 갖는다. **갈리는 것 자체가 학습
내용이므로** 주제 배치는 그대로 두고 카테고리만 밝힌다. 개념을 옮기면 개념 id가 바뀌고
문항의 `topicId`·`conceptId` 참조가 깨진다. `Secrets Manager vs Parameter Store` 비교 개념이
이미 있는데, 둘이 아예 다른 카테고리라는 사실이 이 개정으로 드러난다.

**대상이 아닌 것**: 618개 중 511개다(처음 적을 때는 182개 중 107개였다). ① AWS 서비스가 아닌 것(`DNS`, `리전`, `온프레미스`,
`Spark`) ② 서비스의 기능·설정·유형(S3 스토리지 클래스 7종, `NAT 게이트웨이`, `보안 그룹`)
③ 사실·비교·판단 기준 개념(`Fargate에는 실행 시간 제한이 없다`, `계층으로 갈리는 ALB와 NLB`).
`Fargate`·`DAX`처럼 백서에 카테고리가 있는 서비스라도 이 앱에서 그 이름을 단
개념이 사실·비교 개념이면 넣지 않는다 — 소개 문장이 아닌 곳에 카테고리를 끼우면 그 문단이
무엇을 말하려는지 흐려진다. 기준은 `docs/source/service-categories.md`에 적었다.
`OpenSearch`도 처음에는 이 예에 있었으나, phase 26이 서비스를 소개하는 개념을 들여와
지금은 한 줄을 붙인다 — **이 예는 서비스 이름이 아니라 개념의 성격으로 갈린다.**

**트레이드오프**: 출처가 셋으로 늘어 "두 파일만 읽으면 검수가 끝난다"는 성질이 더 약해진다.
대신 세 번째 출처는 파일 하나로 고정하고 그 안에 URL과 확인 시점을 적어 두었으며,
`data.test.ts`가 107개 배치를 표로 강제한다(처음에는 75개였다). 목록을 늘리거나 표기를 바꾸려면 이 ADR과
`service-categories.md`를 함께 고쳐야 한다 — 슬금슬금 늘어나는 것을 막기 위해서다.
AWS가 카테고리를 재편하면 이 파일이 낡는데, 그때는 확인 시점을 갱신하며 다시 대조해야 한다.

### ADR-020: 검색 결과를 개념 위치로 보낸다 (ADR-013 "검색 결과는 주제 상단으로" 개정)
**결정**: 개념 히트 카드는 `/topic/:topicId#:conceptId`로 링크하고, 착지한 개념 읽기 화면이
그 개념 위치로 스크롤을 옮긴다. 이를 위해 ARCHITECTURE "화면 전환 시 스크롤"의 계약에
**예외를 하나 더한다 — 목적지가 앵커를 지정했으면 맨 위로 되돌리지 않는다.**
주제 히트 카드는 지금처럼 앵커 없이 주제 상단으로 보낸다.

**이유 — 유예해 둔 조건이 충족됐다**: ADR-013은 앵커 이동을 미루면서 "정말 필요해지면
스크롤 계약을 다시 재는 별도 결정으로 다룬다"고 적어 두었다. 이 결정이 그것이다.
ADR-013이 점프 대신 내놓은 완화책은 "결과 카드에 한 줄 요약을 함께 싣는다"였고, 그 카드는
"이게 그거였다"를 확인시켜 준다. 그런데 확인이 끝난 뒤에 남는 일 — 착지한 주제에서 그 개념을
눈으로 찾아 내려가는 일 — 은 줄여주지 못한다. 개념이 20개 가까이 든 주제에서 문서 높이는
2400~3900px이고, 요약을 읽어 목적지를 이미 아는 사람이 그 거리를 다시 훑는다.
ADR-013이 트레이드오프로 명시해 둔 바로 그 비용이다.

**계약과의 충돌은 생각보다 좁다**: ADR-013이 앵커 이동을 막은 근거는 "실측값으로 확정된
스크롤 계약과 정면으로 부딪힌다"였다. 다시 재보니 부딪히는 면은 계약의 한쪽뿐이다.
계약의 핵심인 `POP`(뒤로/앞으로 가기)의 브라우저 기본 복원은 앵커 이동이 건드리지 않는다 —
ARCHITECTURE에 실측표로 남은 네 줄과 "목록을 2069px까지 내린 뒤 돌아오면 그대로 복원된다"는
동작이 모두 `POP` 경로이고 그대로다. 부딪히는 것은 `PUSH`/`REPLACE`의 `scrollTo(0, 0)`
하나이며, 그 규칙이 존재하는 이유는 "링크로 새 화면에 들어오면 이전 화면의 스크롤 위치가
그대로 남는다"는 것이었다. 앵커가 붙은 이동은 목적지가 시작 위치를 스스로 지정한 경우라
그 이유의 범위 밖이다. 그래서 계약을 버리지 않고 예외 한 줄을 더하는 형태로 개정한다.

**스크롤 주인은 한 명이어야 한다**: 예외를 `Layout`에 두는 것이 핵심이다. React는 자식
effect를 부모보다 먼저 실행하므로, `ConceptReadPage`에서 앵커로 옮겨도 직후에 `Layout`의
`scrollTo(0, 0)`이 덮어쓴다. **페이지 쪽에만 코드를 넣으면 동작하지 않는다.**
`setTimeout`이나 `requestAnimationFrame`으로 순서를 비껴가지 마라 — 두 주인이 순서를 두고
경쟁하는 구조가 남고, 실패가 타이밍에 따라 갈린다. `Layout`이 해시를 보고 물러나고,
해시를 읽는 화면이 스크롤을 맡는다.

**구현 제약 셋**: ① 개념 id는 `aws-core-services.ec2`처럼 점을 품는다. `querySelector('#'+id)`는
점을 클래스 구분자로 읽어 아무것도 못 찾으므로 `getElementById`를 쓴다. ② 헤더가
`sticky top-0`(약 77px)이라 여백 없이 스크롤하면 개념 제목이 헤더 밑에 깔린다.
개념마다 `scroll-mt-24`를 둔다. ③ `behavior: 'smooth'`를 쓰지 마라 — UI_GUIDE "애니메이션"이
페이지 전환 애니메이션을 금지하고, ARCHITECTURE도 화면 전환은 즉시라고 못 박았다.

**HashRouter에서 해시가 둘이 된다**: 실제 URL은 `#/topic/database#database.aurora`가 된다.
`HashRouter`는 첫 `#` 뒤 전부를 경로로 넘기고 `history`의 `parsePath`가 뒤쪽 `#`를
`location.hash`로 갈라내므로 그대로 동작한다. 브라우저 기본 앵커 이동은 이 형태에서 작동하지
않지만, 어차피 스크롤은 코드가 옮기므로 의존하지 않는다.

**앵커를 붙이지 않는 곳**: 주제 히트 카드다. 지목할 개념이 없어서 앵커를 붙이면 첫 개념을
임의로 고르는 셈이 된다. 그리고 **개념을 지목하는 색·테두리 강조를 넣지 마라** —
UI_GUIDE "색은 정답/오답/중요도에만 쓴다"에 걸린다. 위치로 데려다주는 것까지가 이 결정이다.

**트레이드오프**: `Layout`의 스크롤 규칙이 두 줄에서 세 줄이 됐다. 앞으로 해시를 쓰는 링크를
만드는 쪽은 그 화면이 스크롤을 책임진다는 것을 알아야 하고, 모르고 만들면 새 화면이 이전
스크롤 위치에 착지한다. 지금 해시를 쓰는 링크는 검색 결과 하나뿐이다. 늘어나면 규칙을
`Layout` 주석이 아니라 공용 훅으로 옮길 것을 검토한다.

### ADR-021: 네 번째 출처로 880문항 덤프 해설집을 인정한다 (ADR-006·ADR-008 개정)
**결정**: `docs/source/dump-gaps/`를 출처로 인정한다. ADR-008이 163문항 덤프에 준 지위를
880문항 해설집(`docs/source/pdf/SAA-C03_해설집.pdf`, 덤프 V29.35)에 동일하게 준다.
그 해설에서 **개념 원문·`exam-gaps.md`에 없는데 정답 근거로 쓰인 것**만 추려 담는다.
**문항 자체는 앱에 넣지 않는다. 개념만 가져온다.**

**이유**: 현재 182개념으로는 이 해설집의 정답 근거를 댈 수 없는 문항이 최소 152개(17%)다.
앱에 아예 없는 서비스가 39종이다 — DMS 29문항, QuickSight 20, CloudFormation 19,
Redshift Spectrum 9, Elastic Beanstalk 9, SageMaker 8, Neptune 8, Lake Formation 7,
Control Tower 7 … 이미 다루는 서비스의 세부 갭(S3 Object Lambda, SAML 2.0 페더레이션 등)은
서비스 이름으로 세는 이 집계에 잡히지 않으므로 실제 갭은 더 크다. 앱이 이걸 다루지 않으면
"이 앱으로 학습하면 덤프를 풀 수 있다"는 전제가 깨진다. ADR-008이 163문항 덤프를 받아들인
것과 같은 이유이고, 대상만 더 큰 덤프로 바뀌었다.

**문항을 넣지 않는 이유**: 복수정답이 78문항이다(5지선다 61 + 6지선다 17). ADR-005가 정한
4지선다 단일정답과 어긋나므로 그대로는 실을 수 없다. 그리고 문제 전문을 저장소에 넣으면
ADR-009의 전사 금지 취지와 정면으로 부딪힌다 — 이 해설집도 외부 자료다.
**개념만 가져오면 둘 다 피하면서 목적을 이룬다.** 문항이 필요하면 기존 문제 은행처럼
개념에서 새로 출제하는 것이지 덤프를 옮겨 담는 것이 아니다.

**ADR-008의 오류 예외를 그대로 승계한다**: 이 해설집은 문서 2쪽에서 스스로 고지했다 —
"원본에 해설이 없던 21개 문제는 새로 작성했고 `[AI 작성 해설]`로 표시했다. 그중 6개 문제는
원본에 기록된 정답이 AWS 기준과 어긋난다." 출처가 스스로 밝힌 불확실성이므로 그대로 옮기지
않는다. 명백한 사실 오류는 싣지 않거나 고쳐 싣고, 어느 쪽이든 원문과 함께 "원본 수정 이력"에
남긴다. ADR-008과 같이 이 예외는 **명백한 사실 오류에만** 적용하고, 모델이 아는 AWS 지식으로
내용을 보강하는 용도로 쓰지 않는다.

**추출본을 커밋하지 않는다**: `docs/source/dump-slices/`는 덤프 전문이라 `concepts-raw.md`와
같이 gitignore로 로컬에만 둔다(ADR-009). 커밋하는 것은 거기서 추린 `dump-gaps/`뿐이고,
그 문장은 직접 쓴다. `scripts/extract-dump.py`가 있으므로 PDF만 있으면 재생성된다.

**트레이드오프**: 출처가 넷이 되어 검수 기준이 하나 더 늘었다. 대신 모든 항목에
`[Q번호 p쪽]` 인용을 붙여 어느 해설에서 왔는지 되짚을 수 있게 한다. `exam-gaps.md`가
`[섹션 #문항 pP]`로 한 것과 같고, 이 덤프는 문항 번호가 전체에서 유일해 섹션명이 필요 없다.

### ADR-022: 카테고리를 13종에서 15종으로 넓힌다 (ADR-019 "카테고리 이름 13종" 개정)
**결정**: ADR-019가 고정한 카테고리 목록에 두 종을 더해 **15종**으로 한다.

| 표기 | 백서 카테고리 |
| --- | --- |
| `기계 학습(Machine Learning and Artificial Intelligence)` | Machine Learning (ML) and Artificial Intelligence (AI) |
| `프런트엔드 웹 및 모바일(Front-end Web and Mobile)` | Front-end web and mobile |

출처는 바뀌지 않는다. ADR-019가 정한 그 백서, 그 페이지의 같은 목록이다.
`src/data/data.test.ts`의 `categories`가 15종을 선언하고 표기를 강제한다.

**이유**: phase 26이 들여오는 서비스 여덟이 13종 밖 카테고리였다.
`SageMaker AI`·`Comprehend`·`Rekognition`·`Lex`·`Transcribe`·`Translate`·`Textract`가
Machine Learning (ML) and Artificial Intelligence (AI)이고 `Amplify`가 Front-end web and mobile이다.
앞의 일곱은 새 주제 `ai-ml-services` 전체다. 13종을 그대로 두면 **그 주제가 만드는 개념에
카테고리 한 줄이 하나도 붙지 않는다.** ADR-019가 이 문장을 넣은 목적은 학습자가 "이게 무슨
갈래의 서비스인지" 모른 채 읽는 것을 막는 것이었는데, 하필 가장 낯선 주제가 통째로 빠지면
그 목적이 그 자리에서만 무너진다. **사용자가 판단해 허용했다.**

**이것은 출처가 늘어나는 것이 아니다**: ADR-019가 13종으로 못박은 것은 목록이 슬금슬금
늘어나는 것을 막기 위해서였지, 13이라는 수가 백서의 전부여서가 아니다. 백서는 21종을 싣고
있고 13종은 그중 **그때 앱에 서비스가 있던 것만**이었다. 앱에 없는 서비스의 카테고리를
미리 적어 둘 이유가 없었을 뿐이다. 이번에 그 서비스들이 들어오므로 같은 목록에서 두 종을
더 쓴다. 여전히 백서에 없는 카테고리를 만들지 않고, 모델이 아는 분류로 채우지도 않는다.

**표기에서 괄호 약어를 뺀다**: 백서의 이름은 `Machine Learning (ML) and Artificial
Intelligence (AI)`인데 표기는 `기계 학습(Machine Learning and Artificial Intelligence)`으로
적는다. 이유는 두 가지다. 표기 형식이 `한글 이름(백서 영문 이름)`이라 괄호가 중첩되고,
이 표기는 개념 본문 문장 안으로 들어가 `SageMaker AI는 AWS 분류로는 기계 학습(...) 쪽
서비스다`가 되므로 읽기가 어려워진다. `(ML)`·`(AI)`는 바로 앞 단어를 줄인 것이라 빼도
가리키는 대상이 달라지지 않는다. 기존 13종도 백서의 문장형 대소문자(`Networking and content
delivery`)를 제목형(`Networking and Content Delivery`)으로 고쳐 적고 있어 같은 성격의
정규화다. 백서의 원래 이름은 `service-categories.md`에 그대로 남겨 대조할 수 있게 한다.

**주제 배치는 여전히 옮기지 않는다**: ADR-019의 "주제를 옮기지 않는다"는 그대로다.
`Amplify`는 `api-gateway-step-functions` 주제에 있으면서 카테고리만 프런트엔드 웹 및 모바일로
밝힌다. 어긋나는 자리는 `service-categories.md`의 "주제 배치와 어긋나는 자리"에 적는다.

**트레이드오프**: `data.test.ts`의 「선언한 카테고리 집합 = 실제로 쓰인 카테고리 집합」
등식이 깨진다. 새 두 종은 step 11(`Amplify`)과 step 20(`ai-ml-services`)이 개념을 만들 때까지
아무도 쓰지 않기 때문이다. 등식을 **부분집합 검사**로 바꾼다 — 이 단언의 목적인 "선언 밖의
표기를 쓰지 않는다"는 그대로 지켜지고, 선언만 해 두고 아직 안 쓰는 상태를 허용한다.
대신 "선언했는데 끝내 아무도 안 쓰는 카테고리"를 테스트가 잡아주지 못하게 되므로,
목록을 늘릴 때는 이 ADR과 `service-categories.md`를 함께 고치는 규칙이 더 중요해진다.

### ADR-023: 주제를 서비스 경계로 재편하고 개념 순서를 기본→갈림길→한계로 잡는다 (PRD "20개 주제"·ADR-021 개정)
**결정**: 주제를 20개에서 **39개**로 재편하고, 경계를 **서비스 단위**로 긋는다.
개념은 182개에서 **618개**가 됐다. 주제 안의 개념 배열은 **1단(그 서비스가 무엇인가) →
2단(헷갈리는 것과 무엇으로 갈리는가) → 3단(한계값·설정·세부 동작)** 순서다.
이 층은 **배열 순서로만** 표현하고 `Concept` 타입에 필드를 두지 않는다.
개념의 출처는 ADR-021이 인정한 `dump-gaps/`이고, 이 ADR이 정하는 것은 **배치와 순서**다.

**크기가 아니라 서비스로 자른 이유**: 개념 618개를 주제 20개에 그대로 담으면 한 주제가
30~60개가 되어 읽을 수 없다. 그렇다고 크기로 자르면 — "한 주제는 개념 15개까지" 같은
규칙을 세우면 — 경계가 학습자의 구획과 아무 상관이 없어진다. 무엇보다 **헷갈리는 짝이
갈린다.** CloudFront와 Global Accelerator가 다른 주제에 놓이면, 이 앱이 가르치려는 것
("언제 무엇을 쓰는가")을 앱이 스스로 깨뜨린다. 둘을 나란히 놓고 갈림길을 세우는 개념을
같은 주제에 두는 것이 이 앱의 학습 단위다. 지켜야 할 짝의 목록은
`docs/source/dump-gaps/topic-plan.md`의 "헷갈리는 짝 배치 표"에 있다.
그래서 자르는 자리는 **서비스 경계**다 — `compute-delivery` 하나가 `ec2-autoscaling`·
`elastic-load-balancing`·`cloudfront-global-accelerator` 셋이 됐고, 셋 다 안에서는
짝이 붙어 있다.

**3단 정렬의 이유**: 기존 182개는 "이 서비스는 무엇인가"에 답하는 지도이고, 새로 들어온
436개는 한계값·설정·갈림길이라 지형의 디테일이다. 섞어 놓으면 지도가 디테일에 묻힌다.
Lambda가 무엇인지 모르는 사람에게 `lambda-layer-size-limit`은 아무것도 주지 않는다.
PRD의 사용자는 "짧게 여러 번 들여다보며 개념을 눌러 담는" 사람이므로, **앞에서부터 읽어
지도를 얻고 나중에 다시 와서 뒤를 읽는다.** 중간에 끊고 나가도 그때까지 읽은 것이
그 주제의 뼈대가 되는 순서다. 그 반대 — 한계값이 앞에 오는 순서 — 는 처음 읽는 사람에게
아무 뼈대도 남기지 못한다.

**타입에 층 필드를 두지 않은 이유**: 배열 순서만으로 학습 순서가 전부 표현된다.
필드를 더하면 순서와 필드가 어긋날 수 있는 두 번째 진실이 생기고, `Concept` 타입·
`ConceptList`·`data.test.ts`를 함께 고쳐야 한다. 순서로 두면 **타입도 UI도 테스트도
하나 바뀌지 않는다.** 층을 화면에 눈에 보이게 표시하는 것(구분선·소제목·접기)은
별개의 판단이고 **이 결정에 포함되지 않는다.** 표시가 필요해지면 그때 다시 정한다.

**진행률을 마이그레이션하지 않은 이유**: 주제 id가 여럿 사라졌지만(`compute-delivery`·
`identity-access`·`analytics-monitoring` 등) `Progress`의 `version`은 2 그대로다.
`Progress.read`는 topicId로 키를 잡는데 `src/lib/stats.ts`가 `topics` 배열을 돌며
`progress.read[topic.id]`를 조회하므로, **사라진 topicId는 조회되지 않고 그냥 남는다.**
`answers`·`wrong`은 questionId 기반이고 문항 id는 이 phase에서 하나도 바뀌지 않았으므로
정오답과 오답노트가 그대로 산다. 잃는 것은 없어진 주제의 "읽음" 표시뿐이고, 그 주제는
화면에 없으므로 표시할 자리도 없다. 죽은 키를 지우는 마이그레이션을 쓸 수는 있지만
`version`을 올려야 하고, 얻는 것이 저장소 몇 바이트다.

**트레이드오프**: **주제 목록이 두 배로 길어졌다.** PRD는 "주제 목록에 필터를 붙이지 마라"를
유지하고 있고, 그 판단의 근거였던 "20개는 훑는 게 더 빠르다"는 39개에서도 맞는지 재보지
않았다. 목록 화면을 어떻게 다룰지는 **열린 문제로 남긴다** — 실물을 보고 정할 일이라
이 결정에서 미리 정하지 않는다. 그리고 **개념은 618개인데 문항은 246개 그대로다.**
문항이 하나도 없는 주제가 5개 생겼고(`s3-access-control`·`redshift-opensearch-quicksight`·
`governance-iac`·`systems-manager`·`ai-ml-services`), 그 주제는 읽기만 되고 점검이 안 된다.
문항을 어디까지 채울지도 **열린 문제다.** 둘 다 다음 phase의 몫이다.

### ADR-024: 검색 결과에서 본문에만 걸린 히트를 접는다 (UI_GUIDE "결과 개수를 자르지 마라" 보완)
**결정**: `searchContent`의 결과를 `splitBodyOnly`로 갈라, 개념 이름·한 줄 요약·주제 제목에
걸린 히트를 먼저 그리고 **본문에만 걸린 히트는 토글 아래로 접는다.** 자르지 않는다 —
개수(`본문에서 66개 더 찾음`)를 밝히고 펼칠 수 있다.

**이유 — 규칙의 전제가 커져 결론이 뒤집혔다**: UI_GUIDE의 "결과 개수를 자르지 마라"는
**"찾으려던 것이 잘린 쪽에 있으면 사용자가 알 방법이 없다"**를 막으려고 쓴 규칙이고,
개념 182개 시절에는 전부 그리는 것이 그 목적을 달성했다. ADR-023이 개념을 618개로 늘린 뒤
한 단어 질의의 결과가 3~7배가 됐다 — `s3` 49→154, `비용` 26→93, `lambda` 24→81,
`복제` 7→51, `iam` 6→42(실데이터에 `search.ts`의 매칭 규칙을 그대로 돌린 값).
154개 카드를 훑는 것 자체가 못 찾는 상태이므로, **전부 그리는 수단이 규칙의 목적을 깨뜨린다.**

**본문 히트를 고른 이유**: 늘어난 것이 거의 전부 본문 히트다. `s3` 154개 중 81개,
`비용` 93개 중 66개, `지연` 67개 중 46개가 이름·요약에 걸리지 않고 본문에만 걸린다.
이름·요약·주제만 세면 `s3` 73개, `비용` 27개, `지연` 21개로 재편 전 규모에 가깝다.
phase 26이 들여온 개념들의 문단이 길어서 생긴 일이므로, 접을 자리도 거기다.

**순위를 새로 만들지 않았다**: ADR-013이 정한 필드 우선순위(`개념 이름 → 주제 제목 →
한 줄 요약 → 개념 본문`)의 **마지막 단계를 접을 뿐이다.** 점수 함수·빈도 가중치·형태소
분석기를 넣지 마라 — ADR-013이 금지한 것이 그대로 살아 있다.

**접지 않는 경우**: 이름·요약에 걸린 히트가 하나도 없으면 접지 않고 본문 히트를 그대로
결과 목록으로 그린다. 남길 것이 없는데 접으면 빈 목록과 토글만 남아 결과가 없는 것처럼
보인다. 결과 개수 표시는 **접힌 것까지 센다** — 찾은 수를 줄여 보고하지 않는다.

**트레이드오프**: 본문에만 있는 말을 찾는 사용자는 클릭 하나가 늘어난다. 대안이었던
"매칭에서 본문을 빼고 `본문까지 찾기` 토글을 둔다"는 쪽은 **접힌 것의 개수를 미리 알려줄 수
없어** "알 방법이 없다"는 원래 문제로 되돌아간다. `더 보기` 방식도 같은 이유로 쓰지 않는다.
그리고 이것은 결과 목록의 문제만 푼다 — 주제 목록이 39개로 길어진 문제(ADR-023의 트레이드오프)는
여전히 열려 있다.

### ADR-025: 전사 검사를 요약·문단으로 한정하고 고유명사 나열을 넘긴다 (ADR-009 「검증」 개정)
**결정**: `scripts/check-verbatim.mjs`의 대상을 `summary`·`paragraphs`로 한정한다(`name`은
보지 않는다). 그리고 겹친 구간에 **한글이 한 글자도 없으면 넘긴다.** 임계값 32자는 그대로다.
넘긴 겹침은 감추지 않고 건수와 내용을 함께 찍는다.

**이유 — 검사가 자기 근거 ADR보다 넓게 보고 있었다**: 검사를 처음 돌리니 5건이 잡혔는데
5건 모두 전사가 아니었다. 4건은 `name`에서 잡혔다. ADR-009는 "`id`·`name`은 건드리지
않는다"고 정했으므로 검사가 요구하는 "문장을 다시 써서 해소하라"를 그 필드에서는 따를 수
없다. 고정하기로 한 필드를 감시하면서 고치라고 말하는 상태였다. `name`이 무방비가 되는 것도
아니다 — `scripts/check-structure.mjs`가 개념 618개의 `id`·`name`을 baseline과 대조한다.

**한글 없는 겹침을 넘기는 이유**: 남은 1건은 문단에서 잡혔지만, 겹친 78자가 전부 S3 스토리지
클래스 다섯 개의 정식 이름을 이어 붙인 것이었다(`S3 Standard`·`S3 Standard-IA`·
`S3 One Zone-IA`·`S3 Glacier Instant Retrieval`·`S3 Intelligent-Tiering`). 그 앞뒤 한국어
문장은 겹치지 않는다 — 문장은 직접 썼고 이름 나열만 겹쳤다. 정규화가 쉼표와 공백을 지우므로
짧은 고유명사 다섯 개가 한 덩어리가 된다. **같은 사실을 쓰는 사람은 누구나 같은 이름을 같은
순서로 적으므로 문장을 다시 써서 해소할 수 없고**, 순서를 흩으면 학습 가치가 떨어진다.

**놓치는 것이 없는지 실측했다**: 원본에서 한글이 없는 32자 이상 구간은 52개(3112자, 원본
20400자의 15%)이고 전부 서비스 이름 나열이거나 PDF 추출 아티팩트(`2PAGE47` 같은 쪽번호·
머리말 잔존)다. **영문 산문은 하나도 없다.** 원본이 한국어 자료이므로 이 규칙으로 넘어가는
전사가 없다. 좁힌 뒤에도 검사가 살아 있는지도 확인했다 — 원본의 한국어 문장 하나를 개념
문단에 심으니 40자 일치로 잡고 exit 1로 끝났다.

**임계값은 32자 그대로다.** ADR-009가 "1-exam-gaps 개념 77개가 전부 통과하는 최소값"으로 잰
값이고, 이번 결정은 **무엇을 보는지**만 좁힌다. 임계값을 올려 해소하는 길은 쓰지 않았다 —
근거가 실측이 아니라 임의값이 되고, ADR-009 본문과 코드 주석이 함께 어긋난다.

**트레이드오프**: 한글이 없는 32자 이상을 원본에서 그대로 옮기면 이제 통과한다. 위 실측으로
그런 구간이 이름 나열과 쪽번호뿐임을 확인했지만, 원본이 바뀌어 영문 산문이 들어오면 이 근거가
무너진다. 그래서 넘긴 겹침을 조용히 버리지 않고 **매번 건수와 내용을 찍는다** — 사람이 한 번은
보게 하는 것이 이 규칙의 안전장치다.

### ADR-026: 문제 은행의 크기를 개념 커버리지로 정한다 (PRD 「문제 은행」 개정)
**결정**: 문제 은행의 크기 기준을 **개념 커버리지**로 바꾼다 — **개념 하나에 최소 1문항이고
목표는 100%다.** PRD의 "총 169문항 목표, 22개 주제에 중요도 비례로 배분"을 대체한다.
지금 덮이지 않은 **443개념을 이 phase가 덮는다.** 실측 도구는 `scripts/coverage.mjs`다.

**이유 — 이 앱의 주 학습 경로가 문제 쪽이다**: 사용자가 이 앱의 목적을 "테스트만 계속 풀어도
개념 공부가 다 되어야 한다. 테스트 보고, 틀린 것 개념 보고, 또 테스트 보면서 암기가 되게 하는
것"이라고 정했다. 그러면 **문항이 가리키지 않는 개념은 그 경로에서 아예 배울 수 없는
사각지대**가 된다. 개념 읽기 화면에는 있지만, 문제를 풀며 공부하는 사람은 그 개념을 만나지
못한다. 중요도 비례 배분은 이 사각지대를 만들면서 만든다 — ★★☆ 주제의 개념도 덮이지 않으면
0점이고, ★★★ 주제라도 개념 33개 중 7개만 덮이면 나머지 26개는 없는 것과 같다.
**중요도는 무엇을 먼저 읽을지를 정하는 값이고, 무엇이 배워지는지를 정하는 값은 커버리지다.**
중요도 표시 자체는 주제 목록에서 그대로 산다 — 버리는 것은 문항 수를 나누는 기준으로서의
중요도뿐이다.

**실측 근거**: 개념 618개 중 문항이 가리키는 것은 **175개(28%)** 다. 문항 246개가 서로 다른
개념 175개를 가리킨다 — 한 개념에 여러 문항이 붙기 때문에 246과 175이 어긋난다.
남은 **443개**가 사각지대이고, 그중 문항이 **하나도 없는 주제가 5개**(개념 44개)다:
`s3-access-control`(13) · `redshift-opensearch-quicksight`(11) · `governance-iac`(7) ·
`systems-manager`(7) · `ai-ml-services`(6). 이 주제들은 확인 문제 화면에 들어갈 수조차 없다.

**왜 지금 하는가 — 근거 찾기가 이미 끝나 있다**: 덮이지 않은 443개념 중 **436개(98%)가
phase 26이 `dump-gaps/`에서 들여온 것이고, 항목마다 근거 문장과 덤프 인용(`[Q번호 p쪽]`)을
갖고 있다**(ADR-021). 출제에서 가장 비싼 일은 사실의 근거를 찾는 것인데 그것이 끝나 있으므로
지금이 가장 싸다. 남은 7개는 원래 있던 개념이라 `concepts-raw.md`·`exam-gaps.md`에 근거가 있다
(`cloudfront-global-accelerator.global-accelerator` · `kinesis-streaming` 3개 ·
`redshift-opensearch-quicksight.redshift` · `cloudwatch-xray.x-ray` ·
`cloudwatch-xray.performance-insight`). **출처 규칙은 하나도 넓히지 않는다** — 이 결정은 크기
기준만 바꾸고, 문항의 사실은 여전히 PRD 「원본」의 네 출처에서만 온다.

**커버리지 목표를 좁히지 않는 이유**: "출제 가치가 있는 개념만"으로 좁히면 무엇이 가치 있는지를
앱이 대신 판단하게 되고, 그 판단이 틀린 자리가 곧 사각지대가 되어 목적이 다시 깨진다.
문항이 0개인 5개 주제의 44개념을 실제로 훑어 확인한 결과 **전부 출제 가능하다.** 서비스 정의
(`ai-ml-services.comprehend`), 변별 축(`athena-vs-redshift-workload`), "이건 아니다" 유형
(`s3-cors-not-authorization`) 셋으로 나뉘고, **마지막 유형이 특히 좋은 문항이 된다** —
잘못된 암기를 걸러내는 것이 PRD가 부정형 대조 문항(`q018`)을 지우지 말라고 한 이유와 같다.

**해설을 짧게 쓰지 않는 이유**: 개념당 1문항이 되면 그 개념에 대해 학습자가 읽는 설명 텍스트는
**그 문항의 해설 하나뿐**이다. 게다가 문항 순서가 열 때마다 섞이고(ADR-011) 랜덤 세트는 일부만
뽑으므로(ADR-012) 앞 문항의 해설이 설명해 줬을 것이라고 가정할 수 없다 — ADR-015가 해설마다
약어를 다시 푼 것과 같은 이유다. 그래서 해설은 **정답을 정당화하는 글이 아니라 그 개념을
가르치는 글**이어야 하고, 정답이 왜 맞는지와 오답이 왜 아닌지를 함께 담는다. "A가 맞다" 수준의
한 줄로 줄이면 커버리지 숫자는 100%가 되면서 **학습은 덮이지 않는다.** 숫자만 채우는 것이
이 결정의 가장 큰 실패 방식이므로 규칙으로 적어 둔다.

**검증은 스크립트로 하고 빌드에 엮지 않는다**: `node scripts/coverage.mjs`가 주제별 표와 전체
비율을 내고, 주제 id를 인자로 주면 그 주제에서 덮이지 않은 개념 id를 전부 찍고 exit 1로 끝난다.
**`npm test`·`npm run build`에는 엮지 않는다** — 문항을 채우는 도중에는 덜 덮인 상태가 정상이고,
빌드를 막으면 채우는 작업 자체가 진행되지 않는다. 다 채운 뒤 `src/data/data.test.ts`가
커버리지 100%를 불변식으로 고정하는 것이 이 phase의 마지막 step이다. 의존성은 더하지 않았다 —
Node 18 표준 모듈만 쓴다.

**트레이드오프**: 문제 은행이 246문항에서 **약 700문항**으로 커진다. 복습 화면(오답 전체)과
`/random/all`이 그만큼 길어지므로 ARCHITECTURE 「화면 전환 시 스크롤」의 실측값이 다시 낡는다
(복습 36891px는 오답 246개로 잰 값이다). **그 화면을 어떻게 다룰지는 이 phase 밖의 열린 문제로
남긴다** — ADR-023이 주제 목록 39개를 실물 보고 정할 일로 남긴 것과 같은 성격이고, 미리 정하면
근거 없는 값이 된다. 문항이 늘어나는 것 자체는 결함이 아니다: 같은 문항이 다시 나오는 반복이
이 앱의 학습 장치이고, `Progress`에 남는 것은 여전히 `answers`의 정오답과 `wrong`의 오답노트뿐이라
스키마도 `version`도 그대로다.

**결과 — 실측으로 확인한 것**: 이 결정을 실행하고 나서 다시 쟀다. 문제 은행이 246문항에서
**732문항**이 됐고(`q001`~`q732`, phase 27이 `q247`부터 486문항을 이어 썼다), **개념 618개 중
618개가 문항으로 덮여 커버리지가 100%다**(`node scripts/coverage.mjs` → `남은 개념 0개`, exit 0).
위 트레이드오프가 예상한 "약 700문항"과 실제 732문항이 거의 같다. 개념당 문항은 1개가
기본이고(618개 중 540개) 축이 양방향으로 갈리는 개념에만 둘 이상을 붙였다. 주제별로는
`governance-iac`·`ai-ml-services`가 가장 적은 7문항, `sqs-sns-eventbridge`가 가장 많은 40문항이다.
**문항이 하나도 없는 주제는 없다** — 위 「실측 근거」가 든 5개 주제가 전부 사라졌다.
커버리지 100%는 이제 `src/data/data.test.ts`의 불변식이다: 개념 전부가 문항 하나 이상을 갖는가,
문항의 `topicId`가 `conceptId`의 주제와 같은가, 문항 id가 빈 번호 없이 이어지는가, 새 구간의
정답 위치가 고르게 퍼져 있는가 넷을 단언한다. **예외 목록을 만들어 통과시키지 마라** —
그 목록이 생기는 순간 다음 사람이 거기에 개념을 추가해 사각지대가 되살아난다.

**"확인 문제 준비 중" 가드는 실데이터에서 더는 타지 않지만 지우지 않는다**: 문항이 0개인 주제가
없어졌으므로 `TopicListPage`의 상태 표시와 `ConceptReadPage`의 대체 주 액션(확인 문제 대신
다음 주제로 보내는 링크)은 지금 데이터로는 한 번도 렌더되지 않는다. **그래도 코드와 테스트를
남긴다.** 앞으로 개념을 새 주제로 들여오는 phase가 또 있고, 그 사이 상태에서 학습자를
"아직 확인 문제가 없습니다" 막다른 화면으로 보내지 않는 것이 이 가드의 일이다.
**실데이터에서 타지 않는 것과 코드가 불필요해진 것은 다른 이야기다.** 두 화면의 테스트는
주입한 고정 데이터로 그 분기를 직접 세우므로 실데이터와 무관하게 계속 돈다 — 커버리지가
100%라고 해서 테스트가 무의미해지지 않는다.

**낡은 실측값 하나를 열린 문제로 남긴다**: ARCHITECTURE 「화면 전환 시 스크롤」의 복습 화면
36891px는 오답 246개로 잰 값이라 732문항에서는 훨씬 길어진다. 위 트레이드오프가 예고한
그대로이고, 표에는 **새 숫자를 넣지 않았다** — 그 절의 규칙이 다시 재기 전에는 넣지 말라고
한다. 표 아래에 낡았다는 한 문장만 덧붙였다.

**다른 ADR이 든 246문항은 고치지 않는다**: ADR-012·ADR-017·ADR-018의 트레이드오프에 나오는
246은 그 결정을 내릴 때의 은행 크기이고, 결정의 근거로 읽혀야 하는 값이다. 지금 크기를 말하는
자리는 ADR-002의 트레이드오프와 이 절 둘이다.

### ADR-027: 해설을 다시 쓸 때의 근거는 개념 본문이다 (ADR-006·ADR-008·ADR-009·ADR-021이 정한 출처를 되짚는 자리)
**결정**: `q001`~`q246`의 `explanation`을 다시 쓸 때 사실의 근거는 세 곳이다.

1. 그 문항 `conceptId`가 가리키는 개념의 본문 — `summary`와 `paragraphs`.
2. 오답 보기가 가리키는 **개념의 본문**. 같은 주제의 이웃 개념이 기본이고, 오답이 주제 밖
   개념을 가리키면 그 개념의 본문을 쓴다 — 단 그때는 사양·수치를 가져오지 않고 그 개념이
   무엇인지(성격)만 쓴다.
3. 그 개념이 `docs/source/exam-gaps.md`에 항목으로 있으면 그 항목.

**이 셋 밖의 사실을 해설에 쓰지 않는다.** 모델이 아는 AWS 지식으로 보강하지 마라.

**이것은 출처를 넓히는 결정이 아니다**: ADR-009는 개념 본문을 다시 쓰면서 "의미는 바꾸지
않는다 — 원본에 있던 사실이 빠져도 안 되고, 모델이 아는 AWS 지식을 끌어와 보태도 안 된다"고
못박았다. 그러므로 지금 개념 본문에 있는 사실은 **이미 두 원본의 사실**이고, `dump-gaps/`에서
들여온 개념 본문의 사실은 ADR-021이 인정한 네 번째 출처의 사실이다. 이 결정은 사실의 집합을
하나도 늘리지 않고, **그 사실을 어디서 되짚는지만 지정한다.** 출처를 하나 더 인정한
ADR-008·ADR-021과는 성격이 다르다 — 저 둘은 앱이 다룰 수 있는 사실 자체를 늘렸다.

**왜 지금 이 결정이 필요한가**: 이 phase는 `docs/source/concepts-raw.md`가 없는 환경에서
진행된다. 그 파일은 외부 참고 자료 추출본이라 ADR-009에 따라 gitignore로 로컬에만 두고,
clone한 환경에는 없는 것이 정상이다. `docs/source/dump-gaps/`는 설계상 기존 개념을 일부러
제외했으므로(ADR-021) `q001`~`q246`이 가리키는 개념 175개의 상당수는 거기에도 근거가 없다.
**근거를 어디서 가져오는지 적어 두지 않으면, 해설을 쓰는 세션이 자기가 아는 AWS 지식으로
빈자리를 메운다.** 그것이 이 phase의 가장 큰 실패 방식이므로 규칙으로 박는다.

**오답 근거를 이웃 개념 본문에서 가져오는 이유**: 해설이 담아야 하는 것의 절반이 "오답이 왜
아닌지"다(ADR-026 「해설을 짧게 쓰지 않는 이유」 — 그 절을 여기 되풀어 적지 않는다).
오답 보기는 PRD 「문제 은행」이 정한 대로 같은 주제의 다른 서비스에서 골라져 있으므로,
**그 보기가 가리키는 이웃 개념의 본문이 곧 오답을 설명할 재료다.** 자기 개념 본문이 짧아
쓸 것이 없어 보이는 문항이라도, 보기 넷이 가리키는 개념 본문을 모으면 재료가 모자라는 경우는
없다. 근거가 정말 없으면 사실을 지어내지 말고 그 문항을 그대로 두고 보고해라.

**주제 밖 오답을 어떻게 다루는가 — 실행하며 다듬은 문구다**: 오답이 늘 같은 주제 안에 있는
것은 아니다. `q059`의 「EFS IA」·「인스턴스 스토어」, `q175`의 「FSx for NetApp ONTAP」,
`q177`의 「S3 수명 주기 정책」이 그런 자리이고, phase 28의 step 2·3·4가 연달아 만났다.
이때 **그 개념의 본문을 쓰는 것이 맞다.** 근거는 사실의 집합이 변하지 않는다는 데 있다 —
주제 경계는 ADR-023이 학습 순서를 위해 그은 선이지 출처의 경계가 아니고, 다른 주제의 개념
본문도 같은 두 원본에서 나와 ADR-009의 규칙으로 쓰인 문장이다. 대신 **사양과 수치는
가져오지 않는다.** 이유는 사실의 출처가 아니라 문항의 성립이다: 주제 밖 서비스의 사양을 쓰면
그 주제를 아직 읽지 않은 학습자가 검증할 수 없는 문장이 해설에 들어가고, 오답 하나를 지우는
데 필요한 것은 사양이 아니라 "그것은 무엇을 하는 것인가"이기 때문이다. `q043`의 「최대 12시간」
보기를 아카이브 계열의 성질로만 지운 것이 이 구분의 예다.

**검증의 한계를 정직하게 적는다**: `scripts/check-verbatim.mjs`는 개념의 `summary`·
`paragraphs`만 보고 문항의 `explanation`은 보지 않는다(ADR-025). 그러므로 **해설에 대한 전사
검사는 원래부터 없었고**, `concepts-raw.md`가 이 환경에 없다는 사실이 이 phase에서 새로 잃게
하는 검증은 하나도 없다. 대신 이 phase는 `scripts/explanation-audit.mjs`로 길이 하한을 재고,
마지막 step이 그 하한을 `src/data/data.test.ts`의 불변식으로 고정한다.

**하한을 187자로 잡은 근거**: phase 27이 ADR-026의 규칙 그대로 쓴 해설 486개(`q247`~`q732`)의
**실측 최소값**이다. 임의로 고른 값이 아니다. 그리고 **길이는 목표가 아니다** — 정답이 왜
맞는지와 오답 셋이 왜 아닌지를 담으면 자연히 넘게 되는 하한선이고, 넘기려고 같은 말을 늘려
쓰면 이 결정을 어긴 것이다. 반대로 이 값을 낮춰서 통과시키지도 마라. 낮추는 순간 근거가
실측에서 임의값으로 바뀐다.

**범위는 `explanation` 필드 하나다**: `prompt`·`choices`·`answerIndex`를 건드리지 않는다.
프롬프트는 phase 17~21이 이미 "읽는 것만으로 전제가 서게" 손봤고, 정답 위치 분포와 보기
구성은 `src/data/data.test.ts`가 구간별로 고정하고 있다. 해설만 고치면 그 단언들이 그대로 산다.

**측정 도구를 빌드에 엮지 않는다**: `node scripts/explanation-audit.mjs`는 보고 전용이고
주제 id를 인자로 주면 그 주제의 미달 문항을 찍고 exit 1로 끝난다. `npm test`·`npm run build`에
엮지 않는 이유는 ADR-026이 `coverage.mjs`를 엮지 않은 것과 같다 — 고치는 도중에는 미달 상태가
정상이고, 빌드를 막으면 고치는 작업 자체가 진행되지 않는다. 의존성도 더하지 않는다(Node 18
표준 모듈만 쓴다). 도구가 함께 내는 "오답 언급" 열은 **참고 지표이지 통과 기준이 아니다** —
영문·숫자 토큰이 해설에 나오는지 보는 근사값이라 한국어 서술형 보기에서는 판정 자체가 안 된다.

**착수 시점의 실측**: `q001`~`q246`의 해설은 평균 126자, 최소 58자, 최대 309자이고 **246개 중
229개가 187자 미달**이다. 이미 넘는 17개도 이 phase의 재작성 대상이다 — 하한을 넘는 것과
ADR-026이 요구하는 "그 개념을 가르치는 글"인 것은 다른 이야기이고, 하한은 통과 조건이지
완료 증명이 아니기 때문이다.

**트레이드오프**: `src/data/questions.json`이 바뀌므로 `scripts/check-structure.mjs`의
`questionsSha256`이 어긋난다. 고치는 도중에는 그것이 정상이고 **마지막 step이 한 번에
갱신한다** — step마다 갱신하면 그 가드가 "의도한 변경만 들어왔는가"를 묻지 못하게 된다.
그리고 해설이 길어지므로 확인 문제 화면의 정답 확인 영역이 길어진다. ADR-026이 복습 화면
길이를 열린 문제로 남긴 것과 같은 성격이라 **여기서 새 실측값을 만들지 않는다** —
ARCHITECTURE 「화면 전환 시 스크롤」의 규칙대로, 다시 재기 전에는 숫자를 적지 않는다.
