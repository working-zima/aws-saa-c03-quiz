## serverless-containers

### `lambda-function-url-iam-auth` — 함수 URL의 AWS_IAM 인증 유형

**한 줄**: 함수 URL을 만들 때 인증 유형을 AWS_IAM으로 두면 서명된 요청만 받고 승인은 IAM 정책이 맡는다.

앱의 `lambda-function-url`은 API Gateway 없이 함수에 HTTPS 주소를 붙인다는 것까지 말한다.
문항이 묻는 것은 그 주소를 누가 부를 수 있느냐다. 함수 URL에는 인증 유형 설정이 있고,
이를 AWS_IAM으로 두면 호출자가 요청에 AWS 서명(Signature Version 4)을 붙여야 하며 그 요청을
허용할지는 IAM 정책이 판단한다.

"HTTPS 엔드포인트로 노출하되 호출 인증은 IAM으로 한다"는 두 조건이 함께 붙으면 이 설정
하나로 끝난다. 앞에 API Gateway REST API를 세우고 Lambda 권한 부여자를 따로 만드는 선택지가
같이 나오는데, 권한 부여자는 보통 IAM이 아닌 외부 토큰 방식을 다루는 자리이고 서비스와
요청당 비용이 하나 더 붙는다.

> [Q201 p140] "인증 유형을 AWS_IAM으로 구성하면, 해당 엔드포인트는 요청이 AWS Signature Version4로 서명되고 IAM 정책에 의해 승인되어야 합니다."

### `cloudfront-functions` — CloudFront Functions

**한 줄**: 엣지에서 도는 가벼운 JavaScript 처리로, Lambda@Edge와는 실행 모델도 용도도 다르다.

앱은 `lambda-at-edge`만 다룬다. 엣지에서 코드를 돌리는 선택지는 둘이고, 문항은 그 둘을
나란히 세워 놓는다. CloudFront Functions는 CloudFront 엣지 로케이션에서 도는 경량 JavaScript
처리이고, Lambda@Edge와는 프로그래밍 모델과 배포 방식이 다르다.

둘 다 겨냥하는 자리는 CDN을 지나는 요청과 응답을 손보는 일이다. 리전에 있는 Lambda
마이크로서비스를 엔드포인트로 열어 주는 장치가 아니므로, "함수를 HTTPS로 노출한다"는
요구에는 둘 다 답이 되지 않는다. 특히 CloudFront Functions에는 함수 URL 같은 AWS_IAM 인증
유형이 없다.

> [Q201 p140] "Lambda@Edge와 CloudFront Functions는 서로 다른 프로그래밍 및 배포 모델을 사용하여 CloudFront 엣지 위치에서 실행되며, IAM 인증을 통해 리전별 Lambda 마이크로서비스 엔드포인트를 노출하는 주요 메커니즘이 아닌 CDN 요청/응답 조작을 위해 설계되었습니다."

### `lambda-execution-role-logs` — 로그를 남기려면 실행 역할에 로그 권한이 있어야 한다

**한 줄**: 함수가 CloudWatch Logs에 기록하려면 실행 역할에 로그 그룹·스트림 생성과 이벤트 기록 권한이 붙어 있어야 한다.

Lambda는 실행될 때 자기 실행 역할의 권한으로 움직인다. 그래서 로그가 남지 않는 문제는
로깅 설정이 아니라 그 역할의 권한 문제인 경우가 많다. 필요한 것은 로그 그룹을 만들고
스트림을 만들고 이벤트를 써 넣는 세 가지 쓰기 권한이다.

이미 실행 역할이 붙어 있다면 그 역할에 연결된 정책에 권한을 더하는 것이 답이고, 대상 리소스
쪽에 역할이나 정책을 새로 만드는 선택지는 빗나간다. S3 버킷 정책은 버킷 접근을 정할 뿐
CloudWatch Logs와 무관하고, 로그 이벤트를 **읽는** 권한은 쓰기를 대신하지 못한다.

> [Q202 p141] "AWS 문서에는 Lambda 함수가 로그를 기록하는 데 필요한 권한으로 logs: CreateLogGroup, logs:CreateLogStream 및 logs:PutLogEvents입니다."

### `lambda-layer-size-limit` — Lambda 레이어의 크기 제한

**한 줄**: 레이어는 압축 50MB·해제 250MB 제한이 있는 불변 아티팩트라 계속 늘어나는 데이터를 담는 자리가 아니다.

레이어는 함수와 함께 배포하는 부속 아티팩트다. 크기 상한이 정해져 있고(압축한 상태로 50MB,
푼 상태로 250MB) 한 번 올리면 내용이 바뀌지 않는다.

그래서 "파일이 계속 쌓이는 공유 저장소"를 레이어로 대신하려는 선택지는 지운다. 데이터가
늘어나면 상한에 걸리고, 늘어날 때마다 레이어를 다시 만들어 함수에 붙여야 한다. 그 자리는
EFS 같은 파일 시스템이 맡는다.

> [Q218 p153] "Lambda 레이어는 엄격한 크기 제한(압축 시 최대 50MB/압축 해제 시 250MB)가 있는 불변 아티팩트이므로 동적이며 지속적으로 증가하는 파일 세트에는 적합하지 않습니다."

### `lambda-reserved-concurrency` — 예약된 동시성은 콜드 스타트를 줄이지 않는다

**한 줄**: 예약된 동시성은 그 함수 몫의 동시 실행 수를 떼어 두는 값이고, 실행 환경을 미리 띄우는 것은 프로비저닝된 동시성이다.

이름이 비슷해 선택지에 나란히 오르는 두 설정이다. 앱의 `lambda` 개념과 `Q001-Q050.md`의
`lambda-provisioned-concurrency-autoscaling`은 프로비저닝된 동시성 쪽만 다룬다.

갈림길은 무엇을 미리 하느냐다. 프로비저닝된 동시성은 실행 환경을 미리 초기화해 두므로
첫 호출의 콜드 스타트가 사라지고 응답 시간이 일정해진다. 예약된 동시성은 용량을 예약해
둘 뿐이라 환경을 미리 만들어 두지 않으며, 콜드 스타트는 그대로 남는다.

"피크 시간대에도 일관되게 낮은 지연"이 조건이면 프로비저닝된 쪽이고, 예약된 동시성이 붙은
선택지는 그 조건을 채우지 못한다.

> [Q245 p169] "예약된 동시 실행은 콜드 스타트를 해결하지 않으며, 단지 용량을 예약할 뿐입니다."

## messaging-backup

### `sqs-visibility-timeout-vs-processing-time` — 가시성 타임아웃은 처리 시간보다 길어야 한다

**한 줄**: 처리가 끝나기 전에 가시성 타임아웃이 지나면 같은 메시지가 다시 보여 중복 처리된다.

`Q001-Q050.md`의 `sqs-batch-and-polling`은 가시성 타임아웃이 "가져간 메시지를 다른 소비자에게
얼마 동안 숨기는 값"이라고만 말한다. 문항이 묻는 것은 그 값을 얼마로 잡느냐다.

소비자가 메시지를 가져가면 그 값 동안 숨겨지고, 처리를 마치고 삭제해야 사라진다. 삭제하기
전에 시간이 지나면 메시지가 다시 큐에 나타나 같은 소비자든 다른 소비자든 한 번 더 집어
간다. 이것이 "중복 메시지를 처리한다"는 증상의 정체이고, 고치는 방법은 가시성 타임아웃을
소비자의 최대 처리 시간 이상으로 올리는 것이다. Lambda를 소비자로 쓰면 그 기준은 함수의
타임아웃 값이 된다.

같이 나오는 **전달 지연**은 다른 값이다. 메시지를 큐에 넣은 뒤 소비자에게 처음 보이기까지를
미루는 설정이라, 이미 가져간 메시지가 되살아나는 재처리에는 손대지 못한다. 메모리를 늘리거나
함수 타임아웃을 더 늘리는 것도 이 증상과는 무관하다.

> [Q207 p144] "Lambda 함수가 가시성 타임아웃 기간 내에 메시지를 처리하고 큐에서 삭제하지 않으면, 메시지가 다시 가시화되어 동일한 함수 인스턴스나 다른 함수 인스턴스에 의해 다시 처리될 수 있습니다."

### `eventbridge-ordering-and-retention` — EventBridge가 보장하지 않는 것

**한 줄**: 이벤트 순서를 보장하지 않고 24시간을 넘겨 보관하지도 않으므로, 순서와 장기 보존이 조건이면 지운다.

EventBridge는 이벤트를 규칙에 맞춰 대상으로 흘려보내는 라우터다. 여러 수신자에게 같은 것을
뿌리는 모양이 스트림과 닮아 보여서 선택지에 함께 오르지만, 두 가지를 약속하지 않는다.

첫째, 보낸 순서대로 도착한다는 보장이 없다. 둘째, 이벤트를 24시간 넘게 들고 있지 않는다.
그래서 "메시지 순서를 엄격히 지켜야 한다"거나 "게시한 것을 몇 달 이상 보관해야 한다"는
조건이 붙으면 이 서비스는 답이 되지 못한다. 그 자리는 샤드 안에서 순서를 지키고 보존 기간을
길게 잡을 수 있는 스트림 쪽이다.

> [Q208 p144] "EventBridge는 엄격한 순서 보장을 제공하지 않으며, 24시간을 초과하는 메시지 보존도 지원하지 않습니다."

## aurora-dynamodb-cache

### `aurora-storage-configurations` — Aurora Standard와 Aurora I/O-Optimized

**한 줄**: Aurora의 스토리지 선택은 볼륨 유형이 아니라 두 가지 클러스터 구성 중 하나를 고르는 일이다.

RDS는 범용 SSD와 프로비저닝된 IOPS처럼 볼륨 유형을 고르지만, Aurora는 그렇지 않다. 클러스터에
붙는 것은 **Aurora Standard**와 **Aurora I/O-Optimized** 두 가지 스토리지 구성이고, 선택지에
General Purpose나 Provisioned IOPS가 보이면 Aurora 문항에서는 그 자체로 어긋난 답이다.

I/O-Optimized는 일관된 고성능을 목표로 한 구성이다. 부하가 늘어도 IOPS를 따로 프로비저닝할
필요가 없고 스토리지 쪽이 알아서 확장되므로, 수동으로 성능을 조정할 일이 줄어든다.
"부하 증가에 맞춰 스토리지 성능을 최적화한다"는 조건이 붙은 자리에 들어간다.

> [Q214 p150] "Aurora I/O-Optimized: 이 스토리지 구성은 Aurora 데이터베이스에 일관된 고성능을 제공하도록 설계되었습니다."

### `dax-encryption-at-rest` — DAX의 저장 중 암호화는 만들 때만 켠다

**한 줄**: 이미 돌아가는 DAX 클러스터에는 저장 중 암호화를 나중에 켤 수 없어서, 암호화를 켠 새 클러스터를 만들어 옮겨야 한다.

앱의 `dynamodb`와 `dax-dynamodb-only`는 DAX를 캐시로만 다룬다. 문항은 그 캐시의 보안 설정을
묻는다. DAX는 저장 중 암호화를 클러스터를 만드는 시점에만 켤 수 있다.

그래서 "암호화가 꺼진 채로 돌고 있는 클러스터를 고쳐라"는 요구의 답은 설정 변경이 아니다.
클러스터를 멈췄다 켜거나 구성을 수정하는 선택지는 전부 지운다. 암호화를 켠 클러스터를 새로
만들고 워크로드를 그쪽으로 옮기는 것이 유일한 경로다.

> [Q227 p158] "DAX는 기존 클러스터에서 저장 중 암호화를 활성화하는 기능을 지원하지 않습니다."

### `read-replica-no-schema-change` — 읽기 전용 복제본에서는 스키마를 바꿀 수 없다

**한 줄**: 복제본은 읽기 전용이라 테이블 구조를 고칠 수 없고, 스키마 변경을 미리 시험하는 자리는 블루/그린 배포다.

앱의 `features`는 읽기 전용 복제본이 읽기 부하를 나눠 받는다는 것과, 블루/그린 배포가 그린
환경에서 변경을 검증한 뒤 트래픽을 넘긴다는 것을 각각 말한다. 문항은 둘을 한 선택지 안에
세워 놓고 고르게 한다.

가르는 사실은 하나다. 읽기 전용 복제본은 스키마 변경을 받지 않는다. 그래서 "복제본에서
스키마를 고친 뒤 승격한다"는 선택지는 첫 단계에서 이미 막힌다. 스키마를 자주 바꿔 시험하고
검증이 끝나면 최소한의 중단으로 운영에 반영해야 한다는 요구는 블루/그린 배포가 맡는다.

> [Q231 p160] "읽기 복제본(옵션 B)은 스키마 변경을 허용하지 않습니다."

## rds-storage-features

### `rds-manual-snapshot-retention` — 수동 스냅샷은 지울 때까지 남는다

**한 줄**: 자동 스냅샷은 보존 기간이 지나면 삭제되지만, 그 스냅샷을 수동으로 복사해 두면 직접 지울 때까지 보존된다.

앱의 `automated-backup-retention`은 자동 백업의 보존 한계가 35일이고 그 이상은 AWS Backup으로
간다고 말한다. 문항은 그 사이에 있는 요구를 낸다 — 계획 전체가 아니라 **특정 스냅샷 하나**를
보존 기간보다 오래 남겨야 하는 경우다.

자동 스냅샷은 설정한 보존 기간이 지나면 자동으로 지워진다. 반면 수동 스냅샷은 만료가 없고
사용자가 명시적으로 지울 때까지 남는다. 그래서 자동 스냅샷을 수동 스냅샷으로 복사해 두는
것이 그 시점의 백업을 오래 들고 있는 표준 방법이 된다.

보존 기간 값을 더 큰 숫자로 바꾸는 선택지는 지원 한계를 넘지 못해 막히고, 스냅샷을 S3로
내보내거나 엔진의 자체 백업 기능을 쓰는 방법은 형식과 복원 절차를 따로 관리해야 해서 손이
더 간다.

> [Q244 p168] "그러나 수동 스냅샷은 사용자가 명시적으로 삭제할 때까지 보존되므로, 자동 스냅샷을 수동 스냅샷으로 변환(복사)하는 것이 장기 보관을 위한 특정 시점 백업을 유지하는 표준 운영 방식입니다."

## block-file-storage

### `efs-cross-account-mount` — 계정을 넘어 EFS를 마운트한다

**한 줄**: 두 VPC 사이에 네트워크 경로를 열고 마운트 대상 보안 그룹에서 NFS 포트를 허용하면 다른 계정의 파일 시스템도 마운트할 수 있다.

앱의 `efs`는 여러 컴퓨터가 같은 파일 시스템을 함께 쓴다는 데까지 말한다. 문항은 그 "여러
컴퓨터"가 다른 AWS 계정에 있을 때를 묻는다. 파일 시스템을 복사하지 않고도 마운트할 수 있고,
필요한 것은 데이터 이동이 아니라 경로다.

세 가지가 있으면 된다. VPC 피어링 같은 네트워크 연결, 마운트 대상 보안 그룹에서 NFS가 쓰는
TCP 2049 포트 허용, 그리고 접근 범위를 좁힐 액세스 포인트와 파일 시스템 정책이다. 이 구성은
시간당 요금이 붙는 장치를 새로 두지 않고, 파일이 늘어나면 EFS가 알아서 커진다.

DataSync로 새 파일 시스템에 복사하는 선택지는 같은 데이터를 두 벌 두게 되고 동기화 시차가
생긴다. 계정마다 함수를 두어 서로 호출하게 하는 구성은 공유 파일 시스템 자체를 주지 못한다.

> [Q218 p153] "EFS 마운트 대상에 네트워크 연결(예: VPC 피어링)을 제공하고 마운트 대상 보안 그룹에서 NFS(TCP 2049)를 허용함으로써, 선택적으로 EFS 액세스 포인트와 파일 시스템 정책을 사용하여 계정 간 액세스 제어를 구현하여 VPC 간 및 AWS 계정 간에 EFS를 마운트할 수 있습니다."

### `fsx-ontap-iscsi-block` — ONTAP은 iSCSI로 블록 스토리지를 내준다

**한 줄**: FSx for NetApp ONTAP은 LUN을 iSCSI로 노출해, 여러 AZ의 인스턴스가 공유하는 블록 스토리지가 된다.

앱의 `fsx`는 ONTAP이 NFS와 SMB를 지원한다고 하고 `fsx-ontap-multi-az`는 다중 AZ 배포와 밀리초
미만 접근을 말한다. 둘 다 파일 공유 이야기다. 문항이 요구하는 것은 **블록** 스토리지이고,
여러 AZ에서 낮은 지연으로 공유되어야 한다는 조건이 붙는다.

ONTAP은 이 자리도 맡는다. LUN을 iSCSI 프로토콜로 노출하면 AZ가 다른 EC2 클라이언트들이 같은
블록 스토리지에 붙을 수 있고, 다중 AZ 배포가 장애 조치를 맡아 고가용성까지 따라온다.

EBS는 한 AZ 안의 인스턴스 하나에 붙는 블록 스토리지라 이 조건을 채우지 못한다. AZ마다 볼륨을
따로 두고 스크립트로 맞추는 선택지는 지연과 복잡성만 늘 뿐 고가용성이 되지 않는다.

> [Q247 p170] "iSCSI 프로토콜을 통해 ONTAP LUN을 노출함으로써, AZ 전반의 EC2 클라이언트에 낮은 지연 시간과 일관된 성능을 갖춘 공유 블록 스토리지 기능을 제공합니다."

## vpc-networking

### `nat-gateway-per-az` — NAT 게이트웨이는 가용 영역마다 둔다

**한 줄**: 게이트웨이 하나는 그 AZ에 묶이므로, 인터넷 경로를 잃지 않으려면 AZ마다 하나씩 두고 경로를 그쪽으로 잡는다.

앱의 `nat-gateway`는 이 장치가 퍼블릭 서브넷에 놓이고 나가는 방향만 열어 준다는 데까지
말한다. 문항은 여러 AZ에 걸친 구성에서 그것을 몇 개 두느냐를 묻는다.

NAT 게이트웨이는 자기가 놓인 가용 영역 안에서 동작한다. 하나만 두면 그 AZ에 문제가 생겼을 때
다른 AZ의 프라이빗 서브넷까지 인터넷으로 나가지 못한다. 그래서 고가용성이 조건이면 AZ마다
퍼블릭 서브넷에 하나씩 두고, 각 AZ의 프라이빗 서브넷이 자기 AZ의 게이트웨이로 나가도록
라우팅을 잡는다.

> [Q232 p161] "고가용성 아키텍처를 구축하려면 각 가용 영역에 NAT 게이트웨이를 생성하고 라우팅을 구성하여 이를 사용하도록 설정하십시오."

## hybrid-connectivity

### `centralized-onprem-egress` — 아웃바운드 인터넷을 온프레미스로 되돌린다

**한 줄**: 클라우드에서 나가는 인터넷 트래픽을 데이터 센터의 NAT·방화벽으로 모으려면 퍼블릭 서브넷을 아예 두지 않는다.

앱은 인터넷으로 나가는 길을 인터넷 게이트웨이와 NAT 게이트웨이로 설명한다. 문항은 그 반대
방향의 요구를 낸다 — 검사와 통제를 한곳에 모으려고 **클라우드의 아웃바운드 트래픽을 기존
데이터 센터를 거쳐 인터넷으로 내보내는** 구성이다.

이때 VPC에는 프라이빗 서브넷만 둔다. 인터넷 게이트웨이를 붙이면 트래픽이 그리로 바로 빠져
나가 중앙 집중이라는 목적이 깨지기 때문이다. 대신 Transit Gateway와 고객 게이트웨이 쪽으로
기본 경로를 잡아, 나가는 트래픽이 전용선이나 VPN을 타고 데이터 센터의 NAT 또는 방화벽을
지나게 한다.

> [Q217 p152] "클라우드 리소스의 인터넷 트래픽을 온프레미스 데이터 센터를 통해 다시 라우팅하려면(중앙 집중식 아웃바운드 전송을 위해), 프라이빗 서브넷만 프로비저닝하고 데이터 센터 내 NAT 또는 방화벽 서비스를 통해 아웃바운드 인터넷 트래픽을 라우팅해야 합니다."

### `outposts-data-residency` — 데이터를 옮기지 않고 관리형 서비스를 데이터 쪽으로 옮긴다

**한 줄**: 규정 때문에 데이터를 클라우드로 올릴 수 없으면, Outposts에 관리형 서비스를 올려 데이터가 있는 자리에서 처리한다.

`Q001-Q050.md`의 `region-attached-edge-options`는 Outposts가 리전과의 연결 위에서 동작한다는
제약을 말한다. 문항이 쓰는 것은 그 반대편, 이 장치가 무엇을 가능하게 하는가다.

Outposts는 AWS 인프라와 서비스를 사용자의 시설로 확장한다. 그래서 "데이터를 클라우드로
이전하면 안 되는데 AWS의 관리형 분석은 쓰고 싶다"는 요구가 성립한다 — 데이터를 옮기는
대신 Outposts 위에 EMR 같은 관리형 서비스를 띄우고 그 자리에서 처리하면 데이터 상주 요건을
지키면서 관리형 서비스의 이점을 얻는다.

리전 안에 관리형 데이터베이스나 클러스터를 만들어 온프레미스와 연결하는 선택지들은 결국
데이터를 클라우드로 옮기거나 내보내는 구성이라 이 요건과 부딪힌다.

> [Q229 p159] "Outposts에서 Amazon EMR을 실행하면 EMR의 관리형 서비스 혜택을 누리면서 로컬에 저장된 데이터를 처리할 수 있습니다."

## analytics-monitoring

### `kinesis-record-size-limit` — 스트림에 넣을 수 있는 레코드 크기

**한 줄**: Kinesis Data Streams의 레코드 하나는 최대 1MB라, 수백 KB짜리 메시지도 그대로 실을 수 있다.

`Q151-Q200.md`의 `kinesis-retention-and-fanout`은 보존 기간과 소비자 구조를 다룬다. 문항이
쓰는 또 하나의 축은 메시지 하나의 크기다.

Kinesis Data Streams는 레코드 하나를 최대 1MB까지 받는다. "메시지가 500KB에 이른다"처럼 크기가
조건으로 오르면 이 한계 안에 들어가는지부터 확인하게 되고, 초당 수천 건과 긴 보존과 순서
보장이 함께 걸린 문항에서 이 값이 스트림을 답으로 굳히는 근거가 된다.

> [Q208 p144] "대용량 메시지: 최대 1MB 크기의 메시지를 지원하므로 500KB 요구 사항을 충족합니다."

### `emr-managed-scaling` — EMR 관리형 스케일링

**한 줄**: 워크로드에 맞춰 클러스터의 노드 수를 자동으로 늘리고 줄여, 놀고 있는 노드의 비용을 없앤다.

`Q001-Q050.md`의 `emr-node-types`와 `emr-transient-cluster`는 노드 역할과 클러스터 수명을
다룬다. 남는 문제가 하나 있다 — 클러스터가 도는 **동안** 노드가 놀고 있는 경우다.

관리형 스케일링은 작업 부하를 보고 노드를 더하거나 뺀다. 긴 작업 안에서도 필요할 때만 노드가
붙어 있으므로 유휴 시간이 줄고 비용도 함께 준다. 로그를 보니 여러 노드가 몇 시간씩 놀고
있더라는 상황의 답이 여기다.

코어 노드를 더 넣는 선택지는 활용도가 낮은 원인을 그대로 두고 놀고 있는 노드만 늘린다.
인스턴스 유형을 메모리 최적화로 바꾸는 것도 유휴 시간을 줄여 주지는 않는다.

> [Q250 p172] "EMR 관리형 스케일링은 워크로드에 따라 노드를 추가하거나 제거하여 클러스터의 크기를 동적으로 조정합니다."

## (주제 미정)

기존 20개 주제 어디에도 자리가 없는 개념이다. 주제 배치는 phase 26이 정한다.

### `control-tower-landing-zone` — Control Tower의 랜딩 존

**한 줄**: 다중 계정 환경의 기준 골격을 자동으로 세워, 계정이 늘어도 같은 통제와 로깅이 처음부터 걸려 있게 한다.

`Q001-Q050.md`의 `control-tower-controls`는 제어가 언제 작동하는지(사전 예방·탐지)를 다룬다.
문항이 쓰는 것은 그 앞 단계, 이 서비스가 애초에 무엇을 만들어 주는가다.

Control Tower는 모범 사례를 따르는 다중 계정 환경을 세우고 관리하는 통로다. 계정 구조와
통제, 중앙 집중식 로깅·모니터링을 갖춘 기준 환경(랜딩 존)을 자동으로 구성하므로, 부서마다
계정을 나눠 쓰는 조직에서 계정이 늘어날 때마다 같은 설정을 손으로 되풀이하지 않아도 된다.

계정별로 무엇을 쓸 수 있는지 제한하는 일은 SCP가 맡고, 모든 계정의 루트 사용자에 MFA를
적용하는 것도 이 환경이 걸어 주는 보호 장치에 포함된다. 계정마다 사용자와 역할을 따로
관리하거나 권한 경계로 서비스 제한을 흉내 내는 선택지는 중앙 통제라는 요구와 어긋난다.

> [Q206 p143] "AWS Control Tower는 AWS 모범 사례를 기반으로 안전한 다중 계정 AWS 환경을 설정하고 관리할 수 있는 간편한 방법을 제공합니다."

### `warm-standby-for-low-rto` — 짧은 RTO는 미리 떠 있는 환경을 요구한다

**한 줄**: 복구 목표가 분 단위 아래로 내려가면 대기 리전의 인스턴스가 실제로 돌고 있어야 하고, 전환은 상태 점검이 자동으로 해야 한다.

복구 시간 목표(RTO)가 백업과 복원으로 감당되는 구간이 있고, 그렇지 않은 구간이 있다.
60초처럼 짧은 값이 걸리면 장애가 난 뒤에 무엇을 만들거나 켜는 절차가 들어갈 자리가 없다.

그래서 두 가지가 미리 준비돼 있어야 한다. 대기 리전에 로드 밸런서와 최소한의 인스턴스가
**실제로 실행 중**이어야 하고, 전환을 사람이나 사후 조작이 아니라 상태 점검을 건 DNS 장애
조치가 맡아야 한다. 데이터 쪽은 리전 간 복제로 미리 따라가 있어야 한다.

대기 인스턴스를 종료해 두는 선택지는 시작 시간을 그대로 RTO에 얹고, 스냅샷이나 템플릿으로
장애 뒤에 인프라를 만드는 선택지는 그보다 더 오래 걸린다. 필요할 때 DNS 레코드를 손으로
바꾸는 방식도 마찬가지다.

> [Q222 p155] "60초 RTO를 달성하려면 DR 환경을 사전 워밍업(EC2 인스턴스 및 Route53 상태 점검 포함)을 미리 준비하는 것이 필수적입니다."

## 원본 수정 이력

덤프 해설을 그대로 따르지 않은 것이다. 근거는 ADR-008의 예외를 승계한 ADR-021.

### 사실 오류라 싣지 않은 것

- **Q214 p150** — Aurora I/O-Optimized를 두고 "실제로 사용한 스토리지와 I/O에 대해서만 비용을
  지불한다"고 설명한다. 이것은 I/O마다 요금이 붙는 Aurora Standard 쪽 과금 방식이고,
  I/O-Optimized는 그 반대로 I/O 요금을 따로 물리지 않는 구성이다. 설명이 두 구성을 뒤바꿔
  놓았으므로 `aurora-storage-configurations`에는 과금 서술을 옮기지 않고, 두 구성이 있다는
  사실과 IOPS를 따로 프로비저닝하지 않는다는 사실만 실었다.
  > [Q214 p150] "비용 효율성: Aurora I/O-Optimized를 사용하면 실제로 사용한 스토리지와 I/O에 대해서만 비용을 지불하므로, I/O 수요가 변동적이고 예측하기 어려운 애플리케이션에 비용 효율적인 솔루션입니다."

- **Q238 p165** — 프라이빗 서브넷들이 라우팅 테이블 하나를 공유하는 쪽을 정답 근거로 들면서,
  서브넷마다 테이블을 두는 것은 "불필요한 복잡성"이라고 적었다. 그런데 같은 해설집이
  Q232에서는 AZ마다 NAT 게이트웨이를 두고 각자 그것을 쓰도록 라우팅하라고 말한다. 테이블
  하나를 공유하면 모든 AZ의 트래픽이 게이트웨이 하나로 몰려 AZ마다 둔 이유가 사라지므로 두
  서술이 서로 어긋난다. `nat-gateway-per-az`에는 Q232 쪽 서술만 실었고 라우팅 테이블 공유
  주장은 가져오지 않았다.
  > [Q238 p165] "옵션 A: 각 서브넷마다 별도의 경로 테이블을 생성하면 불필요한 복잡성이 증가합니다."

- **Q245 p169** — 정답이 B(프로비저닝된 동시성)이고 해설 본문도 프로비저닝된 동시성이
  콜드 스타트를 줄인다고 설명하는데, 마지막 문장만 "예약된 동시 실행을 사용하는 Lambda"가
  최선이라고 적어 자기 정답과 어긋난다. `lambda-reserved-concurrency`는 정답과 본문 쪽을
  따랐다.
  > [Q245 p169] "이 문제는 일관된 낮은 지연 시간을 유지하면서 운영 오버헤드를 최소화하는 방안을 묻고 있으므로, API Gateway와 예약된 동시 실행을 사용하는 Lambda를 기반으로 한 서버리스 패턴이 가장 강력한 AWS 네이티브 솔루션입니다."

### [AI 작성 해설]이라 채택하지 않은 것

해설집이 스스로 새로 썼다고 밝힌 해설이다. 다른 문항의 근거와 교차 확인되지 않아 넘겼다.

- **Q220 p154** — 표시가 `[AI 작성 해설] 기록된 정답 C → AWS 기준 B`다. 정답이 갈리는
  문항이고, 해설이 드는 사실(API Gateway의 사용량 계획과 API 키로 클라이언트별 액세스 제어와
  스로틀링을 한다)은 앱의 `api-gateway`에도 앞 step에도 없어 새 개념이 될 만하다. 다만 근거가
  이 해설 하나뿐이고 이 슬라이스에 교차 확인할 해설이 없다. 뒤 슬라이스에서 같은 사실이 원본
  해설로 확인되면 그때 만든다.

- **Q237 p165** — 표시가 `[AI 작성 해설]`이다. 해설이 드는 사실 둘 중 게이트웨이 엔드포인트가
  S3와 DynamoDB에만 있다는 것은 앱의 `vpc-networking.vpc-endpoint`에 이미 있고, 인터페이스
  엔드포인트로 AWS 서비스 API를 프라이빗하게 부르는 것도 같은 개념에 있다. 남는 것은 프라이빗
  NAT 게이트웨이의 용도인데, 근거가 이 해설 하나뿐이라 넘겼다.
