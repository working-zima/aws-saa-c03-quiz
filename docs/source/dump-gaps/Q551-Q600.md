## data-transfer-services

### `dms-full-load-and-cdc-task` — 전체 로드와 CDC를 한 태스크로 건다

**한 줄**: 원본과 대상을 계속 같은 상태로 두려면 복제 태스크를 전체 로드와 변경 데이터 캡처를 함께 하는 유형으로 만들고, 매핑에서 옮길 테이블을 모두 고른다.

`Q001-Q050.md`의 `dms-sct`는 DMS가 옮기는 동안 생긴 변경까지 이어서 복제한다는 것과 SCT가
스키마를 맞춘다는 것을 다룬다. 문항이 묻는 것은 그 복제를 **어떻게 설정하는가**다.

복제 태스크에는 이미 쌓여 있는 데이터를 한 번에 옮기는 전체 로드와, 그 뒤에 생기는 변경만
따라가는 변경 데이터 캡처(CDC)가 있고 둘을 함께 하는 유형을 고를 수 있다. 애플리케이션을
한 달 간격으로 하나씩 넘기는 것처럼 전환이 길게 이어지면 이 유형이 답이다 — CDC만 걸면
기존 데이터가 넘어가지 않고, 전체 로드만 걸면 그 뒤의 변경이 갈라진다. 테이블 매핑에서
큰 테이블만 고르는 구성도 같은 이유로 지워진다. 동기화 대상은 전체 테이블이다.

복제 태스크를 돌리는 복제 인스턴스도 고르는 값이다. 원본의 읽기·쓰기가 잦아 변경이 많이
발생하면 메모리 최적화 인스턴스가 그 부하에 맞고, 컴퓨팅 최적화 쪽은 이 조건에서 밀린다.
DataSync는 파일과 객체를 옮기는 서비스라 관계형 데이터베이스 마이그레이션의 자리가 아니다.

> [Q594 p400] "올바른 권장 사항은 AWS 스키마 변환 도구(AWS SCT)를 AWS DMS와 함께 사용하여 전체 로드 및 CDC 마이그레이션을 실행함으로써, 단계적 애플리케이션 전환 기간 동안 Oracle과 Aurora PostgreSQL이 동기화 상태를 유지하도록 하는 것입니다."

### `transfer-family-workflow-actions` — 워크플로에 이미 들어 있는 액션들

**한 줄**: 업로드 후 워크플로는 Lambda를 부르는 것 말고도 복호화(DECRYPT)와 복사(COPY) 같은 기본 액션을 그대로 쓸 수 있다.

`Q351-Q400.md`의 `transfer-family-workflow`는 업로드 뒤의 처리를 워크플로로 정의해 Lambda
함수를 호출할 수 있다는 데까지 다룬다. 남는 것은 **함수를 만들지 않고도 되는 일이 있다**는
점이다.

워크플로 단계에는 미리 정의된 액션이 있다. DECRYPT는 올라온 암호화 파일을 푸는 액션이고,
COPY는 그 결과를 같은 버킷의 다른 디렉터리에 놓는 액션이다. SFTP로 암호화 파일을 받아
풀고 다음 처리 디렉터리로 옮기는 요구는 이 둘로 끝나므로, S3 이벤트 알림으로 함수를 부르거나
배치 작업이 버킷을 주기적으로 훑는 구성은 같은 일을 더 많은 부품으로 하는 셈이 된다.

> [Q591 p398] "DECRYPT 액션은 관리형 워크플로의 일환으로 업로드된 암호화된 파일을 복호화하도록 특별히 설계되었습니다."

## aurora-dynamodb-cache

### `aurora-clone` — Aurora 클론은 Aurora에만 있다

**한 줄**: 클러스터를 빠르게 복제하는 클론 기능은 Aurora 전용이라, RDS for Oracle 같은 일반 RDS 엔진에는 쓸 수 없다.

보기 줄에 "클론을 만들어 특정 시점 복원을 대신한다"가 올라오는 문항이 있다. 클론은 실제
기능이지만 붙는 자리가 정해져 있다 — Aurora 클러스터다.

원본이 RDS for Oracle이나 RDS for MySQL 같은 일반 RDS 인스턴스라면 이 선택지는 서비스가
달라서 지워진다. 백업 보존을 길게 가져가면서 특정 시점 복원도 필요한 요구는 그 자리에서
AWS Backup 쪽으로 넘어간다 — 앱의 `messaging-backup.backup-long-term-retention`이 그 판단이고,
RDS 자동 백업의 35일 한계는 앱의 `rds-storage-features.automated-backup-retention`에 있다.

> [Q566 p382] "옵션 C(Aurora 클론): Aurora 클론은 Amazon Aurora 전용 기능으로, Amazon RDS for Oracle에는 적용할 수 없습니다."

### `dynamodb-export-no-read-capacity` — S3 내보내기는 테이블의 읽기 용량을 쓰지 않는다

**한 줄**: 테이블을 S3로 내보내는 작업은 프로비저닝된 읽기 용량을 소모하지 않아, 운영 처리량을 그대로 두고 데이터를 빼낼 수 있다.

`Q501-Q550.md`의 `dynamodb-export-requires-pitr`은 이 기능의 전제 조건을, `dynamodb-s3-export-vs-streams`는
언제 이 기능을 고르는지를 다룬다. 문항이 하나 더 붙이는 조건이 **테이블의 처리량을 유지하라**다.

내보내기는 테이블을 스캔하는 방식이 아니라서 프로비저닝된 읽기 용량을 쓰지 않고, 그동안
테이블 성능도 떨어지지 않는다. 반대로 외부 도구가 테이블을 직접 읽어 가는 구성은 스캔이
일어나 읽기 용량을 소모하고 스로틀링을 부를 수 있다. "처리량을 유지해야 한다"가 조건에
들어 있으면 이 한 줄이 두 선택지를 가른다.

> [Q565 p382] "DynamoDB를 Amazon S3로 내보내는 작업(시점별 내보내기 또는 테이블 백업)은 "읽기 용량을 소모하지 않으며" 테이블 성능에 영향을 미치지 않습니다."

### `dynamodb-ttl-deletion-delay` — TTL 삭제는 만료 시각에 딱 맞춰 일어나지 않는다

**한 줄**: 만료된 항목은 대개 만료 시각으로부터 48시간 안에 지워지므로, 삭제 기한이 시간 단위로 촘촘하면 TTL만으로는 맞추지 못한다.

`Q051-Q100.md`의 `dynamodb-ttl`은 만료 시각 속성을 지정하면 항목이 자동으로 지워진다는
것까지 다룬다. 그 삭제가 **언제** 일어나는지는 문항이 요구 기한을 걸 때 갈림길이 된다.

TTL은 만료 시각이 지난 항목을 배경에서 지우는 구조라 정확히 그 순간에 사라지지 않는다.
보통 만료 시각으로부터 48시간 이내에 삭제가 끝나므로, "삭제 요청 뒤 한 달 안에 지운다"
같은 여유 있는 기한은 TTL 속성 값을 그 시점으로 써 두는 것만으로 충족된다. 사용자가 삭제를
요청할 때 함수가 만료 시각을 계산해 속성에 기록하고, 실제 삭제는 DynamoDB에 맡기는 형태다.
스트림이나 구성 변경 감시 서비스를 얹어 삭제 시점을 직접 잡는 구성은 기본 기능으로 되는 일에
부품을 더한다.

> [Q590 p397] "삭제는 일반적으로 TTL 타임스탬프로부터 48시간 이내에 발생하며, 이는 "1개월 이내"라는 요구 사항을 충족합니다."

## compute-delivery

### `global-accelerator-vs-dns-failover` — DNS 캐시에 발목 잡히지 않는 장애 조치

**한 줄**: 진입점이 변하지 않는 애니캐스트 IP라서 리전을 바꿔도 클라이언트가 새 주소를 다시 조회할 필요가 없고, DNS TTL이 만료되기를 기다리지도 않는다.

`Q001-Q050.md`의 `global-accelerator-static-ip`는 고정 IP가 DNS 관리를 단순하게 만든다는
쪽을 본다. 문항이 쓰는 축은 그 고정 IP가 **장애 조치 속도**에 무엇을 하느냐다.

Route 53의 라우팅 정책으로 리전을 바꾸면 전환은 결국 DNS 응답이 바뀌는 것으로 일어난다.
그런데 리졸버와 클라이언트가 이전 응답을 캐시에 들고 있으면 그 값이 만료될 때까지 옛 리전으로
계속 간다. Global Accelerator는 전 세계에서 같은 애니캐스트 IP로 받고 그 뒤의 경로만 AWS
네트워크 안에서 바꾸므로, 클라이언트가 보는 주소가 변하지 않고 DNS TTL을 기다릴 일도 없다.
엔드포인트 상태를 계속 확인해 비정상 리전을 빼는 것도 이 서비스 쪽에서 일어난다.

그래서 "오래된 DNS 캐시를 피해야 한다", "IP 주소 캐싱에 의존하지 않아야 한다", "두 리전에
단일 엔드포인트를 준다"가 조건에 붙으면 Route 53 라우팅 정책 선택지가 통째로 지워진다.
CloudFront는 콘텐츠를 캐싱해 전달하는 쪽이라 실시간 양방향 통신의 리전 장애 조치를 맡지 않는다.

> [Q564 p382] "AWS는 DNS TTL 값에 의존하지 않고 트래픽을 최적의 정상 리전으로 전송하므로, 오래된 DNS 캐시로 인한 위험을 제거합니다."

### `cloudfront-functions-no-external-calls` — CloudFront Functions는 다른 서비스를 부르지 못한다

**한 줄**: 엣지에서 도는 이 경량 함수에는 네트워크 호출이 없어, 다른 AWS 서비스에 일을 시키는 자리에 놓을 수 없다.

`Q201-Q250.md`의 `cloudfront-functions`는 이것이 엣지에서 도는 경량 JavaScript 처리이고
Lambda@Edge와 모델이 다르다는 것을 다룬다. 문항이 쓰는 한계는 그다음이다.

CloudFront Functions는 요청과 응답의 헤더를 손보거나 URL을 고쳐 쓰는 것처럼 그 자리에서
끝나는 일을 위한 것이고, 외부 AWS 서비스를 호출하는 기능이 없다. 그래서 "엣지 함수를 만들어
이미지 검사 서비스에 넘긴다" 같은 선택지는 서비스 조합 자체가 성립하지 않아 지워진다.
그런 호출이 필요하면 리전에서 도는 Lambda가 그 자리를 맡는다.

> [Q556 p377] "또한 CloudFront Functions는 Rekognition과 같은 외부 AWS 서비스를 호출하는 기능을 지원하지 않습니다."

### `asg-single-instance-self-healing` — 인스턴스가 하나여도 오토 스케일링 그룹에 넣는다

**한 줄**: 최소·최대·희망 용량을 모두 1로 둔 그룹은 확장을 하지 않는 대신, 인스턴스가 죽으면 자동으로 다시 띄운다.

오토 스케일링 그룹은 대수를 늘리고 줄이는 장치로 먼저 배우지만, 하는 일이 하나 더 있다.
그룹은 지정된 용량을 유지하려 하므로 인스턴스가 비정상이 되면 교체한다. 용량을 1로 고정하면
확장은 일어나지 않고 이 교체만 남는다.

모놀리식이라 여러 대로 나눌 수 없는 애플리케이션이 이 구성의 자리다. 대수를 늘리지 못하니
부하는 인스턴스 유형을 키워 감당하고, 가용성은 크기 1짜리 그룹이 맡는다. 데이터베이스 쪽
읽기 부하는 별개의 문제라 읽기 전용 복제본으로 덜어 내는 것이 짝으로 나온다 — 두 조치가
서로 다른 증상을 고친다는 것이 이 문항의 핵심이다.

> [Q574 p387] "크기 1의 오토 스케일링 그룹: 애플리케이션이 모놀리식 구조로 인해 단일 EC2 인스턴스에서만 실행될 수 있지만, 최소 및 최대 크기를 1로 설정하여 오토 스케일링 그룹을 생성하면 장애 발생 시 인스턴스가 자동으로 재시작되거나 교체되어 고가용성을 유지할 수 있습니다."

## serverless-containers

### `api-gateway-websocket-api` — WebSocket API

**한 줄**: 클라이언트가 연결을 열어 둔 채 서버와 메시지를 주고받는 양방향 통신을 위한 API 유형이다.

앱의 `api-gateway`는 REST API와 HTTP API를 비용·기능·JWT 인증으로 갈라 둔다. 세 번째 유형이
WebSocket API이고, 앞의 둘로는 대신할 수 없는 자리가 있다.

REST API와 HTTP API는 요청이 오면 응답을 돌려주고 끝나는 모델이다. 채팅처럼 서버가 먼저
말을 걸어야 하거나 연결된 클라이언트 전체에 메시지를 뿌려야 하면 이 모델로는 되지 않는다.
WebSocket API는 클라이언트가 연결을 오래 유지한 채 백엔드 Lambda 함수와 실시간으로 메시지를
주고받게 한다. CloudFront를 앞에 두는 구성도 대안이 되지 못한다 — 상태를 들고 있는 연결을
유지하는 장치가 아니기 때문이다.

> [Q581 p391] "WebSocket API를 사용하면 클라이언트가 장기 연결을 설정하고 백엔드 Lambda 함수와 실시간으로 메시지를 교환할 수 있습니다."

### `api-gateway-mapping-template-limits` — 매핑 템플릿으로 되는 변환과 안 되는 변환

**한 줄**: 요청·응답의 모양을 바꾸는 매핑 템플릿은 기능이 제한적이라, 형식을 통째로 바꾸는 변환은 Lambda가 맡는다.

API Gateway에는 백엔드로 넘기기 전에 요청을 손보는 매핑 기능이 있다. 필드 이름을 바꾸거나
값을 옮기는 정도는 여기서 끝난다.

한계는 변환이 커질 때 드러난다. JSON으로 들어온 주문을 XML 문서로 만들어 넘기는 것처럼
형식 자체가 달라지는 변환은 매핑 템플릿이 감당하는 범위를 넘고, 그 자리에는 통합 대상으로
Lambda 함수를 두어 코드로 바꾼다. 이미 그 형식을 받는 백엔드가 있다면 그쪽 요청은 변환 없이
프록시 통합으로 그대로 흘려보내고, 새로 받는 형식만 함수를 거치게 하는 것이 부품이 가장 적은
구성이다.

> [Q588 p396] "API Gateway 매핑 템플릿은 기능이 제한적이며 복잡한 변환 작업에는 적합하지 않습니다."

### `lambda-memory-ceiling` — Lambda 한 번 실행의 메모리 상한

**한 줄**: 호출 하나에 최대 10GB까지 메모리를 줄 수 있어, 그 안에 드는 작업은 클러스터를 띄울 이유가 없다.

앱은 실행 시간 상한이 15분이라는 것을 다루고, `Q101-Q150.md`의 `lambda-memory-cpu-proportional`은
메모리를 올리면 CPU가 함께 올라간다는 관계를 다룬다. 남는 것은 그 메모리를 어디까지
올릴 수 있느냐다.

한 번의 호출에 할당할 수 있는 메모리는 최대 10GB다. "호출마다 1GB가 필요하고 30초 안에
끝난다" 같은 조건이 문제문에 적혀 있으면 두 상한 안에 여유 있게 들어가므로, ETL 서비스나
빅데이터 클러스터를 띄우는 선택지는 이 숫자를 근거로 지워진다. 그쪽은 대용량 배치와 분산
처리를 위한 것이라 짧고 작은 작업에는 비용과 관리가 더 붙는다.

> [Q573 p387] "AWS Lambda는 최대 10GB의 메모리와 15분의 실행 시간을 지원하는 함수를 제공합니다."

## messaging-backup

### `eventbridge-event-bus-types` — 기본·사용자 지정·파트너 이벤트 버스

**한 줄**: 이벤트 버스는 세 종류이고, 파트너 버스는 외부 SaaS가 보내는 이벤트를 받는 자리라 내 애플리케이션의 이벤트를 여기에 넣지 않는다.

앱의 `eventbridge`는 AWS 서비스 사이를 이어 준다는 데까지 말한다. 이벤트가 지나는 통로에
종류가 있다는 것은 문항이 보기를 그 이름으로 갈라 놓을 때 필요해진다.

AWS 서비스가 내는 이벤트는 계정마다 있는 기본 이벤트 버스로 들어온다. 내가 만든 애플리케이션이
스스로 이벤트를 올리려면 사용자 지정 이벤트 버스를 만들어 그쪽에 보낸다. 파트너 이벤트 버스는
성격이 다르다 — AWS 밖의 SaaS 공급자가 보내는 이벤트를 받기 위한 통로라, 내 애플리케이션의
주문 이벤트를 여기에 흘리는 구성은 용도가 어긋난다.

어느 버스든 규칙의 대상으로 Lambda 함수를 걸면 그 함수가 이벤트를 받아 처리하고 다른
서비스에 쓸 수 있다. 테이블의 변경을 흘려보내는 스트림 기능과 이벤트를 라우팅하는 이 서비스를
같은 것으로 보지 않는 것도 이 문항이 노리는 지점이다.

> [Q551 p374] "옵션 C와 D는 SaaS 통합을 목적으로 하는 파트너 이벤트 버스를 언급하고 있으며, 사용자 지정 애플리케이션 이벤트와는 무관합니다."

### `eventbridge-event-pattern-vs-polling` — 이벤트 패턴으로 걸면 폴링이 없다

**한 줄**: 규칙을 이벤트 패턴으로 걸면 그 이벤트가 실제로 왔을 때만 대상이 실행되므로, 주기적으로 확인하는 구성보다 지연도 비용도 작다.

`Q051-Q100.md`의 `eventbridge-vs-step-functions`는 이벤트 라우팅과 워크플로 오케스트레이션을
가르고, 앱의 `eventbridge-scheduler`는 정해진 시각이나 주기에 무언가를 실행하는 쪽을 맡는다.
같은 서비스로 두 방식이 다 되기 때문에, 문항은 그중 어느 쪽을 골라야 하는지를 묻는다.

규칙에는 어떤 이벤트에 반응할지 적은 이벤트 패턴을 걸 수 있다. 이렇게 두면 주문이 들어온
그 순간에만 대상이 호출되고, 아무 일도 없는 시간에는 아무것도 실행되지 않는다. 반면 1분마다
함수를 깨워 새 항목이 있는지 확인하는 구성은 최대 1분의 지연이 생기고 빈 확인에도 비용이
든다. 인스턴스를 띄워 폴링하는 구성은 거기에 운영 부담까지 더한다. "즉시 시작해야 한다"와
"가장 비용 효율적"이 함께 걸리면 일정이 아니라 패턴이다.

> [Q561 p380] "EventBridge 이벤트 패턴과 새로운 주문 이벤트 수신 시 AWS Lambda를 호출하는 규칙을 사용하면, 이 솔루션은 폴링을 피하고 실제 작업이 필요한 경우에만 주문을 처리합니다."

### `sns-no-message-body-rewrite` — SNS는 메시지 본문을 고쳐 보내지 못한다

**한 줄**: 구독마다 다른 내용을 보내야 하면 SNS 앞에서 본문을 바꿔야 한다. 토픽 자체에는 전달 전에 본문을 재작성하는 기능이 없다.

수신자마다 볼 수 있는 범위가 다른 구조 — 전체 정보를 가진 쪽이 각 수신자에게 자기 몫만
보내는 경우 — 에서 보기 줄은 "필터 정책으로 본문을 재작성한다"를 자주 내놓는다. 그런 동작은
없다.

SNS가 하는 일은 받은 메시지를 구독자에게 퍼뜨리는 것이고, 전달 직전에 본문을 다시 쓰는
단계가 없다. 그러니 수신자별로 내용을 달리하려면 토픽에 게시하기 **전에** 바꿔야 한다.
큐로 원본을 받아 함수가 수신자에 맞게 본문을 만들고, 그 결과를 해당 토픽에 게시하는 형태가
그것이다. 토픽을 하나 더 두는 구성은 부품만 늘 뿐 재작성 요구를 풀지 못한다.

> [Q554 p375] "SNS에는 전달 전에 메시지 본문을 재작성하는 기능이 없습니다."

## analytics-monitoring

### `redshift-copy-from-s3` — Redshift는 S3에서 COPY로 병렬 적재한다

**한 줄**: 데이터 웨어하우스에 대량으로 넣는 표준 경로는 S3에 파일을 놓고 COPY 명령으로 병렬 로드하는 것이다.

앱의 `redshift`는 대규모 데이터를 빠르게 분석하는 데이터베이스라는 데까지 다룬다. 문항이
묻는 것은 그 안에 데이터를 **어떻게 넣느냐**다.

Redshift는 S3에 있는 파일을 COPY 명령으로 읽어 들이고, 이 적재는 여러 노드가 나눠 병렬로
처리한다. 그래서 다른 저장소에서 정기적으로 대량 적재를 해야 하면 일단 S3로 내보낸 뒤 COPY로
당기는 두 단계가 관리할 것이 가장 적은 경로가 된다. 원본을 직접 읽어 오는 구성은 원본의
처리량을 갉아먹고, 함수를 짜서 옮기는 구성은 코드와 스케줄을 직접 유지해야 한다.

> [Q565 p382] "데이터가 S3에 저장되면 Amazon Redshift는 S3에서 COPY를 통해 효율적으로 데이터를 가져올 수 있으며, 이는 관리가 최소화되는 표준적이고 병렬 처리되는 고처리량 로드 경로입니다."

### `athena-federated-query` — Athena 페더레이션 쿼리

**한 줄**: 커넥터를 붙이면 S3 밖의 데이터 소스도 Athena에서 SQL로 조회할 수 있지만, 이것은 임시 분석용이라 반복되는 대량 적재의 경로가 아니다.

앱의 `athena`는 S3에 둔 데이터를 옮기지 않고 SQL로 질의하는 서비스라는 데까지 다룬다.
페더레이션 쿼리는 그 범위를 S3 밖으로 넓히는 기능이다.

데이터 소스마다 커넥터가 있어서, 운영 데이터베이스에 든 데이터도 옮기지 않고 Athena에서
질의할 수 있다. 다만 이 기능이 겨냥하는 것은 그때그때 들여다보는 임시 분석이다. 데이터
웨어하우스에 정기적으로 대량으로 밀어 넣는 일은 이쪽에 최적화돼 있지 않으므로, 그 조건이
붙은 문항에서는 S3로 내보낸 뒤 적재하는 경로에 밀린다.

> [Q565 p382] "Athena 페더레이션 쿼리(D)는 임시 분석용이며, 대량 및 반복적인 데이터 웨어하우스 로딩에 최적화되어 있지 않습니다."

### `quicksight-ml-forecast` — QuickSight에 들어 있는 ML 예측

**한 줄**: 대시보드 안에서 바로 시계열 예측을 만들 수 있어, 예측이 필요하다고 해서 곧바로 모델 학습 서비스로 갈 이유가 없다.

`Q051-Q100.md`의 `quicksight`는 이 서비스가 Athena에 연결해 대시보드와 보고서를 그리는
쪽을 맡는다는 것을 다룬다. 문항은 여기에 "예측"을 얹는다.

QuickSight에는 머신러닝 기반 예측 기능이 내장돼 있어서, 지금 보고 있는 대시보드 안에서
앞으로의 추세를 만들어 함께 볼 수 있다. 모델을 만들거나 학습시키는 단계도, 그 인프라를
관리하는 단계도 없다. 그래서 "예측을 생성하고 시각화한다"에 "관리 오버헤드를 최소화한다"가
붙으면 학습 서비스를 붙이는 선택지나 미리 만들어진 이미지를 사다 쓰는 선택지는 모두 손이
더 가는 쪽으로 밀린다.

> [Q569 p384] "Amazon QuickSight에는 내장된 ML 기반 예측 기능이 포함되어 있어, ML 경험이나 인프라 관리 없이도 BI 대시보드 내에서 직접 시계열 예측을 생성, 시각화 및 상호 작용할 수 있습니다."

### `glue-databrew` — AWS Glue DataBrew

**한 줄**: 데이터를 분석하기 좋은 모양으로 다듬는 준비 도구이며, 데이터 레이크의 접근 권한을 다루는 서비스가 아니다.

데이터 레이크 문항의 보기 줄에 카탈로그와 짝을 지어 올라오는 이름이다. 무엇을 하는
서비스인지 모르면 지우지 못한다.

DataBrew가 맡는 것은 데이터 준비다. 카탈로그가 메타데이터를 들고 있는 것과 함께 두면 데이터를
찾고 다듬는 데까지는 되지만, 어느 팀이 어느 행을 볼 수 있는지 같은 세분화된 접근 제어는
이 조합이 하는 일이 아니다. 그 자리는 `Q001-Q050.md`의 `lake-formation`이다.

> [Q558 p378] "Glue Catalog + DataBrew: 행 수준 액세스 제어가 아닌 데이터 준비 및 메타데이터 관리에 중점을 둡니다."

### `cloudwatch-alarm-state-change-event` — 알람 상태 변경은 이벤트로 흘러간다

**한 줄**: 알람이 상태를 바꾸면 그 사실이 EventBridge로 전달되므로, 함수를 하나 끼우지 않고도 규칙의 대상을 바로 실행시킬 수 있다.

CloudWatch 알람은 임계값을 넘었을 때 알림을 보내는 장치로 먼저 쓰인다. 그런데 알람이 상태를
바꾸는 사건 자체가 이벤트로 나가므로, 그것을 받아 자동 대응을 붙일 수 있다.

`Q301-Q350.md`의 `guardduty-finding-to-eventbridge`가 탐지 결과를 자동 대응으로 잇는 것과
같은 모양이다. 규칙이 알람의 상태 변경 이벤트를 잡고, 대상으로 조치를 거는 서비스를 직접
호출한다. 사이에 함수를 넣어 같은 일을 시키는 구성도 되지만, 함수 코드를 유지해야 하므로
운영 부담이 한 단계 더 붙는다. 사람에게 알리기만 하는 구성은 자동화라는 요구를 아예 채우지
못한다는 것도 함께 갈린다.

> [Q559 p379] "CloudWatch는 알람 상태 변경 이벤트를 EventBridge로 직접 전송할 수 있으며, AWS 문서에는 알람 상태 변경 사항이 EventBridge로 전달된다고 명시되어 있습니다."

### `macie-finding-to-eventbridge` — Macie의 탐지 결과에 알림을 붙인다

바꿔 놓은 선택지는 앱의 `security-service-lineup`으로 걸러진다.

> [Q589 p397] "EventBridge 규칙: 특정 민감한 데이터 이벤트(예: SensitiveData)에 대해 Macie 탐지 결과를 필터링합니다."

## secrets-encryption

### `kms-key-types-by-management` — 고객 관리 키·AWS 관리 키·AWS 소유 키

**한 줄**: 키를 누가 만들고 관리하느냐로 세 갈래가 갈리고, 정책과 교체 주기를 직접 정할 수 있는 것은 고객 관리 키뿐이다.

앱의 `kms`는 암호화 키를 만들고 보관하는 서비스라는 데까지 말하고, `Q501-Q550.md`의
`kms-automatic-key-rotation`은 고객 관리 키에 자동 교체를 켜면 해마다 새 키 자료가 생긴다는
것을 다룬다. 그 "고객 관리 키"가 무엇과 대비되는 이름인지가 이 개념이다.

KMS 키는 관리 주체로 갈린다. 고객 관리 키는 내가 만들어 키 정책과 수명 주기를 직접 정하고
교체를 켤 수 있다. AWS 관리 키와 AWS 소유 키는 AWS 쪽이 관리하는 키라 그만큼 손댈 것이 없는
대신, 교체 주기를 내가 정하는 유연성도 없다.

그래서 "저장 중 데이터를 암호화하되 키 교체 주기를 통제해야 한다"가 조건이면 답은 고객 관리
키를 만들어 쓰는 것이고, AWS가 관리하는 키에 교체를 구성하겠다는 선택지는 그 통제가 나에게
없어서 지워진다. 키 자료를 밖에서 가져오는 구성은 통제는 되지만 자동 교체를 쓰지 못해
운영 부담이 커진다 — `Q301-Q350.md`의 `imported-key-material-rotation`이 그 제약이다.

> [Q600 p404] "최소 운영 오버헤드: 고객 관리 키를 사용하면 암호화 관리를 간소화할 수 있으며, AWS 관리 키나 AWS 소유 키보다 더 큰 유연성을 제공합니다."

## identity-access

### `iam-group-policy-attachment` — 권한은 사용자가 아니라 그룹에 붙인다

**한 줄**: 같은 일을 하는 사용자를 그룹으로 묶고 정책을 그룹에 붙이면, 사람이 늘어도 고칠 곳이 한 군데다.

앱의 `iam-group-users-only`는 그룹이 사용자 집합이라는 것을, `least-privilege`는 필요한 만큼만
권한을 준다는 원칙을 다룬다. 문항은 그 원칙을 **어떤 구조로** 적용하는지를 묻는다.

정책을 사용자마다 직접 붙여 두면 사람 수만큼 붙는 자리가 생기고, 기준을 바꿀 때 전부를
훑어야 한다. 직무별로 그룹을 만들어 그 그룹에 정책을 붙이고 사용자를 그룹에 넣으면, 권한의
기준이 그룹 하나에 모인다. 사용자에게 직접 붙어 있던 기존 권한을 떼는 것도 같은 이유로
필요한 단계다 — 남겨 두면 그룹의 기준과 별개로 살아 있는 권한이 된다.

모든 사용자를 그룹 하나에 넣고 넓은 정책과 좁은 정책을 함께 붙이는 구성은 최소 권한과
정면으로 어긋난다. 태그를 붙이는 것만으로는 권한이 달라지지 않는다는 것도 함께 갈린다 —
태그로 권한을 가르려면 `Q001-Q050.md`의 `abac`처럼 정책이 그 태그를 조건으로 읽어야 한다.

> [Q593 p399] "옵션 A는 권한을 개별 사용자로부터 부서 기반 IAM 그룹으로 이전하므로, 대규모 환경에서 일관되게 관리하기가 더 쉬워 운영 효율성이 가장 높습니다."

## cost-management

### `compute-optimizer-ebs-recommendations` — 권장 대상에는 EBS 볼륨도 있다

**한 줄**: 활용도가 낮은 볼륨과 비효율적인 구성을 짚고 예상 절감액까지 붙여 주므로, 스토리지 비용을 줄일 근거를 만드는 자리에 쓴다.

앱의 `compute-optimizer`는 리소스 사양 최적화를 권장하되 비용을 팀별로 집계해 보고하는
일은 하지 않는다는 것을 다룬다. 문항이 쓰는 것은 그 권장의 **대상과 형태**다.

권장 대상은 컴퓨팅 인스턴스만이 아니라 EBS 볼륨까지 포함하고, 사용 패턴을 분석해 활용도가
낮은 볼륨과 비효율적인 구성을 짚어 준다. 권장마다 절감 효과에 대한 예측이 함께 나오므로
"제안에 예상 월간 절감액이 들어가야 한다"는 요구가 이 서비스로 채워진다. 지표를 보여 주는
모니터링 서비스는 사용량을 알려 줄 뿐 무엇을 어떻게 바꾸라는 권장을 만들지 않고, 취약점을
평가하는 보안 서비스는 애초에 비용을 다루지 않는다.

> [Q577 p389] "AWS Compute Optimizer는 활용도가 낮은 볼륨, 비효율적인 구성, 잠재적인 비용 절감 효과에 대한 인사이트를 포함하여 Amazon EBS 볼륨 최적화를 위한 상세한 권장 사항을 제공합니다."

## (주제 미정)

### `ssm-run-command` — Systems Manager Run Command

**한 줄**: 관리형 인스턴스에 접속하지 않고 원격으로 명령을 실행시키는 기능이라, 재시작 같은 조치를 자동화하는 자리에 놓인다.

`Q101-Q150.md`는 Session Manager·Patch Manager·Inventory를 다루고
`Q351-Q400.md`의 `ssm-managed-instance-core-policy`는 인스턴스를 관리형으로 만드는 조건을
다룬다. Run Command는 그 관리형 인스턴스에 **명령 한 번을 보내는** 기능이다.

에이전트를 통해 명령이 전달되므로 SSH로 들어가거나 접속 경로를 열어 둘 필요가 없다.
문항에서 이 기능이 답이 되는 자리는 사람이 반복하던 조치를 자동으로 돌릴 때다 — 지표가
임계값을 넘어 알람이 울리면 그 이벤트가 Run Command를 불러 인스턴스를 재시작하는 식이다.
이 경로는 함수를 만들어 같은 명령을 부르는 구성과 결과가 같지만, 유지할 코드가 없어 운영
부담이 더 작다.

> [Q559 p379] "또한 AWS 문서에는 Systems Manager RunCommand가 관리되는 EC2 인스턴스에서 원격으로 명령을 실행할 수 있다고 명시하고 있습니다."

### `rekognition-content-moderation` — Rekognition의 콘텐츠 검토

**한 줄**: 이미 학습된 모델로 이미지를 분석해 부적절한 콘텐츠를 찾아내므로, 모델을 만들거나 훈련시키지 않고 검토를 붙일 수 있다.

`Q401-Q450.md`의 `media-ai-service-lineup`은 이 서비스가 이미지와 영상을 맡는다는 것까지
다룬다. 문항이 쓰는 것은 **무엇을 찾아내는가**와 **훈련이 필요한가**다.

Rekognition은 AWS가 미리 학습시켜 둔 모델을 쓰는 컴퓨터 비전 서비스이고, 올라온 이미지에서
부적절하거나 원치 않는 콘텐츠를 탐지하는 검토 기능이 있다. 그래서 "머신러닝 모델 훈련을
포함해서는 안 된다"가 조건으로 걸린 문항에서 이 서비스가 남는다. 함수가 업로드 시점에
이 서비스를 부르는 형태면 서버를 두지 않고 검토가 붙는다.

같은 이름의 영상용 기능과 갈린다. 정지 이미지를 검토하는 자리에 영상 스트림 분석 쪽을
가져오면 입력의 종류가 어긋나 지워진다. 글을 분석하는 자연어 처리 서비스도 이미지 검토를
맡지 않는다 — `Q501-Q550.md`의 `comprehend`가 그쪽이다.

> [Q556 p377] "Amazon Rekognition은 AWS에서 제공하는 사전 훈련된 모델을 사용하여 이미지를 분석하고 부적절하거나 원치 않는 콘텐츠를 탐지할 수 있는 완전 관리형 컴퓨터 비전 서비스입니다."

### `sagemaker-autopilot` — SageMaker Autopilot

**한 줄**: 모델을 자동으로 만들고 훈련시켜 주는 기능이라, "훈련을 포함하지 말라"는 조건이 붙으면 오히려 그 조건에 걸린다.

`Q051-Q100.md`의 `sagemaker`는 모델을 훈련하는 서비스라는 것을 다룬다. Autopilot은 그 훈련
과정을 자동으로 돌려 주는 기능이고, 보기 줄에서는 "관리 부담이 적다"는 인상으로 올라온다.

판단 기준은 조건 문장이다. 문제가 모델 훈련을 포함하지 말라고 못 박았다면, 훈련을 자동으로
해 준다는 것은 요구를 채우는 것이 아니라 어기는 것이다. 그 자리에는 이미 학습된 모델을
API로 부르는 서비스가 온다. 반대로 자기 데이터로 모델을 만들어야 하는 문항이면 이쪽이 답이
되는 자리다.

> [Q556 p377] "옵션 A는 SageMaker Autopilot이 ML 모델을 구축하고 훈련하도록 설계되었기 때문에 요구 사항을 위반합니다."

## 원본 수정 이력

덤프를 그대로 따르지 않은 항목이다. 근거는 ADR-008의 예외를 승계한 ADR-021.

### 사실 오류라 싣지 않은 것

- **Q560 p379** — 덤프 원문: "Amazon API Gateway는 REST, HTTP, WebSocket 및 gRPC 등 다양한 API
  유형을 지원합니다." API Gateway가 만들 수 있는 API는 REST·HTTP·WebSocket 세 가지이고 gRPC
  API라는 유형은 없다. 같은 해설이 뒤에서 "gRPC API는 RPC 호출을 지원하지만"이라며 실재하는
  유형처럼 다시 언급하지만, 없는 유형이므로 옮기지 않았다. 위 `api-gateway-websocket-api`는
  세 유형만 다룬다. 이 문항의 정답 근거(JWT 인증과 ALB 통합은 HTTP API)는 앱의
  `serverless-containers.api-gateway-jwt-authorizer`에 이미 있다.
- **Q551 p374** — 이 문항은 `정답 C`로 적혀 있는데 해설은 "올바르고 가장 간단한 해결책은
  Lambda 타깃(B)과 함께 사용자 지정 EventBridge 이벤트 버스를 사용하는 것입니다"로 끝나
  B를 정답으로 결론짓는다. 정답 표기와 해설이 어긋나므로 정답 문자는 쓰지 않았고, 해설이
  근거로 든 사실(파트너 이벤트 버스는 SaaS 통합용이다)만 `eventbridge-event-bus-types`로 실었다.

### [AI 작성 해설]이라 채택하지 않은 것

해설집이 문서 2쪽에서 "원본에 해설이 없던 21개 문제는 새로 작성했다"고 밝힌 표시다.
이 슬라이스에는 한 문항(Q585)에 붙어 있다.

- **Q585 p394** — 해설집이 "기록된 정답 A → AWS 기준 C"라고 스스로 밝힌 문항이다. 여기서
  쓰인 사실은 전부 이미 있다 — Aurora 글로벌 데이터베이스의 쓰기 리전과 복제 지연은
  `Q001-Q050.md`의 `aurora-global-database-write-region`과 `Q301-Q350.md`의
  `aurora-global-database-dr-targets`에, ElastiCache의 리전 간 복제는 `Q101-Q150.md`의
  `elasticache-global-datastore`에, DynamoDB 글로벌 테이블은 `Q001-Q050.md`에,
  다중 AZ가 리전 장애를 막지 못한다는 것은 `Q451-Q500.md`의
  `multi-region-failover-for-region-outage`에 있다. 새로 만들 개념이 없어 넘어갔다.

### 중복이라 새로 만들지 않은 것

정답 근거이지만 앱이나 앞 step에 이미 있어 항목으로 만들지 않은 것이다.

  `Q201-Q250.md`의 `control-tower-landing-zone`과 `Q001-Q050.md`의 `control-tower-controls`에 있다.
- **Q553 p375** — 여러 리소스에 트래픽을 나누면서 정상인 것만 응답에 넣는 것은 다중값 응답
  라우팅이다. 앱의 `route53.multivalue-answer-details`에 있다.
- **Q555 p376**·**Q557 p378** — 단일 리전 애플리케이션에 전 세계에서 접속할 때 지연을 줄이는
  것은 Global Accelerator다. 앱의 `compute-delivery.global-accelerator`·
  `global-accelerator-protocols`에 있다. 두 문항에서 새로 실은 것은 DNS 캐시와의 관계뿐이다.
