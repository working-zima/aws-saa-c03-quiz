## identity-access

### `saml-federation-role-to-ad-group-mapping` — 사내 디렉터리를 SAML 2.0으로 붙이고 역할을 그룹에 맵핑한다

**한 줄**: 온프레미스 Active Directory를 SAML 2.0 페더레이션으로 AWS에 통합하면 콘솔과 CLI·API에 단일 로그인이 열리고, IAM 역할을 AD 그룹에 매핑해 권한을 나눈다.

`Q101-Q150.md`의 `identity-center-external-idp`는 IAM Identity Center가 기존 ID 공급자와
SAML 2.0으로 이어진다는 것을 다루고, `Q701-Q750.md`의 `custom-identity-broker-for-non-saml`은
디렉터리가 SAML을 지원하지 **않을** 때의 우회로를 다룬다. 그 사이가 이 항목이다 —
디렉터리가 SAML을 지원할 때 권한을 무엇에 붙이는가.

SAML 2.0 기반 페더레이션은 사내 디렉터리를 AWS와 이어 붙여 기존 자격 증명 그대로 콘솔과
CLI·API에 들어가게 한다. 사용자는 AWS 쪽에서 따로 만들어지지 않으므로 "리소스에 접근하려고
별도의 ID를 관리하는 상황"이라는 요구 조건이 그대로 풀린다. 권한은 IAM 역할에 붙이고 그
역할을 AD 그룹에 매핑하므로, 그룹 소속을 바꾸는 것이 접근 권한을 바꾸는 일이 된다.

사용자마다 IAM 사용자를 만들어 정책을 붙이는 선택지가 함께 오르는데, 이것은 관리해야 할
신원을 온프레미스와 AWS 양쪽에 하나씩 두는 구성이라 요구 조건과 정면으로 어긋난다.

> [Q820 p554] "SAML 2.0 기반 페더레이션을 통해 조직은 온프레미스 Active Directory를 AWS와 통합하여 AWS Management Console 및 AWS CLI/API 액세스를 위한 SSO(Single Sign-On)를 구현할 수 있습니다."

### `config-custom-rule` — 관리형 규칙에 없는 값은 사용자 지정 규칙으로 본다

**한 줄**: AWS Config에는 검사 항목을 직접 정의하는 사용자 지정 규칙이 있어, 프로비저닝된 IOPS처럼 관리형 규칙이 다루지 않는 구성 값을 지켜보다 임계값을 넘으면 알림으로 잇는다.

앱의 `identity-access.aws-config`는 구성 변경 이력을 남긴다는 데까지 말하고,
`Q001-Q050.md`의 `config-rule-remediation`은 규칙이 찾아낸 것을 Systems Manager가 고치는
조합을 다룬다. 남는 축이 둘이다 — 규칙을 직접 정의할 수 있다는 것과, 고치는 대신 알리는
용도로도 쓴다는 것.

사용자 지정 규칙은 리소스의 구성을 읽어 판정을 내리므로, 인스턴스에 붙은 EBS 볼륨의
프로비저닝된 IOPS 같은 값을 감시 대상으로 삼을 수 있다. CloudWatch 지표와 SNS를 함께 두면
과도하게 잡아 둔 IOPS를 추적하다 임계값을 넘었을 때 경고가 나가고, 비용과 성능을 사후가
아니라 미리 조정하게 된다. 볼륨 여러 개를 묶어(스트라이핑) 필요한 성능을 만드는 구성처럼
값이 흩어져 있을 때 이 감시가 특히 필요하다.

> [Q845 p572] "AWS Config를 사용하면 EBS 구성을 모니터링하기 위한 사용자 지정 규칙을 생성할 수 있습니다."

## threat-protection

### `waf-logging-to-firehose` — WAF 로그는 Firehose를 거쳐 S3로 간다

**한 줄**: WAF에서 로깅을 켜면 웹 요청의 상세 로그가 남고, 이를 Data Firehose에 이어 S3로 보내면 트래픽 흐름과 요청 출처, 차단된 요청을 거의 실시간으로 분석할 수 있다.

앱의 `threat-protection.waf`는 요청을 검사해 막는 쪽을 다룬다. 같은 서비스에 축이 하나 더
있는데 **무엇이 지나갔는지 보이게 하는 것**이다. 로깅을 켜면 트래픽 흐름과 요청이 어디서
왔는지, 무엇이 차단됐는지가 로그로 남아 보안 가시성이 함께 올라간다.

로그를 쌓는 경로는 Data Firehose다. WAF 로깅을 Firehose에 연결하면 로그가 S3로 자동으로,
거의 실시간에 가깝게 실려 가고 그 뒤는 분석 도구의 몫이 된다. 그래서 "트래픽 소스를 더 알고
싶고 보안도 강화하고 싶다"처럼 요구가 둘인 문항에서 이 조합 하나가 둘을 함께 채운다.
Firehose가 모아서 보내는 성질은 `Q151-Q200.md`의 `firehose-buffering`에, S3에 쌓은 로그를
질의하는 다음 단계는 `Q251-Q300.md`의 `log-storage-s3-athena`에 있다.

> [Q809 p546] "AWS WAF 로깅을 Amazon Kinesis Data Firehose와 통합하면 분석, 보고 또는 분석 도구와의 연동을 위해 로그 데이터를 Amazon S3로 자동적이고 거의 실시간으로 전송할 수 있습니다."

### `waf-web-acl-region-must-match-rest-api` — REST API에 붙일 Web ACL은 같은 리전에 만든다

**한 줄**: API Gateway REST API에 웹 액세스 제어 목록을 적용하려면 AWS WAF를 그 API와 같은 리전에 배포해야 하고, 같은 리전이면 트래픽이 리전을 건너지 않아 지연도 줄어든다.

앱의 `threat-protection.waf-attach-targets`는 WAF를 **어디에** 붙일 수 있는지를 다루고
`waf-rule-types`는 지리적 일치 규칙 같은 규칙 종류를 다룬다. 여기에 조건이 하나 더 붙는다 —
그 Web ACL을 **어느 리전에** 만드는가.

REST API에 Web ACL을 적용하려면 WAF가 API와 같은 리전에 있어야 한다. 그래서 규칙 내용이
똑같아도 WAF를 다른 리전에 만든 선택지는 구성 자체가 성립하지 않아 먼저 지워진다. 같은
리전에 두면 검사 트래픽이 리전 경계를 넘지 않으므로 지연을 최소화하라는 조건도 함께 풀린다.

API 유형도 이 자리에서 갈린다. HTTP API는 REST API와 달리 WAF를 직접 지원하지 않고 앞에 리전
로드 밸런서를 두는 간접 경로만 있다. `Q701-Q750.md`의 `api-gateway-rest-only-features`가
REST API에만 있는 기능들을 모아 두었는데, WAF 연결이 그 목록에 하나 더 붙는 셈이다.

> [Q812 p549] "AWS 문서에 따르면, API Gateway REST API의 경우 웹 액세스 제어 목록을 적용하려면 AWS WAF를 동일한 리전에 배포해야 합니다."

### `firewall-manager` — 계정이 여러 개면 방화벽 규칙을 한곳에서 건다

**한 줄**: AWS Firewall Manager는 Organizations 조직에 속한 여러 계정의 WAF 규칙을 중앙에서 정의하고 배포해, 계정마다 같은 규칙을 따로 만들어 넣는 일을 없앤다.

앱의 `threat-protection.waf`·`waf-attach-targets`와 `Q051-Q100.md`의
`waf-managed-rule-groups`는 규칙 자체를 다룬다. 계정이 여럿이 되면 축이 하나 더 생긴다 —
그 규칙을 누가 어디에 배포하는가.

Firewall Manager는 전용 보안 계정에 두고 조직 전체에 규칙을 내려보내는 자리다. 마이크로
서비스가 계정마다 흩어져 CloudFront 배포와 공용 로드 밸런서로 노출돼 있어도 규칙 배포가 한
번으로 끝나므로, 계정마다 손으로 WAF 규칙을 적용하는 구성보다 운영 부담이 작다. 규칙이
정책대로 걸려 있는지 확인하는 일은 AWS Config 규칙이 맡아 리전 WAF와 글로벌 WAF 구성을
함께 본다.

Shield Advanced를 대신 두는 선택지가 함께 오르는데, 대규모 DDoS 완화에 초점이 있어 WAF가
주는 세밀한 웹 애플리케이션 보호와 중앙 규칙 관리를 대신하지 못한다.

> [Q848 p573] "AWS Firewall Manager: AWS Organizations 조직 내 여러 계정에 걸쳐 WAF 규칙을 중앙 집중식으로 관리할 수 있습니다."

## compute-delivery

### `memory-optimized-instance-family` — 메모리 최적화 인스턴스 제품군

**한 줄**: 메모리 최적화 인스턴스는 대용량 데이터를 메모리에 올려 처리하는 워크로드용이라, 애플리케이션과 데이터베이스가 둘 다 메모리를 많이 쓰면 양쪽 모두 이 제품군에 올린다.

앱은 EC2를 서비스로 다루지만 **어떤 제품군을 고르는가**라는 축은 없다. 온프레미스에서 잰
성능 데이터가 메모리 사용률이 높다고 말하면 그 값이 그대로 선택 기준이 된다.

메모리 최적화 인스턴스는 메모리 안에서 큰 데이터 집합을 다루는 워크로드에 빠른 성능을
주도록 설계돼 있다. SAP 같은 고성능 데이터베이스와 메모리를 많이 쓰는 애플리케이션이 이
제품군의 자리다. 애플리케이션에는 컴퓨팅 최적화나 HPC 최적화를 쓰고 데이터베이스에만 메모리
최적화를 쓰는 선택지가 함께 오르는데, 두 계층 모두 메모리 수요가 높다고 적혀 있으면 한쪽을
다른 제품군으로 돌리는 순간 그 계층이 필요한 메모리를 받지 못한다. 둘을 같은 제품군으로
맞추면 관리도 단순해진다.

> [Q825 p557] "메모리 최적화 인스턴스: 이 인스턴스는 메모리 내에서 대용량 데이터 세트를 처리하는 워크로드에 대해 빠른 성능을 제공하도록 설계되었습니다."

## serverless-containers

### `lambda-at-edge-response-compression` — 엣지에서 응답을 압축해 전송량을 줄인다

**한 줄**: Lambda@Edge는 콘텐츠가 사용자에게 전달되기 전에 그것을 고칠 수 있고 압축이 그중 하나라, 애플리케이션 코드를 건드리지 않고 나가는 데이터 양과 그에 붙는 요금을 줄인다.

앱의 `serverless-containers.lambda-at-edge`는 인증·권한 부여를 사용자와 가까운 곳에서
처리해 지연을 줄이는 쪽을 다룬다. 같은 자리에서 할 수 있는 일이 하나 더 있다.

요청마다 새로 만들어져 한 번 쓰고 버리는 응답에는 캐시가 듣지 않는다. `Q751-Q800.md`의
`cloudfront-reduces-data-transfer-cost`가 말하는 절감 경로가 이런 콘텐츠에서는 막히므로,
남는 길은 나가는 바이트 자체를 줄이는 것이다. 그 일을 엣지에서 도는 함수가 맡아 전달 직전에
응답을 압축한다. 애플리케이션 소스 코드를 고칠 수 없다는 조건이 붙어 있어도 함수는
애플리케이션 밖에 있으므로 걸리지 않는다.

같은 문항에서 S3 전송 가속화는 응답 속도를 올리는 기능이지 비용을 줄이는 기능이 아니라
밀리고, 멀티파트 업로드는 올리는 쪽을 돕는 기능이라 내려보내는 전송량과 무관하다.

> [Q815 p551] "Lambda@Edge를 사용하면 콘텐츠를 최종 사용자에게 전달하기 전에 압축하거나 수정할 수 있어 전송되는 데이터 양을 줄일 수 있습니다."

## vpc-networking

### `nat-gateway-elastic-ip` — NAT 게이트웨이에는 엘라스틱 IP를 붙인다

**한 줄**: NAT 게이트웨이는 인터넷 쪽에 드러나는 식별자로 엘라스틱 IP를 쓰므로 만들 때 하나를 연결해야 하고, 그 주소는 인터넷 게이트웨이에 붙이는 것이 아니다.

앱의 `vpc-networking.nat-gateway`는 배치 위치가 퍼블릭 서브넷이라는 것과 나가는 방향만
열린다는 것을 다룬다. 구성을 완성하는 조각이 하나 더 있다.

엘라스틱 IP는 NAT 게이트웨이가 인터넷 엔드포인트와 통신할 때 쓰는 주소다. 붙이지 않으면
프라이빗 서브넷의 트래픽이 나갈 출구가 만들어지지 않는다. 반대로 인터넷 게이트웨이는 VPC에
연결하는 것이라 엘라스틱 IP를 붙이는 대상이 아니다 — 이 구분을 모르면 "엘라스틱 IP를 인터넷
게이트웨이에 연결한다"는 선택지를 지우지 못한다.

한 벌로 함께 가는 것이 라우팅이다. 프라이빗 서브넷의 라우팅 테이블에 0.0.0.0/0 경로를 두고
대상을 NAT 게이트웨이로 잡아야 나가는 트래픽이 버려지지 않으며, 퍼블릭 서브넷의 기본 경로는
NAT 게이트웨이가 아니라 인터넷 게이트웨이를 가리켜야 한다. 가용 영역마다 하나씩 두는 이유는
`Q201-Q250.md`의 `nat-gateway-per-az`에 있다.

> [Q833 p563] "옵션 A가 필요한 이유는 NAT 게이트웨이가 인터넷에서 대외적으로 노출되는 식별자로 엘라스틱 IP 주소를 사용하기 때문입니다."

## s3-encryption-batch

### `s3-inventory-report` — 버킷의 객체 목록을 파일로 받아 둔다

**한 줄**: S3 인벤토리는 버킷 안의 객체와 메타데이터를 나열한 평면 파일을 매일이나 매주 만들어 주고 포함할 항목을 고를 수 있어, 마지막 수정 날짜 같은 값으로 대상을 추리는 작업의 출발점이 된다.

접두사가 여러 개인 버킷에 객체가 수백만 개 있으면 무엇을 지울지 정하기 전에 목록을 얻는
일부터 문제가 된다. 인벤토리 보고서가 그 목록을 파일로 내주고, 마지막 수정 날짜를 포함하도록
구성해 두면 몇 년이 지난 객체를 골라낼 근거가 그 파일 안에 들어온다.

목록을 얻은 다음 단계는 아래 `s3-batch-operations-lambda-invoke`가 맡는다. EC2 인스턴스에서
CLI 스크립트를 돌려 지우는 선택지는 서버리스라는 조건에 걸리고, Glue 크롤러로 오래된 객체를
찾는 구성은 ETL 도구를 목록 만들기에 끌어다 쓰는 셈이라 복잡도만 늘어난다.

> [Q818 p553] "S3 인벤토리는 S3 버킷 내의 모든 오브젝트와 해당 메타데이터를 나열한 플랫 파일을 제공하며, 마지막 수정 날짜와 같은 데이터를 포함하도록 구성할 수 있습니다."

### `s3-batch-operations-lambda-invoke` — 배치 작업이 객체마다 Lambda를 부른다

**한 줄**: S3 Batch Operations는 인벤토리 보고서를 대상 목록으로 받아 객체마다 Lambda 함수를 호출할 수 있어, 정해진 동작으로는 표현되지 않는 판단을 서버 없이 얹는다.

앱의 `s3-encryption-batch.batch-operations`는 아주 많은 객체에 같은 작업을 한 번에 적용한다는
데까지 말한다. 남는 축이 **그 작업이 무엇이 될 수 있는가**다.

지울 것과 남길 것이 섞여 있으면 조건을 코드로 적어야 한다. 배치 작업이 Lambda 함수를 부르는
방식이 그 자리를 채운다 — 인벤토리 보고서로 대상을 잡고, 함수가 보존할 것을 걸러 내고,
배치 작업이 나머지에 대해 실행을 맡는다. 이 구성은 처음부터 끝까지 서버리스라 돌릴 인스턴스가
없고, 그래서 운영 관리를 최소화하라는 조건과 대량 삭제라는 조건이 함께 걸린 자리에 선다.

> [Q818 p553] "S3 Batch Operations를 통해 Lambda 함수를 호출함으로써 식별된 객체를 삭제하는 프로세스를 자동화할 수 있으며, 이를 통해 솔루션이 서버리스 방식으로 운영되고 운영 관리가 최소화되도록 보장합니다."

## block-file-storage

### `data-lifecycle-manager` — 스냅샷의 생성·보존·삭제를 정책으로 돌린다

**한 줄**: Amazon Data Lifecycle Manager는 EBS 스냅샷을 정책에 따라 만들고 필요한 기간만 보관한 뒤 지워, 쓰지 않는 스냅샷이 쌓이며 늘어나는 비용을 손대지 않고 줄인다.

`Q401-Q450.md`의 `ebs-recycle-bin`은 지운 스냅샷을 되살리는 쪽이고
`ebs-snapshot-block-public-access`는 공개를 막는 쪽이다. 스냅샷을 **언제까지 남길지** 정하는
자리가 비어 있었고 그것이 이 항목이다.

볼륨을 더 사지 않았는데 EBS 항목의 요금이 매달 오르면 늘어나는 쪽은 대개 스냅샷이다. DLM은
스냅샷을 만드는 일정과 보존 기간을 정책으로 정의해 두면 그 기간이 지난 것을 자동으로
지운다. 쌓인 스냅샷을 한 번 지우고 끝내는 선택지와 갈리는 지점이 여기다 — 정책은 계속
돌기 때문에 다음 달에 같은 일을 다시 하지 않아도 된다.

> [Q823 p556] "Amazon Data Lifecycle Manager(DLM)는 EBS 스냅샷의 생성, 보존 및 삭제를 자동화합니다."

### `fsx-lustre-sub-millisecond-latency` — 1ms 이내라는 조건이 붙으면 Lustre다

**한 줄**: FSx for Lustre는 1ms 이내의 액세스 지연으로 수백 대가 같은 파일 시스템을 병렬로 읽게 하므로, 공유 스토리지에 그 수준의 지연을 요구하는 HPC 조건에서 EFS와 갈린다.

`Q101-Q150.md`의 `fsx-for-lustre`는 높은 IOPS를 요구하는 HPC용이라는 데까지 말하고, 앱의
`block-file-storage.fsx-ontap-multi-az`는 ONTAP 쪽의 밀리초 미만 공유 스토리지를 다룬다.
Lustre에도 수치가 붙는다는 것이 이 항목이고, 문항이 "1ms 이내"를 조건으로 적으면 그 수치가
선택지를 가른다.

Lustre는 수백 개의 인스턴스로 확장되는 병렬 파일 시스템이라 큰 데이터 집합을 여러 노드가
동시에 읽는 처리에 맞춰져 있다. EFS도 여러 대가 공유하는 파일 시스템이지만 범용 쪽이라 같은
수준의 성능과 지연을 주지 못한다. S3를 파일 시스템처럼 마운트하거나 Resource Access
Manager로 버킷을 공유하는 구성도 마찬가지다 — 객체 스토리지는 저지연 병렬 접근을 위해 만든
파일 시스템이 아니다. 처리가 끝난 데이터를 사람이 다시 들여다봐야 하면 그 경로는
`Q751-Q800.md`의 `fsx-lustre-s3-data-repository-association`이 맡는다.

> [Q835 p564] "FSx for Lustre는 1ms 이내의 액세스 지연 시간을 제공하므로 HPC와 같이 성능에 민감한 워크로드에 이상적입니다."

## data-transfer-services

### `transfer-family-service-managed-users` — 사용자와 SSH 키를 서비스가 들고 있는 방식

**한 줄**: Transfer Family는 사용자와 키를 서비스가 직접 관리하는 방식을 지원해, 클라이언트가 쓰던 SFTP 클라이언트와 SSH 키를 그대로 둔 채 서버 쪽만 관리형으로 바꿀 수 있다.

이 방식에서는 사용자와 SSH 공개 키를 서비스에 등록해 두므로 클라이언트 쪽 절차가 바뀌지
않는다. 기존 사용자 관리와 키 생성 과정을 그대로 유지하고 싶다는 조건이 이 방식을 지목한다.
파일이 S3로 곧장 들어가는 것도 함께 얻는데, EC2에 SFTP 소프트웨어를 올려 두고 매시간
스크립트로 버킷에 옮기던 구성이 사라지므로 업로드와 처리 사이의 지연도 함께 없어진다.

> [Q831 p562] "서비스 관리형 사용자를 활성화하면 클라이언트는 기존 도구를 사용하여 계속 파일을 업로드할 수 있습니다."

## messaging-backup

### `eventbridge-resource-change-rule` — 리소스가 바뀌는 순간을 규칙으로 잡는다

**한 줄**: EventBridge 규칙은 누군가 리소스를 만들거나 고치는 것을 실시간으로 감지해 대상을 호출하므로, 설정이 그대로인지 주기적으로 확인하지 않고도 변경 시점에 바로 대응할 수 있다.

앱의 `messaging-backup.eventbridge`는 서비스 사이를 이어 준다는 데까지 말하고,
`Q551-Q600.md`의 `eventbridge-event-pattern-vs-polling`은 패턴으로 걸면 폴링이 사라진다는
것을 다룬다. 여기에 붙는 축이 **무엇을 이벤트로 삼을 수 있는가**다.

리소스의 생성·수정 같은 구성 변경도 이벤트가 된다. 그래서 배포의 로깅 구성이 바뀌는 것처럼
감사에 걸리는 변화에 규칙을 걸어 둘 수 있고, 규칙의 대상으로 Lambda 함수를 두면 변경이
일어난 그 시점에 후속 처리가 돈다. 그 함수가 SNS로 알림을 보내는 것까지가 한 벌이라 담당
팀에게 실시간으로 경고가 간다.

위협 탐지를 켜는 선택지가 같은 자리에 오르는데, 악의적인 활동을 찾는 쪽이라 관리자가 설정을
바꾼 사실 자체는 알려 주지 않는다.

> [Q801 p540] "EventBridge 규칙: CloudFront 배포에 대한 변경 사항을 실시간으로 감지하고 후속 조치를 위해 Lambda 함수를 트리거합니다."

**한 줄**: RDS Custom은 BYOL(Bring Your Own License) 모델을 지원해 이미 보유한 상용 데이터베이스 라이선스를 그대로 쓸 수 있으므로, 특권 액세스가 필요한 이전에서 비용까지 함께 따질 때 근거가 된다.

기능을 유지하는 것이 목적이면 이쪽이다.

> [Q842 p570] "RDS Custom은 BYOL 모델을 지원하여 기존 Oracle 라이선스를 사용하고 라이선스 요구 사항을 준수할 수 있게 해줍니다."

## aurora-dynamodb-cache

### `aurora-cross-region-read-replica` — 리전 간 Aurora 복제본

**한 줄**: 리전 간 Aurora 복제본은 엔진 기본 복제로 다른 리전에 주 DB 클러스터의 복제본을 만들어, 운영을 크게 흔들지 않고 리전 단위 재해에 대비하게 한다.

리전에 복사하는 구성은 Aurora를 그렇게 다루는 방식이 아니고, 중단도 복구 시간도 더 크다.

> [Q846 p573] "AWS 문서에 따르면, 리전 간 Aurora 복제본은 엔진 기본 복제를 사용하여 다른 리전에 주 DB 클러스터의 복제본을 생성하며, 이는 중단이 적은 재해 복구 옵션을 제공합니다."

## (주제 미정)

### `s3-requester-pays` — 요청자 부담 버킷

**한 줄**: 버킷을 요청자 부담으로 구성하면 요청과 데이터 다운로드 비용을 소유자가 아니라 받아 가는 쪽이 내므로, 큰 데이터 집합을 다른 계정에 열어 주면서 전송 요금을 떠안지 않는다.

데이터를 다른 계정과 나누는 장치는 앞 step들이 여럿 다뤘지만 — 버킷 정책의 조건, 계정 간
역할, 액세스 포인트 — 전부 **누가 읽을 수 있는가**를 정하는 쪽이다. 요청자 부담은 축이
다르다. 읽을 수 있는지는 그대로 두고 **누가 요금을 내는가**만 옮긴다.

그래서 "다른 AWS 계정에 데이터를 제공하는 비용을 최소화하라"가 조건이면 접근 경로를 바꾸는
선택지들과 갈린다. 대용량 데이터 집합을 일반에 공개하거나 다른 계정과 공유하면서 소유자의
전송 비용을 줄이는 것이 이 설정의 자리다.

주제가 미정인 이유는 앱의 S3 주제 셋이 스토리지 클래스·버전 관리와 수명 주기·암호화와 배치
작업으로 나뉘어 있어, 버킷의 과금 주체를 정하는 설정이 들어갈 자리가 없기 때문이다.

> [Q841 p570] "Requester Pays 버킷을 사용하면 버킷 소유자가 아닌 요청자가 버킷에 대한 요청 및 데이터 다운로드 비용을 지불하도록 버킷을 구성할 수 있습니다."

  오버헤드(Instant Retrieval·Flexible Retrieval 32KB, Deep Archive 8KB)와 최소 과금 단위

  해설이다. 이 수치들은 이 슬라이스에서 이 해설에만 나오고 다른 문항의 원본 해설로 교차
  확인되지 않아 넘겼다. 작은 파일이 계층 전환의 이득을 깎는다는 성질 자체는 `Q451-Q500.md`의
  `efs-ia-file-size-threshold`가 EFS 쪽에서 다룬다.
