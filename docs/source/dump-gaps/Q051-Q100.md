## s3-storage-classes

### `s3-express-one-zone` — S3 Express One Zone

**한 줄**: 1밀리초 미만의 지연으로 읽고 쓰는 고성능 S3 클래스이며, 이름대로 단일 AZ에 둔다.

앱이 다루는 일곱 클래스는 "조회를 기다리느냐"로 갈렸는데, 이 클래스는 그 축 바깥에 있다.
1밀리초 미만의 지연 시간과 높은 처리량을 내도록 만들어졌고, 여러 컴퓨팅 노드가 같은
데이터에 빠르게 접근해야 하는 머신러닝 모델 훈련 같은 작업이 대상이다.

일시적으로 고속 처리가 필요한 데이터라면 파일 스토리지나 블록 스토리지를 새로 붙이는 것보다
비용도 낮다. "S3에 이미 있는 데이터를 10밀리초 미만으로 읽어야 한다"가 조건일 때 옮길 곳이
여기다.

> [Q053 p39] "Amazon S3 Express One Zone은 1밀리초 미만의 지연 시간과 높은 처리량을 제공하므로, 여러 컴퓨팅 노드와 빠른 액세스가 필요한 ML 워크로드에 이상적입니다."

### `glacier-flexible-retrieval-standard-time` — Glacier Flexible Retrieval의 표준 검색 시간

**한 줄**: 표준 검색은 보통 3~5시간이 걸린다.

덤프 해설은 이 클래스를 몇 분에서 몇 시간 안에 꺼내는 아카이브로 설명하고, 표준 검색이
일반적으로 3~5시간에 끝난다고 못 박는다. "필요할 때 몇 시간 이내에 꺼낼 수 있어야 한다"가
조건인 문항에서 이 값이 정답 근거로 쓰인다.

**앱과 값이 어긋나는 자리다.** 앱의 `s3-storage-classes.glacier-flexible-retrieval`은
"최대 1시간"이라고 쓰고 있고, 그 값은 `concepts-raw.md`에서 왔다. 두 출처가 서로 다른 값을
말하므로 어느 쪽을 개념 데이터에 실을지는 phase 26에서 정해야 한다. 여기서는 덤프가 말한
값을 그대로 남긴다.

> [Q086 p61] "AWS 문서에 따르면 이 스토리지 클래스에서 표준 검색은 일반적으로 3~5시간 내에 완료되며, 이는 몇 시간 내에 기록을 검색해야 하는 요구 사항에 부합합니다."

### `s3-storage-class-cost-order` — 아카이브 계열의 비용 순서

**한 줄**: 장기 보관에서는 Standard-IA보다 Glacier 계열이 싸고, Glacier Flexible Retrieval보다 Deep Archive가 싸다.

앱은 일곱 클래스를 조회 대기 여부와 보관 목적으로 갈랐을 뿐 어느 쪽이 싼지는 말하지 않는다.
덤프 해설은 두 자리에서 이 순서를 밝힌다. 장기 저장 용도에서 S3 Standard-IA는 Glacier보다
비용이 더 들고, 검색 빈도가 낮은 아카이빙에서 Glacier Flexible Retrieval은 Deep Archive보다
비용이 더 든다. Deep Archive는 가장 저렴한 S3 스토리지 클래스로 소개된다.

보관 기간이 7년·10년처럼 길고 "가장 비용 효율적인" 것을 고르라면, 요구된 검색 시간을
만족하는 클래스 중 가장 아래쪽을 고르는 것이 판단 순서다. 복원까지 1주일을 기다려도 되면
Deep Archive까지 내려간다.

> [Q063 p45] "검색 빈도가 낮은 아카이빙 사용 사례의 경우, Glacier Flexible Retrieval은 Glacier Deep Archive보다 비용이 더 많이 듭니다."

## block-file-storage

### `efs-elastic-throughput` — EFS의 Elastic 처리량 모드

**한 줄**: 처리량을 미리 정하지 않고 워크로드에 맞춰 자동으로 오르내리게 하는 모드다.

EFS는 용량을 미리 프로비저닝하지 않아도 자동으로 늘어나는데, 처리량에도 같은 성질을 주는
설정이 Elastic 처리량 모드다. 급증하거나 예측할 수 없는 워크로드에서 처리량을 자동으로
확장하고 축소한다. "사전에 스토리지를 프로비저닝할 필요가 없어야 한다"와 "액세스 패턴이
여러 가지다"가 함께 걸리면 이 모드다.

계층화는 별개의 축이다. 접근이 뜸한 파일을 IA로 옮기는 몫은 앱에 이미 있는 EFS 수명 주기
관리와 Intelligent-Tiering이 맡고, 처리량 모드는 성능 쪽을 맡는다. 둘을 함께 켜면 네이티브
계층화와 자동 확장을 한 파일 시스템에서 얻는다.

> [Q071 p51] "AWS 문서에 따르면 Elastic throughput은 급증하거나 예측 불가능한 워크로드에 대해 처리량을 자동으로 확장하거나 축소하며, 이는 문제의 다양한 액세스 패턴과 일치합니다."

## rds-storage-features

### `rds-custom` — RDS Custom

**한 줄**: OS와 데이터베이스 내부에 직접 손대야 할 때 쓰는 RDS이고, 그만큼 운영 책임이 늘어난다.

일반 RDS는 운영체제 접근을 막아 두는 대신 관리를 AWS가 진다. RDS Custom은 OS 수준과
데이터베이스 수준의 접근·사용자 지정이 필요한 시나리오를 위해 만들어졌고, 그 대가로
운영상의 책임이 커진다.

그래서 "복원력 있는 관리형 데이터베이스"가 조건인 문항에서 RDS Custom은 답이 아니다.
문제가 깊은 맞춤 설정을 명시적으로 요구하지 않는 한, 같은 엔진의 일반 RDS를 다중 AZ로
배포하는 쪽이 더 단순하다.

> [Q091 p63] "옵션 A는 RDS Custom for SQL Server를 사용하며, 이는 OS 수준 및 데이터베이스 수준의 액세스/사용자 지정이 필요한 시나리오를 위해 고안되었습니다."

## aurora-dynamodb-cache

### `dynamodb-ttl` — DynamoDB TTL

**한 줄**: 만료 시각이 담긴 속성을 지정해 두면 그 시각이 지난 항목을 자동으로 지운다.

세션 데이터처럼 수명이 정해진 항목은 만료된 뒤 남겨 둘 이유가 없다. DynamoDB의
TTL(Time To Live)은 항목의 만료 시각이 들어 있는 속성을 하나 고르면 그 시각이 지난 항목을
예약 삭제한다. 지우는 코드를 따로 돌리거나 스케줄러를 붙일 필요가 없다.

"만료된 데이터 삭제를 자동화하라"에 "필요하면 전부 복원할 수 있어야 한다"가 붙으면 TTL과
PITR(특정 시점 복구)을 함께 켜는 것이 답이다. 둘은 서로 다른 것을 맡는다 — TTL은 지우고,
PITR은 되돌린다. PITR의 보존 한계(최대 35일)는 앱에 이미 있다.

> [Q072 p51] "Amazon DynamoDB는 만료된 항목을 자동으로 예약 삭제하기 위한 TTL(Time To Live)을 지원합니다."

### `dynamodb-single-digit-latency` — DynamoDB의 응답 시간

**한 줄**: 규모가 얼마나 커지든 10밀리초 미만의 응답을 유지한다.

문항이 응답 시간에 숫자를 걸고 "사용자 수를 알 수 없다"를 함께 말하면, 그 두 조건을 동시에
만족한다고 소개되는 데이터베이스가 DynamoDB다. 서버리스 방식의 완전 관리형 분산 NoSQL이며,
어떤 규모에서도 10밀리초 미만의 성능을 낸다. 예측할 수 없는 대규모 확장에는 관계형
데이터베이스가 같은 방식으로 대응하지 못한다.

지연을 줄여 준다는 점만 보고 전송 계열 서비스를 고르지 않아야 한다. CloudFront와 Global
Accelerator가 다루는 것은 전송과 네트워크 엣지의 문제이지, 데이터를 저장하고 돌려주는
쪽의 응답 시간이 아니다.

> [Q081 p57] "AWS에 따르면 DynamoDB는 서버리스 방식의 완전 관리형 분산 NoSQL 데이터베이스로, 어떤 규모에서도 10밀리초 미만의 성능을 제공합니다."

## compute-delivery

### `alb-routing-conditions` — ALB가 볼 수 있는 라우팅 조건

**한 줄**: 경로만이 아니라 HTTP 헤더와 호스트 이름으로도 대상을 가른다.

앱은 ALB를 "URL 경로로 라우팅한다"로 소개하지만 조건은 그것 하나가 아니다. 7계층
로드 밸런서라 요청의 내용을 볼 수 있어서 헤더 기반·경로 기반·호스트 기반 라우팅을 모두
지원한다. "HTTPS 헤더를 보고 대상을 나눈다"가 NLB로 풀리지 않는 이유도 같다 — 4계층에서는
헤더가 보이지 않는다.

라우팅과 차단은 다른 일이라는 것도 함께 본다. 규칙으로 특정 요청을 막는 것은 WAF의 몫이고,
ALB에 웹 ACL을 붙이면 헤더 기반 라우팅을 그대로 쓰면서 특정 패턴만 차단할 수 있다.
상호 TLS는 클라이언트 인증서로 신원을 확인하는 기능이라 규칙 기반 차단을 대신하지 못한다.

> [Q052 p39] "애플리케이션 로드 밸런서(ALB)는 헤더 기반 라우팅, 경로 기반 라우팅, 호스트 기반 라우팅을 포함한 HTTP/HTTPS 레이어 7 라우팅을 지원합니다."

### `nlb-tls-listener` — NLB도 TLS 연결을 받는다

**한 줄**: 4계층 로드 밸런서지만 TLS를 처리할 수 있고, 하나의 공용 진입점이 된다.

TLS가 조건에 있으면 ALB부터 떠올리게 되지만, TLS 연결을 받는 일 자체는 NLB도 한다.
NLB는 4계층에서 TLS를 처리하는 데 적합하고, 클라이언트에게 공용 엔드포인트 하나를
노출한다. "TLS 연결을 받는 단일 진입점"까지가 요구면 NLB로 충분하다.

갈림길은 요청의 내용을 봐야 하느냐다. 헤더나 경로로 대상을 갈라야 하면 ALB이고, 연결을
받아 그대로 넘기면 되면 NLB다.

> [Q061 p43] "네트워크 로드 밸런서(NLB)는 레이어 4에서 TLS를 처리하는 데 적합하며, 클라이언트 연결을 위해 단일 공용 엔드포인트를 노출할 수 있습니다."

### `load-balancer-idle-timeout` — 유휴 타임아웃은 경로 전체를 맞춘다

**한 줄**: 오래 붙어 있는 연결을 지키려면 연결이 지나는 모든 구성 요소의 유휴 타임아웃을 함께 늘려야 한다.

몇 시간씩 이어지는 TCP 연결이 중간에 한참 조용해지는 작업이 있다. 이때 연결이 끊기지
않으려면 로드 밸런서 하나만 고쳐서는 안 된다. 연결 경로에 놓인 구성 요소 전부 — 앞단의
ALB, 보안 장비에 트래픽을 분산하는 GWLB, 그리고 방화벽 자신 — 의 유휴 타임아웃을 필요한
시간 이상으로 맞춰야 한다. 한 곳이라도 짧으면 그곳이 연결을 끊는다.

처리 속도를 올리는 것은 이 문제의 답이 아니다. 서버 용량을 늘려 작업을 빨리 끝내도
유휴 상태가 타임아웃보다 길어지는 순간은 그대로 남는다. 방화벽을 하나만 두는 구성은
타임아웃과 무관하게 단일 장애 지점을 만든다.

> [Q074 p52] "애플리케이션이 장기 유지되는 TCP 연결을 사용하고 최대 1시간 동안 타임아웃 없이 유휴 상태를 유지해야 하므로, 연결 경로에 포함된 모든 구성 요소(ALB, GWLB 및 방화벽)의 유휴 타임아웃 값을 최소 1시간으로 설정해야 합니다."

### `ami-and-launch-template` — AMI와 시작 템플릿

**한 줄**: Auto Scaling 그룹이 인스턴스를 새로 띄우려면 복제할 이미지와 시작 설정이 먼저 있어야 한다.

돌고 있는 EC2를 그대로 늘리는 방법은 없다. AMI(Amazon Machine Image)는 그 인스턴스의 상태를
떠 둔 이미지이고, 시작 템플릿은 그 이미지로 인스턴스를 어떻게 띄울지 적어 둔 설정이다.
Auto Scaling 그룹은 이 둘을 받아 수요에 따라 인스턴스 수를 자동으로 조정한다.

예측할 수 없는 트래픽 급증이 조건이면 이 조합 앞에 로드 밸런서를 두는 구성이 표준 답이다.
인스턴스를 몇 대 더 만들어 두거나 지표에 경보만 거는 구성은 오토 스케일링이 없어 급증한
만큼 용량이 따라가지 못한다.

> [Q097 p68] "AMI를 생성하여 애플리케이션 로드 밸런서(ALB) 뒤에 있는 자동 스케일링 그룹에 배포하면 AWS가 수요에 따라 EC2 인스턴스 수를 자동으로 조정할 수 있습니다."

## serverless-containers

### `ecs-awsvpc-mode` — ECS의 awsvpc 네트워크 모드

**한 줄**: 태스크마다 자체 네트워크 인터페이스를 붙여 주는 모드다.

awsvpc 모드를 켜면 ECS 태스크 하나하나가 자기 몫의 엘라스틱 네트워크 인터페이스를 받는다.
태스크가 VPC 안에서 독립된 네트워크 주체가 되므로 프라이빗 서브넷에 안전하게 배치할 수 있고,
로드 밸런서 뒤의 대상으로 등록하는 것도 간단해진다.

프라이빗 서브넷에 둔 태스크가 인터넷으로 나가야 하면 퍼블릭 서브넷의 NAT 게이트웨이를
거친다. 밖으로 드러나는 것은 로드 밸런서 하나뿐이고 태스크로 직접 들어오는 인바운드 경로는
없다 — 공격 표면을 줄이라는 요구가 붙을 때 태스크를 퍼블릭 서브넷에 두는 선택지가 지워지는
이유가 이것이다.

> [Q061 p43] "AWS VPC 네트워크 모드를 사용하면 각 ECS 태스크가 자체 엘라스틱 네트워크 인터페이스를 할당받으므로, 태스크를 프라이빗 서브넷에 안전하게 배치하면서도 로드 밸런서 뒤의 대상으로 등록하는 것이 간단해집니다."

### `fargate-efs-mount` — Fargate 태스크에 EFS를 마운트한다

**한 줄**: 컨테이너에 영구 파일 저장소가 필요하면 Fargate에서 도는 ECS 태스크에 EFS를 붙인다.

컨테이너는 멈추면 안의 파일이 사라진다. 서버를 관리하지 않으면서 영구 저장소를 주려면
Fargate 위의 ECS 태스크에 EFS 파일 시스템을 마운트한다. 컨테이너는 표준 파일 시스템처럼
읽고 쓰며, 운영체제 수준의 권한도 그대로 다룰 수 있다.

"컨테이너와 파일 저장소 둘 다 완전 관리형이어야 한다"가 조건이면 이 조합이 답이다.
저장소로 EC2를 따로 세우는 구성은 관리 대상을 다시 만들어 그 조건을 깬다.

> [Q093 p65] "EFS는 Fargate에서 실행되는 ECS 태스크에 마운트할 수 있어, 컨테이너가 OS 수준 권한을 포함한 … 공유 파일 시스템에 액세스할 수 있게 합니다."

### `batch-fargate-compute-environment` — AWS Batch의 컴퓨팅 환경

**한 줄**: Batch가 컴퓨팅 환경의 프로비저닝과 확장을 맡고, 그 환경을 Fargate로 두면 관리할 인스턴스가 없다.

AWS Batch는 작업을 모아 처리하면서 그 작업을 돌릴 컴퓨팅 환경의 프로비저닝과 스케일링까지
자동화한다. 이 환경을 Fargate로 두면 관리할 인스턴스가 아예 없어진다. 작업이 Windows
기반이라는 것도 걸림돌이 아니다 — Batch가 Windows 기반 작업을 지원한다.

하루 한 번 도는 배치를 옮기면서 운영 부담을 가장 줄이라는 요구에는 이 조합이 답이 된다.
오토 스케일링 그룹으로 EC2 플릿을 세우거나 EC2 위에 EKS를 얹는 쪽은 관리 대상이 남는다.

> [Q098 p68] "AWS Batch는 Windows 기반 작업을 지원하며 컴퓨팅 환경의 프로비저닝 및 스케일링을 자동화합니다."

## messaging-backup

### `eventbridge-vs-step-functions` — 이벤트 라우팅과 워크플로 오케스트레이션

**한 줄**: EventBridge는 이벤트를 어디로 보낼지 정하고, Step Functions는 각 단계의 진행 상태를 중앙에서 추적한다.

둘 다 여러 서비스를 이어 준다는 점 때문에 헷갈리지만 맡는 일이 다르다. EventBridge는 이벤트
라우팅 서비스라 "이 이벤트가 오면 저기로 보낸다"까지가 몫이고, 각 건이 지금 어느 단계에
있는지를 들고 있지 않는다. Step Functions는 워크플로를 상태 머신으로 정의하므로 단계별
진행을 중앙에서 추적하고 여러 마이크로서비스 호출을 조율한다.

"처리 단계를 중앙에서 추적해야 한다"가 조건이면 Step Functions다. 여기에 "처리가 끝날
때까지 안정적으로 저장"이 붙으면 앞단에 SQS를 둔다 — 내구성 있는 작업 큐가 필요한 자리이고,
발행-구독 방식인 SNS는 그 역할을 대신하지 못한다.

> [Q067 p47] "EventBridge는 이벤트 라우팅 서비스이지 워크플로 오케스트레이션 서비스가 아닙니다."

## route53

### `route53-zone-file-import` — DNS 호스팅을 Route 53으로 옮기는 절차

**한 줄**: 퍼블릭 호스팅 영역을 만들고 기존 존 파일을 가져온 뒤, 등록 기관이 Route 53을 보게 바꾼다.

다른 DNS 공급자를 쓰다 Route 53으로 옮기는 문항은 이 절차 세 단계를 그대로 묻는다. 퍼블릭
호스팅 영역을 만들고, 기존 공급자의 존 파일에서 레코드를 가져오거나 다시 만들고, 도메인
등록 기관이 Route 53을 쓰도록 갱신한다. 레코드를 손으로 다시 넣지 않고 존 파일을 가져오는
것이 "신속하게"에 해당하는 부분이다.

프라이빗 호스팅 영역은 연결된 VPC에서만 해석되므로 공용 인터넷 DNS의 자리를 대신하지
못한다. Resolver 인바운드 엔드포인트도 VPC 워크로드를 위한 하이브리드 DNS 전달 기능이지
공용 도메인의 권한 있는 호스팅이 아니다.

> [Q051 p38] "공용 도메인을 이전하려면 공용 호스팅 존을 생성하고, 존 레코드를 가져오거나 다시 생성한 다음, 등록 기관을 업데이트하여 Route 53을 사용하도록 설정합니다."

### `route53-resolver-forward-rule` — 전달 규칙과 VPC 연결

**한 줄**: 아웃바운드 엔드포인트는 하나면 되고, 도메인별 전달 규칙을 쓰려는 VPC마다 연결한다.

앱은 인바운드·아웃바운드 엔드포인트의 방향까지 다루지만 그다음 단계가 비어 있다. VPC에서
나가는 쿼리를 온프레미스 DNS로 보내려면 아웃바운드 엔드포인트만으로는 부족하고, 어떤
도메인 이름을 어느 DNS 서버로 넘길지 정한 **Forward 유형 규칙**이 있어야 한다.

규칙은 만드는 것으로 끝나지 않고 **쓰려는 VPC마다 연결**해야 한다. 반대로 엔드포인트는
VPC마다 둘 필요가 없다 — 아웃바운드 엔드포인트 하나에 규칙 연결만 늘리면 여러 VPC가 함께
쓴다. "VPC가 여럿인데 엔드포인트를 전부에 만든다"는 선택지가 지워지는 근거가 이것이다.

> [Q099 p69] "다음으로, 사용자 지정 도메인 internal.example.com에 대한 DNS 쿼리를 온프레미스 DNS IP 주소로 전달하기 위해 전달 규칙(Forward 유형)을 생성해야 합니다."

## analytics-monitoring

### `kinesis-partition-key-hot-shard` — 파티션 키가 쏠리면 핫 샤드가 생긴다

**한 줄**: 파티션 키 값이 한쪽으로 몰리면 특정 샤드만 과부하가 되어, 전체 용량이 남아도 스로틀링이 난다.

Kinesis Data Streams는 레코드의 파티션 키로 어느 샤드에 넣을지 정한다. 키가 값 몇 개로
쏠리면 그 값이 가리키는 샤드에만 레코드가 몰려 과부하가 되고, 쓰기 요청이
`ProvisionedThroughputExceededException`으로 거절당한다. 스트림 전체가 쓰는 용량은
프로비저닝한 양보다 낮게 나오는데도 오류가 나는 상태가 이것이다.

해결의 방향은 용량이 아니라 분배다. 값이 고르게 흩어지는 속성으로 파티션 키를 바꾸면
레코드가 샤드에 균등하게 나뉜다. 샤드 수를 늘리는 것은 쏠림이 그대로면 소용이 없고,
서비스마다 스트림을 따로 두는 것은 복잡성만 늘린다.

> [Q056 p41] "특정 서비스에서 발생하는 과도한 로그로 인해 일부 샤드가 과부하 상태가 되어 스로틀링 오류가 발생할 수 있습니다."

### `kinesis-capacity-mode` — 프로비저닝 모드와 온디맨드 모드

**한 줄**: 샤드 수를 직접 정하는 프로비저닝 모드와, 처리량 관리를 맡기는 대신 비용이 더 드는 온디맨드 모드가 있다.

Kinesis Data Streams의 용량 모드는 둘이다. 프로비저닝 모드에서는 샤드 수를 직접 정해 그만큼
처리량을 확보한다. 온디맨드 모드는 처리량을 관리할 일을 없애 주지만 비용이 더 든다.

용량 모드를 바꾸는 것으로 덮이지 않는 문제가 있다는 점이 시험에서 갈리는 자리다. 파티션 키
쏠림 때문에 스로틀링이 나는 상황에서 온디맨드로 옮기면 증상은 가려지지만 근본 원인은 그대로
남고 비용만 오른다.

> [Q056 p41] "온디맨드 용량 모드는 처리량 관리를 없애주지만 비용이 더 많이 들고 근본 원인을 해결하지 못합니다."

### `opensearch-text-search` — 검색 워크로드는 OpenSearch다

**한 줄**: 실시간 색인과 텍스트 검색이 요구면 OpenSearch Service이고, DynamoDB는 고급 텍스트 검색을 하지 못한다.

Amazon OpenSearch Service는 실시간 검색·분석·시각화를 맡는 AWS 서비스다. 들어온 데이터를
거의 실시간으로 색인하고 질의할 수 있어서, 온프레미스 검색 애플리케이션을 AWS 네이티브
서비스로 옮기는 자리에 대응된다. 수집은 앞에서 Kinesis Data Streams가 맡고, 시각화는
QuickSight를 붙인다.

앱은 OpenSearch를 로그 분석 선택지로만 다루는데, 검색 자체가 요구인 문항에서는 다른 축이
필요하다. DynamoDB는 고급 텍스트 검색을 지원하지 않아 검색 워크로드의 저장소가 되지 못하고,
배치로 적재한 뒤 조회하는 구성은 실시간 검색에 맞지 않는다.

> [Q089 p62] "Amazon OpenSearch Service는 실시간 검색, 분석 및 시각화를 위한 AWS 네이티브 서비스입니다."

### `quicksight` — Amazon QuickSight

**한 줄**: 보고서와 대시보드를 만드는 시각화 서비스이며, Athena에 연결해 S3의 데이터를 그린다.

QuickSight는 데이터를 그려 보여 주는 쪽을 맡는다. 저장은 S3, 질의는 Athena, 시각화는
QuickSight로 역할이 나뉘고, QuickSight가 Athena에 연결해 대시보드와 보고서를 만든다.

"보고서와 시각화 자료를 생성한다"가 조건에 있으면 이 서비스가 답의 마지막 조각이다.
Redshift의 내장 쿼리 편집기로도 조회는 되지만, 과거 데이터를 가끔 들여다보려고 데이터
웨어하우스를 계속 띄워 두는 것은 비용 면에서 불리하다.

> [Q087 p61] "QuickSight는 대시보드 및 보고서를 위해 Athena에 연결할 수 있습니다."

### `dynamodb-to-s3-analytics` — 운영 테이블의 과거 데이터는 S3로 흘려보낸다

**한 줄**: DynamoDB의 변경분을 Kinesis Data Streams와 Data Firehose로 S3에 쌓고, 조회와 시각화는 Athena·QuickSight가 맡는다.

비용 때문에 오래된 레코드를 지우는 운영 테이블에서 과거 데이터로 보고서를 만들어야 하는
상황이 있다. 테이블에 계속 쌓아 두는 대신 변경 사항을 Kinesis Data Streams로 캡처해 Data
Firehose로 S3에 적재하면, 운영 테이블은 가볍게 유지하면서 이력은 남는다.

S3에 쌓인 뒤로는 서버를 띄우지 않는다. Athena가 S3의 데이터를 그 자리에서 SQL로 조회하고
QuickSight가 그 결과를 시각화하므로, 과거 보고를 위해 데이터 웨어하우스를 따로 유지할
필요가 없다.

> [Q087 p61] "AWS 문서에 따르면 Kinesis Data Streams와 Amazon Data Firehose를 사용하면 DynamoDB의 변경 사항을 거의 실시간으로 캡처하여 Amazon S3로 전송할 수 있습니다."

## secrets-encryption

### `acm-expiration-event` — ACM 인증서 만료 임박 이벤트

**한 줄**: 만료가 다가오면 ACM이 이벤트를 발행하므로, 인증서를 훑는 코드를 만들 필요가 없다.

가져온 인증서의 만료를 미리 알리라는 요구는 스캐너를 만드는 문제로 보이기 쉽다. 하지만
ACM은 인증서 만료가 임박하면 이벤트를 발행하고, EventBridge가 그 이벤트를 잡아 대상
서비스로 곧장 보낸다. 이벤트 유형 이름은 `ACM Certificate Approaching Expiration`이다.

목적지는 알림을 받을 사람에게 닿는 쪽이어야 한다. 이메일 구독이 붙어 있는 SNS 토픽을
대상으로 두면 규칙 하나로 끝나고, SQS 큐를 대상으로 두면 큐를 읽어 알림을 발행하는 소비자를
따로 만들어야 한다. 인증서를 나열하고 날짜를 계산하는 Lambda를 예약 실행하는 방식은 ACM이
이미 내주는 이벤트를 두고 폴링을 다시 만드는 일이다.

> [Q075 p52] "ACM은 인증서 만료가 임박하면 이벤트를 발행하며, EventBridge는 해당 이벤트를 매칭하여 사용자 정의 폴링 로직 없이 대상 서비스로 직접 라우팅할 수 있습니다."

## threat-protection

### `waf-managed-rule-groups` — WAF 관리형 규칙 그룹

**한 줄**: AWS가 관리하는 규칙 묶음을 붙이면 규칙을 직접 쓰지 않고도 알려진 공격 패턴을 막는다.

앱은 WAF 규칙을 IP 세트·지리적 일치·IP 평판으로 나눠 다루는데, 이와 별개로 규칙을 누가
쓰느냐는 축이 있다. AWS 관리형 규칙 그룹은 AWS 보안 팀이 계속 갱신하는 규칙 묶음이라,
OWASP Top 10 취약점처럼 널리 알려진 공격 패턴에 대한 보호를 규칙 작성 없이 얻는다.

사용자 지정 규칙만으로 같은 수준을 만들려면 상당한 운영 부담과 전문 지식이 든다. 그래서
"운영 부담을 줄이면서 애플리케이션 계층 공격을 막아라"가 조건이면 사용자 지정 규칙이 아니라
관리형 규칙 쪽이 답이다.

> [Q055 p40] "AWS WAF는 AWS에서 관리하는 관리형 규칙 그룹을 지원하며, 이를 통해 광범위한 수동 규칙 생성 없이도 OWASP Top 10 취약점 및 일반적인 공격 패턴에 대해 강력하고 검증된 보호 기능을 제공합니다."

### `shield-standard-network-layer` — Shield Standard가 다루지 않는 계층

**한 줄**: 추가 비용 없이 켜져 있지만 네트워크 계층까지이고, 애플리케이션 계층 필터링은 하지 않는다.

Shield Standard는 추가 비용 없이 자동으로 적용되는 기본 DDoS 보호다. 다만 그 범위가 네트워크
계층이라, 정상적인 요청의 모양을 한 애플리케이션 계층 공격은 걸러 내지 못한다.

그래서 "레이어 7 DDoS로부터 보호하라"에 Shield Standard를 붙이는 선택지는 답이 되지 않는다.
애플리케이션 계층의 요청을 검사해 막는 것은 WAF의 몫이고, 전담 대응 팀의 지원이 필요한
규모라면 Shield Advanced로 올라간다.

> [Q055 p40] "AWS Shield Standard는 추가 비용 없이 자동으로 기본적인 네트워크 계층 DDoS 보호 기능을 제공하지만, 애플리케이션 계층 필터링 기능은 제공하지 않습니다."

## identity-access

### `aws-directory-service` — AWS Directory Service와 AD Connector

**한 줄**: 온프레미스 Active Directory를 AWS에 잇는 서비스이고, AD Connector는 디렉터리 정보를 AWS에 저장하지 않는다.

AWS Directory Service는 디렉터리를 AWS에서 쓰게 해 주는 서비스다. 방향이 둘이다. AWS 관리형
Microsoft Active Directory를 AWS 쪽에 만들고 온프레미스 AD와 신뢰 관계를 맺는 방법이 하나,
AD Connector로 기존 온프레미스 AD에 연결만 하는 방법이 다른 하나다. AD Connector는 디렉터리
정보를 AWS에 저장하지 않고 인증을 온프레미스 쪽으로 넘긴다.

인증을 어디서 하느냐와 권한을 어떻게 주느냐는 다른 문제다. 기존 인증 소스를 그대로 두고
여러 계정의 접근을 중앙에서 관리하려면 AD Connector로 디렉터리를 잇고 IAM Identity Center의
권한 세트로 계정별 권한을 준다. 개발자마다 IAM 사용자를 만들거나 계정마다 역할을 손으로
배정하는 방식은 관리 부담이 커지고 ID 모델도 약해진다.

> [Q078 p55] "AWS 문서에 따르면 IAM Identity Center는 여러 AWS 계정에 권한을 할당할 수 있는 단일 창구를 제공하며, AD 커넥터는 AWS에 디렉터리 정보를 저장하지 않고도 AWS 서비스가 기존 디렉터리를 사용할 수 있도록 특별히 설계되었습니다."

## cost-management

### `on-demand-capacity-reservation` — 온디맨드 용량 예약

**한 줄**: 필요한 시점에 용량을 확보해 두는 기능이지 요금을 깎는 수단이 아니다.

이름에 "예약"이 들어가 예약 인스턴스나 절약 플랜과 같은 할인 수단으로 보이지만 성격이 다르다.
온디맨드 용량 예약은 원하는 인스턴스 용량을 미리 잡아 두는 것이고, 비용을 최적화해 주지
않는다.

그래서 "성능은 유지하면서 비용을 최적화하라"는 문항에서 이 선택지는 지워진다. 중단을 견디고
재시작할 수 있는 배치 작업이라면 스팟이 가장 싸고, 이런 패턴에서는 약정 할인인 절약 플랜도
스팟보다 비싸다.

> [Q076 p54] "On-Demand Capacity Reservations는 비용을 최적화하지 않으며, 중단 허용형 배치 패턴의 경우 Savings Plans도 Spot보다 비용이 더 많이 듭니다."

## (주제 미정)

### `s3-cross-account-bucket-policy` — 계정 간 버킷 접근은 버킷 정책으로 연다

**한 줄**: 다른 AWS 계정에 버킷 접근을 주려면 그 계정 ID를 지정한 버킷 정책을 붙인다.

같은 회사가 소유한 계정이라도 계정이 다르면 서로의 S3 버킷에 닿지 못한다. 접근을 열어 주는
표준 방법은 버킷 쪽에 정책을 붙이는 것이다. 권한을 줄 계정의 AWS 계정 ID를 정책에 적으면 그
계정이 버킷을 쓸 수 있고, 서비스를 새로 두거나 데이터를 복사할 필요가 없다.

리전 간 복제로 사본을 만들어 나눠 갖는 방법이나 CloudFront 서명된 URL로 콘텐츠를 내보내는
방법은 목적이 다르다. 앞의 것은 데이터를 두 벌로 만들고, 뒤의 것은 만료되는 임시 접근을
나눠 주는 수단이다.

`s3-presigned-url`·`s3-access-grants`와 같은 이유로 주제가 미정이다 — S3의 접근 제어를 담는
주제가 아직 없다.

> [Q094 p65] "Amazon S3 버킷에 대한 계정 간 액세스 권한을 부여하려면, 액세스 권한을 부여하려는 계정의 AWS 계정 ID를 지정하는 버킷 정책을 사용할 수 있습니다."

### `s3-storage-lens` — S3 Storage Lens

**한 줄**: 스토리지 사용 현황을 분석하고 보고하는 기능이며, 이벤트를 받아 무언가를 실행하는 장치가 아니다.

S3 Storage Lens가 맡는 것은 스토리지 사용 현황의 분석과 보고다. 객체가 만들어졌을 때 함수를
부르는 일과는 성격이 다르고, 그쪽은 S3 이벤트 알림의 몫이다.

"업로드될 때마다 처리하라"는 요구에 이 서비스가 보기로 섞여 나오는 자리가 있다. 이벤트 기반
처리인지 사용 현황 보고인지를 가르면 지워진다.

S3의 분석 기능이라 기존 20개 주제에 담을 자리가 없다.

> [Q064 p46] "옵션 D는 S3 Storage Lens가 이벤트 기반 처리가 아닌 스토리지 분석 및 보고를 위해 설계되었기 때문에 유효하지 않습니다."

### `sagemaker` — Amazon SageMaker AI

**한 줄**: 머신러닝 모델을 훈련하는 서비스이며, S3의 데이터를 옮기지 않고 그대로 학습에 쓴다.

이미지와 동영상을 모아 머신러닝 모델을 훈련하는 문항에서 학습을 맡는 서비스가 SageMaker AI다.
S3와 직접 통합되므로 데이터를 다른 파일 시스템으로 복사하지 않고 S3 버킷을 그대로 학습
데이터의 출처로 지정한다.

그래서 "S3에 올려 두고 ML 훈련에 쓴다"가 요구면 FSx나 EFS로 사본을 만드는 선택지는 파일
시스템 복사본과 비용을 더할 뿐이다. 노트북 인스턴스에 데이터를 직접 올리는 방식은 저장
용량이 그 인스턴스에 묶여 확장 가능한 장기 수집 설계가 되지 못한다.

머신러닝 서비스를 담는 주제가 기존 20개에 없다.

> [Q080 p57] "따라서 SageMaker와 직접 통합되고 Intelligent-Tiering을 지원하는 S3가 가장 확장성이 뛰어나고 비용 효율적인 솔루션입니다."

## 원본 수정 이력

덤프를 그대로 따르지 않은 항목이다. 근거는 ADR-008의 예외를 승계한 ADR-021.

### 사실 오류라 싣지 않은 것

- **Q072 p51** — 덤프 원문: "MemoryDB는 메모리 내 저장소로, 내구성 있는 복구를 위해 설계되지
  않았습니다." MemoryDB는 인메모리이면서 내구성을 갖추도록 만들어진 데이터베이스라 이 서술은
  실제 AWS 동작과 어긋난다. 이 문항의 정답(DynamoDB에 TTL과 PITR을 켜는 구성)은 다른 근거로도
  서므로 이 문장에서는 개념을 만들지 않았고, 같은 해설에서 TTL만 뽑아 `dynamodb-ttl`로 실었다.
  MemoryDB가 무엇인지는 이 슬라이스의 다른 해설에서 설명되지 않으므로 개념으로도 만들지 않는다.

### [AI 작성 해설]이라 채택하지 않은 것

해설집이 문서 2쪽에서 "원본에 해설이 없던 21개 문제는 새로 작성했다"고 밝힌 표시다.
이 슬라이스에는 두 문항(Q079·Q096)에 붙어 있다. 이 표시가 붙은 해설의 사실은 다른 문항의
근거와 교차 확인되는 것만 채택했다.

- **Q079 p56** — 게이트웨이 엔드포인트와 인터페이스 엔드포인트의 차이는 앱의
  `vpc-networking.endpoint-pricing`·`vpc-endpoint`에 이미 있다. 이 해설에만 나오는 것은
  "프라이빗 NAT 게이트웨이는 인터넷이 아닌 온프레미스나 다른 VPC 방향 통신을 중계하는
  장치"라는 설명인데, 다른 문항에서 교차 확인되지 않아 채택하지 않았다. 덧붙여 이 해설은
  선택지 기호가 어긋나 있다 — 공용·프라이빗 NAT 게이트웨이는 A와 E인데 "A와 C"로 적었고,
  C는 정답인 게이트웨이 VPC 엔드포인트다.
- **Q096 p67** — "S3 정적 웹사이트 호스팅은 버킷을 퍼블릭으로 열어야 동작한다"와 "ACM 인증서는
  S3 버킷으로 내보낼 수 없다"는 이 해설에만 있어 채택하지 않았다. 같은 해설의 나머지, 곧
  CloudFront를 앞에 두고 Origin Access Control로 버킷을 비공개로 두는 구성은 Q088의 일반
  해설과 겹치고 OAC 자체는 앱의 `threat-protection.cloudfront`에 이미 있으므로 새로 만들지
  않았다.
