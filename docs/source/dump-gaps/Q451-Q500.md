## s3-storage-classes

### `intelligent-tiering-monitoring-fee` — Intelligent-Tiering에는 객체마다 붙는 감시 요금이 있다

**한 줄**: 계층을 자동으로 옮겨 주는 대가로 객체마다 모니터링·자동화 요금이 붙으므로, 며칠 만에 지워지는 데이터에는 오히려 비싸다.

앱의 `s3-storage-classes.intelligent-tiering`은 접근 패턴을 예측하기 어려울 때 고르는
클래스라고 말하고, `Q101-Q150.md`의 `lifecycle-vs-intelligent-tiering`은 수명 주기 규칙과의
갈림길을 예측 가능성으로 잡는다. 둘 다 **데이터가 오래 남아 있는 것**을 전제로 한다.
그 전제가 깨지는 자리가 이 개념이다.

Intelligent-Tiering은 객체 하나하나의 접근을 추적하기 위해 모니터링·자동화 요금을 객체 수만큼
받는다. 그래서 이 클래스는 30일을 넘겨 머무는 데이터에 맞고, 밤새 만들어져 24시간 뒤에
사라지는 로그처럼 수명이 아주 짧은 객체에는 계층화로 아낄 것보다 감시 비용이 커진다.
크기와 개수를 모르는 단기 데이터에는 오히려 S3 Standard가 답이 된다.

같은 문항이 아카이브 계열도 함께 지운다. Glacier Deep Archive와 One Zone-IA는 조회 대기나
가용 영역 제약이 있어 그날 밤에 바로 처리해야 하는 데이터에 맞지 않는다. **"싼 클래스"가
아니라 "이 데이터가 얼마나 오래 머무는가"가 판단 축이다.**

> [Q467 p317] "Intelligent-Tiering은 액세스 패턴이 변화하는 장기간(일반적으로 30일 이상) 저장되는 데이터를 위해 설계되었으며, 객체당 모니터링 및 자동화 요금이 부과되므로 수명이 매우 짧은 객체에는 비효율적입니다."

## block-file-storage

### `efs-ia-file-size-threshold` — EFS IA는 작은 파일에는 해당하지 않는다

**한 줄**: EFS의 IA 계층은 128KB보다 큰 파일에 맞는 자리라, 잔파일만 잔뜩 있는 파일 시스템에서는 기대한 만큼 비용이 줄지 않는다.

앱의 `block-file-storage.efs-lifecycle-management`는 접근이 뜸한 파일을 EFS IA로 자동으로
옮겨 비용을 줄인다는 것과, 옮겨진 파일도 즉시 읽힌다는 것까지 다룬다. 남는 축이 하나 있다 —
**어떤 파일이 옮겨지는가**다.

EFS IA가 겨냥하는 것은 128KB보다 크면서 자주 읽히지 않는 파일이다. 문항이 "공유 파일의
크기는 최소 1GB"처럼 파일 크기를 굳이 밝히면 그것이 IA 전환이 실효를 낸다는 신호다.
반대로 크기 조건이 걸리지 않는 자잘한 파일 위주라면 계층을 옮겨도 절감 폭이 작다.

> [Q453 p308] "EFS IA는 128KB보다 크고 액세스 빈도가 낮은 파일에 이상적입니다."

### `fsx-windows-storage-auto-scaling` — FSx for Windows는 용량을 자동으로 늘린다

**한 줄**: 데이터가 늘어나는 만큼 파일 시스템 용량을 자동으로 확장해 주므로, 매주 용량이 불어나는 워크로드에 사람이 붙지 않아도 된다.

`Q101-Q150.md`의 `fsx-windows-file-server`는 이 서비스가 SMB로 접근하는 Windows용 관리형
공유 스토리지이고 다중 AZ 배포로 복원력을 얻는다는 것까지 다룬다. 문항이 한 겹 더 묻는 것은
**용량이 계속 자라는 상황**이다.

FSx for Windows File Server는 자동 스토리지 확장을 지원해서, 저장 수요가 주 단위로 늘어나도
용량을 미리 잡아 두거나 사람이 늘려 줄 필요가 없다. 그래서 "SMB를 지원하면서 수요에 따라
자동으로 확장되는 공유 파일 시스템"처럼 프로토콜과 확장이 함께 걸린 요구에서는, 용량을
고정해 프로비저닝하는 선택지가 먼저 지워진다. 앱의 `block-file-storage.fsx`가 가르는 대로
EFS는 NFS라 Windows·SMB 요구를 채우지 못하고, FSx for Lustre는 리눅스 HPC 쪽이다.

> [Q495 p336] "FSx for Windows File Server는 데이터 증가에 따라 파일 시스템 용량을 확장하는 자동 스토리지 스케일링을 지원하여, 최소한의 관리 노력으로 주당 1TB 이상의 용량 증가 요구 사항을 충족합니다."

### `sql-server-always-on-shared-storage` — SQL Server 클러스터에는 공유 스토리지가 필요하다

**한 줄**: SQL Server Always On 가용성 그룹을 직접 구성하려면 여러 노드가 함께 보는 공유 스토리지가 있어야 하고, 그 자리를 FSx for Windows File Server가 맡는다.

`Q351-Q400.md`의 `sql-server-license-cost`와 `Q301-Q350.md`의 `babelfish`는 SQL Server를
**떠나는** 쪽의 판단을 다룬다. 반대로 SQL Server 구성을 그대로 옮겨야 하는 요구도 있다.

Always On 가용성 그룹을 여러 가용 영역의 EC2 인스턴스에 직접 구성하려면 노드들이 함께
접근하는 공유 스토리지 계층이 필요하다. FSx for Windows File Server가 SQL Server 클러스터링과
호환되는 공유 스토리지를 제공하므로 이 조합이 답이 된다. 인스턴스마다 붙는 EBS 볼륨이나
객체 스토리지인 S3는 그 자리를 대신하지 못한다.

관리형 RDS for SQL Server의 다중 AZ 배포는 고가용성을 주지만, **사용자가 Always On 가용성
그룹을 직접 구성하고 운영하겠다는 요구**를 충족하지는 못한다. 문제문이 서비스의 고가용성이
아니라 특정 클러스터 구성을 못 박으면 관리형 쪽이 오답이 되는 자리다.

> [Q489 p333] "FSx가 SQL Server 클러스터링과 호환되는 공유 스토리지를 제공하므로 SQL Server Always On에 가장 적합한 솔루션입니다."

## data-transfer-services

### `transfer-family-structured-logging` — Transfer Family의 구조화된 로깅

**한 줄**: 누가 무엇을 얼마나 내려받았는지를 구조화된 형식으로 S3에 남길 수 있어, 사용량 기반 과금의 근거가 된다.

앱의 `data-transfer-services.transfer-family`는 SFTP·FTPS·FTP로 S3에 파일을 주고받는 관리형
서비스라는 것을 다루고, `Q351-Q400.md`의 `transfer-family-workflow`는 파일을 받은 **뒤**의
처리를 다룬다. 남는 축이 사용 기록이다.

Transfer Family 서버는 사용자 활동을 구조화된 형식으로 S3 버킷에 기록하도록 구성할 수 있고,
그 기록에는 파일 다운로드의 세부 정보가 담긴다. 고객별 월간 전송량으로 요금을 매겨야 하는
요구는 이 로그를 `Q251-Q300.md`의 `log-storage-s3-athena`가 다루는 방식으로 Athena에서
집계해 푼다. 네트워크 계층을 보는 VPC 플로우 로그나 AWS 요금을 보는 Cost Explorer는 **어느
고객이 얼마를 받아 갔는지**를 알려 주지 못한다.

> [Q468 p318] "AWS Transfer for SFTP 서버가 파일 다운로드에 대한 세부 정보를 포함한 사용자 활동을 구조화된 형식으로 Amazon S3에 기록하도록 구성되었는지 확인하십시오."

## rds-storage-features

### `rds-multi-az-db-cluster` — 다중 AZ DB 인스턴스와 다중 AZ DB 클러스터는 다르다

**한 줄**: 다중 AZ 배포에는 대기 인스턴스 하나짜리 DB 인스턴스 배포 말고도 대기 인스턴스 둘을 두고 그 대기 쪽에서 읽기를 받는 DB 클러스터 배포가 따로 있다.

앱의 `rds-storage-features.multi-az-standby-limits`는 다중 AZ의 대기 인스턴스가 아무 트래픽도
처리하지 않는다고 못 박는다. 그 문장이 가리키는 것은 **다중 AZ DB 인스턴스 배포**다.
같은 이름 아래 배포 형태가 하나 더 있다는 것을 알아야 선택지가 갈린다.

다중 AZ DB 클러스터 배포는 대기 인스턴스를 둘 두고, 일부 엔진에서는 그 대기 인스턴스가 읽기를
받는다. 그래서 읽기 트래픽을 보낼 리더 엔드포인트도 함께 생긴다. 다만 덤프는 RDS for MySQL의
트랜잭션과 분석을 가르는 표준 답으로는 여전히 **읽기 전용 복제본**을 든다. 복제가 비동기라
지연이 생기는데, 문제문이 "4시간 이내의 지연은 허용"처럼 지연 허용치를 밝히면 그것이 복제본
쪽을 가리키는 신호다.

정리하면 축이 셋이다. 고가용성은 다중 AZ, 읽기 확장은 읽기 전용 복제본, 그리고 읽을 수 있는
대기 인스턴스가 필요하면 다중 AZ DB 클러스터다. **대기 인스턴스가 읽기를 처리하지 않는다는
앱의 서술은 DB 인스턴스 배포에 대한 것이고, DB 클러스터 배포까지 부정하지는 않는다.**

> [Q459 p312] "옵션 B는 Multi-AZ DB 클러스터 배포를 설명하는데, 이는 일부 RDS 엔진에서 읽기 가능한 스탠바이를 제공하기도 합니다."

## compute-delivery

### `elb-health-check-drives-asg-replacement` — 상태 검사를 어디서 하느냐가 교체를 가른다

**한 줄**: 오토 스케일링 그룹은 로드 밸런서의 상태 검사 결과를 신호로 받아 비정상 인스턴스를 자동으로 교체하므로, 그 검사가 애플리케이션 오류를 보는지가 관건이다.

앱의 `compute-delivery.alb-l7-vs-nlb-l4`는 두 로드 밸런서를 계층으로 가르고, `elb`는 각각이
다루는 프로토콜을 다룬다. 상태 검사의 깊이는 그 갈림의 결과다. NLB는 4계층이라 연결이
되는지까지만 보고, ALB는 URL 경로로 HTTP 요청을 보내 응답 코드까지 판정한다.

그래서 **TCP 연결은 살아 있는데 애플리케이션이 오류를 돌려주는** 고장은 NLB 상태 검사에
잡히지 않는다. 인스턴스가 정상으로 남으니 교체도 일어나지 않고 사람이 재시작하게 된다.
로드 밸런서를 ALB로 바꿔 애플리케이션 계층 상태 검사를 걸면, 오토 스케일링 그룹이 그 결과를
인스턴스 상태로 받아 비정상 인스턴스를 스스로 교체한다. 스크립트를 쓰지 말라는 조건이
붙으면 크론 작업이나 사용자 지정 로직을 넣는 선택지가 먼저 지워진다.

`UnhealthyHostCount` 지표에 경보를 거는 선택지도 함께 나오는데, 애초에 로드 밸런서가 그
인스턴스를 비정상으로 표시하지 않으면 지표가 움직이지 않는다. **원인이 상태 검사의 깊이일
때는 그 위에 얹는 감시를 늘려도 소용이 없다.**

> [Q466 p316] "적절한 헬스 체크 구성(일반적으로 ELB 헬스 체크를 신호로 사용)을 통해, Auto Scaling은 비정상 인스턴스를 자동으로 교체하여 사용자 정의 스크립트 없이도 가용성을 향상시킬 수 있습니다."

### `alb-least-outstanding-requests` — ALB의 분산 알고리즘

**한 줄**: ALB는 라운드 로빈 말고도 처리 중인 요청이 가장 적은 대상으로 보내는 최소 미처리 요청 알고리즘을 쓸 수 있다.

앱의 `compute-delivery.sticky-session-tradeoff`는 스티키 세션을 끄면 라운드 로빈으로 돌아가
부하가 고르게 퍼진다고 말한다. 실제로는 선택지가 하나 더 있다.

ALB는 구성에 따라 라운드 로빈 또는 최소 미처리 요청(least outstanding requests) 알고리즘으로
트래픽을 나눈다. 앞의 것은 대상에 차례대로 넘기고, 뒤의 것은 아직 응답하지 않은 요청이 가장
적은 대상을 고른다. 요청마다 처리 시간이 크게 다른 애플리케이션에서는 차례대로 넘기는 것보다
남은 일이 적은 쪽으로 보내는 편이 고르게 퍼진다.

> [Q479 p325] "ALB는 라운드 로빈 또는 최소 미처리 요청 알고리즘(구성에 따라 다름)을 사용하여 인스턴스 간에 트래픽을 더 고르게 분산합니다."

### `target-tracking-vs-simple-scaling` — 대상 추적과 단순 조정의 갈림길

**한 줄**: 단순 조정은 경보가 울리면 정해진 양만큼 한 번 늘리고 쿨다운을 기다리는 방식이고, 대상 추적은 지표를 목표값에 붙여 두려고 용량을 계속 조절한다.

앱의 `compute-delivery.scheduled-scaling`은 예약된 조정과 대상 추적을 예측 가능성으로 가르고,
`Q401-Q450.md`의 `predictive-scaling`은 그 사이에 예측 조정을 끼워 넣는다. 남은 축이
**단순 조정**이다.

단순 조정은 고정된 조정 폭과 경보 임계값에 쿨다운이 붙는다. 15~20분 만에 끝나는 짧은 급증이
매일 반복되는 상황에서는 반응이 늦거나 과하게 늘리고, 트래픽이 빠진 뒤에도 인스턴스가 남아
비용이 샌다. 대상 추적은 목표값을 유지하려고 수요에 비례해 늘리고 줄이므로 이런 급증에서
모자람과 남음을 함께 줄인다.

지표를 무엇으로 삼는지도 함께 걸린다. 요청량에 맞춰 늘려야 하는 요구라면 로드 밸런서의 요청
수나 그것에서 파생한 사용자 지정 지표가 맞고, 비정상 호스트 수처럼 **수요가 아니라 상태를
재는 지표**로는 부하를 따라갈 수 없다.

> [Q491 p333] "옵션 A(단순 스케일링)는 고정된 조정 값과 경보 임계값(종종 쿨다운이 적용됨)에 의존하기 때문에, 트래픽이 급증하는 경우 일반적으로 비용 효율성이 떨어집니다."

### `cloudfront-s3-upload-with-oac` — CloudFront를 거쳐 S3에 올리기

**한 줄**: CloudFront는 내려받는 길만이 아니라 올리는 길로도 쓸 수 있고, 그때도 버킷을 공개하지 않고 OAC로 접근을 CloudFront에 한정한다.

앱의 `threat-protection.cloudfront`는 OAC를 원본 접근 주체를 CloudFront로 한정하는 방식이라고
다루고, `Q351-Q400.md`의 서명된 URL·쿠키 항목도 배포를 **콘텐츠를 내보내는 통로**로 그린다.
같은 배포에 사용자 지정 도메인을 붙여 파일을 **받는** 구성도 있다.

업로드를 CloudFront로 받게 하려면 S3 쪽에서 그 업로드를 허용하도록 구성하고, 버킷은 공개로
열지 않은 채 OAC를 통해서만 닿게 둔다. 여기에 사용자 지정 도메인을 쓰려면 앱의
`secrets-encryption.acm-cloudfront-region`이 말하는 대로 ACM 인증서를 us-east-1에서 발급해
CloudFront에 붙인다. 버킷이 다른 리전에 있어도 인증서 리전 규칙은 그대로다.

`Q251-Q300.md`의 `s3-website-endpoint-no-https`가 다루는 정적 웹사이트 엔드포인트나 전송
가속화는 이 구성에 필요하지 않다. **업로드 경로를 여는 것과 전송을 빠르게 하는 것은 다른
문제이고, 문제문이 요구한 것은 앞쪽이다.**

> [Q464 p315] "오리진 액세스 제어(OAC)는 버킷을 공개적으로 노출하지 않고도 CloudFront가 S3에 오브젝트를 업로드할 수 있도록 안전하게 허용합니다."

## serverless-containers

### `api-gateway-resource-policy` — API Gateway 리소스 정책

**한 줄**: 어느 AWS 계정이 이 API를 부를 수 있는지는 API에 직접 붙이는 리소스 정책으로 정한다.

`Q301-Q350.md`의 `api-gateway-api-key-not-auth`는 API 키가 인증 수단이 아니라는 것을 다루고,
`Q151-Q200.md`의 `api-gateway-lambda-proxy-integration`은 요청을 백엔드로 넘기는 방식을
다룬다. 남는 축이 **호출할 자격을 누구에게 주는가**다.

API Gateway REST API에는 리소스 정책을 붙일 수 있고, 거기서 호출을 허용할 주체를 지목한다.
다른 계정의 애플리케이션에 프라이빗 API를 열어 주는 요구는 이 정책에 계정을 나열해 푼다.
프라이빗 API가 인터페이스 VPC 엔드포인트를 통해 호출된다는 점 때문에 엔드포인트 정책을 고르는
선택지가 함께 나오는데, 그쪽은 엔드포인트를 지나는 트래픽에 대한 통제를 **더하는** 장치이고
API 자체의 계정 간 접근을 정하는 자리는 리소스 정책이다.

> [Q476 p323] "API Gateway 리소스 정책은 지정된 AWS 계정에서의 액세스를 허용하는 것을 포함하여, 누가 REST API를 호출할 수 있는지 제어하는 기본 방법입니다."

### `api-gateway-aws-service-integration` — API Gateway에서 AWS 서비스를 직접 호출한다

**한 줄**: 백엔드에 Lambda를 두지 않고 API Gateway 메서드를 DynamoDB의 `PutItem` 같은 AWS 서비스 작업에 바로 이어 붙일 수 있다.

앱의 `serverless-containers.api-gateway`는 요청을 ALB·Lambda·ECS·EC2 같은 백엔드로 보낸다고
말한다. 목록에 없는 통합이 하나 더 있다 — **AWS 서비스 자체**다.

REST API의 메서드를 만들 때 통합 유형을 AWS로 두고 서비스와 작업을 고르면, 그 메서드가 해당
서비스의 API를 직접 부른다. 평점을 DynamoDB 테이블에 넣는 일이라면 POST 메서드를 DynamoDB의
`PutItem`에 이어 붙이는 것으로 끝나고, 그 사이에 함수를 둘 필요가 없다. 개발자가 테이블을
직접 만지지 않게 하면서 재사용 가능한 창구를 만드는 요구에 이 방식이 맞는다.

Lambda를 끼우는 선택지도 동작은 하지만 관리할 코드가 하나 더 생긴다. 운영 오버헤드를
최소화하라는 조건이 붙으면 **중간 계층을 없애는 쪽**이 앞선다.

> [Q485 p329] "DynamoDB의 PutItem 액션과 통합되는 POST 메서드를 가진 REST API를 설정함으로써, 개발자는 데이터베이스와 직접 상호 작용할 필요 없이 API Gateway를 통해 DynamoDB 테이블에 데이터(예: 사용자 평점)를 제출할 수 있습니다."

### `eks-aws-load-balancer-controller` — AWS Load Balancer Controller

**한 줄**: EKS 클러스터 안에서 도는 컨트롤러가 쿠버네티스 Ingress를 읽어 ALB를 대신 만들어 주고, 그것이 경로별 마이크로서비스 라우팅의 표준 경로다.

`Q151-Q200.md`의 `eks-connector`, `Q301-Q350.md`의 `eks-cluster-autoscaler`,
`Q401-Q450.md`의 `eks-irsa`는 EKS의 연결·확장·권한을 다룬다. 남는 축이 **바깥에서 들어오는
요청을 어떻게 받는가**다.

AWS Load Balancer Controller는 쿠버네티스 Ingress 리소스를 보고 ALB를 프로비저닝한다.
`/customers`는 이 서비스로, `/orders`는 저 서비스로 보내는 7계층 라우팅이 로드 밸런서
자체의 기능으로 해결되므로 클러스터 안에 라우팅 계층을 하나 더 세울 필요가 없다.
NLB를 고르면 앱의 `compute-delivery.alb-l7-vs-nlb-l4`가 가르는 대로 경로를 볼 수 없어
인그레스 게이트웨이를 따로 붙이게 되고, 비용과 운영이 함께 늘어난다.

API Gateway를 앞에 두는 선택지도 함께 나온다. 스로틀링이나 사용량 계획 같은 API 관리 기능이
필요하면 그쪽이지만, 단순한 경로 기반 분기에는 요청당 비용과 구성이 더 붙는다.

> [Q493 p335] "EKS에서 이러한 방식의 라우팅을 제공하는 가장 직접적이고 비용 효율적인 방법은 Kubernetes Ingress와 AWS Load Balancer Controller를 사용하여 Application Load Balancer(ALB)를 프로비저닝하는 것입니다."

## route53

### `route53-failover-routing` — 페일오버 라우팅 정책

**한 줄**: 주 레코드와 보조 레코드를 두고 주 레코드에만 상태 검사를 연결하면, 주 대상이 비정상이 될 때 Route 53이 보조 대상을 대신 응답한다.

앱의 `route53.routing-policies`는 단순·지리·가중치·지연시간 등 여러 정책을 늘어놓지만
**페일오버 라우팅**은 빠져 있다. 자동 장애 조치를 DNS에서 처리하는 요구가 이 정책의 자리다.

레코드는 둘이다. 주(primary) 레코드는 평소에 쓰는 대상 — 이를테면 ALB — 을 가리키고,
보조(secondary) 레코드는 대체 대상을 가리킨다. **상태 검사는 주 레코드에 연결한다.**
Route 53이 그 검사로 주 대상의 정상 여부를 판정하고, 비정상이 되면 보조 레코드를 응답한다.
이 구성에서 보조 레코드에는 별도의 상태 검사가 필요하지 않다.

대체 대상이 반드시 같은 종류일 필요는 없다. 애플리케이션이 멈췄을 때 S3에 올려 둔 정적
웹사이트를 대신 보여 주는 구성이 그 예다. Lambda 함수로 레코드를 갈아 끼우겠다는 선택지가
함께 나오는데, Route 53에 내장된 기능이 있으므로 직접 만들 이유가 없다.

> [Q451 p307] "Route 53 페일오버 라우팅은 주 리소스가 정상일 때는 주 리소스를 반환하고, 주 리소스가 비정상 상태가 되면 자동으로 보조 리소스를 반환하도록 설계되었습니다."

### `multi-region-failover-for-region-outage` — 리전 장애는 가용 영역으로 막지 못한다

**한 줄**: 리전 하나에 접근할 수 없게 되는 상황에 대비하려면 여러 리전에 배포하고 상태 검사를 붙인 DNS 장애 조치로 정상 리전을 응답해야 한다.

앱의 `aws-core-services.multi-az`는 같은 리전의 여러 가용 영역에 나누어 배치하는 구성이고,
`availability-zone`은 그 영역들이 한 리전 안에 있다고 밝힌다. 그래서 다중 AZ는 데이터
센터 하나가 멈추는 것까지만 막는다.

문제문이 "해당 리전에서 애플리케이션에 접속할 수 없게 되더라도"처럼 **리전 경계**를 못 박으면
가용 영역을 늘리는 선택지는 전부 지워진다. 남는 방법은 여러 리전에 배포하고 Route 53의 상태
검사 기반 장애 조치로 정상 리전에 트래픽을 보내는 것이다. 여러 리전에 배포하더라도 단순
라우팅 레코드를 쓰면 상태를 보지 않고 그대로 응답하므로 자동 전환이 되지 않는다.
**리전을 늘리는 것과 상태를 보고 고르는 것이 함께 있어야 요구가 채워진다.**

> [Q471 p319] "리전 장애에 대비하기 위해 애플리케이션을 여러 리전에 배포해야 합니다."

## security-groups-nacl

### `nacl-deny-at-source-subnet` — 거부 규칙은 보내는 쪽 서브넷에 건다

**한 줄**: A가 B로 보내는 것을 막으려면 A가 있는 서브넷의 NACL에 아웃바운드 거부 규칙을 걸어야 하고, B 쪽 서브넷을 고치면 방향이 반대가 된다.

앱의 `security-groups-nacl.nacl`과 `Q301-Q350.md`의
`security-group-stateful-vs-nacl-stateless`는 NACL이 서브넷 경계에서 동작하고 차단 규칙을
가질 수 있다는 것까지 다룬다. 문항이 한 겹 더 묻는 것은 **그 규칙을 어느 서브넷의 어느
방향에 거는가**다.

NACL은 서브넷마다 붙고 인바운드와 아웃바운드가 따로 있다. 같은 VPC 안의 두 프라이빗 서브넷
사이에서 한쪽 방향만 막아야 한다면, 보내는 쪽 서브넷의 아웃바운드에 상대 IP 대역을 거부하는
규칙을 넣는다. 받는 쪽 서브넷의 아웃바운드를 건드리면 막히는 것은 그쪽이 내보내는 트래픽이라
요구와 방향이 어긋난다.

보안 그룹으로 같은 일을 하겠다는 선택지도 함께 나오는데, 앱이 말하는 대로 보안 그룹에는
차단 규칙 자체가 없다. **차단이 필요하면 자리는 NACL이고, 남는 판단은 서브넷과 방향뿐이다.**

> [Q480 p325] "이렇게 하면 애플리케이션 B가 트래픽을 보내는 것은 막을 수 있지만, 요구 사항은 애플리케이션 A에서 애플리케이션 B로 가는 트래픽을 차단하는 것입니다."

## threat-protection

### `waf-body-inspection-size-limit` — WAF가 검사하는 요청 본문에는 크기 한도가 있다

**한 줄**: WAF는 HTTP 요청 본문을 정해진 크기까지만 들여다보므로, 한도를 넘는 큰 POST 요청은 본문 규칙만으로 걸러지지 않는다.

앱의 `threat-protection.waf`는 WAF가 7계층에서 요청을 검사하고 SQL 인젝션·XSS를 막는다는 것을
다룬다. 그 검사에 붙는 제약이 이 개념이다.

WAF가 평가할 수 있는 요청 본문의 크기에는 한도가 있다. 그보다 큰 본문은 한도까지만 검사되고
나머지는 평가되지 않으므로, 8MB짜리 POST의 뒷부분에 악성 페이로드가 있으면 본문 검사 규칙이
그것을 잡지 못한다. 웹 ACL을 아무리 촘촘히 짜도 못 보는 구간이 남는다는 뜻이다.

덤프가 드는 대응은 규칙 논리로 처리 방침을 정하는 것이다. 큰 요청은 기본적으로 차단하고,
신뢰할 수 있는 출처에서 오는 큰 요청만 우선순위가 앞선 규칙으로 허용한다. 검사할 수 없는
요청에 대해 동작을 확정해 두는 방식이다. Shield Advanced는 DDoS 쪽이라 본문 검사 한도를
늘려 주지 않고, `Content-Type` 헤더를 맞추는 것도 크기 한도와는 무관하다.

> [Q456 p310] "AWS WAF는 검사할 수 있는 HTTP 요청 본문의 크기에 제한이 있습니다."

## secrets-encryption

### `kms-cloudhsm-key-store` — CloudHSM이 뒷받침하는 KMS 키

**한 줄**: 전용 하드웨어 모듈에 키를 두면서도 RDS 같은 서비스의 저장 중 암호화에 그 키를 쓰려면, CloudHSM을 직접 붙이는 것이 아니라 CloudHSM이 뒷받침하는 KMS 키를 쓴다.

앱의 `secrets-encryption.cloudhsm`은 CloudHSM이 매우 높은 수준의 키 보안이 필요할 때 쓰는
전용 하드웨어라는 것까지 다루고, `kms`는 KMS가 암호화 키를 만들고 보관한다고 다룬다.
둘을 **함께** 쓰는 방법은 어느 쪽에도 없다.

RDS의 저장 중 암호화는 KMS 키로 이루어진다. 그래서 "전용 하드웨어 모듈로 키를 보관하고
관리해야 한다"는 규정 요구가 붙으면, CloudHSM에 키를 따로 두고 RDS가 그것을 직접 쓰게 하는
것이 아니라 **CloudHSM이 뒷받침하는 KMS 키**를 만들어 데이터베이스 암호화에 지정한다.
데이터베이스 쪽 설정은 평소의 저장 중 암호화와 같고, 키가 놓인 자리만 달라진다.

CloudHSM에 키를 저장하고 RDS가 곧바로 그것을 쓰게 한다는 선택지, 인스턴스 스토어를
암호화한다는 선택지, S3 관리 키로 스냅샷을 암호화한다는 선택지가 함께 오답으로 나온다.

> [Q481 p327] "Amazon RDS는 AWS CloudHSM이 지원하는 AWS KMS 키를 사용하여 저장 시 암호화를 지원합니다."

## identity-access

### `iam-explicit-deny-precedence` — 명시적 거부가 허용을 이긴다

**한 줄**: 한 정책 안에 허용과 거부가 함께 있으면 조건에 걸린 거부가 언제나 이기고, `aws:SourceIp` 같은 조건은 그 거부를 특정 상황에서만 켜는 스위치가 된다.

앱의 `identity-access.iam`은 IAM 사용자와 역할을 다루고 `least-privilege`는 권한을 좁히는
원칙을 다루지만, **정책 여러 개가 겹칠 때 무엇이 이기는가**는 다루지 않는다.
`Q001-Q050.md`의 `scp-condition-exception`이 조건으로 예외를 두는 방법을 보여 주는데,
그 예외가 왜 성립하는지의 근거가 이 평가 순서다.

평가 순서는 명시적 거부, 허용, 그리고 아무 데도 걸리지 않으면 기본 거부다. 모든 리소스에
작업을 허용하는 문장이 있어도, 같은 작업에 조건부 거부 문장이 붙어 있고 그 조건이 성립하면
요청은 막히고 403이 돌아온다.

조건에는 요청이 어디에서 왔는지도 쓸 수 있다. `aws:SourceIp`로 허용할 IP 대역을 정해 두면
그 대역 밖에서 온 API 호출이 거부에 걸린다. 그래서 권한은 분명히 있는데 요청이 막히는 상황을
만나면, 정책의 작업 목록만 보지 말고 **조건이 붙은 거부 문장이 있는지**를 먼저 본다.

> [Q488 p332] "명시적 거부(Explicit Deny)는 항상 허용(Allow)보다 우선합니다."

### `scp-attachment-targets` — SCP를 붙일 수 있는 자리

**한 줄**: SCP는 루트, 조직 단위, 개별 멤버 계정 중 어디에나 붙일 수 있고, 붙인 자리 아래에만 적용된다.

`Q351-Q400.md`의 `organizational-unit`은 OU에 붙인 SCP가 그 안 계정 전부에 걸린다는 것을
다룬다. 붙일 수 있는 자리가 OU만은 아니다.

SCP는 조직의 루트, OU, 그리고 개별 멤버 계정에 연결할 수 있고 연결한 자리 아래에만 적용된다.
그래서 계정 넷 중 셋만 제한해야 하는 요구는 두 가지로 풀린다 — 그 세 계정에 정책을 각각
연결하거나, 세 계정을 담을 OU를 만들어 옮기고 그 OU에 연결한다. 반대로 **루트에 붙이면
제한할 생각이 없던 계정까지 함께 걸린다.** 제한하지 않을 계정 쪽에 OU를 만들어 거부 정책을
붙이는 선택지는 대상이 정반대라 오답이다.

> [Q473 p321] "AWS Organizations의 서비스 제어 정책(SCP)은 해당 정책이 연결된 계정 또는 OU에 적용됩니다."

## (주제 미정)

### `appconfig` — AWS AppConfig

**한 줄**: 애플리케이션 구성값을 검증하고 배포하는 서비스이며, 자격 증명을 보관하는 Secrets Manager와는 맡는 것이 다르다.

앱의 `secrets-encryption.secrets-manager-vs-parameter-store`는 비밀값을 어디에 둘지 가른다.
같은 문항이 축을 하나 더 세운다 — **비밀값이 아닌 설정값**은 어디에 두는가다.

AWS AppConfig는 애플리케이션 구성을 관리하는 서비스로, 구성을 검증한 뒤 배포하는 절차를
제공한다. 애플리케이션을 멈추지 않고 설정을 바꿔 내보내는 것이 목적이다. 데이터베이스
자격 증명처럼 순환이 필요한 값은 여전히 Secrets Manager가 맡는다. 그래서 "구성을 관리하고
자격 증명을 안전하게 보관한다"는 요구가 함께 나오면 두 서비스를 나누어 쓰는 선택지가 답이다.

구성 파일을 암호화해 S3에 두거나 자격 증명을 RDS 테이블에 넣는 선택지가 함께 나오는데,
둘 다 관리 부담이 늘고 자격 증명 보관 용도로 설계된 자리가 아니다.
이 개념은 기존 20개 주제 어디에도 딱 맞는 자리가 없다 — 배치는 phase 26이 정한다.

> [Q472 p319] "AWS AppConfig는 애플리케이션 구성을 안전하고 검증된 방식으로 관리하도록 설계된 서비스입니다."

- **Q452 p307 — S3에는 인터페이스 엔드포인트가 없고 DynamoDB에는 게이트웨이 엔드포인트가
