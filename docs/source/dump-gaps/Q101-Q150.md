## s3-storage-classes

### `lifecycle-vs-intelligent-tiering` — 수명 주기 규칙과 자동 계층화의 갈림길

**한 줄**: 며칠 뒤에 식는지 알면 수명 주기 규칙, 언제 다시 뜨거워질지 모르면 Intelligent-Tiering이다.

앱은 수명 주기 정책과 Intelligent-Tiering을 각각 설명하지만 둘 중 무엇을 고를지는 말하지
않는다. 덤프가 쓰는 기준은 접근 패턴의 예측 가능성이다. 수명 주기 규칙은 "30일이 지나면
옮긴다"처럼 시간만 보고 움직이는 정적인 규칙이라, 다시 자주 읽히기 시작한 객체를 되돌리지
못한다. Intelligent-Tiering은 객체마다 실제 접근을 추적해 빈번·비빈번 계층 사이를 오간다.

그래서 "일부는 몇 달째 조회가 많고 일부는 일주일 만에 식는다"처럼 객체별로 수명이 갈리는
데이터에서는 규칙을 짜는 쪽이 아니라 맡기는 쪽이 답이 된다. 반대로 "30일 뒤에는 확실히
안 본다"가 조건이면 수명 주기 전환이 더 싸다.

> [Q136 p93] "C: 라이프사이클 규칙은 정적이며 예측 불가능한 액세스 패턴에 동적으로 적응하지 못합니다."

## s3-versioning-lifecycle

### `s3-replication-time-control` — S3 복제 시간 제어(S3 RTC)

**한 줄**: 복제에 걸리는 시간을 보장받는 옵션이며, "몇 분 안에 사본이 있어야 한다"는 요구는 여기로 간다.

기본 복제는 언제 끝난다는 약속이 없다. 복제 규칙에 S3 RTC를 켜면 대부분의 객체는 몇 초
안에, 나머지도 15분 안에 대상 버킷에 도착한다. 복제 상태를 지켜보는 지표와 이벤트도 함께
붙는다.

문항에서 이 옵션을 가리키는 신호는 "복제본이 몇 분 이내에 사용 가능해야 한다"는 시간
조건이다. 시간 조건이 없으면 복제 규칙만으로 충분하고, 있으면 RTC가 붙은 선택지를 찾는다.
복제된 객체는 대상 버킷에 그대로 남으므로 꺼내는 데 따로 시간이 걸리지 않는다.

> [Q110 p76] "몇 분 이내의 가용성 요구 사항은 S3 Replication Time Control을 직접적으로 가리키며, AWS에 따르면 이 기능은 대부분의 오브젝트를 몇 초 내에, 99.9%는 15분 이내에 복제합니다."

### `s3-replication-cross-account-kms` — 복제는 다른 계정 버킷으로도 간다

**한 줄**: 복제 대상은 같은 계정이 아니어도 되며, SSE-KMS로 암호화한 객체는 키 권한을 따로 열어야 복제된다.

`s3-replication`은 리전 간 복제를 다루지만 복제의 경계가 계정이 아니라는 것은 별개의
사실이다. 복제 규칙의 대상 버킷은 다른 AWS 계정에 있어도 되고, 같은 리전 안이어도 된다.
"다른 계정으로 객체를 계속 넘겨야 한다"는 요구에서 백업 작업이나 배치 복사 스크립트가 아니라
복제가 답이 되는 이유다.

암호화가 걸리면 조건이 하나 더 붙는다. SSE-KMS로 암호화된 객체는 복제 구성에 키를 다룰
권한을 추가로 주어야 복제된다. 대상 계정이 소스 버킷의 KMS 키를 쓸 수 있도록 키 정책을
열어 두는 작업이 함께 나오는 것이 이 때문이다.

> [Q110 p76] "S3 복제는 다른 AWS 계정의 버킷을 포함하여 다른 버킷으로 오브젝트를 자동으로 복사하는 기본 메커니즘이므로 올바른 서비스입니다."

## s3-encryption-batch

### `s3-object-lambda` — S3 Object Lambda

**한 줄**: 객체를 돌려주기 직전에 코드를 끼워 넣어 요청하는 쪽마다 다른 모습으로 내보낸다.

같은 원본 데이터를 애플리케이션마다 다르게 보여줘야 할 때, 보통은 가공한 사본을 여러 벌
만들어 버킷을 나눈다. S3 Object Lambda는 그 사본을 만들지 않는다. 요청이 들어오면 S3가
객체를 함수에 넘기고, 함수가 변환한 결과가 호출자에게 돌아간다.

개인 식별 정보(PII)를 어떤 애플리케이션에는 그대로 주고 다른 애플리케이션에는 지워서
주는 구성이 대표적인 예다. 데이터 세트가 하나로 유지되므로 버킷 여러 개를 동기화할 일이
없고, 그만큼 운영 부담이 줄어든다.

> [Q150 p102] "Amazon S3 Object Lambda를 사용하면 애플리케이션으로 반환되기 전에 S3에서 가져온 데이터를 처리하기 위해 자체 코드를 추가할 수 있습니다."

## block-file-storage

### `fsx-windows-file-server` — Amazon FSx for Windows File Server

**한 줄**: Windows 워크로드용 관리형 공유 파일 스토리지이며, SMB로 접근한다.

앱의 `fsx`는 고성능 파일 스토리지라는 한 줄로만 소개돼 있어, FSx가 여러 파일 시스템을
묶은 이름이라는 것이 드러나지 않는다. FSx for Windows File Server는 그중 Windows 쪽이다.
여러 애플리케이션 서버가 같은 파일을 공유해야 하고 접근 방식이 SMB라면 이 서비스가 답이다.

다중 AZ로 배포하면 두 가용 영역에 데이터를 동기식으로 써 두고, 주 파일 서버가 멈추면 다른
영역의 대기 파일 서버로 자동 전환한다. "공유 스토리지인데 복원력도 있어야 한다"는 조건이
붙으면 다중 AZ 배포까지 고른 선택지를 찾는다. S3는 객체 스토리지라 SMB 공유가 되지 않고,
EBS는 보통 인스턴스 한 대에 붙는 블록 스토리지라 여러 대의 공유 파일 시스템이 되지 않는다.

> [Q146 p99] "Amazon FSx for Windows File Server는 Windows 워크로드를 위해 특별히 구축된 AWS 관리형 파일 스토리지 서비스입니다."

### `fsx-for-lustre` — Amazon FSx for Lustre

**한 줄**: 높은 IOPS가 필요한 고성능 컴퓨팅(HPC) 워크로드를 위한 파일 시스템이다.

FSx 계열 중 계산 집약적인 작업 쪽이다. 많은 노드가 같은 파일 시스템을 두드리면서 초당
입출력 횟수가 높게 유지되어야 하는 워크로드를 위해 만들어졌다.

"HPC이고 높은 IOPS"가 조건이면 EFS는 답이 아니다. EFS는 여러 대가 공유하는 파일 시스템이지만
이런 성능을 위해 최적화된 것은 아니다. S3를 파일 시스템처럼 마운트하는 방식도 같은 이유로
빗나간다. 계산 노드 쪽에는 클러스터 배치 그룹을 함께 두어 노드 사이 지연을 줄이는 구성이
짝으로 나온다.

> [Q139 p95] "선택지 B: FSx for Lustre는 높은 IOPS를 요구하는 HPC 워크로드를 위해 설계되었습니다."

### `fsx-file-gateway` — Amazon FSx File Gateway

**한 줄**: 온프레미스에서 FSx 파일 시스템에 접근하게 해 주는 게이트웨이이지, 클라우드 안의 공유 스토리지가 아니다.

이름이 비슷해 FSx 파일 시스템 자체와 헷갈리기 쉽다. FSx File Gateway가 하는 일은 온프레미스
쪽에 접점을 만들어 주는 것이고, 실제 파일이 사는 곳은 FSx다. `storage-gateway`가 S3에 대해
하는 일을 FSx에 대해 하는 셈이다.

그래서 AWS 안에서 도는 애플리케이션들이 서로 공유할 스토리지를 고르는 문항에서는 답이 되지
않는다. 온프레미스라는 조건이 문제문에 없으면 게이트웨이 계열은 지운다.

> [Q146 p99] "옵션 D는 Amazon FSx File Gateway가 Amazon FSx 파일 시스템에 대한 온프레미스 액세스를 제공하는 데 사용되며, 이 클라우드 네이티브 애플리케이션 설계에 필요한 주요 공유 스토리지 서비스가 아니기 때문에 틀렸습니다."

## data-transfer-services

### `storage-gateway-volume-modes` — 저장 볼륨 게이트웨이와 캐시된 볼륨 게이트웨이

**한 줄**: 전체 데이터가 온프레미스에 남으면 저장 볼륨, 주 사본이 AWS에 있고 일부만 로컬에 두면 캐시된 볼륨이다.

앱의 `storage-gateway`는 온프레미스에서 S3를 로컬 저장소처럼 쓰게 해 준다고만 말한다.
볼륨 게이트웨이에는 모드가 둘이고, 문항은 그 둘을 갈라 놓고 하나를 고르게 한다.

저장 볼륨(stored volume)은 데이터 전체를 온프레미스 디스크에 두고, 그것을 iSCSI 블록 장치로
서버에 붙인 뒤 스냅샷을 S3로 비동기 백업한다. 모든 데이터에 대한 로컬 접근이 유지되므로
"기존 백업 장비를 대체하되 로컬 접근은 그대로"라는 요구에 맞는다. 캐시된 볼륨(cached volume)은
반대다 — 주 데이터는 AWS에 있고 자주 쓰는 만큼만 로컬에 캐시하므로, 전체 데이터에 로컬로
닿아야 한다는 조건을 만족하지 못한다.

Snowball 계열이 함께 오답으로 나오는 이유도 같은 축이다. 그쪽은 한 번에 옮기는 이사용
장비이지 계속 돌아가는 백업 경로가 아니다.

> [Q130 p89] "캐시된 볼륨 게이트웨이(옵션 C)는 주 사본을 AWS에 보관하고 일부만 로컬에 캐시하므로, 모든 데이터에 대한 완전한 로컬 액세스 유지 요건을 충족하지 못합니다."

## rds-storage-features

### `read-replica-vs-cache` — 캐시가 듣지 않는 조건

**한 줄**: 같은 쿼리가 반복되지 않으면 캐시는 이득이 없고, 읽기 부하는 읽기 복제본으로 던다.

읽기가 무겁다는 말만 보고 ElastiCache를 고르면 걸리는 자리가 있다. 캐시는 같은 결과를 여러 번
돌려줄 때 값어치가 생기는 장치다. 문제문이 "같은 쿼리를 두 번 이상 실행하는 경우가 거의 없다"
거나 "데이터가 자주 바뀐다"고 못 박으면 캐시 적중이 일어나지 않아 아무것도 얻지 못한다.

이때 남는 선택은 읽기를 다른 인스턴스로 옮기는 것이다. 읽기 복제본에 조회·보고 트래픽을
보내면 주 인스턴스는 쓰기에 집중하고, 복제는 비동기로 따라간다. 캐시와 읽기 복제본 둘 다
"읽기를 도와주는 것"이지만 갈리는 축은 반복 여부다.

> [Q106 p74] "이는 데이터가 자주 변경되지만 쿼리가 거의 반복되지 않아 캐싱의 이점을 얻지 못하는 워크로드에 특히 효과적입니다."

## aurora-dynamodb-cache

### `aurora-replica-auto-scaling` — Aurora Auto Scaling은 레플리카를 늘린다

**한 줄**: 자동으로 늘고 주는 것은 읽기 전용 레플리카이고, 쓰기를 받는 라이터는 한 번에 하나다.

Aurora 클러스터에는 쓰기를 받는 인스턴스가 하나 있고 나머지가 읽기 전용 레플리카다.
Aurora Auto Scaling은 부하에 따라 이 레플리카 수를 자동으로 조정하는 기능이라, "예측할 수
없는 읽기 급증을 자동으로 감당해야 한다"는 요구에 그대로 맞는다. 주말·월말처럼 읽기가
몰리는 시점이 있는 워크로드가 대표적이다.

**"라이터에 오토 스케일링을 건다"는 선택지는 답이 아니다.** 라이터는 한 번에 하나이므로
수요에 맞춰 여러 대로 늘리는 대상이 아니고, 늘어나는 것은 언제나 레플리카 쪽이다.
장애 조치는 레플리카 하나를 새 라이터로 올리는 방식으로 일어난다. 레플리카들이 같은 스토리지를
공유하기 때문에 레플리카를 더해도 데이터를 복사해 옮기는 일이 생기지 않는다.

> [Q122 p84] "데이터베이스 측면에서는 Aurora PostgreSQL이 Aurora Replica를 추가하여 읽기 용량을 확장할 수 있도록 지원하며, Aurora Auto Scaling은 수요에 따라 Replica 수를 자동으로 조정할 수 있습니다."

### `elasticache-global-datastore` — ElastiCache 글로벌 데이터스토어

**한 줄**: 캐시를 여러 리전에 걸쳐 복제하고, 재해 시 다른 리전의 클러스터를 주 클러스터로 올린다.

캐시에도 리전 장애 대비가 필요할 때가 있다. ElastiCache의 글로벌 데이터스토어는 리전 간
복제를 관리형으로 제공하고, 다른 리전에 둔 복제 클러스터를 주 클러스터로 승격시켜 장애를
넘긴다. 전 세계 사용자를 상대로 지연을 낮게 유지하면서 재해 복구까지 요구할 때 이 기능이
정답 근거가 된다.

수동으로 스냅샷을 복사해 다른 리전에서 복원하거나 DMS로 캐시 데이터를 옮기는 선택지가 함께
나오는데, 둘 다 사람이 개입해야 하고 실시간 복제가 아니다. 리전 간 데이터 전송을 암호화해야
한다는 조건도 이 기능이 전송 중·저장 시 암호화를 지원하는 것으로 풀린다.

> [Q131 p90] "글로벌 데이터스토어는 완전 관리형 리전 간 복제를 지원하며, 다른 리전의 읽기 복제본 클러스터를 승격시켜 자동 페일오버를 지원합니다."

## compute-delivery

### `cloudfront-alb-origin` — CloudFront의 오리진은 버킷만이 아니다

**한 줄**: ALB를 오리진으로 두면 EC2가 만들어 내는 동적 콘텐츠도 CloudFront가 앞에서 받는다.

앱은 CloudFront를 캐시로 콘텐츠를 빠르게 전달하는 서비스로 소개한다. 그래서 "동적 콘텐츠"가
조건으로 나오면 CDN은 아니라고 지레 지우기 쉬운데, 덤프의 판단은 반대다. 기존 ALB를 오리진으로
지정한 배포를 만들면 정적·동적 콘텐츠 모두 사용자와 가까운 엣지를 거치게 되고, 애플리케이션
서버의 부하와 지연이 함께 줄어든다.

전 세계 사용자에게 동적 콘텐츠를 비용 효율적으로 내보내라는 요구에서, Route 53의 지리 기반
라우팅이나 Direct Connect보다 이 구성이 먼저다. 앞의 둘은 요청을 어디로 보낼지 정할 뿐
엣지에서 받아 주지는 않는다.

> [Q102 p72] "기존 ALB를 오리진으로 설정하면 CloudFront가 전 세계 사용자에게 더 가까운 위치에서 동적 및 정적 콘텐츠를 캐싱할 수 있어 성능이 향상되고애플리케이션 서버의 부하를 줄일 수 있습니다."

### `alb-cookie-stickiness` — 스티키 세션은 ALB의 기능이다

**한 줄**: 쿠키로 같은 인스턴스에 붙여 두는 것은 7계층에서 하는 일이라 ALB가 맡고, 4계층인 NLB는 이 방식이 아니다.

앱은 스티키 세션의 부작용(부하 쏠림)을 다루지만 그 기능이 어느 로드 밸런서의 것인지는 말하지
않는다. 세션 상태를 서버 메모리에 들고 있는 상태 유지형(stateful) 애플리케이션을 오토 스케일링
그룹으로 옮기면, 같은 사용자의 다음 요청이 같은 인스턴스로 가야 화면이 일관되게 보인다.
HTTP·HTTPS 애플리케이션에서 이것을 쿠키로 처리하는 것이 ALB다.

그래서 "상태 유지 웹 애플리케이션 + 일관된 사용자 경험"이 조건이면 NLB가 든 선택지는 지운다.
NLB는 4계층이라 7계층의 쿠키 기반 고정 동작을 그대로 주지 않는다. 근본적으로는 세션 상태를
서버 밖으로 빼는 것이 낫지만, 문제문이 리팩터링을 말하지 않으면 스티키 세션이 답이다.

> [Q122 p84] "ALB는 레이어 7에서 작동하며 쿠키 기반 세션 고정 기능을 기본적으로 지원하기 때문입니다."

### `enhanced-networking` — 향상된 네트워킹

**한 줄**: 인스턴스 유형이 지원해야 켜지는 기능이며, 대역폭과 초당 패킷 처리량을 올리고 지연을 낮춘다.

클러스터 배치 그룹은 인스턴스를 물리적으로 가까이 모아 주지만, 그것만으로 네트워크 성능이
끝까지 나오지는 않는다. 향상된 네트워킹을 지원하는 인스턴스 유형을 골라야 더 높은 대역폭과
초당 패킷 처리량, 그리고 일관되게 낮은 인스턴스 간 지연을 얻는다.

그래서 "인스턴스 사이 처리량을 최대화하고 지연을 최소화하라"는 문항의 정답은 배치 그룹과
이 조건을 함께 갖춘 선택지다. 둘 중 하나만 있는 선택지는 요구를 절반만 만족한다.

> [Q149 p102] "향상된 네트워킹: 향상된 네트워킹을 지원하는 인스턴스 유형을 선택하면 더 높은 대역폭, 더 높은 초당 패킷 처리량(PPS) 성능, 그리고 일관되게 낮은 인스턴스 간 지연 시간을 확보할 수 있습니다."

### `ec2-image-builder` — EC2 Image Builder

**한 줄**: AMI를 만들고 패치하고 검사하는 과정을 파이프라인으로 자동화한다.

사용자 지정 AMI로 인스턴스를 띄우는 환경에서는 취약점이 배포 시점에 딸려 들어온다. 실행 중인
인스턴스에 패치를 미는 방식으로는 이 경로를 막지 못한다 — 새로 뜨는 인스턴스가 여전히 옛
이미지에서 나오기 때문이다.

EC2 Image Builder는 이미지를 만드는 단계 자체를 파이프라인으로 만든다. 빌드 구성 요소에
운영체제 업데이트를 넣어 두면 새 이미지가 만들어질 때마다 패치가 적용되고, 그 이미지를 기존
오토 스케일링 그룹이 쓰게 하면 이후 시작되는 인스턴스는 처음부터 패치된 상태다. 파이프라인이
재사용되므로 애플리케이션이 수십 개로 늘어도 같은 방식이 통한다.

> [Q105 p73] "EC2 Image Builder는 AMI의 생성, 패치 적용, 보안 강화 및 테스트를 자동화하도록 특별히 설계된 AWS 관리형 서비스입니다."

## serverless-containers

### `lambda-container-image` — Lambda를 컨테이너 이미지로 배포한다

**한 줄**: 이미 컨테이너로 돌던 짧은 작업은 이미지를 그대로 Lambda에 올릴 수 있다.

Lambda는 코드를 압축해 올리는 방식만 있는 것이 아니라 컨테이너 이미지를 패키징 형식으로
받는다. EC2에서 직접 관리하던 도커 컨테이너가 몇 분 안에 끝나는 가벼운 작업이라면, 이미지에
필요한 손질을 한 뒤 Lambda 함수로 옮기는 것이 운영 부담이 가장 적은 선택이 된다.

같은 상황에서 ECS나 EKS를 Fargate로 돌리는 선택지가 함께 나오는데, 실행 시간이 Lambda의
한계 안에 들어오면 그쪽은 더 비싸게 친다. EKS는 쿠버네티스 관리 구조가 남고, ECS도 태스크
정의·서비스·네트워킹을 여전히 사람이 관리해야 하기 때문이다.

> [Q114 p79] "해당 기업은 이미지에 필요한 변경을 자유롭게 수행할 의향이 있으므로, 워크로드를 Lambda 컨테이너 이미지로 패키징하는 것이 운영 오버헤드가 가장 적은 옵션입니다."

### `lambda-memory-cpu-proportional` — Lambda는 메모리를 올리면 CPU가 함께 올라간다

**한 줄**: 설정할 수 있는 값은 메모리 하나이고, CPU는 그 값에 비례해 배정된다.

Lambda에는 vCPU를 직접 고르는 설정이 없다. 메모리를 늘리면 함수가 쓸 수 있는 CPU도 비례해서
늘어나므로, 짧게 CPU를 몰아 쓰는 작업도 메모리를 넉넉히 잡는 것으로 대응한다.

그래서 "평소 CPU 사용률은 낮은데 작업이 돌 때만 최대치를 쓴다"는 워크로드가 Lambda에서 밀리지
않는다. 매시간 10초씩 도는 작업이라면 나머지 시간의 유휴 비용이 사라지므로, 인스턴스를 계속
띄워 두거나 시작·중지를 오케스트레이션하는 구성보다 싸다.

> [Q132 p91] "1GB의 메모리를 할당하면 사용 가능한 CPU가 비례적으로 증가하므로 짧은 CPU 버스트에 적합합니다."

### `fargate-per-second-billing` — Fargate의 최소 과금 단위

**한 줄**: 초 단위로 계산하되 1분이 최소라, 수십 초짜리 작업에는 Lambda가 더 싸다.

Fargate는 태스크가 돌아간 시간을 초 단위로 재지만 최소 1분을 매긴다. 10초 만에 끝나는 작업을
매시간 돌리면 실제 사용량보다 여섯 배를 내는 셈이고, 여기에 컨테이너 이미지를 만들고 태스크를
정의하는 수고가 더해진다.

비용을 묻는 문항에서 Lambda와 Fargate가 나란히 나오면 이 값이 갈림길이 된다. 실행이 짧고
간헐적일수록 Lambda 쪽이고, 실행이 길거나 Lambda의 시간 제한을 넘으면 Fargate 쪽이다.

> [Q132 p91] "Fargate 태스크(A)는 1분 단위의 최소 요금이 적용되는 초 단위 과금 방식이며 컨테이너 패키징이 필요합니다."

## messaging-backup

### `sns-is-not-a-queue` — SNS는 큐가 아니다

**한 줄**: 밀려드는 요청을 쌓아 두고 뒷단이 감당할 속도로 꺼내 쓰는 버퍼는 SQS이고, SNS는 그 일을 하지 못한다.

앱은 SQS를 대기열, SNS를 여러 대상에 보내는 알림으로 각각 설명하지만, 문항은 둘을 바꿔 놓은
선택지로 이 구분을 시험한다. "들어오는 주문을 SNS로 큐에 넣는다"처럼 쓰인 선택지가 그것이다.

뒷단의 처리 속도가 앞단의 유입 속도보다 느릴 수 있다면 필요한 것은 내구성 있는 버퍼다.
SNS는 발행-구독 방식이라 메시지를 받아 즉시 구독자에게 밀어낼 뿐, 쌓아 두었다가 나중에
꺼내 가게 하거나 실패한 처리를 다시 시도하게 하지 못한다. 반대로 이메일 한 통을 보내면 되는
자리에 SQS를 끼우는 것도 답이 아니다 — 그때는 알림이 필요한 것이지 버퍼가 필요한 것이 아니다.

> [Q117 p81] "SNS는 큐가 아닌 퍼블리시/서브스크립션(pub/sub) 서비스입니다."

## hybrid-connectivity

### `direct-connect-vif-types` — Direct Connect의 가상 인터페이스(VIF)

**한 줄**: 전용선 위에 무엇을 얹을지는 VIF 종류가 정하며, Transit Gateway로 가려면 트랜짓 VIF다.

Direct Connect 회선 하나에 논리적인 연결을 여러 개 만드는데 그것이 가상 인터페이스(VIF)다.
프라이빗 VIF는 VPC의 가상 프라이빗 게이트웨이나 Direct Connect 게이트웨이로 붙어 사설 IP
대역에 닿고, 퍼블릭 VIF는 AWS의 공용 엔드포인트로 향한다. 트랜짓 VIF는 Direct Connect
게이트웨이에 붙이기 위한 종류다.

계정과 VPC가 많아 Transit Gateway로 묶어 둔 환경에서 온프레미스를 연결하려면 이 조합이
정해져 있다 — 트랜짓 VIF로 Direct Connect 게이트웨이에 연결하고, 리전마다 둔 Transit Gateway를
그 게이트웨이에 붙인다. 하나의 Direct Connect 게이트웨이에 여러 리전의 Transit Gateway를
연결할 수 있으므로, 회선 하나로 여러 리전의 VPC에 닿는다.

> [Q138 p94] "트랜짓 VIF는 Direct Connect 연결을 Direct Connect 게이트웨이에 연결하는 데 특화되어 있으며, DXGW는 여러 트랜짓 게이트웨이에 연결될 수 있고(리전 간에도 사용 가능) 온프레미스에서 TGW에 연결된 VPC로 중앙 집중식 연결을 가능하게 합니다."

### `virtual-private-gateway` — 가상 프라이빗 게이트웨이(VGW)

**한 줄**: VPN이나 Direct Connect가 VPC로 들어오는 AWS 쪽 종단이며, VPC 하나에 하나씩 붙는다.

앱은 온프레미스 쪽 종단인 Customer Gateway를 다루지만 AWS 쪽 종단은 이름이 없다. 그것이
가상 프라이빗 게이트웨이다. VPC마다 하나씩 붙는 장치라, 프라이빗 VIF를 VGW에 연결하면 그
회선은 VPC 한 곳에 묶인다.

여기서 확장의 한계가 나온다. VPC가 수천 개인 환경에서 VGW를 하나씩 연결해 가는 구성은 관리가
불가능하고, 이미 만들어 둔 Transit Gateway 허브 구조와도 맞물리지 않는다. 규모가 커지면
VGW가 아니라 Direct Connect 게이트웨이와 Transit Gateway 쪽으로 간다.

> [Q138 p94] "옵션 A는 Direct Connect를 단일 VPC와 연결된 가상 사설 게이트웨이(VGW)에 묶어두기 때문에 너무 제한적이며 확장성이 부족합니다."

### `transit-gateway-cross-region-peering` — 리전 간 Transit Gateway 피어링

**한 줄**: 리전마다 둔 Transit Gateway를 서로 피어링해 리전을 넘는 경로를 만든다.

앱의 `transit-gateway`는 여러 VPC와 온프레미스를 한데 묶는 허브로 소개돼 있고, 그 허브가
리전 안에 있다는 것까지는 드러나지 않는다. 리전이 여러 개면 리전마다 Transit Gateway를 두고
그것들을 피어로 연결하는 것이 AWS 쪽 라우팅을 푸는 방법이다.

한 리전에서 배운 온프레미스 경로가 피어링 관계를 타고 다른 리전의 워크로드까지 닿을 수 있어,
전용선이 한 리전에만 들어와 있어도 나머지 리전이 그 경로를 함께 쓴다. VPC 피어링이 1:1이라
개수가 늘면 연결이 폭증하는 것과 달리, 이쪽은 리전 수만큼만 늘어난다.

> [Q138 p94] "리전 간 TGW 피어링을 통해 한 리전의 DXGW/TGW를 통해 학습된 온프레미스 경로는 라우팅 구성에 따라 TGW 피어링 관계를 통해 다른 리전의 워크로드로 도달할 수 있습니다."

## route53

### `route53-query-logging` — Route 53 쿼리 로깅

**한 줄**: DNS 질의와 응답 코드를 기록해 CloudWatch Logs로 보내는 기능이다.

DNS에서 무슨 일이 있었는지 되짚으려면 응답 코드가 남아야 한다. Route 53의 쿼리 로깅을 켜면
질의된 도메인, 레코드 유형, 요청지 IP, 응답 코드가 기록되어 CloudWatch Logs에 쌓인다.

혼동하기 쉬운 선택지가 둘 붙는다. CloudTrail은 AWS 서비스로 가는 API 호출을 남기는 것이라
DNS 질의 트래픽 자체는 담지 않는다. CloudWatch 지표는 질의 수처럼 합쳐진 값이라 질의 하나
하나의 응답 코드가 없다. "응답 코드"라는 말이 문제문에 있으면 쿼리 로깅이다.

> [Q134 p92] "옵션 A는 Route 53 쿼리 로깅을 활성화하며, 이는 쿼리된 도메인, 레코드 유형, 소스 IP 및 DNS 응답 코드와 같은 DNS 쿼리에 대한 상세 정보를 기록합니다."

## analytics-monitoring

### `flink-kinesis-source-sink` — Flink는 스트림 사이에 끼워 넣는다

**한 줄**: Kinesis 스트림을 입력과 출력 양쪽으로 쓸 수 있어, 애플리케이션 코드를 고치지 않고 처리 단계를 더할 수 있다.

Managed Service for Apache Flink는 예전 이름이 Kinesis Data Analytics다. 덤프에는 옛 이름이
그대로 나오는 자리가 있다. 이 서비스의 특징은 Kinesis Data Streams를 소스로도 싱크로도
받는다는 것이다.

그래서 이미 스트림을 읽고 있는 애플리케이션에 실시간 이상 탐지 같은 처리를 끼워 넣을 때,
원본 스트림을 Flink에 물리고 결과를 두 번째 스트림으로 내보내면 애플리케이션은 스트림
하나만 바꿔 읽으면 된다. "느슨하게 결합되고, 완전 관리형이며, 서버리스이고, 코드를 고칠 수
없다"는 조건이 겹쳐 나오면 이 구성이다. EC2나 ECS로 같은 일을 하는 선택지는 서버리스도
완전 관리형도 아니라서 지워진다.

> [Q103 p72] "Kinesis Data Streams에서 데이터를 수집하고, 이상 탐지를 수행한 다음, 결과를 다른 Kinesis 스트림으로 출력할 수 있습니다."

### `redshift-concurrency-scaling` — Redshift 동시성 확장

**한 줄**: 쿼리가 몰릴 때 임시 용량을 자동으로 붙였다 떼는 기능이며, 클러스터 크기를 건드리지 않는다.

월말 보고처럼 특정 시점에 사용자가 몰리는 데이터 웨어하우스에서, 클러스터를 미리 키웠다가
다시 줄이는 방식은 사람이 개입해야 하고 그 과정에서 가용성이 흔들린다. 동시성 확장을 켜 두면
Redshift가 동시 쿼리 급증을 감지해 임시 용량을 스스로 붙이므로 클러스터를 그대로 둔 채
성능이 올라간다. 워크로드 관리(WLM) 큐 단위로 켤 수 있다.

크기 조정 쪽 선택지가 둘 나오는데, 탄력적 크기 조정이 기존 방식보다 빠르긴 해도 여전히
사람이 시점을 정해 조작해야 한다는 점은 같다. "가용성에 영향을 주지 않으면서"가 조건이면
동시성 확장이다.

> [Q140 p96] "동시 실행 스케일링을 사용하면 Amazon Redshift가 동시 쿼리 급증에 대응하기 위해 일시적인 용량을 자동으로 추가할 수 있습니다."

### `redshift-spectrum` — Redshift Spectrum

**한 줄**: Redshift에 적재하지 않은 S3의 데이터를 그 자리에서 쿼리하는 기능이다.

이름이 Redshift에 붙어 있어 성능·확장 기능으로 오해하기 쉽지만, 하는 일은 조회 대상을 S3까지
넓히는 것이다. 웨어하우스에 넣지 않은 데이터를 S3에 둔 채로 함께 조회할 때 쓴다.

그래서 동시 쿼리가 몰려 느려지는 문제에는 아무 도움이 되지 않고, 실시간 이상 탐지 같은
스트리밍 처리에도 맞지 않는다. 두 자리 모두에서 오답 보기로 나온다.

> [Q140 p96] "Redshift Spectrum은 동시성 문제를 해결하기 위한 것이 아니라 S3의 데이터를 쿼리하기 위해 설계되었습니다."

### `oltp-vs-olap` — OLTP와 OLAP

**한 줄**: 주문·결제처럼 짧은 트랜잭션을 많이 처리하는 쪽이 OLTP, 쌓인 데이터를 분석하는 쪽이 OLAP다.

문제문이 "온라인 트랜잭션 처리(OLTP)"라고 밝히면 답은 관계형 데이터베이스 계열이고, 데이터
웨어하우스는 지운다. Redshift가 자주 오답으로 나오는데, 대규모 분석(OLAP)을 위한 웨어하우스이지
트랜잭션 데이터베이스가 아니기 때문이다.

두 성격이 한 시스템에 섞여 있는 문항도 있다. 운영은 트랜잭션인데 월말 보고가 분석에 가까운
경우다. 그때는 웨어하우스로 갈아타는 것이 아니라 읽기 부하를 복제본으로 떼어 내는 쪽이
답이 된다.

> [Q112 p77] "Redshift(A)는 트랜잭션 데이터베이스가 아닌 데이터 웨어하우스입니다."

### `cloudwatch-agent-memory-metric` — 메모리 사용률은 기본 지표가 아니다

**한 줄**: EC2의 메모리 사용률은 CloudWatch에 저절로 올라오지 않으며, CloudWatch 에이전트를 설치해야 수집된다.

CPU 사용률은 별도 설치 없이 CloudWatch에 올라오지만 메모리는 그렇지 않다. 인스턴스 안에서
봐야 알 수 있는 값이기 때문이다. CloudWatch 에이전트를 설치하면 `mem_used_percent` 같은
사용자 지정 지표가 올라오고, 그때부터 그 값으로 경보나 조정 정책을 만들 수 있다.

메모리 사용률로 오토 스케일링을 하라는 문항의 정답은 그래서 두 부분이다 — 에이전트로 지표를
만들고, 그 지표에 대상 추적 정책을 건다. Systems Manager 에이전트는 이 지표를 만드는 도구가
아니므로 그쪽이 든 선택지는 지운다.

> [Q145 p99] "메모리 사용량 메트릭은 기본적으로 보고되지 않으므로, 이를 수집하려면 Amazon CloudWatch 에이전트가 필요합니다."

### `cloudwatch-network-monitor` — CloudWatch Network Monitor

**한 줄**: AWS와 온프레미스 사이의 패킷 손실과 왕복 시간을 AWS가 관리하는 프로브로 재는 기능이다.

하이브리드 연결의 품질을 재려면 보통 양쪽에 무언가를 띄워 서로 신호를 주고받게 한다. 서브넷마다
EC2나 Lambda를 두고 스크립트를 돌리는 선택지가 그것인데, 프로브를 직접 만들고 일정을 관리해야
하므로 운영 부담이 커진다.

CloudWatch Network Monitor는 그 프로브를 AWS가 맡는다. 패킷 손실과 지연을 포함한 연결 상태를
재서 CloudWatch 대시보드·경보로 바로 넘긴다. "운영 오버헤드를 최소화하면서 패킷 손실과 왕복
시간(RTT)을 모니터링하라"가 조건이면 이쪽이다.

> [Q144 p98] "AWS CloudWatch Network Monitor(이전 명칭: VPC Network Manager)는 AWS와 온프레미스 네트워크 간의 패킷 손실 및 지연 시간을 포함한 연결 상태를 모니터링하는 관리형 솔루션을 제공합니다."

## threat-protection

### `amazon-inspector` — Amazon Inspector

**한 줄**: 워크로드의 취약점을 찾아 알려 주는 서비스이며, 찾아 줄 뿐 고치지는 않는다.

앱은 GuardDuty(위협 탐지)와 Macie(민감 데이터 식별)를 다루지만 취약점 쪽은 비어 있다.
Inspector가 그 자리다. 운영체제와 애플리케이션의 알려진 취약점을 찾아내는 것이 역할이다.

**패치를 적용하는 서비스가 아니라는 점이 문항에서 갈림길이 된다.** "취약점이 유입되지 않게
하라"는 요구는 발견이 아니라 조치를 요구하므로, 이미지를 만드는 단계에서 패치를 넣는
EC2 Image Builder 같은 선택지가 답이 된다.

> [Q105 p73] "Amazon Inspector(옵션 A)는 취약점을 식별하지만 AMI 자체에 패치를 적용하지는 않습니다."

## identity-access

### `identity-center-external-idp` — IAM Identity Center와 외부 IdP의 연결

**한 줄**: 회사가 이미 쓰는 ID 공급자를 SAML 2.0으로 붙여 그 자격 증명으로 여러 AWS 계정에 들어간다.

앱의 `identity-center`는 여러 계정의 인증·권한을 한곳에서 관리한다고만 말한다. 문항이
반복해서 묻는 것은 그 한곳이 회사의 기존 ID 공급자(IdP)와 이어진다는 사실이다. SAML 2.0
페더레이션으로 외부 IdP를 연결하면 직원은 쓰던 자격 증명으로 로그인하고, 사용자와 그룹은
IdP에서 프로비저닝돼 자동으로 동기화된다.

수천 명 규모에서 계정마다 IAM 사용자를 만드는 선택지가 함께 나오는데, 관리 대상이 계정 수만큼
곱해지므로 확장되지 않는다. 계정마다 SAML 공급자를 따로 설정하는 것도 마찬가지다 — Identity
Center가 중앙에서 그 일을 하고 있으면 계정별 설정은 중복이다.

> [Q101 p71] "IAM Identity Center는조직 내 여러 AWS 계정에 대한 중앙 집중식 액세스 관리를 제공하며, SAML 2.0 페더레이션을 통해 기존 IDP(Identity Provider)와 원활하게 통합됩니다."

### `identity-center-permission-set` — 권한 세트

**한 줄**: Identity Center가 계정에 권한을 부여하는 단위이며, 그룹에 할당해 최소 권한을 적용한다.

권한 세트는 사용자가 대상 계정에서 무엇을 할 수 있는지를 묶어 정의한 것이다. 사용자 개개인이
아니라 그룹에 할당하고, 그 그룹이 어느 계정에 접근할지를 정한다. 계정마다 IAM 사용자와
정책을 따로 만들지 않고도 팀 단위 접근이 서는 것이 이 구조 덕분이다.

최소 권한 원칙이 조건으로 붙는 문항에서 답이 여기로 오는 이유는, 넓은 권한을 상시로 주는
대신 필요한 만큼만 담은 권한 세트를 여러 개 만들어 나눠 줄 수 있기 때문이다. 이미 Identity
Center를 쓰고 있다는 전제가 문제문에 있으면 IAM 사용자·역할을 새로 만드는 선택지는 지운다.

> [Q133 p91] "AWS 문서에 따르면, 권한 세트는 IAM Identity Center가 AWS 계정 및 리소스에 최소 권한 액세스를 부여하기 위해 사용하는 핵심 메커니즘입니다."

### `cross-account-iam-role` — 계정 간 IAM 역할과 신뢰 정책

**한 줄**: 자원을 가진 계정에 역할을 만들고, 신뢰 정책으로 다른 계정의 주체가 그 역할을 맡게 한다.

여러 계정에서 도는 워크로드가 한 계정의 자원에 접근해야 할 때, 접근 키를 만들어 나눠 주는
방식은 장기 자격 증명이 흩어진다. 대신 자원이 있는 계정에 역할을 만들고 그 역할의 신뢰
정책에 접근을 허용할 주체를 적는다. 그 주체가 역할을 맡으면 임시 자격 증명으로 일하게 되므로
접근이 일시적이고, 감사할 수 있고, 한곳에서 통제된다.

버킷 정책으로 여는 방법과 갈리는 자리가 있다. 특정 워크로드에만 열어야 하는데 서비스 이름
전체를 허용하는 버킷 정책을 쓰면 조직 밖의 같은 서비스까지 들어올 수 있어 범위가 너무 넓다.

> [Q126 p87] "가장 안전한 방법은 중앙 로깅 계정에서 계정 간 IAM 역할을 사용하고, 멤버 계정의 승인된 Lambda 함수가 해당 역할을 인수할 수 있도록 허용하는 것입니다."

### `organizations-consolidated-billing` — Organizations의 통합 청구

**한 줄**: 관리 계정이 멤버 계정 전부의 사용량을 합친 청구서 하나를 받는다.

앱은 Organizations를 SCP와 함께만 다루지만, 계정을 나누는 또 하나의 이유가 청구다. 사업부마다
계정을 따로 두면 워크로드가 계정 경계로 격리되고, 관리 계정의 청구서 하나로 사업부별 비용을
갈라 볼 수 있다.

계정 하나를 함께 쓰면서 태그로 비용을 가르는 구성이 대안으로 나오는데, 격리 요구를 만족하지
못한다. 반대로 사업부마다 조직을 따로 만드는 것은 통합 청구의 이점을 스스로 버리는 셈이다.
격리와 통합 청구를 함께 요구하면 조직 하나에 멤버 계정 여러 개가 답이다.

> [Q121 p84] "AWS 문서에 따르면 관리 계정은 모든 멤버 계정의 사용량을 합산한 단일 청구서를 수신하며, 이는 통합된 월별 비용 전가 보기를 직접 지원합니다."

### `cloudtrail-lake` — AWS CloudTrail Lake

**한 줄**: CloudTrail 이벤트를 오래 보관하고 쿼리하는 관리형 저장소이며, AWS 밖에서 온 이벤트도 받는다.

CloudTrail은 API 호출을 기록하지만, 그 기록을 몇 년씩 두고 조회하려면 보통 S3에 내려 분석
환경을 따로 만든다. CloudTrail Lake는 그 단계를 서비스 안으로 들인다. 이벤트를 수집·저장하고
그 자리에서 쿼리하며, 장기 보존을 지원해 7년 같은 규정 준수 요구를 만족한다.

AWS 서비스가 아닌 곳에서 나온 활동도 사용자 지정 통합으로 받아들인다는 점이 감사 로그를
한곳에 모으라는 문항의 결정적 근거가 된다. S3에 데이터 레이크를 짓는 선택지는 같은 일을
하지만 만들고 유지할 것이 늘어난다.

> [Q148 p101] "AWS CloudTrail Lake는 AWS 및 비 AWS 서비스 모두에 대한 CloudTrail 이벤트를 수집, 저장 및 쿼리할 수 있는 완전 관리형 서비스입니다."

## cost-management

### `budget-actions` — AWS Budgets의 예산 조치

**한 줄**: 예산 임계값에 닿았을 때 알리는 데서 그치지 않고 정책을 적용하거나 자원을 멈추게 한다.

앱은 Budgets를 예산을 세우고 초과를 알려 주는 서비스로 설명한다. 그런데 문항은 "예산을 넘지
못하게 막으라"고 요구할 때가 있고, 알림만으로는 그 요구를 만족하지 못한다. 예산 조치가 그
차이를 메운다 — 임계값에 도달하면 조직 단위에 SCP를 붙여 추가 사용을 거부하게 하거나,
알림을 받아 실행 중인 인스턴스를 멈추는 흐름을 태울 수 있다.

비용 계열 서비스 셋이 오답으로 함께 나온다. Cost Explorer는 지난 비용을 분석하는 자리이고,
Cost Anomaly Detection은 평소와 다른 지출을 알아채는 자리이며, CloudWatch 경보는 비용
임계값을 직접 다루는 장치가 아니다. 셋 다 알려 줄 뿐 막지 않는다.

> [Q129 p89] "AWS Budgets는 임계값에 도달했을 때 자동으로 제어를 적용할 수 있는 예산 조치를 지원합니다."

## (주제 미정)

기존 20개 주제 어디에도 들어맞지 않는 개념이다. 주제 배치는 phase 26에서 정한다.

### `resource-access-manager` — AWS Resource Access Manager(AWS RAM)

**한 줄**: 계정 사이에 리소스를 공유하는 서비스이며, 사용자 인증과는 관계가 없다.

RAM은 서브넷이나 Transit Gateway 같은 리소스를 다른 계정이 쓸 수 있게 공유하는 서비스다.
공유되는 것은 리소스이지 사람이 아니다.

이름에 "액세스"가 들어 있어 사용자 접근 관리 문항에서 그럴듯한 오답으로 나온다. 외부 ID
공급자로 직원을 인증시키라는 요구에 RAM은 답이 되지 못한다 — 인증 수단을 제공하지 않기
때문이다. 리소스 공유를 묻는지 사용자 접근을 묻는지로 가른다.

> [Q101 p71] "AWS Resource Access Manager(RAM)는 계정 간 AWS 리소스를 공유하는 데 사용되며, 계정 간 사용자 액세스 연동을 위한 것이 아닙니다."

### `ec2-instance-connect-endpoint` — EC2 Instance Connect 엔드포인트

**한 줄**: 퍼블릭 IP도 배스천 호스트도 없이 프라이빗 서브넷의 인스턴스에 SSH로 붙게 해 준다.

프라이빗 서브넷의 인스턴스에 접속하려고 배스천 호스트를 세우면 관리할 서버가 하나 늘고 공격
면도 늘어난다. EC2 Instance Connect 엔드포인트는 그 자리를 대신한다. 인스턴스와 같은 서브넷에
엔드포인트를 만들고 개발자에게 해당 IAM 관리형 정책을 주면, 콘솔에서 인증한 뒤 인스턴스로
연결된다.

**보안 그룹에서 여는 포트는 22가 아니라 443이다.** SSH 트래픽이 HTTPS로 엔드포인트를 통해
터널링되기 때문이고, 포트 22를 연 선택지가 오답으로 붙는 이유다. 인바운드 인터넷 접근을
열지 않아도 되고, 개발자에게는 수명이 짧은 키가 그때그때 전달된다.

> [Q124 p85] "EC2 Instance Connect Endpoint는 바스티온 호스트, 공용 IP 주소 또는 인바운드 인터넷 액세스 없이도 프라이빗 서브넷에 있는 EC2 인스턴스에 대한 안전한 SSH 액세스를 가능하게 합니다."

### `ssm-session-manager` — Systems Manager Session Manager

**한 줄**: 포트를 열지 않고 인스턴스에 셸을 여는 기능이며, SSH를 쓰지 않는다.

Session Manager도 배스천 없이 인스턴스에 붙는 길이지만 방식이 다르다. 인바운드 포트를 전혀
열지 않고 443으로 동작하며, SSH 프로토콜을 쓰지 않는다.

그래서 "SSH로 연결해야 한다"가 명시된 요구에는 맞지 않고, 그 자리는 EC2 Instance Connect
엔드포인트가 가져간다. 반대로 접속 수단을 특정하지 않고 포트를 열지 않는 접근만 요구하면
이쪽이다. 인스턴스에는 Systems Manager를 쓸 수 있는 IAM 역할이 붙어 있어야 한다.

> [Q124 p85] "Systems Manager Session Manager는 SSH를 사용하지 않으며, 인바운드 포트를 열지 않고 포트 443을 통해 작동합니다."

### `ssm-patch-manager` — Systems Manager Patch Manager

**한 줄**: 이미 돌고 있는 인스턴스에 패치를 적용하는 도구이며, 이미지 자체를 고치지는 않는다.

Patch Manager는 실행 중인 인스턴스를 대상으로 운영체제 패치를 배포한다. 인스턴스가 오래
살아 있는 환경에서는 이것으로 충분하다.

그런데 오토 스케일링 그룹이 사용자 지정 AMI에서 인스턴스를 계속 새로 띄우는 환경이면 이야기가
달라진다. 새로 뜨는 인스턴스는 여전히 옛 이미지에서 나오므로, 취약점이 배포 시점에 유입되는
것을 막지 못한다. 그 요구는 이미지를 만드는 단계에서 풀어야 한다.

> [Q105 p73] "Patch Manager(옵션 C)는 실행 중인 인스턴스에 패치를 적용하지만, 새로운 AMI를 통해 취약점이 유입되지 않도록 보장해야 하는 것이 요구 사항입니다."

### `ssm-inventory` — Systems Manager Inventory

**한 줄**: 인스턴스의 구성과 설치 목록을 모으는 기능이며, 리소스 사이의 관계를 그려 주지는 않는다.

Inventory는 어떤 인스턴스에 무엇이 설치돼 있고 설정이 어떤지를 수집한다. 물어보는 것이
"무엇이 있는가"이면 이 기능이 답이 될 수 있다.

물어보는 것이 "무엇이 무엇과 이어져 있는가"이면 아니다. Inventory는 구성·인벤토리 데이터에
초점이 있어 아키텍처 다이어그램이나 리소스 사이의 관계 전체를 만들어 내지 않는다.

> [Q137 p94] "Systems Manager Inventory(옵션 A)는 구성 및 인벤토리 데이터(주로 인스턴스 및 일부 리소스) 수집에 중점을 두며, 아키텍처 다이어그램이나 전체 관계 뷰를 생성하지 않습니다."

### `elastic-disaster-recovery` — AWS Elastic Disaster Recovery(AWS DRS)

**한 줄**: 온프레미스 서버를 블록 단위로 계속 복제해 두었다가 재해 시 AWS에서 띄우는 서비스다.

백업을 받아 두었다가 복원하는 방식은 복구에 걸리는 시간이 길다. DRS는 원본 머신의 디스크
변경을 지속적으로 복제해 두므로, 전환이 필요할 때 복제해 둔 상태로 인스턴스를 띄우는 것으로
끝난다. 복구 시간 목표가 15분처럼 짧게 걸린 문항에서 답이 되는 이유다.

장애 조치를 실제로 일으키지 않고 시험해 볼 수 있고, 그 과정이 자동화돼 있다는 점도 함께
근거로 쓰인다. DataSync·Storage Gateway로 데이터를 옮겨 두고 EC2로 환경을 꾸리는 선택지는
전환 절차를 사람이 만들어야 해서 같은 목표를 세우기 어렵다.

> [Q118 p82] "지속적인 블록 수준 복제를 사용하여 온프레미스 머신을 AWS로 복제합니다."

### `workload-discovery` — Workload Discovery on AWS

**한 줄**: 여러 계정과 리전의 리소스를 훑어 관계를 담은 아키텍처 다이어그램을 그려 주는 도구다.

인수인계 없이 넘겨받은 환경에서 무엇이 어디에 있고 서로 어떻게 이어져 있는지를 알아내야 할
때 쓴다. 리소스를 자동으로 탐색하고, 관계를 시각화한 다이어그램을 만들며, 내보낼 수 있다.
계정과 리전이 여러 개인 환경을 한 번에 본다는 점이 핵심이다.

X-Ray가 오답으로 붙는데, X-Ray는 요청이 지나가는 경로를 추적하는 것이라 계정 전체의 리소스
지도를 만들어 주지 않는다. Step Functions로 정보를 모아 손으로 그리는 선택지도 같은 이유로
밀린다 — 요구가 "가장 운영 효율적으로"이기 때문이다.

> [Q137 p94] "AWS의 Workload Discovery는 여러 계정 및 리전에 걸쳐 AWS 리소스를 자동으로 탐색하고 리소스 관계를 보여주는 시각적 아키텍처 다이어그램을 생성하는 도구입니다."

### `parallelcluster` — AWS ParallelCluster

**한 줄**: 과학 계산 같은 배치 성격의 HPC 클러스터를 꾸리는 도구이며, 상호작용형 애플리케이션용이 아니다.

이름에 클러스터가 들어가 컴퓨팅 확장이 필요한 문항이면 어디든 맞을 것처럼 보이지만, 대상이
정해져 있다. 고성능 컴퓨팅으로 계산 작업을 돌리는 환경을 꾸리는 도구다.

사용자 요청에 실시간으로 응답하며 수요에 따라 늘었다 줄었다 해야 하는 워크로드에는 맞지
않는다. 게임 서버처럼 동적이고 상호작용이 잦은 애플리케이션에서 오답으로 나오는 이유다.

> [Q143 p97] "HPC를 사용하는 ParallelCluster(D)는 동적이고 상호작용적인 게임이 아닌 배치 과학 워크로드를 위해 설계되었습니다."

## 원본 수정 이력

덤프를 그대로 따르지 않은 항목이다. 근거는 ADR-008의 예외를 승계한 ADR-021.

### 사실 오류라 싣지 않은 것

- **Q144 p98** — 덤프 원문: "AWS CloudWatch Network Monitor(이전 명칭: VPC Network Manager)는
  AWS와 온프레미스 네트워크 간의 패킷 손실 및 지연 시간을 포함한 연결 상태를 모니터링하는 관리형
  솔루션을 제공합니다." 괄호 안의 옛 이름은 실제와 어긋난다 — CloudWatch Network Monitor는
  이름을 바꾼 서비스가 아니고, `Network Manager`는 다른 서비스의 이름이다. 이 문항의 정답 근거는
  괄호 밖 문장으로 충분히 서므로 `cloudwatch-network-monitor` 항목에는 옛 이름을 옮기지 않았다.
  인용 줄은 원문 그대로 두었다.

- **Q110 p76** — 덤프는 S3 복제 시간 제어가 "99.9%는 15분 이내에" 복제한다고 적었다. AWS가
  밝히는 값은 이보다 높아 자릿수가 어긋나므로, `s3-replication-time-control` 본문에는 비율
  대신 "대부분은 몇 초 안에, 나머지도 15분 안에"라고만 적었다. 정답 근거인 "몇 분 이내"라는
  시간 조건은 어느 값을 쓰든 그대로 선다. 인용 줄은 원문 그대로 두었다.
