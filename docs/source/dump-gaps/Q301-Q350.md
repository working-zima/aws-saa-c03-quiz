## rds-storage-features

### `rds-multi-az-failover-rto` — 다중 AZ 장애 조치에 걸리는 시간

**한 줄**: 다중 AZ 배포의 장애 조치는 대략 1~2분 안에 끝나므로, 복구 시간 목표가 5분 이내라는 조건을 이 기능 하나로 채운다.

앱의 `rds-storage-features.features`와 `multi-az-standby-limits`는 다중 AZ가 고가용성 전용이고
대기 인스턴스가 트래픽을 처리하지 않는다는 것까지 말한다. 문항이 한 걸음 더 요구하는 것은
**숫자**다. "복구 시간이 5분 미만이어야 한다"처럼 시간을 못 박은 조건이 붙으면, 그 조건을
어느 기능이 만족하는지 알아야 선택지를 가를 수 있다.

다중 AZ는 리전 안에서 쓰는 재해 복구 수단이고 장애 조치에 걸리는 시간이 1~2분 수준이다.
읽기 전용 복제본은 읽기 확장이 주된 목적이라 이 자리에 들어오지 못하고, 주기적인 스냅샷과
템플릿은 복구를 사람이 시작해야 하므로 애초에 자동 장애 조치 장치가 아니다.

> [Q330 p225] "AWS 권장 지침에 따르면 Multi-AZ 배포는 약 1~2분의 RTO(복구 시간 목표)를 갖는 리전 내 DR(재해 복구) 옵션으로 제시되며, 이는 5분 미만이라는 요구 사항을 충분히 충족합니다."

## aurora-dynamodb-cache

### `aurora-global-database-dr-targets` — Aurora 글로벌 데이터베이스가 채우는 RPO와 RTO

**한 줄**: 리전 간 복제 지연이 보통 1초 미만이고 보조 리전 승격이 몇 분 안에 끝나므로, RPO 1분·RTO 5분 같은 조건을 만족한다.

`Q001-Q050.md`의 `aurora-global-database-write-region`은 이 구성이 액티브-액티브가 아니라는
것을 다룬다. 문항이 쓰는 축은 다른 쪽이다 — **얼마나 잃고 얼마나 빨리 복구되는가**.

글로벌 데이터베이스는 스토리지 수준에서 리전 사이를 복제하며 지연이 보통 1초 미만이라
복구 지점 목표를 분 단위로 잡아도 여유가 있다. 재해가 나면 보조 리전의 클러스터를 새 라이터로
승격시키고, 이 전환은 대개 몇 분 안에 끝난다. 리전 간 읽기 전용 복제본을 두는 선택지는 같은
수준의 자동 다중 리전 장애 조치를 주지 않고, 논리적 복제에 사용자가 만든 전환 자동화를 붙이는
구성은 손이 더 가면서 오류가 나기 쉽다. 스냅샷을 복제해 두었다가 복원하는 구성은 복원 자체에
시간이 걸려 5분 목표를 맞추지 못한다.

> [Q323 p221] "리전 간 물리적 스토리지 수준 복제 기능을 제공하며, 일반적으로 1초 미만의 지연 시간을 보여 1분 RPO를 쉽게 충족합니다."

### `babelfish` — Babelfish for Aurora PostgreSQL

**한 줄**: Aurora PostgreSQL이 SQL Server의 T-SQL과 통신 프로토콜을 알아듣게 해, 애플리케이션이 쓰던 SQL Server 드라이버를 그대로 두고 옮길 수 있게 한다.

`Q001-Q050.md`의 `dms-sct`는 이기종 데이터베이스를 옮길 때 스키마는 SCT, 데이터는 DMS가
맡는다는 것을 다룬다. 남는 문제가 하나 있다 — **애플리케이션 코드**다. SQL Server를 쓰던
애플리케이션은 SQL Server 방언과 드라이버에 묶여 있어서, 데이터가 옮겨져도 쿼리를 다시
써야 하는 상황이 생긴다.

Babelfish를 켜면 Aurora PostgreSQL이 SQL Server의 T-SQL과 와이어 프로토콜을 이해한다.
그래서 애플리케이션은 SQL Server 드라이버로 계속 접속하고 쿼리도 그대로 둘 수 있다.
"코드 변경을 최소화하면서 옮긴다"가 조건이면 이 기능이 답의 한 조각이고, 나머지 조각은
스키마·데이터 이전을 맡는 SCT와 DMS다. RDS Proxy는 연결을 모아 주는 장치일 뿐 프로토콜을
번역하지 않으므로 이 자리를 대신하지 못한다.

> [Q328 p224] "Babelfish가 포함된 Amazon Aurora PostgreSQL을 사용하면 Aurora가 SQL Server T-SQL 및 SQL Server 와이어 프로토콜을 이해할 수 있습니다."

### `dynamodb-capacity-modes` — 프로비저닝된 용량과 온디맨드 용량

**한 줄**: RCU·WCU를 미리 정해 두는 프로비저닝 모드는 그 한도를 넘으면 요청을 제한하고, 온디맨드 모드는 용량 계획 없이 급증을 흡수한다.

앱은 DynamoDB가 무엇인지와 응답 시간까지 다루지만 용량을 어떻게 사는지는 말하지 않는다.
문항은 이 지점을 정면으로 묻는다 — 평소 트래픽은 적은데 가끔 급증하면 스로틀링 오류가 나서
사용자에게 오류가 보이는 상황이다.

프로비저닝 모드에서는 읽기 용량 단위와 쓰기 용량 단위를 미리 정해 두고, 트래픽이 그 한도를
넘으면 초과분이 제한된다. 온디맨드 모드로 바꾸면 사용량에 맞춰 자동으로 확장되므로 용량을
예측하지 못하는 워크로드에서 스로틀링이 사라지고 용량을 관리하는 부담도 없어진다. 예약
용량은 예측 가능한 사용량의 요금을 깎아 주는 결제 방식이라 한도를 넘는 급증 자체를 막지
못한다. 같은 갈림길이 Kinesis Data Streams에도 있다(`Q051-Q100.md`의 `kinesis-capacity-mode`).

> [Q337 p230] "DynamoDB 온디맨드 용량 모드는 용량 계획 수립 없이도 갑작스러운 트래픽 증가를 처리하도록 자동으로 확장되기 때문입니다."

### `dynamodb-read-consistency` — 최종 일관성 읽기와 강력한 일관성 읽기

**한 줄**: 읽기에는 두 가지 일관성이 있고, 강력한 일관성 쪽이 용량을 더 쓰므로 비용이 올라간다.

DynamoDB의 읽기는 기본이 최종 일관성이다. 방금 쓴 값이 아주 짧은 시간 동안 반영되지 않을 수
있는 대신 같은 용량으로 더 많이 읽는다. 강력한 일관성 읽기로 바꾸면 최신 값을 보장받지만
읽기 용량을 더 쓰고 그만큼 비용이 오른다.

**용량이 모자라 요청이 제한되는 상황에서 일관성을 올리는 것은 해결책이 아니다.** 읽는 값이
최신인지와 읽을 수 있는 양이 얼마인지는 서로 다른 축이라, 강력한 일관성으로 바꾸면 비용만
늘고 제한은 그대로 남는다. 이 자리를 푸는 것은 용량 모드 쪽이다.

> [Q337 p230] "옵션 D는 읽기 비용을 증가시키며 용량 제약을 해결하지 못합니다."

### `dynamodb-item-size-limit` — DynamoDB 항목 크기 제한

**한 줄**: 항목 하나는 400KB를 넘을 수 없어서 이미지나 동영상 같은 바이너리를 그대로 담지 못한다.

`Q001-Q050.md`의 `blob-offload-to-s3`는 큰 바이너리를 데이터베이스가 아니라 S3에 둔다는
판단 기준을 다룬다. 그 기준이 DynamoDB에서는 권고가 아니라 **한도**로 나타난다.

DynamoDB 항목 하나에 담을 수 있는 크기는 400KB까지다. 고해상도 이미지처럼 이 한도를 넘는
데이터는 애초에 들어가지 않고, 한도 안이라도 바이너리를 담으면 성능이 나빠진다. 그래서 표준
설계는 파일 자체를 S3에 두고 DynamoDB에는 키와 S3 주소 같은 메타데이터만 남기는 것이다.
이렇게 나누면 조회는 DynamoDB의 저지연 읽기가 맡고 용량은 S3가 받아낸다.

> [Q307 p211] "DynamoDB는 적합하지만, 항목 크기 제한(400KB) 및 성능 문제로 인해 실제 바이너리 이미지 데이터를 DynamoDB에 저장하는 것은 권장되는 방식이 아닙니다."

## compute-delivery

### `internal-load-balancer` — 내부 로드 밸런서

**한 줄**: 로드 밸런서를 내부용으로 만들면 사설 IP만 갖게 되어 VPC 안이나 연결된 사설 네트워크에서만 닿는다.

앱은 ALB와 NLB의 차이를 계층으로 가르지만, 같은 로드 밸런서를 인터넷에 열지 말지는 다루지
않는다. 문항은 "애플리케이션이 VPC 안에서만 접근 가능해야 한다"는 조건으로 이 축을 묻는다.

인터넷에 노출된(internet-facing) 로드 밸런서는 공용 주소를 받아 밖에서 접속할 수 있다.
내부(internal) 로드 밸런서는 사설 주소만 가지므로 VPC 안이나 VPN·Direct Connect로 이어진
사설 네트워크에서만 접근된다. **네트워크 접근과 이름 해석은 별개다** — 내부 로드 밸런서를
써도 이름을 퍼블릭 호스팅 영역에 올리면 주소가 밖으로 드러난다. 둘 다 사설로 두려면 내부
로드 밸런서와 프라이빗 호스팅 영역을 함께 쓴다.

> [Q319 p219] "내부 ALB를 사용하면 VPC 내부 또는 연결된 사설 네트워크에서만 로드 밸런서에 접근할 수 있습니다."

## serverless-containers

### `fargate-spot` — Fargate Spot

**한 줄**: ECS 태스크를 여유 용량으로 돌려 크게 싸지는 대신 중단될 수 있으며, 시작 시각이 유연한 단기 작업에 쓴다.

`Q151-Q200.md`의 `spot-workload-fit`은 어떤 워크로드가 스팟에 올라갈 수 있는지를 다루고,
앱의 `fargate-no-time-limit`은 Lambda의 15분 제한을 넘기는 작업이 Fargate로 간다고 말한다.
이 둘이 만나는 자리가 Fargate Spot이다.

Fargate Spot은 ECS의 용량 공급자로 지정해 쓰며, 온디맨드 요금보다 크게 싸다. 대가로 용량이
회수되면 태스크가 중단되므로, 매일 밤 한 번 돌리는 배치처럼 시작 시각이 유연하고 중단을
견디는 작업에 맞는다. 서버를 직접 띄우지 않으므로 EC2를 켜고 끄는 구성보다 운영 부담도 적다.

> [Q309 p212] "AWS Fargate Spot 용량은 시작 시간이 유연한 단기 작업에 가장 비용 효율적이고 서버리스한 컨테이너 옵션입니다."

### `eks-cluster-autoscaler` — 파드를 늘리는 것과 노드를 늘리는 것은 다르다

**한 줄**: Horizontal Pod Autoscaler는 파드 수만 조정하므로, 노드가 꽉 차면 Cluster Autoscaler가 노드 자체를 늘려야 한다.

앱의 `serverless-containers.eks`는 EKS가 무엇인지까지만 말한다. 문항이 묻는 것은 확장이
어느 층에서 막히는가다. Horizontal Pod Autoscaler는 부하에 따라 파드 수를 늘리지만, 그
파드를 올릴 노드에 여유가 없으면 스케줄링되지 못한 채 대기한다. 그래서 파드 오토스케일러만
켜 두면 노드가 최대 용량에 닿는 순간 성능 문제가 그대로 남는다.

Cluster Autoscaler는 스케줄링되지 못한 파드를 감지해 노드 그룹의 노드 수를 늘리고, 사용률이
낮아지면 줄인다. EKS에서 이 역할은 Auto Scaling 그룹만으로는 채워지지 않는다 — 그룹은
인스턴스를 늘릴 수 있어도 파드가 대기 중이라는 사실을 모르기 때문이다. 메모리 사용률을
지표로 삼거나 Lambda로 크기 조정을 직접 구현하는 선택지는 이미 있는 기능을 다시 만드는 일이다.

> [Q316 p217] "클러스터 오토스케일러는 리소스 부족으로 인해 스케줄링할 수 없는 포드를 감지한 후, 관리 부담을 최소화하면서 노드를 자동으로 확장합니다."

### `step-functions-long-running-workflow` — Step Functions는 하루를 넘기는 작업도 맡는다

**한 줄**: 실행이 최대 1년까지 이어질 수 있어, Lambda의 15분 제한 때문에 갈라지는 다단계 장시간 작업의 오케스트레이터가 된다.

앱의 `step-functions`와 `messaging-backup.step-functions-features`는 이 서비스가 단계를 잇고
재시도를 내장한다는 것을 다룬다. 문항이 더하는 것은 **시간 한도**다. 개별 태스크는 5분이지만
작업 전체가 24시간까지 걸리고 실패한 태스크는 다시 처리해야 한다는 조건이 붙으면, 여기서
Lambda 하나로 전 과정을 감싸는 선택지가 떨어져 나간다.

Step Functions의 실행은 최대 1년까지 유지되므로 하루를 넘기는 작업도 상태를 들고 끝까지
간다. 시작 신호는 S3에서 온다 — 버킷이 EventBridge로 이벤트를 보내고, 상태 머신을 대상으로
지정한 EventBridge 규칙이 업로드마다 워크플로를 시작시킨다.

> [Q343 p234] "이 구성은 복원력이 뛰어나며 최대 1년 동안의 실행 기간을 지원합니다."

### `api-gateway-api-key-not-auth` — API 키는 인증 수단이 아니다

**한 줄**: API 키는 호출자를 구분해 사용량을 재는 식별자일 뿐, 사용자가 누구인지 검증하지 않는다.

`serverless-containers.api-gateway-jwt-authorizer`와 앱의 `identity-access.cognito`는 API를
보호하는 정식 경로를 다룬다. 문항은 그 옆에 API 키를 놓아 두고 이것으로 충분한지 묻는다.

API Gateway의 API 키는 어떤 클라이언트가 호출했는지 구분하는 식별 장치다. 사용자의 신원을
확인하지 않으므로, 로그인이나 외부 자격 증명 공급자 연동이 요구되는 자리에는 답이 되지 못한다.
그 자리는 사용자 풀이나 권한 부여자가 맡는다.

> [Q306 p210] "API 키는 인증이 아닌 식별 기능을 제공하며, 이 사용 사례에는 부적합합니다."

## messaging-backup

### `eventbridge-private-api-target` — 프라이빗 API로 이벤트를 넣는 길

**한 줄**: 공용 주소 없이 VPC 안의 API로 이벤트를 보내려면, 같은 VPC에 연결한 Lambda를 대상으로 두고 그 함수가 API를 호출하게 한다.

`Q151-Q200.md`의 `eventbridge-api-destination`은 이벤트를 AWS 밖의 HTTP API로 내보내는
방향을 다룬다. 반대쪽 요구가 이 개념이다 — 대상이 **인터넷에 노출되면 안 되는** VPC 안의
API인 경우다.

EventBridge는 Lambda를 기본 대상으로 지원하고, VPC에 연결된 Lambda 함수는 사설 주소로
그 API를 호출할 수 있다. 그래서 규칙의 대상을 함수로 두고 함수가 다리 역할을 하는 구성이
공용 IP 없이 이벤트를 전달하는 길이 된다. 인터넷에 노출된 로드 밸런서를 앞에 세우고 보안
그룹으로 막는 구성은 공용 주소를 쓰지 않는다는 요구를 이미 어긴다. EventBridge가 사설 API를
직접 대상으로 삼는 경로도 있지만 연결과 VPC Lattice 리소스 구성이 따로 필요하므로,
엔드포인트를 그대로 대상 자리에 적어 넣는 선택지와는 다른 이야기다.

> [Q350 p238] "최신 EventBridge의 직접 사설 API 타겟팅은 단순히 사설 VPC 엔드포인트를 원시 타겟으로 지정하는 것이 아니라, 연결 및 VPC Lattice 리소스 구성이 필요하기 때문입니다."

## route53

### `route53-alias-record` — 별칭 레코드

**한 줄**: 도메인 이름을 ALB 같은 AWS 리소스에 직접 겨누는 레코드라, 뒤에 있는 인스턴스가 바뀌어도 DNS를 고칠 일이 없다.

앱의 `route53.routing-policies`는 요청을 어느 리소스로 보낼지 정하는 정책들을 다루지만,
레코드가 무엇을 가리킬 수 있는지는 말하지 않는다. 문항은 "인스턴스가 교체돼도 자동으로
라우팅돼야 한다"는 조건으로 이 축을 묻는다.

별칭 레코드는 이름을 로드 밸런서 같은 AWS 리소스에 연결한다. 로드 밸런서가 안정적인 접속
지점이 되고 그 뒤의 대상 그룹이 인스턴스 등록을 맡으므로, 인스턴스가 교체되면 대상 그룹만
바뀌고 DNS 레코드는 그대로다. 반대로 이름을 인스턴스의 공용 IP에 직접 묶으면 교체될 때마다
사람이 레코드를 고쳐야 한다. 특정 인스턴스로만 보내야 한다면 그 인스턴스를 전용 대상 그룹에
두고 호스트 이름을 보는 리스너 규칙으로 그쪽에 전달한다.

> [Q318 p218] "이 설계는 ALB가 안정적인 엔드포인트를 제공하고, Route 53이 개발용 DNS 이름을 ALB에 별칭으로 지정할 수 있기 때문에 효과적입니다."

## analytics-monitoring

### `emr-runtime-role` — EMR 런타임 역할

**한 줄**: 클러스터 전체가 아니라 제출하는 작업마다 IAM 역할을 붙여, 팀별로 접근할 수 있는 데이터를 갈라 놓는다.

`Q001-Q050.md`의 `emr-node-types`와 `emr-transient-cluster`는 클러스터의 구성과 수명을
다룬다. 여러 팀이 한 클러스터를 함께 쓸 때 남는 문제는 권한이다 — 기본 구성에서 작업은
클러스터 EC2 인스턴스의 인스턴스 프로파일 권한으로 실행되므로, 같은 클러스터에 작업을 낸
모든 팀이 같은 권한을 갖는다.

런타임 역할을 쓰면 작업을 제출할 때 그 작업이 쓸 IAM 역할을 지정한다. 팀마다 다른 역할을
주면 각 작업은 허용된 S3 데이터에만 닿고, 인스턴스에서 인스턴스 메타데이터 서비스를 통해
클러스터 자격 증명을 집어 오는 경로도 막힌다. 켜는 곳은 EMR 보안 구성이고
`EnableApplicationScopedIAMRole`을 true로 둔다. 신뢰 관계의 방향에 주의한다 — 인스턴스
프로파일이 런타임 역할을 인수할 수 있어야 하고(`sts:AssumeRole`), 런타임 역할 쪽은 인스턴스
프로파일 역할을 신뢰해야 한다. 반대로 걸면 동작하지 않는다.

> [Q315 p216] "EMR 런타임 역할은 작업별로 세분화된 권한을 허용하여, 각 팀이 사용 권한이 부여된 서비스에만 액세스할 수 있도록 합니다."

### `firehose-lambda-transformation` — Firehose가 적재 전에 Lambda로 데이터를 고친다

**한 줄**: 스트림이 목적지에 쓰기 전에 Lambda 함수를 불러 레코드를 변환하므로, 원본이 저장되기 전에 민감 정보를 가릴 수 있다.

`Q151-Q200.md`의 `firehose-buffering`은 이 서비스가 모아서 보낸다는 지연 특성을 다룬다.
문항이 쓰는 것은 그 사이에 무엇을 끼울 수 있는가다.

Firehose는 목적지에 적재하기 전에 Lambda 함수를 호출해 레코드를 변환할 수 있다. 그래서
개인 식별 정보를 탐지해 가리는 처리를 파이프라인 안에 넣으면, 원본이 데이터 레이크에 그대로
쌓이는 일 자체가 없어진다. 버킷을 나중에 훑어 민감 정보를 찾아내는 서비스는 이미 저장된
데이터를 분류하는 쪽이라 수집 시점에 값을 바꾸지 못하고, 서버 측 암호화는 저장된 데이터를
보호할 뿐 값을 마스킹하지 않는다.

> [Q304 p209] "Kinesis Data Firehose 파이프라인의 일부로 Lambda 함수를 사용하면 데이터가 S3에 기록되기 전에 PII를 실시간으로 탐지하고 마스킹할 수 있습니다."

### `kinesis-video-streams` — Amazon Kinesis Video Streams

**한 줄**: 카메라 같은 장치에서 들어오는 영상을 실시간으로 받아 처리하는 서비스이고, 미리 녹화해 둔 영상을 보관하고 내려주는 자리에는 맞지 않는다.

Kinesis 계열 가운데 영상 스트림을 맡는 갈래다. 실시간으로 흘러 들어오는 비디오를 수집해
분석이나 처리로 넘기는 것이 용도이므로, 이미 만들어 둔 강의 영상 파일을 여러 화질로 보관해
두고 사용자에게 내려주는 요구와는 성격이 다르다. 그런 파일은 S3에 두는 것이 표준이다.

**오답 보기에서 이름만 보고 고르지 않도록 갈래를 기억해 둔다.** 이름에 Kinesis가 붙어
있어도 이 서비스는 스트리밍 수집 쪽이고, 저장된 미디어 배포는 스토리지와 콘텐츠 전송의
몫이다.

> [Q327 p223] "Kinesis Video Streams는 실시간 비디오 스트리밍을 위해 설계되었으며, 사전 녹화된 비디오를 저장하고 제공하는 데는 적합하지 않습니다."

## security-groups-nacl

### `security-group-stateful-vs-nacl-stateless` — 상태 저장과 상태 비저장

**한 줄**: 보안 그룹은 나간 요청의 응답을 자동으로 되돌려 보내는 상태 저장 방식이고, NACL은 오가는 방향을 각각 따로 허용해야 하는 상태 비저장 방식이다.

앱의 `security-group`과 `nacl`은 적용 범위(리소스 대 서브넷)와 규칙의 종류(허용만 대
허용·차단)를 가른다. 시험이 한 겹 더 묻는 축이 상태 추적이다.

보안 그룹은 상태를 기억한다. 인바운드를 허용한 연결의 응답 트래픽은 아웃바운드 규칙이 없어도
나가고, 그 반대도 마찬가지다. NACL은 상태를 기억하지 않으므로 들어오는 방향과 나가는 방향에
각각 규칙이 있어야 통신이 성립한다. 여기에 보안 그룹은 차단 규칙을 만들 수 없다는 성질이
겹치면, 특정 IP 하나를 막으라는 요구는 보안 그룹으로 풀리지 않는다는 결론이 나온다.
서브넷 경계에서 IP로 막는 NACL이나 웹 요청을 검사하는 WAF가 그 자리를 맡는다.

> [Q332 p226] "네트워크 ACL(NACL)은 서브넷 수준에서 작동하며 상태 비저장형입니다."

## secrets-encryption

### `imported-key-material-rotation` — 가져온 키 자료를 교체하는 방법

**한 줄**: 같은 KMS 키에 새 키 자료를 다시 가져오면 키 ID와 ARN이 그대로 유지되므로 애플리케이션이 멈추지 않고, 자동 교체는 이 유형에 쓸 수 없다.

`Q251-Q300.md`의 `kms-imported-key-material`은 외부에서 만든 키 자료를 가져다 쓸 수 있고
그 보관 책임이 사용자에게 남는다는 것을 다룬다. 문항이 이어서 묻는 것은 **교체**다.

키 자료를 바꾸는 방법은 새 키를 만드는 것이 아니라 기존 KMS 키에 새 키 자료를 다시
가져오는 것이다. 키 ID와 ARN이 바뀌지 않으므로 그 키를 참조하던 애플리케이션은 중단 없이
암호화 작업을 이어 간다. 기존 키 자료에 만료 시각을 걸어 두면 그 시점에 자료가 지워지고 다시
가져오도록 강제되므로, 정해진 주기로 교체하라는 규정 요구를 이 방식으로 충족한다. **KMS가
자동으로 돌려주는 키 교체는 이 유형에 쓸 수 없다** — 자동 교체는 KMS가 직접 만든 키 자료를
가진 키에서만 동작한다. 키를 지우고 새로 만드는 선택지는 키 ID가 바뀌어 접근이 끊기고,
기존 키와 같은 ID를 가진 키를 새로 만드는 것은 애초에 불가능하다.

> [Q340 p232] "또한 기존 키 자료에 만료 시간을 설정할 수 있으며, 이 시간이 지나면 AWS KMS는 기존 자료를 삭제하고 새로운 키 자료의 가져오기를 요구하여 규정 준수 요구 사항에 따라 정기적인 교체를 강제합니다."

### `guardduty-finding-to-eventbridge` — 탐지 결과를 자동 대응으로 잇는다

**한 줄**: GuardDuty가 찾아낸 결과는 EventBridge로 흘러가고, 그 이벤트로 Lambda를 불러 문제가 된 인스턴스를 자동으로 격리할 수 있다.

서비스들은 이 워크플로에서 탐지 결과의 출발점이 되지 않는다.

> [Q305 p209] "Amazon GuardDuty는 암호화폐 채굴을 감지하고 결과를 Amazon EventBridge로 전송합니다."

## identity-access

### `cognito-social-idp-federation` — Cognito 사용자 풀과 소셜 로그인 연동

**한 줄**: 사용자 풀이 SAML이나 OIDC로 외부 소셜 자격 증명 공급자와 연동되고, 그 풀을 API Gateway에 붙이면 API 호출자의 신원을 확인한다.

앱의 `identity-access.cognito`와 `cognito-pools`는 사용자 풀이 인증을, 자격 증명 풀이 AWS

계정에 로그인하는 직원 쪽 이야기라 대상이 다르다. 이 개념은 **애플리케이션 최종 사용자**가
외부 계정으로 로그인하는 경로다.

사용자 풀은 SAML이나 OpenID Connect 같은 표준 프로토콜로 외부 자격 증명 공급자와 연동된다.
그래서 사용자가 흔히 쓰는 소셜 계정으로 로그인하게 하면서 애플리케이션은 인증을 직접 구현하지
않는다. 이 사용자 풀을 API Gateway REST API에 통합하면 API가 호출자의 신원을 확인하게 된다.
여기에 관리형 규칙을 붙인 WAF 웹 ACL을 함께 두면, 인증과 애플리케이션 계층 공격 방어가 각각
제자리를 잡는다.

> [Q306 p210] "Amazon Cognito는 안전한 인증을 제공하며 OIDC 또는 SAML을 사용하여 소셜 IDP와의 연동을 지원합니다."

### `permissions-boundary` — 권한 경계

**한 줄**: 역할이나 사용자가 아무리 넓은 정책을 붙여도 넘어설 수 없는 권한의 상한선이며, SCP로 그 부착을 의무화할 수 있다.

앱의 `identity-access.organizations-scp`와 `Q001-Q050.md`의 `scp-condition-exception`은
계정 전체가 할 수 없는 일을 정하는 장치를 다룬다. 권한 경계는 결이 다르다 — **개별 주체가
가질 수 있는 권한의 최대치**를 정한다.

권한 경계를 붙이면 그 주체의 실제 권한은 붙어 있는 정책과 경계가 겹치는 범위로 줄어든다.
그래서 팀에게 역할을 만들 자유를 주면서도 관리자 권한을 가진 역할은 만들지 못하게 하려는
요구를 이 장치로 푼다. 다만 경계는 붙여야 효력이 있으므로, 역할을 만들 때 경계 부착을 조건으로
요구하는 SCP를 함께 걸어 예방적 통제로 만든다. 규정을 어긴 역할을 나중에 찾아 지우는 방식은
만들어진 뒤에야 작동하므로 같은 수준의 보장을 주지 못한다.

> [Q347 p236] "서비스 제어 정책(SCP)을 사용하여 권한 경계를 적용하면, 연결된 정책에 관계없이 생성된 모든 역할이 제한을 받도록 보장할 수 있습니다."

지정 집계를 원하는 대로 만들기 어렵다. 그 요구가 나오면 원본 데이터를 직접 다루는 쪽으로 간다.

비용 및 사용량 보고서는 상세한 항목별 청구 데이터를 S3 버킷으로 내보낸다. 파일이 S3에
있으므로 Athena로 외부 테이블을 만들어 SQL로 집계하고, QuickSight를 Athena에 연결해 대시보드를
만들어 공유한다. `Q051-Q100.md`의 `quicksight`가 말하는 저장·질의·시각화 분담이 청구 데이터에
그대로 적용되는 구성이다. CloudWatch 대시보드는 지표와 로그를 그리는 자리라 이 데이터셋을
다루지 않고, 파일을 옮기는 전송 서비스는 조회 수단이 아니다.

> [Q325 p222] "AWS 비용 및 사용량 보고서(CUR)는 상세하고 항목별 청구 데이터를 Amazon S3로 제공합니다."

## (주제 미정)

### `amplify` — AWS Amplify

**한 줄**: 웹·모바일 애플리케이션을 개발하고 호스팅하는 것을 돕는 서비스이며, 백엔드 처리 결과를 사용자에게 푸시 알림으로 보내는 장치가 아니다.

오답 보기에서 이름이 익숙하다는 이유로 골라지기 쉬운 서비스다. Amplify가 맡는 것은
애플리케이션을 만들고 배포해 서비스하는 쪽이고, 업로드된 파일을 처리한 뒤 사용자에게 알림을
보내는 자리는 알림 전용 서비스가 맡는다. 처리 완료 알림이 요구에 들어 있으면 그 조각은
SNS 쪽이라고 보면 된다.

> [Q308 p211] "AWS Amplify는 주로 애플리케이션 개발 및 호스팅을 지원하지만, 이 백엔드 워크플로우에 대한 직접적인 푸시 알림 기능을 기본적으로 제공하지는 않습니다."

## 원본 수정 이력

이 슬라이스에서 덤프 해설을 그대로 따르지 않은 것이다. 근거는 ADR-008의 예외를 승계한 ADR-021.

### 사실 오류라 싣지 않은 것

- **Q340 p232** — 해설이 오답을 지우며 "자동 로테이션은 AWS 관리 키에서만 사용할 수 있으며,
  가져온 키 자료에는 사용할 수 없습니다"라고 적었다. 앞의 절반이 사실과 다르다. 자동 키 교체는
  고객이 만든 KMS 키에서도 켤 수 있고, 갈리는 기준은 소유 주체가 아니라 **키 자료를 누가
  만들었는가**다. KMS가 만든 키 자료를 가진 키에서만 자동 교체가 동작하고 가져온 키 자료에는
  쓸 수 없다. `imported-key-material-rotation`에는 이 정확한 기준만 실었다.

- **Q327 p223** — 해설이 정답을 설명하며 "단일 Amazon EC2 인스턴스에서 비디오를 제공하면
  저지연 전송이 보장되며"라고 적었다. 같은 문항의 문제문이 예측할 수 없는 트래픽 급증을
  감당해야 한다고 요구하는데, 인스턴스 한 대는 그 요구를 채우지 못하고 단일 장애점이 된다.
  이 문항에서 가져온 것은 Kinesis Video Streams의 용도뿐이고, 서빙 구성은 개념으로 만들지
  않았다. 대용량 미디어를 S3에 둔다는 사실은 `Q001-Q050.md`의 `blob-offload-to-s3`에 이미 있다.

### [AI 작성 해설]이라 채택하지 않은 것

- **Q338 p231** — 이 슬라이스의 유일한 `[AI 작성 해설]`이다. Control Tower의 Account Factory와
  Account Factory for Terraform(AFT)으로 계정 프로비저닝을 자동화한다는 내용인데, 이 슬라이스의
  다른 문항에서 교차 확인되지 않는다. Control Tower가 랜딩 존을 세워 다중 계정 환경의 기준
  골격을 만든다는 사실은 `Q201-Q250.md`의 `control-tower-landing-zone`에 이미 있으므로, 확인되지
  않은 하위 기능 이름을 새로 만들지 않고 넘겼다. 같은 해설이 드는 "Organizations의 CreateAccount
  API는 빈 계정만 만든다"도 같은 이유로 싣지 않았다.
