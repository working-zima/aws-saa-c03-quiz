## block-file-storage

### `ebs-encryption-by-default` — EBS 기본 암호화는 계정 속성이다

**한 줄**: EC2 계정 속성에서 기본 암호화를 켜면 그 계정에서 새로 만드는 EBS 볼륨이 전부 암호화되고, 암호화하지 않은 볼륨은 만들 수 없게 된다.

앱의 `block-file-storage.ebs`는 EBS가 무엇인지까지만 말한다. 문항이 묻는 것은 "앞으로
만들어질 볼륨이 빠짐없이 암호화되게 하라"는 요구를 어디서 처리하느냐다. 그 자리는 볼륨마다
거는 설정이 아니라 리전별 계정 속성이다. EC2 콘솔의 계정 속성에서 EBS 암호화를 켜고 기본
KMS 키나 고객 관리 키를 지정하면 그 다음부터 만드는 볼륨에 자동으로 적용된다.

**"보장한다"와 "막는다"를 한 번에 요구하는 문항에서 이 설정이 갈림길이 된다.** 규정 준수
규칙으로 암호화되지 않은 볼륨을 찾아내는 선택지는 이미 만들어진 것을 나중에 발견하는
장치라서 생성 자체를 막지 못한다. 계정 속성은 만드는 시점에 걸린다.

> [Q286 p197] "Amazon EC2에서는 계정 속성을 설정하여 새로운 EBS 볼륨을 자동으로 암호화할 수 있습니다."

### `spread-placement-group` — 분산 배치 그룹

**한 줄**: 인스턴스를 서로 다른 기본 하드웨어에 흩어 놓는 배치 전략이고, 여러 가용 영역에 걸쳐 쓰면 고가용성까지 얻는다.

앱은 `cluster-placement-group` 하나만 다룬다. 클러스터는 인스턴스를 한데 모아 지연을 줄이는
전략이라 목적이 정반대다. "두 노드가 같은 물리 하드웨어에서 돌면 안 된다"는 조건이 붙으면
답은 분산 배치 그룹이다.

분산 배치 그룹은 각 인스턴스를 다른 랙·다른 하드웨어에 배치해 동시 장애를 줄인다. 여기에
가용 영역을 여럿 쓰면 하드웨어 장애와 가용 영역 장애를 동시에 막게 되어 99.99% 같은 높은
가용성 요구를 채운다. 하나의 가용 영역에만 배치하는 선택지는 분리는 되지만 그 가용 영역이
통째로 나가면 함께 멈춘다.

> [Q300 p206] "스프레드 배치 그룹의 인스턴스는 서로 다른 기본 하드웨어에 배치되며, 여러 가용 영역에 배포될 경우 고가용성을 제공합니다."

## data-transfer-services

### `file-gateway-vs-datasync-continuous` — 지속 수집과 예약 전송의 갈림길

**한 줄**: 활성 파일 공유에서 계속 생겨나는 파일을 준실시간으로 S3에 넣는 일은 파일 게이트웨이의 자리이고, DataSync는 대량·주기적 전송 쪽이다.

앱의 `datasync`와 `storage-gateway`는 두 서비스가 무엇인지 말하고, `Q151-Q200.md`의
`datasync-scope-limits`는 DataSync가 데이터베이스 변경 스트림을 다루지 못한다고 말한다.
여기서 갈리는 축은 하나 더 있다 — **파일을 다루는 경우에도 전송이 한 번씩 끊기는가, 계속
이어지는가**다.

DataSync 작업은 실행할 때마다 원본과 대상을 맞춰 주는 방식이라 일정을 걸어 돌린다. 그래서
"하루가 끝날 때"처럼 주기가 붙으면 그 사이에 생긴 파일은 다음 실행까지 기다린다. 분석이
거의 실시간이어야 한다는 조건에서는 이 간격이 그대로 지연이 된다. 파일 게이트웨이는 공유에
쓰인 파일을 계속 올려 보내므로 그 간격이 없다.

애플리케이션이 이미 네트워크 공유에 쓰고 있다면 공유 경로만 게이트웨이 쪽으로 바꾸면 되고,
전송을 오케스트레이션하는 코드나 폴링 스크립트를 새로 만들지 않는다.

> [Q252 p173] "예약된 전송(예: 일일 종료 시 DataSync)과 비교하여, S3 File Gateway는 새 파일이나 변경된 파일을 지속적으로 업로드하므로 준실시간 요구 사항을 더 잘 충족합니다."

## aurora-dynamodb-cache

### `elasticache-multi-az-failover` — ElastiCache의 다중 AZ 자동 장애 조치

**한 줄**: 다중 AZ를 켜면 다른 가용 영역의 복제 노드를 두고, 주 노드가 죽으면 그 복제본을 자동으로 승격시킨다.

앱의 `elasticache`는 캐시로 읽기를 빠르게 한다는 것까지만 말한다. 문항은 캐시 계층 자체의
가용성을 묻는다 — 노드 하나가 죽었을 때 사람이 손대지 않고 넘어가야 한다는 요구다.

ElastiCache의 다중 AZ 구성은 주 노드와 복제 노드를 서로 다른 가용 영역에 둔다. 장애를
감지하면 복제본을 주 노드로 승격시키는 일까지 서비스가 맡으므로 다운타임이 짧다.
읽기 복제본만 켜 두고 필요할 때 승격시키는 선택지는 그 승격이 수동이라 "자동으로"라는
조건을 채우지 못하고, 백업을 떠 두었다가 다른 클러스터로 복원하는 선택지는 장애 조치가
아니라 재해 복구라 시간이 훨씬 오래 걸린다.

> [Q259 p179] "자동 페일오버가 포함된 Multi-AZ를 활성화하면 Amazon ElastiCache가 장애를 자동으로 감지하고, 다운타임을 최소화하여 읽기 레플리카를 프라이머리로 승격시킵니다."

## compute-delivery

### `cloudfront-multiple-origins` — 배포 하나에 오리진을 여럿 둔다

**한 줄**: 한 CloudFront 배포가 S3 버킷과 로드 밸런서를 함께 오리진으로 가질 수 있어서, 정적·동적 콘텐츠가 같은 진입점을 쓴다.

`Q101-Q150.md`의 `cloudfront-alb-origin`은 오리진이 버킷만이 아니라는 것을 말한다. 그다음
질문이 남는다 — 정적은 버킷, 동적은 ALB일 때 배포를 둘로 나눠야 하는가. 아니다. 배포 하나에
오리진을 여러 개 등록하고 경로에 따라 갈라 보낼 수 있다.

이 사실이 갈림길이 되는 자리는 Global Accelerator가 함께 나오는 문항이다. 배포를 둘로
나누면 도메인도 둘이 되고, 그 둘을 다시 묶으려고 가속기를 얹는 구성이 그럴듯해 보인다.
오리진을 한 배포에 모으면 도메인이 하나로 유지되므로 그 구성 자체가 필요 없어지고,
Route 53에서 그 배포 하나를 가리키면 끝난다.

> [Q285 p197] "AWS문서에는 CloudFront가 S3 오리진과 로드 밸런서 오리진을 모두 지원하며, 단일 배포에 여러 오리진을 포함할 수 있다고 명시되어 있습니다."

### `cloudfront-signed-cookie` — CloudFront 서명된 쿠키

**한 줄**: 파일마다 URL을 새로 만드는 서명된 URL과 달리, 쿠키 하나로 여러 파일에 대한 접근을 열어 주므로 URL은 모두에게 같다.

`Q001-Q050.md`의 `cloudfront-signed-url`은 서명된 URL이 만료되는 임시 접근이라는 것을
말한다. 그 방식에는 다른 제약이 하나 더 있다 — **서명이 URL 안에 들어가므로 파일마다 URL이
달라진다.**

"모든 사용자에게 같은 주소를 준다"는 조건이 붙으면 그래서 서명된 URL이 아니라 서명된
쿠키다. 접근 권한을 쿠키에 담아 발급하면 주소는 그대로 두고 그 쿠키를 가진 사람만 콘텐츠를
받아 간다. 파일이 여러 개인 경우 URL을 파일 수만큼 만들어 관리할 일도 사라진다.

> [Q263 p182] "CloudFront 서명된 쿠키를 사용하면 회사는 단일하고 일관된 URL을 유지하면서 프리미엄 사용자에게 액세스 권한을 제공할 수 있습니다."

### `nlb-ip-targets` — NLB는 VPC 밖의 IP도 대상으로 받는다

**한 줄**: 대상을 IP 주소로 등록할 수 있어서 온프레미스 서버까지 같은 로드 밸런서 뒤에 세울 수 있고, 고정 IP도 함께 제공한다.

앱의 `alb-l7-vs-nlb-l4`는 두 로드 밸런서를 계층으로 가른다. 문항이 쓰는 축은 하나 더
있다 — **무엇을 대상으로 등록할 수 있는가**다.

NLB의 대상 그룹은 IP 주소를 받는다. 그래서 AWS 안의 EC2와 Direct Connect 너머의 온프레미스
서버를 한 대상 그룹에 함께 넣고 트래픽을 나눠 줄 수 있다. 여기에 NLB가 가용 영역마다
고정 IP를 갖고 Elastic IP도 붙일 수 있다는 점이 겹치면, "공급업체가 허용 목록에 넣어야 해서
주소가 바뀌면 안 된다"는 조건까지 한 서비스로 끝난다.

같은 요구에 Route 53 Resolver나 API Gateway가 오답으로 함께 나온다. 앞쪽은 이름을 주소로
바꾸는 DNS 쪽 서비스라 트래픽을 나누지 않고, 뒤쪽은 HTTP 기반 API를 위한 자리다.

> [Q270 p186] "네트워크 로드 밸런서(NLB)는 IP 주소 기반 타겟을 지원하므로 EC2 및 온프레미스 엔드포인트를 모두 사용할 수 있습니다."

## serverless-containers

### `api-gateway-behind-cloudfront` — API도 CloudFront 뒤에 둘 수 있다

**한 줄**: API Gateway HTTP API를 오리진으로 등록하면 동적 응답도 엣지를 거쳐 나가고, 캐시해도 되는 응답은 엣지에서 돌려준다.

앱의 `api-gateway`는 REST API와 HTTP API의 차이까지 다루지만, 그 앞에 무엇을 세울 수
있는지는 말하지 않는다. 전 세계 사용자에게 정적·동적 콘텐츠를 함께 내보내면서 비용을
줄이라는 문항에서 이 사실이 정답을 가른다.

정적 파일은 S3에 두고 CloudFront가 캐싱하는 것이 표준 조합이다. 여기서 한 걸음 더 나가,
동적 응답을 내주는 HTTP API도 같은 배포의 오리진으로 등록하면 응답이 엣지에서 시작하는
연결을 타므로 지연이 줄고, 캐시해도 되는 응답은 오리진까지 가지 않는다. 버킷 웹사이트
주소를 그대로 나눠 주고 API만 따로 두는 구성은 정적 쪽에도 동적 쪽에도 엣지가 없어
글로벌 지연이 그대로 남는다.

> [Q257 p178] "Amazon API Gateway HTTP API를 통해 노출되는 동적 콘텐츠도 CloudFront의 오리진으로 사용할 수 있어, 전 세계 사용자에게 지연 시간을 줄이고 적절한 응답을 캐시할 수 있는 기능을 제공합니다(안전한 경우)."

### `lambda-kinesis-event-source` — Lambda가 스트림 레코드를 직접 처리한다

**한 줄**: Kinesis Data Streams의 레코드를 Lambda가 이벤트로 받아 처리할 수 있어서, 스트림 소비자를 위해 인스턴스를 띄우지 않아도 된다.

앱의 `lambda`와 `kinesis-data-streams`는 각각 무엇을 하는 서비스인지까지만 말하고, 둘이
어떻게 붙는지는 말하지 않는다. 그래서 "스트림을 실시간으로 처리·변환한 뒤 저장하라"는
문항에서 처리 계층에 EC2를 두는 선택지가 그럴듯해 보인다.

Lambda는 스트림 소스의 이벤트를 받아 실행되므로 소비자 애플리케이션을 올려 둘 인스턴스가
필요 없다. 수집은 Kinesis Data Streams, 처리·변환은 Lambda, 적재는 DynamoDB로 이어지는
구성이 운영 부담이 가장 작은 조합이 되는 이유다. 큐로 받는 선택지가 함께 나오는데, 큐는
작업을 하나씩 꺼내 쓰는 자리이고 문항이 말하는 것은 스트리밍 데이터다.

> [Q269 p186] "AWS 문서에 따르면 Lambda는 인프라 관리 없이도 Kinesis와 같은 스트림 소스의 이벤트를 처리할 수 있습니다."

## messaging-backup

### `backup-ec2-resource-assignment` — EC2를 백업 대상으로 지정하면 볼륨과 구성이 함께 들어간다

**한 줄**: 백업 계획의 리소스로 EBS 볼륨이 아니라 EC2 인스턴스를 지정해야 인스턴스 구성과 연결된 볼륨이 모두 백업된다.

앱의 `messaging-backup.backup`은 AWS Backup이 여러 서비스의 백업을 한곳에서 자동화한다는
것까지 말한다. 문항이 파고드는 것은 **무엇을 리소스로 지정하느냐**다.

볼륨만 지정하면 데이터는 남지만 인스턴스를 다시 세우는 데 필요한 구성이 빠진다. EC2
인스턴스를 지정하면 인스턴스 구성과 거기 붙은 EBS 볼륨이 함께 백업 대상이 되어 복구가
한 번에 끝난다. 그래서 "인스턴스의 구성과 데이터를 매일 백업하라"는 문항에서 볼륨을 지정한
선택지와 인스턴스를 지정한 선택지가 나란히 오르고, 답은 뒤쪽이다.

일정과 보존, 다른 리전으로의 사본 만들기가 모두 백업 계획 안에 들어 있으므로 스냅샷을 뜨고
복사하는 함수를 직접 만드는 선택지는 운영 부담만 늘린다.

> [Q264 p183] "EC2 인스턴스를 리소스로 추가하면 백업에 구성 및 연결된 볼륨이 모두 포함됩니다."

### `organizations-backup-policy` — Organizations의 백업 정책

**한 줄**: 조직 단위로 백업 계획을 정해 회원 계정 전체에 내려보내는 정책이라, 계정마다 따로 설정하지 않는다.

여러 계정에 흩어진 리소스를 백업하라는 문항에서 갈리는 축은 **어디서 정하느냐**다. 계정마다
AWS Backup을 각자 설정하는 선택지와 조직에서 정책으로 내려보내는 선택지가 함께 나온다.

AWS Organizations의 백업 정책은 백업 계획을 조직 수준에서 정의해 회원 계정에 적용한다.
계정이 새로 늘어나도 같은 규칙이 따라붙으므로 중앙에서 관리한다는 요구가 이 정책 하나로
충족된다. 계정마다 설정하는 구성은 결과물은 비슷해도 관리 지점이 계정 수만큼 늘어난다.

> [Q266 p184] "AWS Organizations의 AWS Backup 정책은 회원 계정 전반의 백업 계획에 대해 중앙 집중식 거버넌스와 자동화를 제공합니다."

### `backup-cross-account-copy` — 백업 사본을 다른 계정에 둔다

**한 줄**: 리전을 옮기는 것은 리전 장애를 대비하는 일이고, 계정을 옮기는 것은 그 계정이 뚫리거나 실수로 지워지는 것을 대비하는 일이다.

백업 사본의 목적지를 묻는 문항에서 "다른 리전"과 "다른 계정"이 나란히 나온다. 둘은 막는
사고가 다르다.

백업이 원본과 같은 계정에만 있으면, 그 계정에서 충분한 권한을 얻은 사람이 원본과 백업을
함께 지울 수 있다. 실수로 지우는 경우도 마찬가지다. 사본을 다른 계정에 두면 관리 주체가
갈라져 그 경로가 끊긴다. 반면 리전 간 사본은 리전 하나가 통째로 멈추는 상황을 대비하지만,
계정 수준의 침해에는 같은 계정 안에 있는 한 함께 노출된다.

**문항이 "계정에 대한 악의적인 공격이나 실수로 인한 삭제"를 조건으로 걸면 리전이 아니라
계정이 답이다.** 리전 간 복원력만 보고 고르면 어긋난다.

> [Q266 p184] "백업이 동일한 계정에만 남아 있다면, 해당 계정에서 충분한 권한을 가진 공격자가 백업을 변경하거나 삭제할 가능성이 있습니다."

### `backup-s3-continuous-backup` — S3의 연속 백업과 특정 시점 복원

**한 줄**: AWS Backup은 S3를 대상으로 연속 백업을 만들 수 있어서, 하루 한 번 뜨는 백업보다 되돌릴 수 있는 지점이 촘촘하다.

앱의 `backup-long-term-retention`은 장기 보존을 AWS Backup이 맡는다고 말한다. 문항이
"데이터 손실 가능성을 최대한 줄이라"고 요구하면 축이 하나 더 붙는다 — **얼마나 촘촘한
시점으로 되돌릴 수 있는가**다.

S3 버킷에 연속 백업을 걸면 특정 시점으로 복원할 수 있다. 하루 한 번 백업하는 구성은 사고가
난 시점과 마지막 백업 사이의 변경분을 잃지만, 연속 백업은 그 구간이 훨씬 짧다. 그래서
"고가용성 스토리지 + 손실을 최소화하는 백업"이 함께 요구되면 S3에 연속 백업을 거는 구성이
답이 되고, 인스턴스에 파일을 두고 매일 백업하는 선택지는 두 조건 모두에서 밀린다.

> [Q297 p204] "또한 AWS Backup 문서에 따르면 Amazon S3의 경우 지속적인 백업을 생성하고 특정 시점으로 데이터를 복원할 수 있어, 단순한 일일 백업보다 데이터 손실 위험을 더 효과적으로 줄일 수 있습니다."

## vpc-networking

### `vpc-flow-logs` — VPC 플로우 로그

**한 줄**: VPC의 네트워크 인터페이스를 드나드는 트래픽의 메타데이터를 기록하는 기능이고, API 호출을 기록하는 CloudTrail과는 다른 것이다.

앱의 `vpc-networking` 주제에는 네트워크 트래픽을 관찰하는 자리가 없다. "인터페이스를 오가는
트래픽 정보를 거의 실시간으로 모으라"는 요구가 나오면 그 출처가 플로우 로그다. 기록되는
것은 패킷 내용이 아니라 출발지·목적지·포트·허용 여부 같은 메타데이터다.

**목적지를 CloudTrail 트레일로 적은 선택지는 지운다.** CloudTrail이 남기는 것은 누가 어떤
API를 불렀는가이고, 플로우 로그는 트레일에 실리지 않는다. 플로우 로그의 목적지는
CloudWatch Logs 같은 로그 대상이고, 거기 쌓인 로그를 다시 분석 도구로 보내는 구간에서는
전달 자체가 관리형인 Firehose가 소비자를 직접 만들어야 하는 Kinesis Data Streams보다 손이
덜 간다.

> [Q282 p195] "VPC 내 네트워크 인터페이스의 송수신 트래픽 메타데이터를 캡처하려면 올바른 텔레메트리 소스는 VPC Flow Logs입니다."

### `nat-gateway-traffic-uses-public-endpoints` — NAT를 거친 AWS 서비스 접근은 공용 엔드포인트를 지난다

**한 줄**: NAT 게이트웨이로 나가면 목적지가 AWS 서비스라도 그 서비스의 공용 엔드포인트로 가므로, "공용 IP를 쓰지 않는다"는 조건을 채우지 못한다.

앱의 `comparison`은 NAT Gateway를 인터넷용, VPC Endpoint를 AWS 서비스용으로 가른다. 문항은
그 구분의 **이유**를 답으로 요구한다 — 프라이빗 서브넷에서 AWS 서비스를 부르는 데 NAT
게이트웨이도 쓸 수 있는데 왜 답이 아닌가.

NAT를 거치는 경로는 목적지가 그 서비스의 공용 엔드포인트다. 인스턴스에 공용 IP가 없더라도
트래픽 자체는 공용 주소로 나갔다 오는 셈이라 "공용 IP 주소를 사용해서는 안 된다"는 요구를
어긴다. 인터페이스 엔드포인트를 두면 서비스 엔드포인트가 VPC 안의 사설 주소로 잡히고
트래픽이 AWS 백본 안에 머문다. 비용까지 함께 묻는 문항이면 서브넷마다 NAT 게이트웨이를
띄우는 구성과 견주게 되는데, 그쪽은 게이트웨이 수만큼 시간당 요금이 붙는다.

> [Q272 p187] "NAT 게이트웨이는 여전히 공용 AWS 서비스 엔드포인트에 의존하므로, 문제에서 설명한 프라이빗 연결 방식에 해당하지 않습니다."

## route53

### `latency-record-for-non-aws-endpoint` — 온프레미스 엔드포인트에도 지연 시간 레코드를 만든다

**한 줄**: AWS 밖에 있는 엔드포인트는 그것과 가장 가까운 AWS 리전에 연결해 지연 시간 레코드를 만든다.

앱의 `routing-policies`는 지연 시간 기반 라우팅이 지연이 가장 짧은 리전을 고른다고 말한다.
여기서 막히는 문항이 있다 — **한쪽 엔드포인트가 온프레미스 데이터 센터라 리전이 없는
경우**다.

이때는 그 데이터 센터에서 가장 가까운 리전을 골라 레코드에 연결한다. Route 53은 그 리전과
사용자 사이의 지연 측정값을 그 엔드포인트의 값으로 삼아 비교하므로, AWS에 올린 사이트와
온프레미스 사이트를 같은 기준으로 놓고 사용자마다 빠른 쪽을 고를 수 있다.

장애 조치 라우팅이 오답으로 함께 나오는데, 그쪽은 주 엔드포인트가 정상인 한 모든 트래픽을
한쪽으로만 보내므로 사용자별 지연을 줄이지 못한다.

> [Q281 p192] "AWS가 아닌 엔드포인트(예: 온프레미스 데이터 센터)의 경우, Route 53을 사용하여 지연 시간 라우팅 레코드를 생성하고 해당 엔드포인트에서 가장 가까운 AWS 리전에 연결할 수 있습니다."

## analytics-monitoring

### `athena-encrypted-and-pay-per-query` — Athena의 과금 단위와 암호화된 데이터

**한 줄**: 실행한 쿼리가 스캔한 데이터에만 요금이 붙고, KMS로 암호화된 S3 객체도 그대로 조회할 수 있다.

앱의 `athena`는 S3 데이터를 SQL로 조회한다는 것까지 말한다. 문항이 "가장 비용 효율적인"을
붙이면 축이 하나 더 생긴다 — **쓰지 않는 동안에도 돈이 나가는가**다. Athena는 서버리스라
띄워 두는 비용이 없고, 쿼리가 스캔한 데이터 양에만 요금이 붙는다. 그래서 가끔 실행하는
분석에서는 클러스터를 세우는 선택지보다 싸다.

암호화가 조건에 끼어 있어도 Athena를 지울 이유가 되지 않는다. KMS와 연동되므로 암호화된
객체를 읽도록 구성해 두면 그대로 조회할 수 있고, 열 지향 형식인 Parquet은 필요한 열만 읽어
스캔량 자체를 줄인다.

> [Q289 p199] "AWS 문서: Athena는 S3에 있는 암호화된 Parquet 파일과 호환되므로, 이 시나리오에 이상적인 선택이며 비용과 복잡성을 모두 줄여줍니다."

### `athena-vs-redshift-workload` — 임시 쿼리와 반복되는 고성능 쿼리

**한 줄**: 어쩌다 한 번 던지는 질의는 Athena, 성능이 일정해야 하는 반복 분석은 Redshift다.

둘 다 SQL로 분석한다는 점이 같아 선택지에 함께 오른다. 갈리는 축은 데이터의 성격이 아니라
**쿼리가 어떻게 들어오는가**다.

Athena는 필요할 때 실행하고 그만큼만 내는 구조라 임시 분석에 맞는다. 대신 전용 자원을 잡고
있지 않으므로 복잡한 쿼리가 몰리는 상황에서 일정한 응답 시간을 약속하지 못한다. 분석가가
복잡한 SQL을 계속 던지고 성능이 일관돼야 한다는 조건이 붙으면 그 자리는 웨어하우스인
Redshift다.

> [Q267 p184] "A: Athena는 임시 쿼리에는 적합하지만, 일관되고 고성능의 SQL 워크로드에는 적합하지 않습니다."

### `redshift-hot-cold-split` — 자주 쓰는 데이터만 웨어하우스에 넣는다

**한 줄**: 자주 조회하는 데이터는 Redshift로 적재하고 나머지는 S3에 둔 채 Spectrum으로 읽으면, 성능을 지키면서 웨어하우스 비용을 줄인다.

`Q101-Q150.md`의 `redshift-spectrum`은 Spectrum이 S3의 데이터를 그 자리에서 읽는 기능이라고
말한다. 그 기능이 비용 판단에 쓰이는 방식이 이 문항의 정답 근거다.

데이터 전체를 웨어하우스에 넣으면 조회 빈도와 무관하게 저장 비용이 붙는다. 조회가 몰리는
데이터만 Redshift로 올리고 나머지는 S3에 남겨 Spectrum으로 필요할 때만 읽으면, 자주 쓰는
쪽은 웨어하우스의 성능을 그대로 받고 덜 쓰는 쪽에는 웨어하우스 비용이 붙지 않는다.
"일부 데이터가 다른 데이터보다 더 자주 조회된다"는 문장이 문제문에 있으면 이 분리를
묻는 신호다.

> [Q267 p184] "핫 데이터를 Redshift에 로드하여 빠르게 액세스하고, S3에 있는 콜드 데이터는 Spectrum을 통해 쿼리함으로써 비용과 성능을 모두 최적화할 수 있습니다."

### `log-storage-s3-athena` — 가끔 조회하는 로그는 S3에 쌓고 Athena로 읽는다

**한 줄**: 로그를 어디에 둘지는 조회 빈도로 갈린다 — 가끔이면 S3와 Athena, 자주·저지연이면 OpenSearch, 실시간 감시면 CloudWatch Logs다.

앱의 `log-analysis-options`는 OpenSearch와 CloudWatch Logs Insights 둘을 세운다. 여기에
세 번째 선택지가 빠져 있다.

하루에 수십 GB씩 쌓이는 로그를 오래 보관하면서 가끔만 조회한다면 S3에 두고 Athena로 읽는
구성이 가장 싸다. 저장은 객체 스토리지 값이고 조회는 실행한 만큼만 낸다. OpenSearch는
검색이 잦고 응답이 빨라야 할 때 값어치가 있지만 클러스터를 띄워 두는 비용이 계속 붙고,
CloudWatch Logs는 지금 벌어지는 일을 보는 자리라 대용량 장기 보관과 분석에는 맞지 않는다.

> [Q298 p204] "로그 데이터에 대한 비정기적이거나 임시적인 쿼리의 경우, Amazon S3 + Amazon Athena가 가장 비용 효율적이고 서버리스이며 확장 가능한 분석 솔루션을 제공합니다."

### `lake-formation-blueprint-and-athena` — 블루프린트로 모으고 Athena로 권한을 적용한다

**한 줄**: 블루프린트는 데이터베이스의 데이터를 데이터 레이크로 끌어오는 수집 장치이고, Athena를 거쳐 조회하면 Lake Formation의 열 수준 권한이 그대로 걸린다.

`Q001-Q050.md`의 `lake-formation`은 권한을 행·열 수준까지 나눌 수 있다는 것을 말한다.
문항이 한 걸음 더 나간다 — **그 권한이 실제로 적용되려면 어떤 경로로 읽어야 하는가**,
그리고 **데이터는 어떻게 레이크로 들어오는가**다.

블루프린트는 관계형 데이터베이스 같은 소스에서 데이터 레이크로 데이터를 가져오는 정형화된
수집 방식이다. 수집과 권한 관리가 같은 서비스 안에서 이어지므로 파이프라인을 따로 만들지
않는다. 그리고 시각화 도구가 Athena를 데이터 소스로 쓰면 Athena가 Lake Formation의 열 수준
권한을 적용해 조회하므로, 도구 쪽에 접근 제어 로직을 다시 만들 필요가 없다. 수집할 때 열을
빼 두거나 IAM·버킷 정책으로 대신하려는 선택지는 SQL 질의 단위의 열 권한이 되지 못한다.

> [Q277 p190] "QuickSight가 Athena를 데이터 소스로 사용할 때, Athena는 Lake Formation의 열 수준 권한을 자동으로 적용합니다."

### `ec2-detailed-monitoring` — 상세 모니터링은 1분 간격이다

**한 줄**: EC2 지표는 기본이 5분 간격이고, 상세 모니터링을 켜야 1분 간격으로 올라온다.

앱의 `cloudwatch`는 리소스를 모니터링한다는 것까지만 말한다. 문항은 간격을 조건으로 건다 —
"2분보다 잘게 성능을 분석해야 한다"처럼 숫자가 붙는 자리다.

기본 상태에서 EC2 지표는 5분 간격이라 이 요구를 채우지 못한다. 인스턴스에 상세 모니터링을
켜면 1분 간격이 되고, 그때부터 짧은 급증도 지표에서 보인다. 로그를 다른 저장소로 옮겨
분석 도구를 붙이는 선택지가 함께 나오는데, 지표로 끝나는 일에 파이프라인을 만드는 셈이라
더 복잡하기만 하다.

> [Q276 p189] "상세 모니터링을 활성화하면 1분 간격으로 메트릭을 수집할 수 있으며, 이를 통해 트래픽 피크 시간대의 성능을 분석하는 데 필요한 세분성을 확보할 수 있습니다."

## secrets-encryption

### `kms-imported-key-material` — 가져온 키 자료

**한 줄**: 외부에서 만든 키 자료를 KMS에 넣어 쓸 수 있지만, 그 키를 보관하고 다시 넣는 책임이 사용자에게 남는다.

`Q001-Q050.md`의 `kms-multi-region-key`는 같은 키를 여러 리전에서 쓰는 방법을 다룬다. 그
문항의 오답 보기에 "가져온 키 자료를 여러 리전에 넣는다"가 함께 오르므로, 이 선택지가 왜
밀리는지 알아야 한다.

KMS는 키 자료를 직접 만들어 관리하는 것이 기본이지만, 사용자가 외부에서 만든 키 자료를
가져와 쓸 수도 있다. 이 방식은 키 자료의 원본을 안전하게 보관하고 필요할 때 다시 넣는 일이
사용자 몫으로 남는다. "키를 직접 관리하고 싶지 않다"거나 "운영 부담을 최소화한다"는 조건이
붙으면 그래서 이쪽이 아니라 KMS가 만들어 주는 키다.

> [Q273 p188] "가져온 키 자료(옵션 B)는 키 관리 책임을 증가시킵니다."

## cost-management

### `budget-forecasted-alert` — 예산 알림은 예측값에도 걸 수 있다

**한 줄**: 실제 지출이 임계값에 닿았을 때만이 아니라, 이대로 가면 넘길 것으로 예측될 때도 알린다.

앱의 `aws-budgets`는 예산을 세우고 초과를 알린다고 말하고, `Q101-Q150.md`의 `budget-actions`는
임계값에서 조치를 실행하는 기능을 다룬다. 남는 축이 **언제 알리는가**다.

Budgets의 알림 기준은 두 가지다. 실제 비용이 임계값에 닿는 시점과, 이번 기간의 예상 지출이
임계값을 넘을 것으로 계산되는 시점이다. 뒤쪽을 쓰면 돈을 다 쓰기 전에 손을 쓸 수 있어서
"가능한 한 빨리 감지해야 한다"는 조건을 채운다. 알림은 SNS 주제로 보낼 수 있으므로,
같은 일을 하려고 비용을 계산하는 함수를 직접 만드는 선택지는 "맞춤형 솔루션을 만들지
않는다"는 조건과도 어긋난다. 하루 한 번 보고서를 만들어 확인하는 구성도 그만큼 늦다.

> [Q293 p202] "AWS 문서에 따르면 Budgets는 Amazon SNS로 알림을 전송할 수 있으며, 사용자 정의 코드 없이도 실제 및 예측 알림을 모두 지원합니다."

## (주제 미정)

### `s3-website-endpoint-no-https` — 정적 웹사이트 엔드포인트는 HTTPS를 지원하지 않는다

**한 줄**: S3의 REST API 주소는 HTTPS로 접근되지만 정적 웹사이트 호스팅 엔드포인트는 HTTP뿐이라, 브라우저에 HTTPS로 주려면 앞에 CloudFront를 세운다.

앱은 S3의 정적 웹사이트 호스팅을 `waf-attach-targets`에서 한 번 언급한다 — 그 엔드포인트에는
WAF를 직접 붙일 수 없어 앞에 CloudFront를 둔다는 내용이다. 같은 자리에 제약이 하나 더 있다.

정적 웹사이트 엔드포인트로 제공하는 사이트는 HTTPS를 지원하지 않는다. 버킷에 인증서를 붙이는
선택지가 오답인 이유가 이것이다. 그래서 "S3에 올린 웹사이트를 HTTPS로 제공하라"는 요구는
CloudFront 배포를 만들어 버킷을 오리진으로 두고, 그 배포에 인증서를 붙이는 두 단계로 풀린다.
로드 밸런서를 앞에 세우는 구성은 S3가 로드 밸런서의 대상이 아니라 성립하지 않는다.

> [Q254 p175] "S3는 REST API 액세스에 대해 HTTPS를 지원하지만, 정적 웹사이트 엔드포인트에서는 HTTPS를 지원하지 않습니다."

## 원본 수정 이력

이 슬라이스에서 덤프 해설을 그대로 따르지 않은 것이다. 근거는 ADR-008의 예외를 승계한 ADR-021.

### 사실 오류라 싣지 않은 것

- **Q270 p186** — 해설이 "애플리케이션 로드 밸런서(ALB)는 인스턴스 또는 Lambda 타깃만
  지원하며, VPC 외부의 IP 주소는 지원하지 않습니다"라고 단정한다. ALB의 대상 그룹에도 IP
  대상 유형이 있고, Direct Connect나 VPN으로 닿는 온프레미스 주소를 등록할 수 있다.
  이 문항의 정답이 NLB인 근거는 대상 유형이 아니라 **고정 IP**이므로, `nlb-ip-targets`에는
  NLB가 IP 대상과 고정 IP를 함께 제공한다는 사실만 실었다. ALB를 배제하는 근거로는 쓰지 않는다.

- **Q276 p189** — 해설이 상세 모니터링을 켜면 "CPU 사용률, 메모리 사용량, 디스크 I/O,
  네트워크 처리량"을 분석할 수 있다고 적었다. 메모리 사용률은 상세 모니터링을 켜도 올라오지
  않고 CloudWatch 에이전트가 필요하다 — `Q101-Q150.md`의 `cloudwatch-agent-memory-metric`에
  이미 있는 사실이고 근거도 같은 덤프(Q145)다. `ec2-detailed-monitoring`에는 수집 간격이
  5분에서 1분으로 바뀐다는 사실만 실었다.

- **Q262 p181** — 정답 조합이 인터페이스 VPC 엔드포인트 구성과 "VPC 라우팅 테이블에
  엔드포인트에 대한 경로를 추가합니다"를 함께 든다. 라우팅 테이블에 경로가 필요한 것은
  게이트웨이 엔드포인트 쪽이고, 인터페이스 엔드포인트는 서브넷에 만들어진 ENI와 프라이빗
  DNS로 동작한다. 두 유형의 구분은 앱의 `vpc-networking.vpc-endpoint`에 이미 있으므로
  이 문항에서는 새로 만든 항목이 없다.

- **Q255 p177** — 해설이 오답을 지우며 "프라이빗 서브넷은 공용 IP를 지원하지 않습니다"라고
  적었다. 서브넷이 공용 IP 할당 자체를 막는 것은 아니고, 인터넷 게이트웨이로 가는 경로가
  없어서 통신이 되지 않는 것이다. 정답 근거인 NAT 게이트웨이는 앱의
  `vpc-networking.nat-gateway`와 `Q201-Q250.md`의 `nat-gateway-per-az`에 있어 새로 만들지 않았다.

### [AI 작성 해설]이라 채택하지 않은 것

- **Q275 p189** — 이 슬라이스의 유일한 `[AI 작성 해설]`이다. 해설이 드는 사실 셋은 모두
  이미 있다. 아웃바운드 전용 인터넷 게이트웨이가 IPv6 전용이라는 것은 앱의
  `vpc-networking.egress-only-igw`에, NLB가 4계층이라 지연이 낮다는 것은
  `compute-delivery.alb-l7-vs-nlb-l4`에, awsvpc 모드에서 태스크에 ENI가 붙는다는 것은
  `Q051-Q100.md`의 `ecs-awsvpc-mode`에 있다. 새로 만들 것이 없어 넘겼다.

### 중복이라 새로 만들지 않은 것

정답 근거이지만 앱이나 앞 step에 이미 있어 항목으로 만들지 않은 것이다.

- **Q251 p173** — EFS가 NFS를 그대로 지원하고 FSx for Windows File Server는 SMB 쪽이라는
  갈림길. 앱의 `block-file-storage.efs`·`fsx`와 `Q101-Q150.md`의 `fsx-windows-file-server`에 있다.
- **Q253 p174**·**Q258 p178** — 같은 결과를 반복 조회할 때 ElastiCache로 덜어 내고 DAX는
  DynamoDB 전용이라는 것. 앱의 `aurora-dynamodb-cache.elasticache`와 `dax-dynamodb-only`에 있다.
- **Q256 p177**·**Q260 p180** — 비용 할당 태그는 활성화해야 보고서에 나타난다.

- **Q261 p180**·**Q292 p201** — 최소 권한을 지키는 IAM 역할과 인스턴스 프로파일, 장기 액세스
