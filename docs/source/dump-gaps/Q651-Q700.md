## serverless-containers

### `eks-compute-options` — EKS의 컴퓨팅은 세 갈래이고 관리 책임이 다르다

**한 줄**: 자체 관리형 노드 · 관리형 노드 그룹 · Fargate 순으로 사용자가 지는 인프라 책임이 줄고, Fargate만 EC2 인스턴스를 아예 다루지 않는다.

앱의 `serverless-containers.eks`는 쿠버네티스를 관리형으로 운영하는 서비스라는 데까지
말하고, `Q501-Q550.md`의 `eks-fargate-pod-isolation`은 Fargate로 돌린 파드가 실행 환경을
나눠 쓰지 않는다는 것을 다룬다. 남는 축이 **파드를 무엇 위에서 돌리는가**다. 문항은 이
축을 정면으로 묻는다 — "기본 컴퓨팅 인프라를 직접 관리하고 싶지 않다"가 조건이고,
보기 네 개가 자체 관리형 노드 · 관리형 노드 그룹 · Fargate · Karpenter를 붙인 관리형
노드 그룹으로 갈린다.

자체 관리형 노드는 EC2 인스턴스를 사용자가 직접 띄우고 관리한다. 관리형 노드 그룹은
노드를 만들고 교체하는 일을 EKS가 거들지만, **EC2 인스턴스의 패치와 관리 책임은 여전히
사용자에게 남는다.** Karpenter를 얹어도 조정이 자동화될 뿐 인스턴스를 관리해야 한다는
사실은 그대로다. Fargate만 인스턴스도 클러스터 용량도 프로비저닝하지 않는다 — 파드를
정의해 배포하면 필요한 컴퓨팅을 Fargate가 알아서 띄운다. 어떤 파드를 Fargate에서 돌릴지는
**Fargate 프로필**로 지정한다.

그래서 "관리형"이라는 말이 보기에 들어 있다고 인프라 관리가 사라지는 것이 아니다.
운영 부담을 최소화하라는 조건에서 관리형 노드 그룹과 Fargate가 함께 올라오면 Fargate가 답이다.

> [Q652 p440] "관리형 노드 그룹은 일부 오버헤드를 줄여주지만, EC2 인스턴스의 패치 적용 및 관리 책임은 여전히 사용자에게 있습니다."

### `app2container` — AWS App2Container

**한 줄**: 온프레미스나 가상 머신에서 돌던 기존 Java·.NET 애플리케이션을 코드를 거의 고치지 않고 컨테이너로 만들어 주는 명령줄 도구다.

`Q351-Q400.md`의 `elastic-beanstalk`이 코드를 올리면 실행 환경을 대신 꾸려 주는 쪽이라면,
이쪽은 **이미 돌고 있는 애플리케이션을 컨테이너 이미지로 바꾸는** 쪽이다. 모놀리식
애플리케이션을 AWS로 옮기면서 컨테이너로 전환하라는 문항에서, 애플리케이션을 다시 짜는
선택지와 나란히 올라온다.

App2Container는 대상 애플리케이션을 분석해 컨테이너 이미지와 배포에 필요한 산출물을
만들어 낸다. 최소한의 리팩터링만으로 끝나므로 "운영 부담을 최소화하면서 컨테이너로
옮겨라"라는 조건에 맞는다. 옮긴 컨테이너는 ECS나 EKS에 올리고, 함께 쓰던 관계형
데이터베이스는 같은 엔진의 관리형 서비스로 옮기는 것이 문항의 표준 짝이다 — SQL Server면
RDS for SQL Server이고, 프런트엔드를 S3로 옮기거나 데이터 계층을 DynamoDB로 바꾸는
선택지는 애플리케이션을 다시 설계하라는 말이라 "최소 변경"과 어긋난다.

> [Q658 p445] "AWS App2Container는 온프레미스 또는 가상 머신에서 실행 중인 기존 Java 및 .NET 애플리케이션을 최소한의 리팩토링으로 컨테이너화하는 데 도움을 주는 명령줄 도구입니다."

### `step-functions-map-state` — Map 상태로 목록의 항목마다 한 번씩 실행한다

**한 줄**: 목록을 받아 항목마다 같은 작업을 한 번씩 돌리는 상태이며, 함수 안의 반복문을 밖으로 꺼내 타임아웃을 없앤다.

앱의 `serverless-containers.step-functions`와 `messaging-backup.step-functions-features`는
단계를 잇고 재시도와 수동 승인을 넣는다는 것을 다루고, `Q301-Q350.md`의
`step-functions-long-running-workflow`는 실행 시간 한도를 다룬다. 이 개념이 더하는 것은
**반복**이다.

Lambda 함수 하나가 목록을 돌며 다른 함수를 여러 번 부르는 구조는 항목 수가 늘면 15분
제한에 걸린다. Map 상태를 쓰면 그 반복을 상태 머신이 맡아 항목마다 함수를 한 번씩
호출하고, 병렬로 돌리거나 배치 단위로 나눠 돌릴 수 있다. 핵심은 **기존 함수를 고치지
않는다**는 것이다 — 반복문을 밖으로 옮기는 것이라 함수 코드는 그대로 둔 채 확장된다.
그래서 "함수를 수정하지 않고 타임아웃을 피하라"가 조건이면 호출 주기를 바꾸는 스케줄러나
실행 환경을 EC2로 옮기는 선택지가 아니라 이쪽이 답이다.

> [Q662 p447] "AWS Step Functions는 Lambda 코드를 수정하지 않고도 Lambda 실행을 조정할 수 있으며, Map 상태는 목록의 각 항목에 대해 Lambda 함수를 한 번씩 실행하도록 설계되어 있어 많은 장치를 병렬로 또는 제어된 배치 단위로 활성화하는 데 적합합니다."

### `ecr-image-scan-on-push` — Amazon ECR과 푸시 시 스캔

**한 줄**: ECR은 컨테이너 이미지를 두는 프라이빗 레지스트리이고, '푸시 시 스캔'을 켜면 올라오는 이미지마다 알려진 취약점(CVE) 검사가 자동으로 돈다.

앱은 컨테이너를 `serverless-containers.ecs`·`eks`로 다루지만 **이미지를 어디에 두는지는
말하지 않는다.** ECR이 그 자리다. ECS 태스크 정의는 보통 이미 ECR 이미지를 참조하고
있으므로, 스캔을 켜는 데 오케스트레이션 쪽을 손댈 필요가 없다.

기본 스캔의 '푸시 시 스캔' 설정을 켜면 리포지토리에 올라오는 새 이미지가 전부 CVE 대상으로
검사된다. 결과는 AWS가 관리해 한곳에서 본다. "이미 도는 워크로드를 최소한으로 바꾸면서
컨테이너 이미지를 스캔하라"가 조건이면, 이미지를 S3에 두고 다른 서비스로 검사하는 선택지나
EKS로 옮기는 선택지가 아니라 이쪽이 답이다. Macie는 S3의 민감 데이터를 찾는 서비스라
컨테이너 이미지 취약점 스캔의 자리가 아니다.

`Q151-Q200.md`가 이 사실을 `Q166`의 `[AI 작성 해설]` 하나에서만 보고 "뒤 슬라이스에서 같은
사실이 원본 해설로 확인되면 그때 만든다"고 미뤄 두었다. **Q691이 원본 해설로 같은 사실을
말하므로 여기서 만든다.**

> [Q691 p465] "ECR은 '업로드 시 스캔(scan on push)'을 사용하여 활성화할 수 있는 내장형 취약점 스캔 기능을 제공하므로, 리포지토리에 업로드되는 모든 새 이미지가 알려진 CVE에 대해 자동으로 스캔됩니다."

## compute-delivery

### `cloudfront-alb-origin-access-restriction` — ALB 오리진은 보안 그룹으로 CloudFront만 들이게 한다

**한 줄**: 오리진이 ALB일 때 CloudFront를 거치지 않은 직접 접근을 막는 표준 방식은 CloudFront 엣지 IP 범위만 허용하는 보안 그룹을 ALB에 붙이는 것이다.

`Q101-Q150.md`의 `cloudfront-alb-origin`은 ALB도 오리진이 될 수 있다는 데까지 다루고,
`Q451-Q500.md`의 `cloudfront-s3-upload-with-oac`는 오리진이 **S3일 때** 접근을 CloudFront로
좁히는 방법(OAC)을 다룬다. 남는 자리가 **오리진이 ALB일 때 같은 일을 어떻게 하는가**다.
ALB는 인터넷에 열려 있으므로 배포 주소를 우회해 ALB 이름으로 바로 들어오는 경로가 남는다.

이 경로를 닫는 표준 방식은 ALB에 붙인 보안 그룹이 CloudFront 엣지의 공용 IP 범위에서 오는
인바운드만 허용하게 하는 것이다. ALB 리스너 규칙으로 같은 조건을 거는 방법도 있다.
네트워크 ACL로 같은 일을 하려는 선택지는 정밀도가 떨어지고 상태를 기억하지 않아 운영
부담이 커진다 — 앱의 `security-groups-nacl.security-group`·`nacl`이 가르는 두 계층의 차이가
여기서 그대로 판단 기준이 된다.

> [Q656 p443] "ALB 오리진의 경우, 보안 그룹이나 ALB 리스너 규칙을 사용하여 CloudFront 엣지 IP 범위에서만 ALB로의 인바운드 트래픽을 허용하는 것이 표준 방식입니다."

## threat-protection

### `waf-rate-based-rule` — WAF 속도 기반 규칙

**한 줄**: 정해 둔 요청 임계값을 넘긴 IP 주소를 자동으로 차단하는 규칙이라, 같은 곳에서 쏟아지는 요청을 사람이 목록을 갱신하지 않아도 걸러낸다.

앱의 `threat-protection.waf-rule-types`는 WAF 규칙을 IP 세트·지리적 일치·IP 평판으로
나누고, `Q051-Q100.md`의 `waf-managed-rule-groups`는 규칙을 누가 쓰느냐를 가른다.
셋 다 **어떤 요청인가**를 보는 규칙이다. 속도 기반 규칙은 축이 다르다 — 요청의 내용이
아니라 **한 IP에서 오는 빈도**를 본다.

특정 IP에서 원치 않는 요청이 높은 빈도로 들어오는 상황에서, 임계값을 넘긴 IP를 자동으로
막는 것이 이 규칙이다. 목록을 손으로 관리하는 IP 세트나 네트워크 ACL과 달리 대상이
바뀌어도 따라간다. CloudFront가 앞에 있으면 배포에 WAF를 붙여 **악성 요청이 ALB와 EC2에
닿기 전에** 엣지에서 끊는다. Shield는 이런 세분화된 속도 제어를 주지 않고, Auto Scaling으로
용량을 늘리는 것은 비용만 늘릴 뿐 요청을 막지 못한다.

> [Q654 p442] "속도 기반 규칙은 정의된 요청 임계값을 초과하는 IP 주소를 자동으로 차단하므로, 악의적인 트래픽 패턴을 완화하는 데 이상적입니다."

### `shield-advanced-protection-group` — Shield Advanced 보호 그룹

**한 줄**: 보호 대상 리소스를 묶어 한 단위로 다루는 그룹이고, 그룹에 리소스를 넣으면 개별 설정 없이 같은 보호를 받는다.

앱의 `threat-protection.shield`와 `shield-advanced-drt`는 Shield가 DDoS를 막는다는 것과
Advanced가 대응팀 지원을 준다는 것을 다룬다. 이 개념이 더하는 것은 **보호 대상을 묶는
단위**다.

Shield Advanced는 보호 그룹에 여러 리소스를 넣고, 그룹 전체의 트래픽 양을 어떻게 합칠지
집계 유형을 고르게 한다. 블루/그린 배포처럼 같은 역할의 리소스를 새로 띄워 트래픽을
옮기는 상황에서, 새 리소스를 **기존 보호 그룹에 넣기만 하면** 보호가 그대로 이어진다.
그룹을 새로 만들면 보호가 두 덩어리로 갈려 통합된 판단을 받지 못하므로, 이미 있는 그룹에
더하는 쪽이 답이다.

> [Q657 p444] "AWS Shield Advanced를 사용하면 보호 그룹에 여러 보호 리소스(예: ALB)를 추가하고, 완화 및 청구에 사용할 집계 유형을 선택할 수 있습니다."

## secrets-encryption

### `secrets-manager-batch-get-secret-value` — 여러 비밀값을 한 번의 호출로 가져온다

**한 줄**: `BatchGetSecretValue` API가 여러 시크릿을 한 번에 돌려주므로, 값마다 호출을 반복하는 코드를 짜지 않아도 된다.

앱의 `secrets-encryption.secrets-manager`와 `secrets-manager-vs-parameter-store`는 무엇을
어디에 보관하는지를 가른다. 문항이 한 겹 더 얹는 조건은 **여러 사람의 자격 증명을 한꺼번에
읽어 와야 한다**는 것이고, 이 조건 때문에 보기 줄에 값을 하나씩 읽는 구성과 배치 처리
서비스를 끼워 넣는 구성이 함께 오른다.

Secrets Manager에는 시크릿 여러 개를 한 번의 호출로 가져오는 API가 있다. 이름이 `Batch`로
시작하지만 **AWS Batch와는 무관하다** — 배치 처리 서비스를 끼우는 선택지는 이 이름을 노린
함정이다. 값을 가져오는 일에 컴퓨팅 계층을 하나 더 둘 이유가 없다. 사용자 이름과 비밀번호를
보관하는 자리도 Parameter Store가 아니라 Secrets Manager다.

> [Q664 p448] "BatchGetSecretValue API에 대한 AWS 문서에 따르면, Secrets Manager는 단일 호출로 여러 시크릿을 검색할 수 있도록 지원하며, 이는 여러 직원의 자격 증명을 처리해야 하는 요구 사항에 부합합니다."

## aurora-dynamodb-cache

### `dynamodb-streams-batch-size` — 스트림 소비의 배치 크기를 조정한다

**한 줄**: 스트림을 받는 쪽의 배치 크기를 항목 크기에 맞춰 키우면 한 번의 호출이 더 많은 레코드를 처리해 밀림이 줄어든다.

`Q151-Q200.md`의 `dynamodb-streams`와 `Q251-Q300.md`의 `lambda-kinesis-event-source`는
스트림의 레코드가 Lambda로 흘러간다는 경로까지 다룬다. 그 경로가 성수기에 밀릴 때 손댈
곳이 어디인지는 다루지 않는다.

배치 크기는 함수 한 번의 호출이 받는 레코드 수다. 항목 크기에 맞춰 이 값을 정하면 호출
횟수가 줄고 한 번에 처리하는 양이 늘어 지연이 줄어든다. 함께 봐야 할 것이 **어느 테이블의
용량이 모자란가**다. 변경을 흘려보내는 원본 테이블이 아니라 **갱신을 받는 대상 테이블**의
쓰기 용량이 병목이므로, 늘려야 할 것은 대상 테이블의 쓰기 용량 단위다. 원본 테이블의 읽기
용량을 늘리거나 보조 인덱스를 더하는 선택지는 밀림의 자리와 무관하고, 함수 타임아웃을
늘리는 것은 한 번의 호출이 오래 걸려도 되게 할 뿐 처리량을 늘리지 못한다.

> [Q665 p449] "배치 크기 최적화는 지연 시간을 줄이고 Lambda 함수가 한 번에 더 많은 양의 데이터를 처리할 수 있게 하여, 피크 부하 시 성능을 향상시킵니다."

### `dynamodb-streams-retention-24h` — 스트림은 24시간만 보존한다

**한 줄**: DynamoDB Streams의 레코드 보존 기간은 24시간이라, 며칠치 기록을 남겨야 하는 요구를 스트림으로 대신할 수 없다.

앱의 `aurora-dynamodb-cache.dynamodb-pitr`가 특정 시점 복구의 한계를 35일로 못 박았듯이,
스트림에도 한도가 있다. 문항은 "감사 기록을 7일 동안 보관해야 한다"는 조건으로 이 한도를
정확히 노린다.

스트림은 변경을 흘려보내는 통로이지 기록을 쌓아 두는 곳이 아니다. 24시간이 지난 레코드는
사라지므로, 7일치 감사 기록을 요구하는 자리에서 DynamoDB와 스트림을 묶은 선택지는
그것만으로 지워진다. 함께 붙은 온디맨드 백업도 마찬가지다 — 사람이 자주 걸어 주지 않는
한 복구 지점 목표(RPO)를 몇 시간 안으로 보장하지 못한다.

> [Q666 p449] "또한 Streams는 7일이 아닌 24시간만 보존하며, 온디맨드 백업은 빈번한 스케줄링 없이는 본질적으로 5시간 미만의 RPO를 보장하지 않습니다."

### `aurora-continuous-backup-rpo` — Aurora의 지속적 증분 백업이 RPO를 좁힌다

**한 줄**: Aurora는 변경을 S3로 계속 증분 백업해 보존 기간 안의 어느 시점으로든 되돌릴 수 있으므로, 몇 시간짜리 RPO 요구를 스냅샷 주기 없이 충족한다.

`Q601-Q650.md`의 `rds-pitr-transaction-log-interval`은 RDS의 특정 시점 복구가 5분 단위라는
것을 다뤘다. Aurora 쪽은 백업이 도는 방식 자체가 다르다.

Aurora는 스냅샷을 주기적으로 뜨는 대신 변경을 **끊이지 않고 S3에 증분으로 쌓는다.** 그래서
보존 기간(최대 35일) 안이라면 임의의 시점으로 복구할 수 있고, 복구 지점 목표는 몇 초 수준까지
좁혀진다. "RPO가 5시간 미만이어야 한다"가 조건일 때, 5시간마다 스냅샷을 뜨는 구성은 마지막
스냅샷 이후의 변경을 잃을 수 있어 **최대 5시간**이 되지 5시간 미만이 되지 않는다.
스냅샷 주기를 조건보다 짧게 잡는 선택지가 나란히 오르는 이유가 이것이고, 지속적 백업 쪽이
그 계산 자체를 없앤다.

> [Q666 p449] "특정 시점 복구(PITR) 기능을 갖춘 Amazon S3로의 지속적인 증분 백업을 제공하여, 보존 기간(일반적으로 최대 35일) 내의 어느 시점으로든 복구할 수 있습니다."

### `aurora-serverless-max-acu` — 용량 상한은 ACU로 정한다

**한 줄**: Aurora Serverless의 용량 단위는 ACU이고, 최대 ACU를 급증을 받을 만큼 높게 잡아 두면 그 범위 안에서 알아서 오르내린다.

앱의 `aurora-dynamodb-cache.aurora-serverless-v2`는 용량이 1초 단위로 자동 조정된다는
데까지 말한다. 문항이 묻는 것은 **그 범위를 무엇으로 정하는가**이고, 답이 Aurora 용량
단위(ACU)다.

평소 트래픽이 적다가 가끔 급증하며 그때 데이터베이스에 쓰기 부하가 몰리는 상황에서,
웹 계층만 늘리는 구성은 오히려 동시 쓰기를 늘려 상황을 악화시킨다. 최대 ACU를 급증에
맞춰 올려 둔 Aurora Serverless는 고정 크기 인스턴스보다 이 모양의 부하를 매끄럽게 받는다.
**애플리케이션 코드를 고칠 수 없다**는 조건이 함께 붙어도 이쪽이 남는다 — 엔진이 호환되므로
연결 대상을 새 엔드포인트로 바꾸는 것은 인프라 설정 변경이지 코드 재작성이 아니다.
`Q601-Q650.md`의 `cache-requires-application-change`가 캐시를 끼우는 선택지를 같은 조건에서
지우는 것과 짝이 되는 판단이다.

> [Q682 p460] "적절한 최대 용량을 설정함으로써, Aurora Serverless는 고정 크기의 RDS 인스턴스보다 더 원활하게 트래픽 급증을 처리할 수 있어 예측 불가능한 수요 발생 시 가용성을 향상시킵니다."

## block-file-storage

### `fsx-ontap-multi-protocol-tiering` — ONTAP은 NFS와 SMB를 함께 받고 계층을 자동으로 나눈다

**한 줄**: FSx for NetApp ONTAP은 한 파일 시스템을 NFS와 SMB 양쪽으로 열어 주고, 접근 빈도에 따라 SSD와 용량 풀 사이로 데이터를 자동으로 옮긴다.

앱의 `block-file-storage.efs`는 NFS만, `Q101-Q150.md`의 `fsx-windows-file-server`는 SMB만
맡는다. 그래서 **Windows·Mac·Linux가 같은 데이터를 SMB와 NFS로 함께 써야 한다**는 조건이
나오면 둘 중 어느 쪽도 답이 되지 못한다. 앱의 `fsx-ontap-multi-az`와 `Q151-Q200.md`의
`fsx-ontap-snapmirror`, `Q201-Q250.md`의 `fsx-ontap-iscsi-block`이 ONTAP의 다른 면을
다루지만 프로토콜 축은 비어 있다.

ONTAP은 두 프로토콜을 모두 지원한다. 여기에 **자동 계층화**가 붙는다 — 자주 쓰는 데이터는
SSD에 두고 뜸해진 데이터는 값이 싼 용량 풀로 내려보낸다. "일부는 정기적으로, 나머지는
드물게 접근한다"는 조건이 프로토콜 조건과 함께 오면 이 둘이 한 서비스에서 풀린다.
S3 계열로 옮기는 선택지는 파일 프로토콜 요구를 채우지 못하고, 게이트웨이를 세우는 구성은
같은 리전 안에서 도는 인스턴스에 굳이 계층을 하나 더 얹는 일이다.

> [Q689 p464] "Amazon FSx for ONTAP은 NFS 및 SMB 프로토콜을 모두 지원하며, SSD와 용량 풀 스토리지 간의 자동 계층화를 포함하여 비용과 성능을 최적화합니다."

## data-transfer-services

### `datasync-manifest` — 매니페스트로 전송 대상을 좁힌다

**한 줄**: 옮길 객체 이름을 적은 매니페스트 파일을 주면 DataSync가 그 목록에 있는 것만 전송한다.

앱의 `data-transfer-services.datasync`는 대량 전송에 쓴다고만 말하고, `Q151-Q200.md`의
`datasync-scope-limits`는 이 서비스가 맡지 않는 일을 가른다. 문항이 묻는 것은
**옮길 대상을 어떻게 고르는가**다.

원본 전체를 주기적으로 통째로 옮기던 구성에서 "필요한 데이터만 옮기고 나머지는 무시하라"는
요구가 붙으면, 데이터를 만드는 쪽이 대상 목록을 매니페스트 파일로 만들어 두고 DataSync
작업이 그 파일을 참조하게 한다. 목록에 없는 파일은 전송하지 않으므로 불필요한 전송량과
그에 딸린 비용이 함께 줄어든다.

여기에 **언제 도는가**가 붙는다. 정해진 주기를 기다리지 않고 가능한 한 빨리 옮기라는
조건이면, 매니페스트가 S3에 올라오는 것을 이벤트 알림으로 잡아 `StartTaskExecution`
API로 작업을 그 자리에서 실행시킨다. 매니페스트를 DynamoDB에 적재하는 구성은 같은 일을
하는 데 저장소를 하나 더 끼우는 것이라 자리가 아니다.

> [Q699 p470] "매니페스트를 사용하면 AWS DataSync가 지정된 파일만 전송하므로 불필요한 데이터 전송과 관련 비용을 줄일 수 있습니다."

### `datasync-task-status-event` — 작업 실행 상태는 EventBridge 이벤트로 나온다

**한 줄**: DataSync 작업 실행의 상태가 SUCCESS나 ERROR로 바뀌면 EventBridge가 그 변화를 이벤트로 받아 알림으로 이을 수 있다.

전송이 끝났는지 알아야 한다는 요구에 대해, 상태를 주기적으로 물어보는 함수를 따로 만드는
선택지와 상태 변화를 이벤트로 받는 선택지가 함께 오른다. DataSync는 작업 실행의 상태
변화를 이벤트로 내보내므로, 규칙 하나로 SNS 주제에 이어 이메일까지 보낼 수 있다.

`Q551-Q600.md`의 `cloudwatch-alarm-state-change-event`가 경보의 상태 변화를 이벤트로 받는
것과 같은 모양이다. 상태를 확인하는 Lambda 함수를 새로 만드는 구성은 관리할 코드를 늘릴 뿐
같은 결과를 준다 — 이벤트를 이미 내보내는 서비스에 폴링 계층을 얹지 않는다.

> [Q699 p470] "그런 다음 DataSync 태스크의 실행 상태를 모니터링하고 상태가 SUCCESS 또는 ERROR로 변경될 때 해당 SNS 토픽으로 이메일 알림을 전송하는 Amazon EventBridge 규칙을 설정합니다."

## cost-management

### `rds-reserved-instance` — 예약 인스턴스는 RDS에도 있다

**한 줄**: RDS 인스턴스도 예약해 두면 온디맨드보다 싸므로, 관리형 데이터베이스를 오래 돌린다는 조건에서는 이쪽이 비용 최적해다.

`Q001-Q050.md`의 `reserved-instance-types`는 예약 인스턴스를 표준과 전환 가능으로 가르지만
대상이 EC2다. 앱의 `cost-management.savings-plan`과 `savings-plan-details`가 다루는 컴퓨팅
절약 플랜도 EC2·Fargate·Lambda가 적용 범위다. **관계형 데이터베이스에도 같은 약정 할인이
있다**는 것은 어디에도 없다.

여러 해 동안 돌릴 관리형 MySQL을 가장 싸게 두라는 조건이면, 관리형이 아닌 EC2 자체 설치는
운영 부담 때문에, Aurora 클러스터는 필요 이상의 구성 때문에 지워지고, 남는 두 선택지가
같은 RDS를 온디맨드로 쓰느냐 예약하느냐로 갈린다. 기간이 길고 사용이 꾸준하면 예약 쪽이다.

> [Q669 p451] "Amazon RDS for MySQL 예약 인스턴스는 데이터베이스를 장기간 운영할 계획일 때 온디맨드 요금 대비 상당한 비용 절감 효과를 제공합니다."

## 원본 수정 이력

덤프를 그대로 따르지 않은 항목이다. 근거는 ADR-008의 예외를 승계한 ADR-021.

### 사실 오류라 싣지 않은 것

- **Q651 p440 — VPC 피어링으로 다른 계정의 S3 버킷에 닿는다는 서술.** 덤프 원문:
  "E: 비공개 라우팅을 허용하기 위해 네트워킹 VPC를 S3 버킷을 호스팅하는 계정의 VPC와
  피어링합니다." `Q401-Q450.md`가 `Q416`에서 같은 서술을 이미 사실 오류로 남겼고, 이유도
  같다 — 앱의 `vpc-networking.s3-is-regional`대로 S3는 리전 수준 서비스라 VPC 안에 있지
  않으므로 VPC끼리 잇는 피어링으로는 버킷에 닿는 경로가 만들어지지 않는다. 다른 계정의
  버킷을 쓰게 하는 것은 `Q051-Q100.md`의 `s3-cross-account-bucket-policy`가 다루는 버킷
  정책이다. 이 문항에서 새로 만들 개념은 없다 — 프라이빗 VIF 쪽 사실은 `Q101-Q150.md`의
  `direct-connect-vif-types`에 이미 있다.
- **Q656 p443 — CloudFront에 VPC 오리진이 없다는 서술.** 덤프 원문: "CloudFront에는 "VPC
  오리진" 객체가 없으며, 대신 CloudFront는 ALB DNS 이름을 참조합니다." CloudFront에는
  VPC 오리진이라는 기능이 실제로 있으므로 이 문장은 옮기지 않았다. 위
  `cloudfront-alb-origin-access-restriction`은 해설이 "표준 방식"으로 든 보안 그룹 쪽 사실만
  실었고, 없는 기능이라는 서술은 빼 두었다. 문항의 정답 근거는 보안 그룹으로 CloudFront
  IP 범위만 허용한다는 쪽이므로 그것만으로 선택지가 갈린다.
- **Q680 p459 — Step Functions에 TestState API와 데이터 흐름 시뮬레이터가 없다는 서술.**
  덤프 원문: "옵션 A 및 B: TestState API는 Step Functions에서 유효한 옵션이 아닙니다."
  Step Functions에는 상태 하나를 따로 실행해 보는 `TestState` API가 있고, 검사 수준을
  올리면 HTTP 태스크의 요청·응답을 그대로 돌려준다. 없는 기능이라는 전제 위에서 정답이
  정해진 문항이라 **이 문항에서는 개념을 만들지 않았다.** 해설이 고른 "로그 수준을 ALL로
  올려 요청·응답을 남긴다"도 함께 옮기지 않았다 — 정답 자체가 갈리는 자리에서 그 근거만
  떼어 실으면 잘못된 선택을 가르치게 된다.

### [AI 작성 해설]이라 채택하지 않은 것

해설집이 문서 2쪽에서 "원본에 해설이 없던 21개 문제는 새로 작성했다"고 밝힌 표시다.
**이 슬라이스에는 해당 문항이 없다.**

한편 `Q151-Q200.md`가 `Q166`의 `[AI 작성 해설]`에서 본 ECR '푸시 시 스캔'을 교차 확인이
안 된다는 이유로 미뤄 두었는데, 이 슬라이스의 **Q691이 원본 해설로 같은 사실을 말한다.**
그래서 위 `ecr-image-scan-on-push`를 여기서 만들었다.

### 중복이라 새로 만들지 않은 것

정답 근거이지만 앱이나 앞 step에 이미 있어 항목으로 만들지 않은 것이다.

- **Q653 p441** — 계층마다 보안 그룹을 두고 소스로 앞 계층의 보안 그룹을 지정하며, 보안
  그룹은 상태를 기억하므로 반환 트래픽에 아웃바운드 규칙이 필요 없다. 앱의
  `security-groups-nacl.security-group-referencing`과 `Q301-Q350.md`의
  `security-group-stateful-vs-nacl-stateless`에 있다.
- **Q655 p442** — 자격 증명을 주기적으로 자동 교체해야 하면 Secrets Manager이고 RDS와
  기본 통합된다. 앱의 `secrets-encryption.rotation-heuristic`·`secrets-manager`에 있다.
- **Q659 p445** — 온프레미스 NFS 출력을 그대로 받아 S3로 올리는 것은 S3 파일 게이트웨이이고,
