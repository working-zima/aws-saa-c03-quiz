## aws-core-services

### `exam-heuristics` — 시험에서 자주 통하는 판단 기준

**한 줄**: 덤프 해설이 반복해서 명시한, 선택지를 지우는 데 쓰는 판단 기준이다.

선택지에 '수동으로', '직접 스크립트를 짜서', '매번 담당자가' 같은 표현이 들어가면
대부분 오답이다. AWS가 이미 관리형 기능으로 제공하는 일을 사람이 하겠다는 뜻이기 때문이다.

사용자가 급격히 늘고, 이미지·파일 처리가 끼어 있고, 운영 비용을 최소화하라는 조건이
함께 나오면 서버리스(Lambda + S3 + DynamoDB) 조합이 정답인 경우가 많다.

> [S3 #3 p6] "문제에서 '수동으로 무언가를 처리한다'는 내용이 나오면 대부분 오답인 경우가 많다."
> [데이터베이스 #36 p75] "수동으로 무언가를 하는 건 비효율적이어서 시험에서는 대부분 오답이다."
> [비용관리 #163 p339] "'급격한 사용자 증가'와 '이미지 처리', '운영 비용 최소화'라는 키워드에는 서버리스가 정답인 경우가 많다."

## s3-versioning-lifecycle

### `object-lock-prerequisites` — 객체 잠금의 전제 조건과 MFA 삭제의 한계

**한 줄**: 객체 잠금은 버전 관리가 켜져 있어야만 쓸 수 있고, MFA 삭제로는 루트 사용자를 막지 못한다.

S3 객체 잠금은 버전 관리가 활성화된 버킷에서만 동작한다. "버전 관리를 끄고 객체 잠금을 건다"는
구성 자체가 성립하지 않는다.

버전 관리 + MFA 삭제 조합은 삭제를 어렵게 만들 뿐이다. 루트 사용자가 MFA 인증을 거치면
삭제할 수 있으므로, "루트 사용자조차 삭제할 수 없어야 한다"는 요구에는 객체 잠금의
규정 준수 모드만 답이 된다.

> [S3 #8 p16] "S3 객체 잠금(Object Lock)은 버전 관리가 활성화된 상태에서만 사용 가능하다."
> [S3 #12 p24] "버전 관리 기능과 MFA 삭제 기능을 활용하면 삭제를 어렵게 만들지만, 루트 사용자가 MFA를 인증하면 삭제할 수 있으므로"

### `event-notification` — S3 이벤트 알림

**한 줄**: 객체가 새로 생성될 때 다른 서비스를 자동으로 호출해주는 기능이다.

파일이 업로드되는 즉시 Lambda 등을 트리거해야 할 때 쓴다. 주기적으로 확인하는
폴링 방식보다 지연이 없다.

주의할 점은 **새로 생성되는 객체에만** 이벤트가 발생한다는 것이다. 이미 버킷에 쌓여 있던
기존 객체에는 이벤트가 발생하지 않으므로, 과거 데이터를 처리하는 용도로는 쓸 수 없다.

> [S3 #6 p12] "S3 Event Notification은 새로 생성되는 객체에만 이벤트가 발생한다. '3년간 쌓인 기존 데이터'는 이벤트가 트리거되지 않아 Lambda가 실행되지 않는다."
> [컴퓨팅3 #86 p178] "파일이 업로드되는 '즉시' 처리를 시작해야 하므로, 폴링 방식이 아닌 이벤트 트리거 방식이 적합하다."

## s3-encryption-batch

### `envelope-encryption` — 봉투 암호화 (Envelope Encryption)

**한 줄**: 데이터를 데이터 키로 암호화하고, 그 데이터 키를 다시 마스터 키로 암호화하는 방식이다.

문제에 "봉투 암호화를 사용해야 한다"는 조건이 나오면 KMS를 쓰는 SSE-KMS를 가리킨다.
여기에 "암호화 키가 주기적으로 자동 교체되어야 한다"는 조건이 붙으면 더 확실해진다.
SSE-S3와 SSE-C에는 자동 순환 기능이 없기 때문이다.

> [S3 #9 p18] "SSE-KMS는 AWS KMS 서비스를 활용해서 서버 측 암호화를 진행한 방식이다. 키를 주기적으로 자동 교체해주는 자동 순환(Rotation) 기능을 제공한다."

### `sse-kms-cost` — SSE-KMS의 비용 구조와 S3 Bucket Key

**한 줄**: SSE-KMS는 객체 하나당 KMS API를 호출하므로, 객체 수가 많으면 KMS 호출 비용이 급증한다.

객체를 암호화할 때마다 KMS API를 부르는 구조라, 초당 수백만 건이 쌓이는 워크로드에서는
KMS 호출 비용이 전체 청구서의 상당 부분을 차지하게 된다.

S3 Bucket Key를 켜면 버킷 단위의 데이터 키를 캐싱해 재사용하므로 KMS API 호출 수가 크게 줄어든다.
암호화 방식은 여전히 SSE-KMS이므로 보안 수준은 그대로다. KMS 키 자동 순환을 끄거나
데이터를 압축하는 것은 이 비용과 무관하다.

> [S3 #13 p26] "SSE-KMS 방식은 객체 하나당 KMS API 호출을 해야 하는 방식이라 데이터의 양이 많을 수록 비용이 급격하게 증가한다. S3 버킷 키를 활용하면 객체마다 KMS API를 호출하지 않고, 버킷 단위의 데이터 키를 캐싱해서 재사용할 수 있게 된다."

## block-file-storage

### `cluster-placement-group` — 클러스터 배치 그룹

**한 줄**: EC2 인스턴스를 물리적으로 최대한 밀집 배치해 낮은 네트워크 지연과 높은 처리량을 얻는 방식이다.

수천 개 노드가 동시에 데이터를 읽고 쓰는 HPC(고성능 컴퓨팅) 워크로드에서
FSx for Lustre 같은 고성능 스토리지와 짝을 이뤄 등장한다.

> [스토리지 #15 p31] "클러스터 배치 그룹은 EC2 인스턴스를 최대한 밀집 배치하여 낮은 네트워크 지연과 높은 처리량을 제공하는 방식을 의미한다."

### `ebs-elastic-volumes` — EBS Elastic Volumes

**한 줄**: EC2에 연결된 상태 그대로 EBS 볼륨 크기를 늘릴 수 있는 기능이다.

볼륨을 떼었다 붙이거나 새 볼륨을 추가하지 않아도 되므로 운영 중단이 발생하지 않는다.
파일 시스템 확장 작업까지 Lambda로 자동화하면 스토리지 확장을 무중단으로 처리할 수 있다.

EBS를 EFS로 옮기거나 새 EBS를 연결하는 방식은 중단이 생긴다.

> [스토리지 #19 p39] "EBS Elastic 볼륨은 EC2에 연결된 상태에서도 볼륨 크기를 확장할 수 있다."

### `efs-lifecycle-management` — EFS 수명 주기 관리

**한 줄**: 일정 기간 접근이 없는 파일을 자동으로 EFS IA 클래스로 옮겨 비용을 줄이는 기능이다.

EFS가 파일의 액세스 패턴을 감지해서 자동으로 옮긴다. EFS IA로 이동한 파일도
밀리초 단위 지연으로 즉시 액세스할 수 있으므로, "오래된 데이터도 필요할 때는 즉시
써야 한다"는 조건과 충돌하지 않는다.

같은 상황에서 S3 Glacier Deep Archive로 옮기는 선택지는 즉시 액세스가 불가능해 오답이 된다.

> [스토리지 #20 p41] "EFS 수명 주기 관리는 파일의 액세스 패턴을 감지하여 일정 기간 동안 접근이 없는 파일을 자동으로 더 저렴한 EFS IA 스토리지 클래스로 이동시켜 준다."
> [스토리지 #22 p45] "IA 클래스에 있는 파일도 밀리초 단위의 지연 시간으로 즉시 액세스할 수 있다."

### `fsx-ontap-multi-az` — FSx for NetApp ONTAP의 다중 AZ 배포

**한 줄**: FSx 유형 중 ONTAP은 다중 AZ 배포가 가능하고, 밀리초 미만 응답이 필요한 공유 스토리지에 쓴다.

여러 AZ에 분산된 서버들이 공유 데이터에 밀리초 미만으로 동시 접근해야 하는 상황에서,
EBS는 다중 AZ를 지원하지 않고 EFS와 S3는 고성능 스토리지가 아니라서 답이 되지 못한다.
남는 선택지가 FSx for NetApp ONTAP이다.

> [스토리지 #17 p35] "FSx for NetApp ONTAP은 다중 AZ 배포가 가능하며, 고성능 파일 시스템이기 때문에 밀리초 미만의 속도로 액세스하는 용도로 사용하기에 적합하다."

## rds-storage-features

### `storage-type-names` — RDS 스토리지 유형의 실제 이름

**한 줄**: 범용 SSD는 gp2·gp3, 프로비저닝된 IOPS SSD는 io1·io2로 표기된다.

문제와 선택지에는 서술형 이름 대신 이 약칭이 그대로 나온다.
쓰기 작업량이 급격히 치솟는 워크로드에서 지연 시간을 보장해야 하면
IOPS를 직접 지정할 수 있는 io1/io2를 고른다.

> [데이터베이스 #30 p63] "프로비저닝된 IOPS (io1/io2)는 일관되고 빠른 성능을 보장하기 위해 설계된 스토리지 유형이다."

### `multi-az-standby-limits` — 다중 AZ 대기 인스턴스로는 할 수 없는 것

**한 줄**: 대기(Standby) 인스턴스는 읽기 쿼리를 처리하지 못하고, 쓰기는 항상 주(Primary) 인스턴스에서만 일어난다.

다중 AZ 배포는 고가용성 전용 기능이다. 대기 인스턴스는 장애 조치를 기다릴 뿐
아무 트래픽도 처리하지 않으므로, 분석 쿼리를 대기 인스턴스로 보내는 선택지는 오답이다.
읽기 부하를 나누려면 읽기 전용 복제본을 따로 만들어야 한다.

다중 AZ라고 해서 쓰기가 분산되지도 않는다. 쓰기는 언제나 주 인스턴스 한 곳으로 몰린다.

> [데이터베이스 #40 p83] "Multi-AZ의 대기(Standby) 인스턴스는 읽기 쿼리를 처리할 수 없으며, 분석 트래픽을 보낼 수 없다."
> [컴퓨팅3 #80 p166] "RDS(기본)는 다중 AZ 환경에서도 주(Primary) 인스턴스에만 쓰기가 가능하다."

### `automated-backup-retention` — RDS 자동 백업의 보존 한계

**한 줄**: RDS 자동 백업의 최대 보존 기간은 35일이다.

"90일 이상 보관해야 한다" 같은 규정 준수 요구가 나오면 RDS 자동 백업만으로는 충족할 수 없다.
이때는 AWS Backup으로 백업 계획을 세워 보존 기간·리전 간 복제·만료 후 자동 삭제를
한꺼번에 관리한다. 수동 스냅샷을 직접 관리하는 방식은 운영 부담이 크다.

> [컴퓨팅3 #94 p194] "RDS 자체 자동 백업은 최대 보존 기간이 35일로 제한되어 있다. 따라서 90일이라는 장기 보존 요구 사항을 충족하기 위해서는 AWS Backup을 통해 '백업 계획'을 세우는 것이"

### `connection-issue-heuristic` — 연결(Connection) 문제의 정답 신호

**한 줄**: DB 연결 수·연결 지연·연결 거부가 문제의 증상이면 RDS Proxy가 답이다.

"Too many connections", "Connection refused", 연결이 빈번하게 열리고 닫히면서 생기는 지연,
Lambda의 폭발적인 동시 연결 — 이런 증상은 전부 연결 관리 문제다.

읽기 전용 복제본은 읽기 부하를 나눌 뿐 연결 관리를 해결하지 않고, 다중 AZ는 가용성 기능이라
최대 연결 수를 늘려주지 않으며, ElastiCache는 캐시 미스와 쓰기 시의 연결 급증을 막지 못한다.
인스턴스 사양을 올리는 것도 근본 원인을 그대로 둔다.

> [데이터베이스 #42 p87] "RDS에서 연결(Connection)으로 인한 문제가 발생한 내용이 나오면 99%는 RDS Proxy가 포함된 선택지가 정답이다."
> [데이터베이스 #45 p93] "연결 거부 오류는 인스턴스가 죽어서가 아니라 연결 한도를 초과해서 발생하는 것이므로 다중 AZ로는 해결되지 않는다."

## aurora-dynamodb-cache

### `aurora-serverless-v2` — Aurora Serverless v2

**한 줄**: 데이터베이스 용량을 워크로드에 맞춰 1초 단위로 자동 조정하는 Aurora 구성이다.

플레이어 수가 시시각각 바뀌는 게임 서버처럼 변동이 심한 트래픽에 쓴다.
관계형 데이터베이스가 필요하면서 용량 예측이 어려울 때 선택지에 등장한다.

> [컴퓨팅2 #69 p143] "Aurora Serverless v2: 데이터베이스 용량을 워크로드에 맞춰 1초 단위로 자동 조정하므로, 변동이 심한 게임 트래픽에 최적화되어 있다."

### `aurora-reader-endpoint` — Reader Endpoint는 Aurora 전용

**한 줄**: 읽기 전용 복제본들에 자동으로 부하를 분산해주는 Reader Endpoint는 Aurora에만 있다.

RDS for MySQL에는 Reader Endpoint를 통한 부하 분산 기능이 없다.
RDS에서 읽기를 나누려면 읽기 전용 복제본을 만들고 애플리케이션이
분석 쿼리를 그쪽으로 직접 라우팅해야 한다.

> [데이터베이스 #40 p83] "Reader Endpoint를 통한 부하 분산은 Amazon Aurora에서만 제공하는 기능이다. Amazon RDS for MySQL은 이러한 Reader Endpoint를 통한 부하 분산 기능을 지원하지 않는다."

### `documentdb` — Amazon DocumentDB

**한 줄**: MongoDB와 호환되는 NoSQL 데이터베이스 서비스다.

"기존에 MongoDB를 쓰고 있는데 코드를 바꿀 수 없다"는 조건이 나오면 DocumentDB가 답이다.
DynamoDB는 쿼리 방식과 데이터 구조가 달라 애플리케이션 코드를 대폭 고쳐야 하고,
EC2에 MongoDB를 직접 설치하면 운영 부담이 크다.

DocumentDB도 DynamoDB와 마찬가지로 영상 같은 대용량 파일을 담기에는 적합하지 않다.

> [컴퓨팅2 #68 p141] "'코드 변경 불가능'이라는 조건이 핵심이다. MongoDB와 호환되는 DocumentDB를 사용해야 한다."
> [데이터베이스 #30 p63] "DocumentDB는 NoSQL(MongoDB 호환) 서비스로"

### `dynamodb-pitr` — DynamoDB PITR의 보존 한계

**한 줄**: 특정 시점 복구(PITR)는 최대 35일까지만 되돌릴 수 있다.

"7년 보관" 같은 장기 보존 요구에는 PITR을 쓸 수 없고 AWS Backup으로 간다.
RDS 자동 백업의 35일 한계와 같은 구조의 함정이다.

> [컴퓨팅3 #95 p196] "PITR (Point-in-Time Recovery): 최대 35일까지만 데이터를 복구할 수 있는 기능으로, 7년이라는 장기 보존 요구 사항에는 적합하지 않다."

### `dax-dynamodb-only` — DAX는 DynamoDB 전용

**한 줄**: DAX는 DynamoDB에만 붙는 캐시이고, RDS 앞에는 붙일 수 없다.

DynamoDB의 읽기 용량이 소진되어 다른 애플리케이션 접속이 지연되는 상황이면
아키텍처 변경 없이 DAX를 얹는 것이 답이다.

반대로 RDS의 읽기 부하를 줄이려면 ElastiCache를 쓴다. RDS 문제에 DAX가 보이면 오답이다.

> [데이터베이스 #49 p101] "DAX 기능은 DynamoDB 전용이므로 RDS에서는 사용할 수 없는 기능이다."
> [데이터베이스 #48 p99] "DAX: DynamoDB 호환 캐시 서비스로 쉽게 바로 적용할 수 있다."

## compute-delivery

### `warm-pool` — Auto Scaling 웜 풀

**한 줄**: 인스턴스를 미리 부팅해 설정까지 끝낸 뒤 '중지' 상태로 대기시켜, 확장 시 초기화 지연을 없애는 기능이다.

트래픽이 급증할 때 새 인스턴스가 부팅되고 애플리케이션이 뜨기까지 시간이 오래 걸려
응답이 지연되는 문제를 푼다.

중지 상태로 두기 때문에 EC2 실행 비용은 발생하지 않고 EBS 스토리지 비용만 든다.
여유 인스턴스를 계속 실행 상태로 두는 오버 프로비저닝보다 훨씬 저렴하다.

> [컴퓨팅1 #62 p128] "웜 풀 기능을 사용하면 인스턴스를 미리 부팅하고 애플리케이션 설정을 마친 상태로 대기시킬 수 있다. 이 인스턴스들을 '중지(Stopped)' 상태로 유지하면 컴퓨팅 비용은 들지 않고 스토리지(EBS) 비용만 발생하므로"

### `scheduled-scaling` — 예약된 조정과 대상 추적의 갈림길

**한 줄**: 트래픽 시점이 예측 가능하면 예약된 조정, 예측 불가능하면 대상 추적이다.

예약된 조정(Scheduled Scaling)은 "매일 아침 9시"처럼 몰리는 시각을 미리 알 때
용량을 앞당겨 늘려두는 방식이다.

문제에 "예측할 수 없는(unpredictable, unexpected) 트래픽 급증"이라고 못 박혀 있으면
예약된 조정은 무조건 오답이고, 지표 목표값을 벗어나면 즉시 반응하는 대상 추적이 답이다.

> [컴퓨팅1 #61 p126] "예약된 조정(Scheduled Scaling): 이 방식은 트래픽이 몰리는 시간이 '예측 가능할 때' 미리 용량을 늘려두는 방식이다. 언제 트래픽이 튈지 모르는 상황에서는 효과가 없다."

### `alb-l7-vs-nlb-l4` — 계층으로 갈리는 ALB와 NLB

**한 줄**: ALB는 7계층이라 URL 경로 기반 라우팅이 되고, NLB는 4계층이라 되지 않는다.

"요청의 URL 경로를 분석해 적절한 페이지로 연결한다"는 요구가 나오면 ALB다.
NLB는 전송 계층 로드 밸런서라 경로를 들여다볼 수 없다.

웹 애플리케이션의 보안을 이야기할 때 등장하는 L7은 애플리케이션 계층,
TCP/UDP를 이야기할 때의 L4는 전송 계층을 가리킨다.

> [컴퓨팅1 #63 p130] "NLB는 4계층(전송 계층) 로드 밸런서로, URL 경로 기반 라우팅을 지원하지 않는다."
> [보안2 #133 p277] "NLB: L4(전송 계층) 로드 밸런서로, 웹 공격(L7)을 방어하거나 HTTP 요청의 상세 내역을 분석하는 데는 한계가 있습니다."

### `sticky-session-tradeoff` — 스티키 세션의 부작용

**한 줄**: 세션을 같은 서버에 고정하는 대신, 특정 인스턴스에만 부하가 몰릴 수 있다.

ALB 뒤의 인스턴스 하나에만 트래픽이 집중되고 나머지는 유휴 상태인 불균형이 보이면
스티키 세션이 켜져 있는지 의심한다. 헤비 유저가 소수이거나 트래픽 패턴이 편중되면
그 사용자들이 붙은 인스턴스만 과부하가 된다.

끄면 라운드 로빈으로 고르게 분산된다. 로드 밸런서 타입을 바꾸거나 인스턴스를 더 붙이는
것은 원인을 그대로 두는 조치다.

> [컴퓨팅1 #56 p116] "이 기능이 활성화되어 있으면 특정 사용자의 트래픽이 계속 동일한 인스턴스로만 전달된다. ... 이를 끄면 라운드 로빈 방식으로 트래픽이 고르게 분산된다."

### `global-accelerator-protocols` — Global Accelerator가 처리하는 것

**한 줄**: TCP와 UDP를 모두 지원하고, 리전 장애 시 정상 리전으로 자동 우회한다.

전 세계 사용자를 가장 가까운 AWS 엣지로 진입시켜 지연을 줄이고,
네트워크 상태에 따라 트래픽을 정상 리전으로 라우팅한다.
실시간 게임 서버나 TCP 기반 영상 전송처럼 HTTP가 아닌 트래픽을 가속할 때 쓴다.

CloudFront는 HTTP/HTTPS 콘텐츠 캐싱에 특화되어 있어 일반 TCP 가속에는 맞지 않는다.
둘의 갈림길은 "캐싱할 콘텐츠인가, 가속할 연결인가"다.

> [컴퓨팅1 #55 p114] "AWS Global Accelerator: 전세계 사용자들 더 나은 성능을 제공한다. TCP와 UDP를 모두 지원하며, 리전 간 장애 조치(Failover)도 가능하다."
> [컴퓨팅1 #59 p122] "CloudFront는 주로 HTTP/HTTPS 캐싱에 특화되어 있다."

### `cloudfront-ttl` — CloudFront TTL과 캐시 무효화의 관계

**한 줄**: TTL이 만료되기 전에는 원본이 바뀌어도 엣지가 옛 파일을 계속 내보낸다.

배포는 성공했는데 브라우저에 여전히 이전 버전이 보이는 상황의 원인이 이것이다.
S3에는 최신 파일이 올라가 있어도, 엣지 로케이션에 캐싱된 사본의 TTL이 남아 있으면
CloudFront는 그 사본을 제공한다.

무효화(Invalidation)를 실행하면 엣지 캐시가 삭제되어 다음 요청 때 원본에서 새로 가져온다.

> [보안2 #129 p269] "파일의 TTL(Time-to-Live)이 만료되기 전까지는 S3의 원본 파일이 바뀌더라도 CloudFront는 기존 캐싱되어 있는 파일을 제공한다."

### `edge-keyword` — 'Edge'라는 키워드

**한 줄**: 전 세계에 퍼져 있는 AWS 서버 중 사용자와 가장 가까운 곳에서 요청을 처리한다는 뜻이다.

엣지 최적화 API 엔드포인트, 엣지 로케이션, Lambda@Edge처럼 여러 서비스에 붙어 나온다.
API Gateway의 엣지 최적화 엔드포인트는 CloudFront의 글로벌 네트워크를 사용해
가장 가까운 엣지에서 API 요청을 받는다.

"전 세계 사용자의 지연 시간을 줄여야 한다"는 조건과 함께 나오면 이 방향이 답이다.

> [컴퓨팅2 #73 p151] "AWS에서 Edge라는 키워드가 자주나오는데, 전세계에 퍼져있는 여러 AWS 서버 중 가장 가까운 서버에 요청을 보내 처리하는 방식이다. 자주 나오니 기억해두자."

## serverless-containers

### `eks` — Amazon EKS (Elastic Kubernetes Service)

**한 줄**: 쿠버네티스를 AWS에서 관리형으로 운영하는 서비스다.

기존 환경이 쿠버네티스면 EKS로 옮겨야 코드와 배포 프로세스를 그대로 쓸 수 있다.
같은 컨테이너 서비스라도 ECS로 옮기면 공수가 많이 든다.

반대로 온프레미스에서 순수 Docker 컨테이너로 돌리던 것을 옮길 때는 ECS가 맞다.
EKS와 ECS는 "원래 쿠버네티스였는가"로 갈린다.

> [컴퓨팅2 #68 p141] "Amazon EKS & AWS Fargate: 기존 쿠버네티스 환경을 코드 변경 없이 그대로 옮겨오기 위해 EKS를 사용해야 한다."
> [컴퓨팅2 #66 p137] "(A) EKS: Docker로 운영하던 애플리케이션을 마이그레이션하기에 적절한 서비스는 ECS이다."

### `fargate-no-time-limit` — Fargate에는 실행 시간 제한이 없다

**한 줄**: Lambda의 15분 제한을 넘기는 작업은 Fargate로 간다.

비디오 한 편 처리에 20분, 배치 작업에 2~3시간이 걸리는 워크로드에서
Lambda는 선택지에서 바로 지워진다.

Fargate는 서버를 프로비저닝·관리할 필요가 없고 사용한 vCPU·메모리와 시간만큼만
과금되므로, 하루 몇 시간만 도는 작업에 EC2 예약 인스턴스를 사는 것보다 저렴하다.

다만 10초짜리 초단기 작업이라면 컨테이너를 띄우는 오버헤드 때문에 Lambda가 낫다.

> [컴퓨팅2 #64 p133] "AWS Fargate는 트래픽에 따라 유연하게 확장할 수 있다. Lambda와 달리 실행 시간 제한(15분)이 없어 20분 이상 소요되는 비디오 처리 작업에 적합하다."
> [컴퓨팅3 #91 p188] "10초짜리 초단기 작업을 위해 컨테이너를 띄우는 것은 Lambda보다 초기 구동 시간이나 설정 면에서 오버헤드가 더 큽니다."

### `lambda-function-url` — Lambda 함수 URL

**한 줄**: API Gateway 없이 Lambda 함수에 직접 HTTP(S) 엔드포인트를 부여하는 기능이다.

관리자가 필요할 때 눌러서 보고서를 만드는 정도의 단순한 호출이면
API Gateway를 앞에 두는 것보다 구성이 간단하고 비용이 적게 든다.

> [컴퓨팅3 #84 p174] "Lambda 함수 URL: Lambda 함수에 전용 HTTP(S) 엔드포인트를 제공하는 기능으로, API Gateway 없이도 함수를 직접 호출할 수 있어 비용 효율적이고 구성이 간단하다."

### `lambda-at-edge` — Lambda@Edge

**한 줄**: CloudFront의 엣지 로케이션에서 코드를 실행하는 방식이다.

인증·권한 부여 로직을 사용자와 가장 가까운 곳에서 처리하므로
로그인 과정의 지연까지 줄일 수 있다.

같은 로직을 리전의 일반 Lambda로 돌리면 엣지보다 지연이 길어진다.

> [보안3 #153 p318] "Lambda@Edge: CloudFront의 엣지 로케이션에서 코드를 실행하여 클라이언트와 가장 가까운 곳에서 권한 부여 로직을 처리하므로 지연 시간이 매우 짧다."

### `lambda-vpc-access` — Lambda의 VPC 연결

**한 줄**: 프라이빗 서브넷의 EC2와 사설 IP로 통신하려면 Lambda도 같은 VPC에 연결해야 한다.

Lambda를 VPC 밖에 두고 공용 인터넷으로 통신하는 방식은 프라이빗 서브넷의 리소스에
닿지 못하고 보안상으로도 맞지 않는다. Lambda를 퍼블릭 서브넷에 둔다고 해서
프라이빗 서브넷의 EC2와 직접 통신할 수 있게 되는 것도 아니다.

> [비용관리 #157 p327] "프라이빗 서브넷에 있는 EC2와 통신하려면 Lambda도 같은 VPC에 연결되어야 사설 IP로 통신할 수 있다."

### `api-gateway-jwt-authorizer` — HTTP API의 JWT 권한 부여자

**한 줄**: API Gateway HTTP API는 JWT 인증과 ALB 프라이빗 통합을 기본으로 지원한다.

JWT로 사용자를 인증하는 퍼블릭 API를 ALB와 직접 통합해야 한다는 요구가 나오면
REST API가 아니라 HTTP API가 답이다. REST API로도 가능하지만 비용이 높고 설정이 복잡하다.

API Gateway가 제공하는 유형은 REST API와 HTTP API 둘뿐이다.

> [컴퓨팅2 #72 p149] "API Gateway HTTP API: REST API보다 비용이 저렴하고 지연 시간이 짧으며, ALB와의 프라이빗 통합 및 JWT 권한 부여(Authorizer) 기능을 기본적으로 지원한다."

### `aws-batch` — AWS Batch

**한 줄**: 여러 작업을 한꺼번에 모아서 처리하는 배치 처리 서비스다.

이름 때문에 "여러 단계를 순서대로 실행"과 헷갈리기 쉽지만, 순차 워크플로를 조율하는
서비스가 아니다. 그건 Step Functions의 역할이다.

> [컴퓨팅3 #85 p176] "(C) Batch: 여러 작업을 순차적으로 실행하는 용도로 쓰이지 않고, 여러 작업을 한꺼번에 모아서 처리(=Batch 처리)하기 위해 사용되는 서비스이다."

## messaging-backup

### `msk` — Amazon MSK (Managed Streaming for Apache Kafka)

**한 줄**: Apache Kafka를 AWS가 관리해주는 완전 관리형 서비스다.

이미 Kafka로 이벤트 기반 아키텍처를 돌리고 있다면, 코드를 크게 바꾸지 않고
그대로 옮길 수 있는 곳이 MSK다.

SQS는 Kafka와 동작 방식이 다르고 EventBridge는 이벤트 버스라 성격이 달라서,
둘 다 단순 마이그레이션 대상이 되지 못한다. EC2에 Kafka를 직접 설치하면
패치·관리·확장을 전부 떠안게 된다.

> [컴퓨팅2 #65 p135] "기존에 Kafka를 사용하고 있었다면, 코드를 크게 변경하지 않고 그대로 사용할 수 있는 완전 관리형 서비스인 MSK가 가장 적합하다."

### `sqs-details` — SQS의 보존 기간과 표준 대기열의 약점

**한 줄**: 메시지 보존 기간은 최대 14일까지 설정할 수 있고, 표준 대기열은 중복과 순서 뒤바뀜이 생길 수 있다.

"저장된 지 48시간이 지나면 자동 삭제" 같은 요구를 SQS 보존 기간 설정만으로 처리할 수 있다.

표준 대기열은 무제한에 가까운 처리량을 주는 대신 드물게 메시지가 중복 전달되고
순서가 바뀔 수 있다. "정확히 한 번(Exactly-Once)" 처리가 필요한 결제나 수강 신청에는
FIFO 대기열을 써야 한다.

> [컴퓨팅3 #76 p158] "SQS는 메시지 보존 기간을 설정할 수 있으며(최대 14일), 2일로 설정하면 요구 사항을 만족한다."
> [컴퓨팅3 #81 p168] "SQS 표준 대기열: 무제한 처리량을 제공하지만, 드물게 메시지가 중복 전달될 수 있으며 순서가 바뀔 수도 있다."

### `sqs-queue-depth-scaling` — 대기열 깊이 기반 오토 스케일링

**한 줄**: CPU가 아니라 대기열에 쌓인 메시지 수를 지표로 삼아 처리 인스턴스를 늘리고 줄이는 패턴이다.

웹 계층이 SQS에 넣고 백엔드가 꺼내 처리하는 구조에서, 백엔드 CPU가 100%를 치고
큐가 가득 차면 병목은 처리 용량이다. 이때 큐에 쌓인 메시지 수를 기준으로
백엔드를 자동 확장하는 것이 근본 해결책이다.

"처리해야 할 작업의 양"을 직접 재는 지표이므로 CPU 사용률보다 반응이 빠르고 정확하다.
프런트엔드에 CloudFront나 API Gateway를 붙이는 것은 백엔드 병목을 풀지 못한다.

> [컴퓨팅3 #82 p170] "CPU 사용률보다는 '처리해야 할 작업의 양(대기열에 쌓인 메시지 수)'을 기준으로 오토 스케일링을 하는 것이 훨씬 반응성이 좋고 정확하다."
> [컴퓨팅3 #77 p160] "병목 현상이 백엔드 처리(CPU 100%, 큐 적체)에 있으므로, 대기열에 쌓인 메시지 수에 따라 백엔드 처리 인스턴스를 자동으로 늘려주는 것이 근본적인 해결책이다."

### `eventbridge-scheduler` — EventBridge Scheduler

**한 줄**: 특정 시각이나 주기에 작업을 실행시키는 기능이다.

"평일 업무 시간에만 개발용 RDS를 켜둔다" 같은 스케줄 기반 자동화에서
Lambda와 짝을 이뤄 나오는 정석 조합이다.

주의할 점은 시간 기반이라는 것이다. "업로드되는 즉시" 같은 요구에는
주기적으로 확인하는 방식이 되어 오히려 오답이 된다. 그때는 S3 이벤트 알림이다.

> [컴퓨팅3 #89 p184] "특정 시각(업무 시작/종료)에 작업을 수행하는 것은 EventBridge(또는 EventBridge Scheduler)의 주된 기능입니다."
> [컴퓨팅3 #86 p178] "EventBridge Scheduler: '주기적'으로 확인하는 방식은 '즉시' 처리 요구사항을 만족시키지 못하며 불필요한 지연을 발생시킨다."

### `step-functions-features` — Step Functions의 수동 승인과 재시도

**한 줄**: 워크플로 중간에 사람의 승인 단계를 넣을 수 있고, 실패 시 재시도가 내장되어 있다.

여러 단계를 순서대로 실행하면서 오류 처리와 자동 재시도가 필요하고,
중간에 관리자 승인이 끼어야 하는 워크플로는 Step Functions로 간다.
같은 로직을 애플리케이션 코드로 짜면 개발·운영 부담이 훨씬 커진다.

12시간짜리 장기 작업도 조율할 수 있어 Lambda의 15분 제한을 우회하는 통로가 된다.

> [컴퓨팅3 #76 p158] "Step Functions: '수동 승인 단계'가 있는 워크플로를 구현하기에 가장 적합한 서비스이다."
> [컴퓨팅3 #85 p176] "AWS Step Functions: 12시간 걸리는 장기 실행 작업에 적합하다. 또한 재시도(Retry) 기능이 내장되어 있다."

### `ses` — Amazon SES (Simple Email Service)

**한 줄**: 이메일 발송에 최적화된 서비스다.

보고서를 만들어 담당자 이메일로 보내야 하거나, 문의 양식 제출을 알려야 할 때
Lambda에서 SES를 호출한다. SNS로도 알림은 가능하지만,
이메일 자체가 목적이면 SES가 제 자리다.

> [컴퓨팅3 #84 p174] "SES (Simple Email Service): 대량의 이메일 발송에 최적화된 서비스로, 특정 사용자(관리자)에게 보고서를 전달하는 요구사항에 적합하다."

### `backup-long-term-retention` — AWS Backup으로 넘어가야 하는 순간

**한 줄**: 서비스 자체 백업의 보존 한계를 넘거나 리전 간 복제가 필요하면 AWS Backup이다.

RDS 자동 백업 35일, DynamoDB PITR 35일을 넘는 보존 요구가 나오면 AWS Backup으로
백업 계획을 세운다. 스케줄링·보존 정책·리전 간 복제·만료 후 자동 삭제를
코드 없이 콘솔 설정으로 처리한다.

EC2를 백업할 때 'EBS 볼륨'이 아니라 'EC2 인스턴스'를 리소스로 지정하면
연결된 모든 볼륨뿐 아니라 인스턴스 유형·네트워크 설정 같은 구성 정보까지 함께 백업되어,
다른 리전에서 바로 복구할 수 있다.

> [컴퓨팅3 #93 p192] "'EC2 인스턴스' 자체를 리소스로 지정하면, 연결된 모든 EBS 볼륨뿐만 아니라 인스턴스 유형, 네트워크 설정 등 인스턴스 구성 정보(AMI)가 함께 백업되어 보조 리전에서 즉시 복구하기에 가장 유리하다."
> [컴퓨팅3 #95 p196] "AWS Backup: DynamoDB를 포함한 여러 AWS 서비스의 백업을 중앙에서 관리할 수 있는 완전 관리형 서비스이다."

## vpc-networking

### `endpoint-pricing` — 엔드포인트 유형별 비용 차이

**한 줄**: 게이트웨이 엔드포인트는 무료이고, 인터페이스 엔드포인트는 시간당 비용이 발생한다.

S3와 DynamoDB는 두 유형 모두로 접근할 수 있지만, 비용 효율을 묻는 문제에서는
게이트웨이 엔드포인트가 답이다. 인터페이스 엔드포인트는 S3 접근에도 쓸 수 있으나
시간당 요금이 붙는다.

접근해야 할 AWS 서비스가 여러 종류(S3, DynamoDB, CloudWatch 등)로 넓어지면
그때는 포괄적인 인터페이스 엔드포인트로 간다. 인터페이스 엔드포인트라도
NAT 게이트웨이 대비 데이터 처리 비용은 저렴하다.

> [네트워크1 #98 p203] "(C) 인터페이스 엔드포인트: S3 접근에 사용 가능하지만, 게이트웨이 엔드포인트와 달리 시간당 비용이 발생한다. S3/DynamoDB는 게이트웨이 엔드포인트(무료)를 사용하는 것이 비용 효율적이다."

### `egress-only-igw` — Egress-only 인터넷 게이트웨이

**한 줄**: IPv6 전용 아웃바운드 게이트웨이다.

IPv4에서 NAT 게이트웨이가 하는 역할(안에서 밖으로만 나가기)을
IPv6에서 담당한다. 선택지에 나왔는데 문제가 IPv4 상황이면 오답이다.

> [네트워크1 #98 p203] "(A) Egress-only IGW: IPv6용 아웃바운드 전용 게이트웨이이다."

### `nat-instance` — NAT 인스턴스와 NAT 게이트웨이의 차이

**한 줄**: NAT 인스턴스는 EC2로 직접 운영하는 NAT라서, 트래픽이 몰리면 병목이 된다.

관리형인 NAT 게이트웨이와 달리 인스턴스 사양에 묶여 있어 네트워크가 포화되면
그 뒤의 Lambda나 EC2가 간헐적으로 타임아웃을 낸다.

S3처럼 엔드포인트로 우회할 수 있는 대상이면, NAT를 키우는 대신
게이트웨이 엔드포인트로 트래픽을 빼는 것이 병목과 보안을 한 번에 푼다.

> [네트워크1 #101 p209] "NAT 인스턴스 네트워크의 트래픽 포화로 인해 객체를 업로드하려고 시도하는 동안 간헐적으로 Lambda 함수 시간이 초과됩니다. ... 게이트웨이 엔드포인트: S3 트래픽을 NAT 인스턴스(인터넷)를 거치지 않고 AWS 내부 네트워크로 직접 라우팅하여 병목 현상을 해결하고"

### `vpc-peering-scaling-limit` — VPC 피어링의 확장 한계

**한 줄**: 피어링은 1:1 연결이라, VPC가 늘어나면 맺어야 할 연결 수가 폭증한다.

수백 개 VPC로 확장할 계획이 있다는 조건이 나오면 피어링은 관리가 불가능해진다.
그 자리는 Transit Gateway다.

반대로, 두 VPC가 서로 통신하면 안 된다는 조건이 있으면 피어링과 Transit Gateway 둘 다
조건 위반이 된다. 이때는 각 VPC에 Site-to-Site VPN을 따로 맺는다.

> [네트워크1 #108 p223] "VPC 피어링은 VPC 수가 늘어날수록 연결이 기하급수적으로 증가하여, 수백 개 VPC 환경에서는 확장성과 관리 측면에서 적합하지 않다."
> [네트워크1 #107 p221] "VPC 피어링: 두 VPC를 연결하게 되므로 서로 통신할 수 있으면 안 된다는 조건에 위배된다."

### `s3-is-regional` — S3는 리전 수준 서비스다

**한 줄**: S3는 VPC나 서브넷 안에 만들 수 없고, 보안 그룹도 쓰지 않는다.

"S3를 VPC 내부로 옮긴다", "S3를 프라이빗 서브넷에 생성한다", "S3에 보안 그룹을 붙인다"는
선택지는 전부 성립하지 않는 문장이다.

VPC에서 S3로 가는 트래픽을 인터넷 밖으로 빼려면 VPC 엔드포인트를 쓰고,
S3의 접근 제어는 버킷 정책이나 ACL로 한다. 같은 리전에 버킷을 만든다고 해서
네트워크 경로가 바뀌지도 않는다.

> [네트워크1 #100 p207] "S3는 VPC 내부가 아닌 리전 수준 서비스이므로 특정 서브넷에 생성할 수 없습니다."
> [보안2 #128 p267] "S3는 보안 그룹(Security Group)을 사용하지 않습니다. S3는 버킷 정책(Bucket Policy)이나 ACL로 접근을 제어합니다."

## hybrid-connectivity

### `direct-connect-caveats` — Direct Connect의 두 가지 함정

**한 줄**: 전용선이지만 트래픽을 암호화하지 않고, 설치에 몇 주에서 몇 달이 걸린다.

"네트워크 계층에서 암호화되어야 한다"는 요구가 나오면 Direct Connect는 오답이고
Site-to-Site VPN이 답이다. Direct Connect는 인터넷을 우회할 뿐 암호화 서비스가 아니다.

"빠르게 연결해야 한다"는 조건도 마찬가지다. 물리 회선을 깔아야 해서 즉시 설정이 불가능하다.
소량 트래픽을 빨리 붙여야 하면 VPN이 비용과 시간 양쪽에서 낫다.

Direct Connect가 답이 되는 조건은 "일관되고 지연 시간이 짧은" 성능과
"퍼블릭 인터넷을 쓰지 않는다"가 함께 나올 때다.

> [네트워크1 #103 p213] "(A) AWS Direct Connect: 온프레미스와 AWS 간에 통신할 수 있는 전용 회선을 제공하지만, 트래픽을 암호화하지는 않는다."
> [네트워크1 #106 p219] "물리적 회선 설치가 필요하여 설정에 몇 주~몇 달이 걸릴 수 있어서"

### `direct-connect-gateway` — Direct Connect Gateway

**한 줄**: Direct Connect와 Transit Gateway를 묶어 대규모 하이브리드 네트워크를 구성하는 통로다.

"일관되고 낮은 지연 시간"(Direct Connect)과 "수백 개 VPC 연결"(Transit Gateway)이
동시에 요구되면 이 둘을 Direct Connect Gateway로 통합한다.

> [네트워크1 #108 p223] "Direct Connect Gateway를 통해 이 둘을 통합하면 대규모 하이브리드 네트워크를 효율적으로 구성할 수 있습니다."

### `client-vpn` — AWS Client VPN

**한 줄**: 개별 사용자가 원격에서 VPC에 접속하기 위한 서비스다.

Site-to-Site VPN이 네트워크 대 네트워크를 잇는 것과 달리, Client VPN은 사람 한 명이
자기 노트북에서 붙는 용도다. 온프레미스 데이터 센터와 AWS를 연결하는 문제에서
Client VPN이 보이면 오답이다.

> [네트워크1 #106 p219] "(A) Client VPN: 개별 사용자가 AWS 서비스에 원격으로 접속할 때 사용하는 서비스이다. 온프레미스와 AWS 서비스 간에 네트워크를 연결하는 용도가 아니다."

### `access-terms` — Customer Gateway와 Bastion Host

**한 줄**: Customer Gateway는 VPN의 온프레미스 쪽 장치, Bastion Host는 내부 서버로 들어가는 중간 서버다.

Customer Gateway는 Site-to-Site VPN을 맺을 때 고객 측 종단을 가리키는 구성 요소다.
VPC에서 S3로 가는 경로 같은 문제에 나오면 맥락이 다른 오답이다.

Bastion Host는 인터넷에서 프라이빗 서브넷의 서버로 안전하게 접속하기 위해 두는
중간 서버다. 이것도 온프레미스와 AWS를 잇는 용도가 아니다.

> [네트워크1 #98 p203] "(E) Customer Gateway: VPN 연결용이다."
> [네트워크1 #106 p219] "(C) Bastion Host: 인터넷에서 내부 서버로 안전하게 접속하기 위한 중간 서버를 의미한다."

### `data-locality-cost` — 데이터 지역성으로 전송 비용 줄이기

**한 줄**: 큰 중간 데이터는 AWS 안에서 처리하고, 작은 결과물만 밖으로 내보낸다.

쿼리 결과가 50MB인데 최종 시각화 결과물은 500KB라면, 시각화 도구를 AWS 안에 두어야 한다.
도구를 온프레미스에 두면 매번 50MB가 Direct Connect를 타고 나가면서 전송 비용이 커진다.

처리는 데이터 가까이서 하고 결과만 옮긴다 — 데이터 전송 비용 문제의 일반 원칙이다.

> [네트워크1 #109 p225] "대용량 데이터(50MB)가 발생하는 쿼리 작업은 AWS 내부에서 처리하여 전송 비용을 없애고, 사용자에게는 결과물인 소량의 데이터(500KB)만 Direct Connect를 통해 전송함으로써"

### `onprem-connectivity-heuristic` — 온프레미스 연결 문제의 출발점

**한 줄**: 온프레미스와 AWS가 통신해야 한다는 말이 나오면 Site-to-Site VPN과 Direct Connect부터 떠올린다.

이 둘 중 무엇이냐는 "암호화가 필요한가 / 일관된 성능이 필요한가 / 얼마나 빨리 붙여야 하는가"로 갈린다.
여기에 VPC가 여러 개거나 앞으로 늘어난다는 조건이 붙으면 Transit Gateway가 더해진다.

PrivateLink는 VPC 간 애플리케이션 연결용이라 온프레미스와는 통신하지 못하고,
NAT 게이트웨이는 인터넷 액세스를 줄 뿐 터널을 만들지 않는다.

> [네트워크1 #105 p217] "AWS 서비스와 온프레미스가 통신해야 한다는 내용이 문제에 나오면 Site-to-Stie VPN이랑 Direct Connect 이 2가지를 떠올릴 수 있어야 한다."
> [네트워크1 #105 p217] "(C) PrivateLink: ... 온프레미스의 시스템과 통신할 수는 없다."

## route53

### `private-hosted-zone` — 프라이빗 호스팅 영역과 퍼블릭 호스팅 영역

**한 줄**: 프라이빗 호스팅 영역은 VPC 내부에서만 쓰는 DNS 관리용이다.

VPC 안에서만 통하는 도메인 이름을 관리할 때 쓴다. 온프레미스에 있는
Active Directory 도메인을 해석하는 문제는 프라이빗 호스팅 영역으로 풀리지 않는다.
그건 Route 53 Resolver 아웃바운드 엔드포인트의 몫이다.

사내 내부 도메인을 퍼블릭 호스팅 영역에 올리는 것도 답이 아니다.
외부에 노출되면 안 되고, 해석되지도 않을 수 있다.

> [네트워크2 #114 p236] "(B) Route 53 프라이빗 호스팅 영역은 VPC 내부 DNS 관리용으로, 온프레미스 AD 도메인 해석을 직접 해결하지는 못한다."
> [네트워크2 #115 p238] "(D) 퍼블릭 호스팅 영역: 사내 내부 도메인(인트라넷 등)은 퍼블릭 DNS에 노출되면 안 되며"

### `multivalue-answer-details` — 다중값 응답 라우팅의 세부 동작

**한 줄**: 최대 8개의 정상 레코드를 무작위로 반환하며, 각 레코드에 헬스 체크를 연동할 수 있다.

두 리전에 같은 사이트를 띄워 트래픽을 나누되 한쪽이 비정상이면 그쪽으로 보내지 않아야 한다면
이 정책이 답이다. 헬스 체크가 붙어 있어 장애가 난 곳은 응답에서 빠진다.

단순 라우팅은 상태 확인 기반 조건부 라우팅을 지원하지 않는다.
다중값 응답은 사용자의 위치를 고려하지 않는다는 점도 기억해 둔다.

> [네트워크2 #113 p234] "다중값 응답 라우팅: 여러 IP 주소를 반환할 수 있는 라우팅 정책이다. 이 정책은 각 레코드에 헬스 체크 기능이 연동되어 있어 장애가 발생한 곳에는 트래픽을 보내지 않고"
> [네트워크2 #112 p232] "(C) 다중값 응답(Multivalue Answer): 무작위로 선택된 최대 8개의 상태가 양호한 레코드를 반환하여 단순한 부하 분산과 가용성을 제공할 뿐, 사용자의 위치를 고려하지 않습니다."

## analytics-monitoring

### `glue-crawler` — AWS Glue Crawler

**한 줄**: S3에 저장된 데이터를 스캔해 바로 쿼리할 수 있는 상태로 준비해주는 기능이다.

Glue의 ETL 작업(Glue Job)과 역할이 다르다. Crawler는 데이터를 훑어 구조를 파악해두고,
그 결과를 Athena가 SQL로 조회한다.

S3에 막 들어온 데이터를 신속하게 분석해야 하는 문제에서 Crawler + Athena 조합이 정석이다.

> [데이터분석 #116 p241] "AWS Glue Crawler: Amazon S3에 저장된 데이터를 스캔하여, 바로 쿼리 및 분석을 할 수 있게 준비해주는 역할을 한다."

### `log-analysis-options` — 로그 분석 선택지: OpenSearch와 CloudWatch Logs Insights

**한 줄**: 간헐적인 대용량 로그 분석은 S3 + Athena, 실시간 로그 조회는 CloudWatch Logs Insights다.

Amazon OpenSearch는 강력하지만 클러스터를 계속 띄워둬야 해서,
"필요할 때만 가끔 조회한다"는 요구에는 비용과 운영 부담이 과하다.

CloudWatch Logs Insights는 실시간성 로그와 모니터링에 맞고,
대용량 로그의 장기 저장과 복잡한 분석에서는 S3 + Athena 조합보다 떨어진다.

> [데이터분석 #118 p245] "(B) Amazon OpenSearch: 데이터를 쿼리하고 분석하는 건 가능하지만, OpenSearch를 클러스터로 운영하는 게 비용이 많이 들며 '간헐적인' 분석 용도로는 오버헤드가 크다."
> [데이터분석 #118 p245] "(D) Amazon CloudWatch Logs Insights: 실시간성 로그 및 모니터링에는 적합하지만, 대용량 로그의 장기 저장 및 복잡한 데이터 분석의 측면에서는 S3 + Athena 조합보다 효율성이 떨어진다."

## security-groups-nacl

### `security-group-referencing` — 보안 그룹 참조

**한 줄**: 보안 그룹 규칙의 소스로 IP 대신 다른 보안 그룹 ID를 지정하는 방식이다.

특정 EC2 인스턴스들만 DB에 접근하게 하려는데 Auto Scaling으로 인스턴스 IP가 계속 바뀐다면,
IP 기반 규칙으로는 관리할 수 없다.

DB 보안 그룹의 인바운드 소스로 애플리케이션 보안 그룹의 ID를 지정하면,
그 보안 그룹에 속한 인스턴스만 통과한다. IP가 바뀌어도 자동으로 따라간다.

> [보안1 #120 p250] "보안 그룹 규칙에서 다른 보안 그룹 ID를 소스로 지정할 수 있다. ... Auto Scaling을 통해 EC2 인스턴스의 IP가 수시로 변하더라도, 보안 그룹 기반 필터링은 이를 자동으로 추적하므로 별도의 관리 부담이 없다."

### `nacl-rule-limit` — NACL의 규칙 수 제한

**한 줄**: NACL은 규칙 수에 제한이 있어(일반적으로 20~40개 권장) 대량의 IP나 국가 대역을 담을 수 없다.

매장 5만 곳의 공인 IP를 허용하거나 국가별 IP 대역을 차단하는 요구는
NACL로 처리할 수 없다. 이 규모의 IP·국가 필터링은 WAF의 IP 세트나
지리적 일치 규칙으로 간다.

> [보안2 #131 p273] "네트워크 ACL은 규칙 수에 제한(일반적으로 20~40개 권장)이 있어 50,000개의 매장 IP를 개별적으로 등록하는 것은 불가능하다."
> [보안2 #134 p279] "국가별 IP 대역은 수시로 변경되고 그 수가 매우 많아 NACL의 규칙 제한(Rule Limit) 내에서 관리하는 것이 불가능합니다."

### `web-acl-vs-nacl` — Web ACL과 네트워크 ACL은 다른 것

**한 줄**: Web ACL은 WAF에서만 쓰는 개념이고, 네트워크 ACL(NACL)과 아무 관계가 없다.

이름이 비슷해서 헷갈리기 쉽다. Web ACL은 웹 요청을 허용할지 차단할지 판단하는
WAF의 규칙 묶음이고, NACL은 서브넷 경계에서 IP 기반으로 트래픽을 통제하는 기능이다.

> [보안2 #131 p273] "참고로, Web ACL이랑 NACL이랑은 완전히 별개의 개념이다. Web ACL은 WAF에서만 쓰이는 개념이고, 웹 요청을 허용/차단할 지 판단하는 접근 제어를 의미한다."

## secrets-encryption

### `acm-cloudfront-region` — CloudFront에 붙일 인증서는 us-east-1에서 발급한다

**한 줄**: CloudFront에서 사용자 지정 도메인에 HTTPS를 적용하려면 ACM 인증서를 반드시 us-east-1(버지니아 북부)에서 만들어야 한다.

S3 버킷이 eu-west-1에 있든 어디에 있든 상관없다. CloudFront는 글로벌 서비스지만
인증서 관리가 us-east-1과 연동되어 있어서, 다른 리전에서 발급한 ACM 인증서는
CloudFront가 직접 쓸 수 없다.

이 제약은 리전 이름까지 그대로 묻는 형태로 출제된다.

> [보안3 #151 p314] "Amazon CloudFront에서 사용자 지정 도메인에 HTTPS를 적용하려면, SSL/TLS 인증서는 반드시 us-east-1(버지니아 북부) 리전에서 생성해서 가져와야 한다. 이건 CloudFront가 글로벌 서비스임에도 불구하고 인증서 관리 시스템이 해당 리전과 연동되어 있기 때문이다."

### `lambda-env-var-kms` — Lambda 환경 변수의 KMS 암호화

**한 줄**: 환경 변수에 KMS 키를 지정하면 관리 콘솔에서도 값이 가려지고, 복호화 권한이 있는 사용자만 열람할 수 있다.

Lambda 환경 변수에 DB 접속 정보나 API 키를 평문으로 두면 콘솔 접근 권한이 있는
개발자가 그대로 읽을 수 있다. KMS 키로 암호화하면 저장 시 암호화되고,
콘솔에서도 별도의 복호화 권한을 가진 사용자만 내용을 볼 수 있다.

다만 자격 증명을 주기적으로 자동 교체해야 한다면 이 방식으로는 부족하다.
순환 로직을 직접 만들어야 하므로 Secrets Manager로 간다.

> [보안1 #122 p254] "Lambda 환경 변수를 설정할 때 KMS 키를 선택하면, AWS 관리 콘솔에서도 해당 값이 암호화되어 보이며 '복호화' 버튼을 누를 수 있는 별도의 권한이 있는 사용자만 내용을 확인할 수 있다."

### `cloudhsm` — AWS CloudHSM

**한 줄**: 전용 하드웨어 보안 모듈로 매우 높은 수준의 키 보안이 필요할 때 쓴다.

KMS로 충분한 일반적인 암호화에 CloudHSM을 도입하는 것은 비용과 관리 복잡성이
지나치게 높다. 선택지에 나오면 "이 정도 요구에 이게 필요한가"를 먼저 따진다.

> [보안1 #122 p254] "(B) CloudHSM: 매우 높은 수준의 보안이 필요한 경우에 사용하지만, 단순 Lambda 환경 변수 암호화를 위해 도입하기에는 비용과 관리 복잡성이 지나치게 높다."

### `rotation-heuristic` — 자동 순환이 나오면 Secrets Manager

**한 줄**: 비밀번호·자격 증명을 주기적으로 자동 교체하라는 요구가 나오면 Secrets Manager다.

"30일마다 마스터 비밀번호 변경", "자격 증명을 정기적으로 교체", "자동 순환(Rotation)" —
표현이 무엇이든 같은 신호다. Secrets Manager는 RDS와 통합되어 이 기능을 기본 제공한다.

Systems Manager Parameter Store는 비밀값을 저장할 수는 있지만 자동 순환 기능이 없고,
KMS는 암호화 키를 관리하는 서비스이지 비밀값을 저장하는 서비스가 아니다.
Lambda + EventBridge로 직접 구현하는 선택지는 관리 부담 때문에 오답이 된다.

> [보안1 #123 p256] "'자동 순환' 또는 '자격 증명을 주기적으로 자동 변경하고 싶다'와 관련된 내용이 나오면 대부분 AWS Secrets Manager가 정답이다."
> [보안1 #125 p260] "비밀번호를 주기적으로 변경할 수 있는 기능인 순환(Rotation) 기능이라는 얘기가 나오면 AWS Secrets Manager가 정답이다."

## threat-protection

### `waf-attach-targets` — WAF를 붙일 수 있는 곳

**한 줄**: 로드 밸런서 중에서는 ALB에만 붙고 NLB에는 붙지 않으며, CloudFront 배포에는 붙는다.

S3 정적 웹사이트 엔드포인트에는 WAF를 직접 연결할 수 없다.
S3를 WAF로 보호하려면 앞에 CloudFront를 두고 CloudFront에 WAF를 붙인다.

CloudFront에 붙이면 트래픽이 AWS 네트워크나 온프레미스 오리진에 닿기 전에 검사되므로,
멀티 오리진 구성에서 전체 시스템을 한 번에 보호할 수 있다.

> [컴퓨팅1 #54 p112] "AWS WAF는 로드밸런서 중에서 ALB에만 연동할 수 있다."
> [보안2 #136 p283] "S3의 정적 웹 사이트 호스팅 엔드포인트에는 AWS WAF를 직접 연결할 수 없습니다(CloudFront를 껴야 함)."
> [보안2 #130 p271] "CloudFront에 WAF를 연결하면 트래픽이 AWS 네트워크나 온프레미스로 들어오기 전, 웹 취약성 공격을 미리 차단할 수 있어"

### `waf-bot-control` — AWS WAF Bot Control

**한 줄**: 봇 트래픽을 탐지하고 제어하는 데 특화된 WAF 기능이다.

전 세계에서 오는 악성 봇이 불필요한 요청을 대량으로 보내 컴퓨팅 리소스를 낭비하는
상황에 쓴다. 요청 속도 같은 행동 패턴을 기준으로 판단한다.

알려진 악성 IP를 막는 IP 평판 규칙보다 범위가 넓고, DDoS 방어에 초점을 둔
Shield와는 목적이 다르다.

> [보안2 #127 p265] "AWS WAF Bot Control: 봇 트래픽을 탐지하고 제어하는 데 초점이 맞춰진 기능이다."

### `waf-rule-types` — WAF 규칙의 종류

**한 줄**: IP 세트, 지리적 일치, IP 평판 규칙으로 트래픽을 걸러낸다.

IP 세트는 수많은 IP 주소를 묶어서 허용하거나 차단할 때 쓴다.
단일 악성 IP를 즉시 막는 것도, 매장 5만 곳의 IP만 허용하는 것도 IP 세트다.

지리적 일치 규칙은 국가 코드 기준으로 허용·차단한다.
"미국과 한국에서 오는 트래픽만 허용"이 여기에 해당한다.

IP 평판 규칙은 이미 알려진 악성 IP를 차단하는 관리형 규칙이다.

> [보안2 #131 p273] "AWS WAF의 IP 세트 일치 규칙은 수많은 IP 주소를 효율적으로 관리하고 필터링할 수 있는 기능이다."
> [보안2 #134 p279] "AWS WAF 지리적 일치는 특정 국가 코드를 기반으로 트래픽을 허용하거나 차단하는 기능이다."
> [보안2 #127 p265] "(D) IP 평판 규칙: 알려진 악성 IP를 차단하는 데 유용하지만"

### `shield-advanced-drt` — Shield Advanced와 DRT

**한 줄**: 정교한 DDoS 공격에 대비하고 AWS 전담 대응 팀(DRT)의 지원을 받으려면 Shield Advanced가 필요하다.

기본 Shield를 넘어서는 영역이다. 문제에 "AWS의 전담 대응 팀 지원"이나
"대규모 볼륨 공격에 대한 인프라 보호"가 나오면 Advanced를 고른다.

WAF는 애플리케이션 계층 공격 방어에는 유효하지만 DRT 지원은 제공하지 않는다.

> [보안2 #135 p281] "(A) AWS WAF: 애플리케이션 계층 공격 방어에는 유효하지만, DRT 지원이나 대규모 볼륨 공격에 대한 인프라 보호는 Shield Advanced의 영역입니다."

### `guardduty-db-login` — GuardDuty의 데이터베이스 로그인 이상 탐지

**한 줄**: GuardDuty는 Aurora 등에 대한 비정상 로그인 실패 패턴과 수상한 접속 시도를 탐지한다.

계정 수준의 해킹 모니터링만 하는 것이 아니라 데이터베이스 로그인 이상까지 잡아낸다.
CloudTrail은 AWS API 호출을 기록할 뿐 데이터베이스 내부의 로그인 시도는 남기지 않으므로
같은 요구를 충족하지 못한다.

> [보안2 #138 p287] "GuardDuty가 데이터베이스에 대한 비정상적인 로그인을 탐지하는 기능을 가지고 있다."
> [보안2 #138 p287] "(D) CloudTrail은 AWS API 호출을 기록하지만, 데이터베이스 내부의 로그인 시도는 기록하지 않으므로 요구 사항을 충족할 수 없다."

### `security-service-lineup` — 헷갈리기 쉬운 보안 서비스 네 가지

**한 줄**: Detective는 조사, Inspector는 취약점 스캔, Firewall Manager는 규칙 통합 관리, Network Firewall은 네트워크 방화벽이다.

**Amazon Detective** — 보안 문제를 조사하고 분석하는 도구다. 트래픽을 능동적으로
차단하지 않으므로 "즉시 차단"이 요구인 문제에서는 오답이다.

**Amazon Inspector** — EC2 인스턴스의 보안 취약점을 스캔한다.
소프트웨어 패치 누락, CVE 취약점을 탐지하며 DDoS 방어와는 무관하다.

**AWS Firewall Manager** — 여러 계정의 방화벽 규칙을 통합 관리한다.
단일 계정·단일 ALB 상황이라면 WAF를 직접 쓰는 편이 간단하다.

**AWS Network Firewall** — 네트워크 계층 방화벽이다. 웹 애플리케이션 계층(L7) 보안에는
WAF가 더 적합하고, 정적 웹 호스팅에 쓰기에는 과한 구성이 된다.

> [보안2 #132 p275] "(B) Amazon Detective: 보안 문제를 조사하고 분석하는 도구이지, 트래픽을 능동적으로 차단하는 방화벽 서비스가 아닙니다."
> [보안2 #135 p281] "(C) Amazon Inspector: EC2 인스턴스의 보안 취약점을 스캔하는 서비스입니다. 소프트웨어 패치 누락, CVE 취약점 등을 탐지하지만, DDoS 공격 방어와는 무관합니다."
> [보안2 #131 p273] "(B) Firewall Manager: 여러 계정의 규칙을 통합 관리하는 도구입니다."
> [보안2 #136 p283] "(C) NLB & Network Firewall: 정적 웹 호스팅을 위해 EC2와 비싼 Network Firewall을 사용하는 것은 과도한 아키텍처(Over-engineering)입니다."

## identity-access

### `least-privilege` — 최소 권한 원칙 (Least Privilege)

**한 줄**: 업무 수행에 딱 필요한 만큼의 권한만 부여하는 보안의 기본 원칙이다.

개발자 실수로 인한 데이터 유출을 막으려는 문제에서 답의 방향을 정하는 원칙이다.
계정 공유나 모든 리소스에 접근 가능한 액세스 키 지급은 이 원칙을 정면으로 어긴다.

권한을 IAM 사용자 개개인에게 직접 붙이는 대신 IAM 역할로 관리하면
권한 관리가 쉬워지고 보안성도 올라간다.

> [보안3 #140 p292] "최소 권한 원칙 (Least Privilege): 보안의 기본 원칙으로, 업무 수행에 딱 필요한 만큼의 권한만 부여하는 것을 의미한다."

### `instance-profile` — IAM 인스턴스 프로파일

**한 줄**: IAM 역할을 EC2 인스턴스에 붙이는 매개체다. 역할은 장기 액세스 키를 갖지 않는다.

EC2가 S3나 Secrets Manager 같은 다른 AWS 서비스를 호출해야 할 때는
인스턴스 안에 액세스 키를 저장하지 않고 IAM 역할을 인스턴스 프로파일에 연결한다.
이것이 보안 모범 사례이며, 어떤 형태로든(하드코딩·파일 저장·스크립트 조회)
장기 키를 인스턴스에 두는 선택지는 오답이다.

IAM 역할은 액세스 키 ID와 비밀 액세스 키를 갖지 않는다. 대신 STS를 통해 임시 자격 증명을 받는다.
"역할의 키를 만들어 연결한다"는 선택지는 기술적으로 성립하지 않는 문장이다.

> [보안3 #142 p296] "IAM 역할은 EC2 인스턴스 프로파일에 연결하고, 해당 프로파일을 인스턴스에 할당하는 방식으로 연동한다."
> [보안3 #142 p296] "IAM 역할은 장기 액세스 키(Access Key ID/Secret Access Key)를 가지지 않으며, STS를 통해 임시 자격 증명을 받습니다."

### `iam-group-users-only` — IAM 그룹에는 EC2를 넣을 수 없다

**한 줄**: IAM 그룹은 IAM 사용자들의 집합이라, EC2 같은 컴퓨팅 리소스를 넣을 수 없다.

EC2에 권한을 주는 선택지로 "IAM 그룹에 인스턴스를 추가한다"가 나오면 성립하지 않는 문장이다.
컴퓨팅 리소스에는 IAM 역할을 쓴다.

리소스 자체에 ID 기반 정책을 직접 붙이는 것도 불가능하다.
반드시 IAM 역할이라는 자격 증명 주체를 거쳐야 한다.

> [보안3 #152 p316] "(D) IAM 그룹: IAM 그룹은 IAM 사용자들의 집합이며, EC2 인스턴스(컴퓨팅 리소스)를 IAM 그룹에 직접 추가할 수는 없습니다."
> [보안3 #147 p306] "(D) 직접 권한 부여: EC2 인스턴스 자체(리소스)에 ID 기반 정책을 직접 붙일 수는 없습니다."

### `sts-assume-role` — STS로 임시 자격 증명 받기

**한 줄**: 온프레미스 서버나 외부 계약직처럼 AWS 밖의 주체가 장기 키 없이 리소스를 쓰는 방법이다.

온프레미스 애플리케이션이 S3에 로그를 올려야 하는데 장기 자격 증명을 쓸 수 없다면,
STS로 역할을 맡아(AssumeRole) 유효 기간이 있는 임시 자격 증명을 받는다.

단기 프로젝트에 투입된 외부 인원에게 권한을 줄 때도 마찬가지다.
시간이 지나면 자동으로 만료되므로 별도의 회수 절차가 필요 없다.
영구적인 IAM 사용자를 만들었다가 나중에 지우는 방식은 삭제를 잊으면 보안 구멍이 된다.

> [보안3 #148 p308] "AWS STS (Assume Role): 온프레미스 환경에서 장기 자격 증명(액세스 키)을 저장하지 않고 AWS 리소스를 사용하려면, STS를 통해 임시 자격 증명을 발급받는 것이 보안적으로 안전한 방식이다."
> [보안3 #144 p300] "시간이 지나면 자동으로 만료되므로 별도의 회수 절차가 필요 없기 때문이다."

### `cognito-pools` — Cognito 사용자 풀과 자격 증명 풀

**한 줄**: 사용자 풀은 인증을, 자격 증명 풀은 AWS 리소스 접근 권한을 담당한다.

사용자 풀(User Pool)로 로그인을 처리하고, 자격 증명 풀(Identity Pool)로
인증된 사용자에게 S3 같은 AWS 리소스에 접근할 임시 권한을 준다.
"사용자 풀만으로 S3 접근 권한을 준다"는 선택지는 역할이 어긋난 문장이다.

Cognito는 구글·페이스북 같은 외부 소셜 ID 공급자(IdP)를 통한 로그인도 지원한다.
API Gateway를 보호하면서 소셜 로그인을 붙여야 하는 문제에서 이 조합이 답이 된다.

> [보안3 #149 p310] "(B) 사용자 풀: 인증(Authentication)을 담당하며, AWS 리소스 접근 권한(Authorization)은 자격 증명 풀이 담당합니다."
> [보안3 #154 p320] "(C) Amazon Cognito: 외부의 소셜 로그인 기능을 가지고 있다."

### `organizations-scp` — AWS Organizations와 SCP

**한 줄**: 여러 AWS 계정을 묶어 관리하며, SCP는 계정이 절대 해서는 안 되는 행동을 제한하는 정책이다.

SCP(서비스 제어 정책)는 금지 목록을 거는 도구다. 비정상 패턴을 탐지하거나
분석하는 기능은 없으므로, 위협 탐지를 묻는 문제에서 SCP가 보이면 오답이다.

Organizations 환경에서 비용 할당 태그를 쓸 때는 관리 계정에서 한 번만 활성화하면 되고,
멤버 계정에서 개별로 활성화할 필요가 없다.

> [보안2 #138 p287] "(A) SCP: 서비스 제어 정책(SCP)은 계정이 절대 해서는 안 되는 행동을 제한하는 정책을 의미한다. 비정상적인 패턴을 탐지하거나 분석하는 기능은 제공하지 않는다."
> [비용관리 #162 p337] "(C) 멤버 계정에서 개별적으로 태그를 활성화할 필요는 없으며, 그렇게 해도 조직 전체 비용 집계에는 반영되지 않는다."

## cost-management

### `cost-allocation-tag-activation` — 비용 할당 태그는 활성화해야 보인다

**한 줄**: 리소스에 태그를 붙인 것만으로는 Cost Explorer에 나타나지 않는다. 결제 콘솔에서 활성화해야 한다.

순서가 중요하다. 먼저 리소스에 태그를 붙이고, 그다음 결제 대시보드에서
그 사용자 정의 태그를 활성화(Activate)해야 비용 분석 도구에서 쓸 수 있다.

이 두 단계를 함께 고르는 형태로 반복 출제된다. `aws:createdBy` 같은 시스템 태그는
부서별 비용 분석용이 아니다.

> [비용관리 #158 p329] "태그를 달았다고 바로 비용 리포트에 뜨지 않습니다. 반드시 결제 콘솔에서 해당 태그를 '활성화(Activate)'를 해야만 비용 분석 도구에서 사용할 수 있다."
> [비용관리 #162 p337] "(D) aws:createdBy는 시스템 태그로, 부서별 비용 분석과는 직접적인 관련이 없다."

### `savings-plan-details` — 절약 플랜의 적용 범위와 결제 옵션

**한 줄**: 컴퓨팅 절약 플랜은 EC2·Fargate·Lambda를 모두 덮고, 약정은 1년/3년에 선결제 여부를 고를 수 있다.

EC2와 Lambda를 함께 쓰거나 EC2와 Fargate를 섞어 쓰는 환경에서는
EC2 인스턴스 절약 플랜으로 할인을 받지 못하는 부분이 생긴다. 컴퓨팅 절약 플랜을 고른다.

결제 옵션은 선결제 없음(No Upfront), 부분 선결제(Partial Upfront), 전액 선결제(All Upfront)가 있다.
"다년 계약에 묶이고 싶지 않다"는 조건이면 1년 + 선결제 없음이 답이다.

> [비용관리 #157 p327] "Compute Savings Plans: EC2뿐만 아니라 Lambda 사용량에도 할인이 적용되는 절약 플랜이다."
> [비용관리 #160 p333] "No Upfront & 1 Year: '다년 계약에 묶이는 걸 원치 않는다'는 조건 때문에 선 결제가 없는 조건이 적절한 선택지이다."

### `cost-anomaly-detection` — Cost Anomaly Detection

**한 줄**: 예산 초과가 아니라 '평소와 다른 이상 지출 패턴'을 감지하는 기능이다.

"예산의 60%에 도달하면 알림"처럼 임계값 기반 요구에는 AWS Budgets가 맞다.
이상 탐지는 목적이 다르므로 그런 문제에서는 오답이다.

> [비용관리 #156 p325] "(B) Anomaly Detection: 이는 예산 초과보다는 '평소와 다른 이상 패턴'을 감지하는 데 쓰입니다."

### `compute-optimizer` — AWS Compute Optimizer

**한 줄**: 리소스 사양을 최적화하도록 권장해주는 도구이지, 비용을 집계하거나 보고하지 않는다.

팀별 비용을 집계해 보고서를 만드는 문제에 나오면 오답이다.
그 자리는 비용 할당 태그 + Cost Explorer다.

권장 사항을 제공한다는 점에서 Trusted Advisor와 성격이 비슷하고,
둘 다 예산 임계값 알림 기능은 없다.

> [비용관리 #161 p335] "(C) Compute Optimizer는 리소스 최적화 도구로, 비용을 집계하거나 보고하는 기능과는 무관하다."

## 원본 수정 이력

덤프 해설이 실제 AWS 동작과 어긋나는 곳이다. 학습자에게 틀린 사실을 가르치지 않기 위해
정확한 쪽으로 고쳐서 실었고, 원문을 함께 남긴다.

### 1. WAF를 붙일 수 있는 대상 — `threat-protection.waf-attach-targets`

- 덤프 원문 [컴퓨팅1 #54 p112]: "AWS WAF는 로드밸런서 중에서 ALB에만 연동할 수 있다."
- 문제: 이 문장만 읽으면 "WAF는 ALB에만 붙는다"로 읽힌다. 실제로는 CloudFront·API Gateway 등에도 붙고,
  덤프 자신도 다른 문항에서 CloudFront + WAF를 정답으로 쓴다.
- 반영: "로드 밸런서 중에서는 ALB에만"이라는 한정을 살리고, CloudFront에 붙는다는 사실을 함께 적었다.

### 2. NLB의 스티키 세션 — 싣지 않음

- 덤프 원문 [컴퓨팅1 #54 p112]: "(A) NLB: Sticky Session을 지원하지 않으며"
- 문제: 실제 NLB는 대상 그룹 고정(stickiness)을 지원한다. 덤프의 단순화로 보인다.
- 반영: 이 주장은 개념으로 싣지 않았다. `compute-delivery.sticky-session-tradeoff`는
  스티키 세션의 부하 편중 부작용만 다루며, NLB 지원 여부는 언급하지 않는다.

### 3. '가장 가까운 리전' 라우팅 정책 — 싣지 않음

- 덤프 원문 [네트워크2 #112 p232]: "지리적 근접(Geoproximity) 라우팅: 사용자 위치와 리소스 위치를
  기준으로 가장 가까운 AWS 리전으로 라우팅하는 정책"
- 문제: "지연 시간을 최소화한다"는 조건에서는 지연 시간 기반(Latency-based) 라우팅이
  더 표준적인 답이다. 두 정책의 경계가 덤프에서 흐릿하게 처리되어 있다.
- 반영: 라우팅 정책 선택을 묻는 개념·문항을 새로 만들지 않았다.
  `route53.multivalue-answer-details`는 다중값 응답의 동작만 다룬다.
