**데이터·테스트·코드는 이 step에서 한 글자도 바꾸지 않는다.** 재정렬은 step 1부터다.

## 작업

### 1. ADR-023 — 폐기하지 않고 개정 관계를 보이게 한다

사용자가 "ADR-023은 폐기하지 말고 ADR-033에 의해 개념 배열 규칙 부분이 개정되었다는 관계가
명확하게 보이게 해 줘"라고 했다. **ADR-023 본문의 기존 문장은 지우거나 고치지 않는다.**
아래 두 곳만 바꾼다.

**(가) 제목 줄.** 괄호 안 끝에 개정 관계를 덧붙인다.

바꾸기 전:

```
### ADR-023: 주제를 서비스 경계로 재편하고 개념 순서를 기본→갈림길→한계로 잡는다 (PRD "20개 주제"·ADR-021 개정)
```

바꾼 뒤:

```
### ADR-023: 주제를 서비스 경계로 재편하고 개념 순서를 기본→갈림길→한계로 잡는다 (PRD "20개 주제"·ADR-021 개정 / ADR-033으로 「개념 순서」 개정)
```

**(나) 개정 안내 한 문단.** ADR-023의 **결정** 문단(`**결정**: 주제를 20개에서 **39개**로 재편하고`로
시작해 `이 ADR이 정하는 것은 **배치와 순서**다.`로 끝나는 문단) 바로 뒤, `**크기가 아니라 서비스로
자른 이유**` 문단 앞에 아래 문단을 넣는다. 앞뒤로 빈 줄 하나씩을 둔다.

```
**ADR-033이 이 결정의 개념 순서 부분을 개정했다.** 3단(기본 → 갈림길 → 한계)은 이제 주제 전체가
아니라 **서비스 블록 안에서** 적용한다. 주제를 서비스 경계로 자른 결정, 헷갈리는 짝을 한 주제에
두는 결정, 층을 배열 순서로만 표현하고 `Concept`에 필드를 두지 않는 결정은 그대로다. 아래
「3단 정렬의 이유」는 이 ADR을 쓸 때의 근거로 남겨 둔다.
```

### 2. ADR-033을 `docs/ADR.md` 끝에 붙인다

파일의 마지막 ADR(ADR-032) 뒤에 빈 줄 하나를 두고 아래 텍스트를 **줄바꿈까지 그대로** 붙인다.
문장을 다듬거나 줄이지 마라 — 사용자가 승인한 내용이고 수치는 전수 점검 결과다.
파일은 개행 하나로 끝나게 둔다.

```
### ADR-033: 개념 배열을 서비스 블록 단위로 잡는다 (ADR-023 「개념 순서」 개정)
**결정**: 주제 안의 개념 배열 규칙을 바꾼다. ADR-023은 주제 **전체**에 1단(그 서비스가 무엇인가) →
2단(헷갈리는 것과 무엇으로 갈리는가) → 3단(한계값·설정·세부 동작)을 한 번 적용했다. 이제는 아래
다섯 규칙을 따른다. 사용자가 정한 문구를 그대로 옮긴다.

1. 서비스별 블록을 먼저 만든다.
2. 각 서비스 블록 안에서 `기본 개념 → 주요 기능/갈림길 → 세부 기능·설정·한계` 순으로 배치한다.
3. 같은 하위 기능에 속한 개념은 가능한 한 연속해서 둔다.
4. 둘 이상의 서비스를 비교하는 개념은 비교 대상 서비스 블록이 모두 나온 뒤에 둔다.
5. 어떤 개념이 다른 개념을 이해의 전제로 삼는다면 전제 개념을 먼저 둔다. 이 규칙은 위 규칙보다
   우선한다.

서비스가 하나뿐인 주제(`rds-storage-features`·`aurora`·`dynamodb`·`lambda`·`route53`·
`iam-permissions`)는 하위 기능을 블록으로 삼아 같은 규칙을 적용한다. 블록과 층은 여전히
**배열 순서로만** 표현하고 `Concept` 타입에 필드를 두지 않는다.

**이유 — 3단을 주제 단위로 적용해서 서비스가 왕복했다**: 사용자가 `data-transfer-services`를 읽고
"DataSync → Transfer Family → 다시 DataSync → 다시 Transfer Family처럼 같은 서비스가 여러 번 떨어져
등장한다. 초보자가 읽을 때 한 서비스의 개념을 이해하다가 다른 서비스로 넘어갔다가 다시 돌아와야
해서 가독성이 떨어진다"고 지적했다. 39개 주제를 전수 점검해 보니 이것은 그 주제 하나의 사고가
아니라 **ADR-023을 지킨 결과**였다. 서비스가 여럿인 주제에서는 1단에 모든 서비스의 기본 개념이
먼저 깔리고 3단에서 각 서비스의 세부가 다시 나오므로, 왕복이 규칙대로 생긴다. 한 서비스(서비스가
하나뿐인 주제에서는 하위 기능)를 떠났다가 돌아오는 왕복이 **39개 중 37개 주제**에 있었고, 서로
다른 서비스 사이를 세 번 이상 오가는 주제가 **23개**였다. 가장 심한 `sqs-sns-eventbridge`는 개념
33개 사이에서 12번 왕복했다.

**ADR-023에서 그대로인 것**: 주제를 서비스 경계로 자른 결정과 헷갈리는 짝을 한 주제에 두는 결정은
그대로다. 3단 정렬의 근거 — "Lambda가 무엇인지 모르는 사람에게 `lambda-layer-size-limit`은 아무것도
주지 않는다" — 도 그대로 산다. **기본이 세부보다 앞선다는 것은 블록 안에서 여전히 지켜진다.**
달라진 것은 3단을 적용하는 **단위**가 주제 전체에서 서비스 블록으로 내려온 것 하나다. 층을 화면에
표시하지 않는다는 판단도 그대로다.

**블록 안에서 주요 기능과 그 세부를 붙이는 법**: 규칙 2와 3이 부딪히는 자리가 있다. 주요 기능에
세부가 딸려 있으면 기능은 가운데 층에, 세부는 마지막 층에 있어 둘이 떨어진다. 그럴 때는 그 주요
기능을 **가운데 층의 끝, 자기 세부 바로 앞**에 둔다. 층 순서도 지켜지고 기능과 세부도 붙는다.
사용자가 `data-transfer-services`의 Transfer Family 블록을 이렇게 정했다 — 사용자 지정 DNS 이름·
ID 공급자·서비스 관리형 사용자(갈림길) 다음에 업로드 후 워크플로(주요 기능)를 두고, 바로 뒤에 그
워크플로의 미리 정의된 액션(세부)을 둔다.

**비교 개념과 전제의 자리**: 규칙 4에 따라 두 서비스를 가르는 개념은 둘 다 소개된 뒤에 온다.
`cloudfront-global-accelerator`의 `cloudfront-reduces-data-transfer-cost`는 CloudFront와 Global
Accelerator를 비용으로 가르므로 두 블록 뒤에 선다. 규칙 5는 규칙 4보다도 앞선다 —
`elastic-load-balancing`의 `alb-l7-vs-nlb-l4`는 ALB와 NLB를 가르는 비교 개념이지만, 첫 개념
`elb`가 둘을 이미 소개했고 ALB 블록의 `alb-routing-conditions`가 이 비교를 전제로 쓰므로 ALB 블록
앞에 둔다. 주제마다 어떤 블록을 어떤 순서로 두었고 어디에 규칙 5를 적용했는지는
`src/data/data.test.ts`의 주제별 순서 단언 주석에 적는다.

**트레이드오프 — 주제의 서비스를 먼저 한 번씩 훑는 효과를 잃는다**: ADR-023은 1단을 몰아 두어
앞의 몇 개만 읽어도 그 주제의 서비스를 모두 한 번씩 만나게 했다. 서비스 블록으로 묶으면 그 효과가
없어진다. 대가를 쟀다 — 앞 블록의 개념이 뒤 블록의 서비스를 먼저 언급하는 자리가 **6개 주제에
9곳** 남는다(`ebs-instance-store` 1, `sqs-sns-eventbridge` 2, `secrets-encryption` 1,
`waf-shield` 3, `organizations-cloudtrail-config` 1, `cost-management` 1). 모두 "X는 이 일을 하지
않는다" 식의 대비 문장이고, 같은 문장 안에서 X가 무엇인지 말한다. `waf-shield`는 WAF와 Shield가
서로를 대비로 부르는 짝이라 어느 쪽을 앞에 두어도 남는다. 본문을 고쳐 없앨 수는 있지만 이 결정의
범위(배열 순서) 밖이다.

**구조 스냅샷도 같은 순서로 옮긴다**: `scripts/check-structure.mjs`는 개념 순서를
`scripts/topics-baseline.json`과 대조하고, `scripts/sync-baseline.mjs`는 순서가 바뀌면 갱신을
거부한다 — 순서 변경은 구조 변경이라 사람이 스냅샷을 고쳐야 한다는 설계다. 그래서 재정렬한 주제의
개념 항목 순서만 `topics.json`과 같게 옮긴다. id·name·주제 메타데이터·`conceptLineCount`·
`questionsSha256`은 그대로다.

**범위 — 순서만 바뀐다**: 개념 id·name·summary·paragraphs, 문항과 문항 배열, 주제 메타데이터,
용어 표기는 한 글자도 바뀌지 않는다. 문항은 `conceptId`로만 개념을 가리키고 출제 때 섞이므로
(ADR-011) 순서의 영향을 받지 않는다. 진행률은 topicId·questionId를 키로 쓰고 `ConceptList`는 배열
순서대로 그리므로 코드도 바뀌지 않는다. 재정렬이 필요 없는 주제는 `aws-core-services`와
`s3-storage-classes` 둘이다 — 앞의 것은 서비스마다 세부 개념이 없어 왕복할 대상이 없고, 뒤의 것은
클래스 여덟 다음의 개념이 여러 클래스를 가로지르는 비교 축이다.

**대체된 기록**: `docs/source/dump-gaps/topic-plan.md`의 「주제 안의 개념 순서 — 3단으로 정렬한다」
절과 주제별 「3단 구분」은 phase 26의 기획 기록이다. 그 절의 규칙은 이 ADR로 대체됐고, 파일은
당시 기록으로 그대로 둔다.
```

### 3. `docs/ARCHITECTURE.md`의 개념 배열 규칙을 바꾼다

**(가) `interface Concept` 코드 블록 바로 아래의 주석 한 줄.**

바꾸기 전:

```
// concepts 배열의 순서가 학습 순서다: 1단(기본) → 2단(갈림길) → 3단(한계). 아래 절을 봐라.
```

바꾼 뒤:

```
// concepts 배열의 순서가 학습 순서다: 서비스 블록마다 기본 → 갈림길 → 한계. 아래 절을 봐라.
```

**(나) 그 아래 개념 배열 절 전체.** 아래 "바꾸기 전" 블록(굵은 글씨 문장부터 `지금은 하지 않는다
(ADR-023).`까지 11줄)을 "바꾼 뒤" 블록으로 통째로 바꾼다. 그 앞뒤의 다른 절은 건드리지 않는다.

바꾸기 전:

```
**주제 안의 개념 배열은 1단 → 2단 → 3단 순서다.** 근거는 ADR-023.

| 단 | 무엇 | 예 |
|---|---|---|
| 1단 | 그 서비스가 무엇인가 — 지도 | `lambda.lambda`, `ecs-eks-fargate.ecs` |
| 2단 | 헷갈리는 것과 무엇으로 갈리는가 | `ecs-eks-fargate.eks-compute-options` |
| 3단 | 한계값·설정·세부 동작 | `lambda.lambda-layer-size-limit` |

**`Concept`에 층 필드를 두지 마라.** 순서 자체가 층이고, 필드를 더하면 배열 순서와
필드가 어긋날 수 있는 두 번째 진실이 생긴다. 층을 화면에 표시하는 것은 별개의 판단이고
지금은 하지 않는다 (ADR-023).
```

바꾼 뒤:

```
**주제 안의 개념 배열은 서비스 블록 순서다.** 근거는 ADR-033이고, ADR-023의 3단 정렬을 개정한 것이다.

1. 서비스별 블록을 먼저 만든다.
2. 각 서비스 블록 안에서 `기본 개념 → 주요 기능/갈림길 → 세부 기능·설정·한계` 순으로 배치한다.
3. 같은 하위 기능에 속한 개념은 가능한 한 연속해서 둔다.
4. 둘 이상의 서비스를 비교하는 개념은 비교 대상 서비스 블록이 모두 나온 뒤에 둔다.
5. 어떤 개념이 다른 개념을 이해의 전제로 삼는다면 전제 개념을 먼저 둔다. 이 규칙은 위 규칙보다
   우선한다.

| 블록 안의 자리 | 무엇 | 예 (`data-transfer-services`의 DataSync 블록) |
|---|---|---|
| 기본 | 그 서비스가 무엇인가 | `data-transfer-services.datasync` |
| 주요 기능·갈림길 | 헷갈리는 것과 무엇으로 갈리는가 | `data-transfer-services.file-gateway-vs-datasync-continuous` |
| 세부 기능·설정·한계 | 한계값·설정·세부 동작 | `data-transfer-services.datasync-manifest` |

서비스가 하나뿐인 주제는 하위 기능을 블록으로 삼는다. 주요 기능에 세부가 딸려 있으면 그 기능을
가운데 층의 끝, 자기 세부 바로 앞에 둔다 — 층 순서(규칙 2)와 연속성(규칙 3)이 함께 지켜진다.
주제마다 어떤 블록을 어떤 순서로 두었는지는 `src/data/data.test.ts`의 주제별 순서 단언이 개념 id
전부로 못박고, 그 주석이 블록과 예외를 적는다.

**`Concept`에 층·블록 필드를 두지 마라.** 순서 자체가 블록과 층이고, 필드를 더하면 배열 순서와
필드가 어긋날 수 있는 두 번째 진실이 생긴다. 블록이나 층을 화면에 표시하는 것은 별개의 판단이고
지금은 하지 않는다 (ADR-023·ADR-033).
```
