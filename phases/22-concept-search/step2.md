# Step 2: search-entry

## 배경

step 1이 `/search` 라우트와 검색 화면을 만들었다. 지금은 주소창에 직접 쳐야 들어갈 수 있다.
이 step은 헤더에 진입 링크를 붙여 앱 안에서 도달 가능하게 만든다.

**이 step의 핵심은 링크를 언제 숨기는가다.** 헤더는 320px에서 링크 두 개가 상한이다.

## 읽어야 할 파일

- `CLAUDE.md` — 아키텍처 규칙과 TDD 규칙.
- `docs/UI_GUIDE.md` — **"상단 고정 헤더 > 헤더 안의 링크"** 절 전체. 도표와 금지 항목이
  거기 있다. "랜덤 문제 진입점" 절도 읽어라 — 같은 320px 제약 때문에 헤더행이 거절된 선례다.
- `docs/ARCHITECTURE.md` — **"헤더의 컨텍스트 링크"** 절.
- `docs/ADR.md`의 **ADR-013**.
- `src/components/Layout.tsx` — 이 step에서 고치는 **유일한 소스 파일**이다.
- `src/components/Layout.test.tsx` — 헤더 링크·터치 높이·스크롤 회귀 테스트가 여기 있다.
- `src/App.test.tsx` — 라우트별 헤더 링크를 확인하는 테스트가 있다.

## 작업

CLAUDE.md의 TDD 규칙에 따라 **테스트를 먼저 쓰고 실패를 확인한 뒤** 구현한다.

`src/components/Layout.tsx`의 `<nav>`에 검색 링크를 추가한다.

```
[AWS SAA-C03]              [검색]   [복습]      ← 주제 목록·복습·개념 읽기·랜덤
[AWS SAA-C03]           [근거 개념]  [복습]      ← 확인 문제
```

- 링크 문구는 `검색`, 목적지는 `/search`다.
- **`복습` 왼쪽에 둔다.** `근거 개념`이 들어가는 자리와 같은 쪽이다.
- 기존 `linkClassName`을 그대로 쓴다. 새 클래스 문자열을 만들지 마라.

### 확인 문제 화면에서는 렌더하지 않는다

- 판별은 **이미 파일에 있는 `quizMatch`를 쓴다.** `useMatch('/topic/:topicId/quiz')`의
  결과이고, 지금 `근거 개념`을 켜는 데 쓰이고 있다. 같은 값으로 `검색`을 끈다.
- **두 번째 `useMatch`나 `useLocation` 분기를 만들지 마라.** 이유: 조건이 둘로 갈리면
  한쪽만 고쳤을 때 링크 세 개가 동시에 뜨는 상태가 조용히 생긴다.
- **회색 비활성 상태로 남기지 마라.** 조건부로 아예 렌더하지 않는다.
  UI_GUIDE가 헤더에 비활성 항목을 두는 것을 금지한다(하단 바의 비활성 화살표는 가운데
  버튼이 밀리지 않게 자리를 지키는 것이고, 헤더에는 그런 이유가 없다).
- 왜 숨기는지: 320px에서 헤더 링크가 세 개가 되면 로고와 부딪힌다. 확인 문제 화면은
  `근거 개념`이 이미 한 칸을 쓰고 있다. 문제를 푸는 중에 개념으로 가는 길은 그 링크가
  맡으므로 잃는 경로가 없다.
- **랜덤 문제 화면(`/random/:count`)에는 `검색`이 뜬다.** `quizMatch`가 매치되지 않아
  자동으로 그렇게 된다. `/random`용 분기를 따로 넣지 마라.

## 테스트

`src/components/Layout.test.tsx`에 덧붙인다. 기존 테스트의 렌더 헬퍼 패턴을 따른다.

1. 일반 화면(`/`)에서 `검색` 링크가 `href="/search"`로 렌더된다.
2. 확인 문제 화면(`/topic/:topicId/quiz`)에서는 `검색` 링크가 **없다**.
   같은 화면에서 `근거 개념`은 있다(기존 테스트가 이미 검증한다면 중복하지 마라).
3. **어느 화면에서도 `주요 내비게이션` 안의 링크가 두 개를 넘지 않는다.**
   최소한 일반 화면과 확인 문제 화면 두 경우를 확인한다.
   이 테스트가 이 step의 제약을 코드로 고정하는 장치다 — 320px 폭은 jsdom에서 잴 수 없으므로
   **링크 개수로 대신 지킨다.** 빼지 마라.
4. `검색` 링크가 최소 터치 높이(`min-h-[44px]`) 클래스를 갖는다.
   기존 "로고와 내비게이션 링크의 최소 터치 높이를 보장한다" 테스트가 링크를 순회하는
   방식이라면 그 테스트가 자동으로 덮는다 — 그렇다면 새로 만들지 마라.

`src/App.test.tsx`의 기존 테스트 중 헤더 링크를 단언하는 것이 있으면 깨지지 않는지 확인한다.

## 금지사항

- **헤더에 링크를 세 개 이상 만들지 마라.** 이유: 320px에서 로고와 부딪힌다.
  확인 문제 화면에서 `검색`을 숨기는 것이 이 규칙을 지키는 방법이다.
- **돋보기 아이콘으로 바꿔 네 항목을 다 넣으려 하지 마라.** 이유: 아이콘(52px)으로 줄여도
  세 칸 합이 로고를 밀어낸다. 아이콘이 없애는 것은 폭이 아니라 "무슨 링크였는지"다.
- **헤더 높이를 바꾸지 마라.** 77px은 `py-4`와 `min-h-[44px]`에서 나온 값이다.
- **`src/pages/` 아래 파일을 고치지 마라.** 이유: step 1이 이미 검증한 화면이다.
  이 step은 `Layout` 하나만 건드린다.
- **주제 목록에 검색 입력을 추가하지 마라.** 이유: PRD가 개정된 범위는 개념 검색 화면
  하나뿐이고, "주제 20개는 목록으로 훑는 게 더 빠르다"는 판단은 그대로다.
- 기존 테스트를 깨뜨리지 마라.
