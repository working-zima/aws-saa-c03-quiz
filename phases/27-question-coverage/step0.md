# Step 0: coverage-rule — 문제 은행의 크기 기준을 커버리지로 바꾼다

## 읽어야 할 파일

- `/CLAUDE.md` — 특히 "아키텍처 규칙"과 "원본 데이터", "개발 프로세스"(TDD)
- `/docs/PRD.md` — 「사용자」·「목표」·**「문제 은행」(step 0이 개정했다. 크기 기준이 커버리지다)**
- `/docs/ARCHITECTURE.md` — 「데이터 모델」·「테스트 경계」
- `/docs/ADR.md` — **ADR-026**(step 0이 추가한 커버리지 결정), ADR-021(덤프 해설의 지위),
  ADR-009(전사 금지), ADR-011(문항 표현 규칙), ADR-017(오답노트), ADR-023(주제 재편)
- `/src/types/content.ts` — `Question` 타입
- `/src/data/questions.json` — 고칠 대상. **여기에만 더한다**
- `/src/data/topics.json` — 근거 개념. **읽기만 한다**
- `/src/data/data.test.ts` — 문항 불변식

이 step은 **문서와 작은 스크립트만** 만든다. `src/`를 건드리지 마라.

## 배경 — 이 phase가 존재하는 이유

이 앱의 목적은 **"확인 문제만 계속 풀어도 개념 공부가 다 되는 것"** 이다. 문제를 풀고,
틀린 것만 개념으로 되짚고, 다시 풀면서 암기가 되게 하는 순환이 주 학습 경로다.

그런데 실측하면 **개념 618개 중 문항이 가리키는 것은 175개뿐이다(28%).** 나머지 443개는
문제만 푸는 학습자에게 존재하지 않는다. 게다가 주제 5개(`s3-access-control`·`redshift-opensearch-quicksight`·`systems-manager`·`governance-iac`·`ai-ml-services`)는
문항이 0개라 확인 문제 화면에 들어갈 수조차 없다.

PRD 「문제 은행」은 **"총 169문항 목표, 22개 주제에 중요도 비례로 배분"** 이라고 적혀 있다.
이것은 개념이 182개이던 시절의 기준이고, 위 목적과 어긋난다. **중요도가 아니라 커버리지가
기준이어야 한다.** 이 기준은 뒤에 올 step 1~19가 전부 물려받으므로 여기서 먼저 바꾼다.

## 작업

### 1. PRD 「문제 은행」을 개정한다

- 크기 기준을 **개념 커버리지**로 바꾼다: **개념당 최소 1문항.** 출제되지 않은 개념을 남기지
  않는다. "총 169문항 목표"와 "중요도 비례 배분"은 낡은 기준이므로 그 자리에서 대체하되,
  **왜 바뀌었는지 한 문장을 남긴다**(기록을 지우지 마라).
- **해설의 역할을 규칙으로 적는다**: 해설은 정답을 정당화하는 글이 아니라 그 개념을 가르치는
  글이다. 정답 사실과 오답이 왜 아닌지를 함께 담고, 짧게 줄이지 않는다. 이유: 문제만 푸는
  사용자에게는 해설이 유일한 설명 텍스트다.
- 기존 규칙(오답을 같은 범주에서 고른다, 정답 키워드가 곧 답이 되지 않게 한다, 부정형 대조
  문항을 둔다)은 **그대로 살린다.** 이 개정은 크기 기준과 해설 규칙만 다룬다.
- 「MVP 제외 사항」의 검색 항목 등 다른 절은 건드리지 마라.

### 2. ADR-026을 추가한다

마지막 ADR 번호를 확인하고 그 다음 번호를 쓴다(지금은 ADR-025가 마지막이다).
제목은 `문제 은행의 크기를 개념 커버리지로 정한다 (PRD 「문제 은행」 개정)` 꼴로 한다.
담을 것:

- **결정**: 개념당 최소 1문항. 커버리지 100%를 목표로 하고, 이 phase가 443개념을 덮는다.
- **이유**: 위 배경. 목적이 "문제만 풀어도 공부가 된다"이므로 출제되지 않은 개념은 사각지대다.
- **실측 근거**: 618개념 중 175개(28%) 덮임. 문항 246개가 서로 다른 개념 175개를 가리킨다
  (한 개념에 여러 문항이 붙기 때문). 문항 0개 주제 5개.
- **왜 지금 하는가**: 덮이지 않은 443개념 중 **436개(98%)가 이미 `dump-gaps/`에 근거 항목과
  덤프 인용(`[Q번호 p쪽]`)을 갖고 있다.** 근거 찾기가 끝나 있으므로 지금이 가장 싸다.
- **트레이드오프**: 문제 은행이 246개에서 약 700개로 커진다. 복습 화면(오답 전체)과
  `/random/all`이 그만큼 길어진다 — ARCHITECTURE 「화면 전환 시 스크롤」의 실측값(복습 36891px)이
  다시 낡는다. 그 결정은 이 phase 밖의 열린 문제로 남긴다.
- **해설을 짧게 쓰지 않는 이유**도 함께 적는다.

### 3. `scripts/coverage.mjs`를 만든다

step 1~19가 자기 담당을 다 덮었는지 **실행으로** 확인할 수 있어야 한다.

```
node scripts/coverage.mjs              # 주제별 커버리지 표와 전체 비율
node scripts/coverage.mjs <topicId>…   # 주어진 주제만. 덮이지 않은 개념 id를 전부 찍는다
```

- 의존성을 더하지 마라. Node 18 표준 모듈만 쓴다(`node:fs` 등).
- `src/data/topics.json`과 `src/data/questions.json`을 읽어 `conceptId`로 대조한다.
- 인자로 준 주제가 **전부 100%면 exit 0, 아니면 남은 개념 id를 찍고 exit 1.**
- `npm test`·`npm run build`에 엮지 마라. 이유: step 20이 커버리지를 테스트로 고정할 때까지는
  개발 중 상태가 정상이고, 빌드를 막으면 step 1~19가 진행되지 않는다.

## Acceptance Criteria

```bash
npm run build                                   # 컴파일 에러 없음
npm test                                        # 기존 테스트 그대로 통과
node scripts/coverage.mjs | tail -3             # 전체 커버리지 28%가 찍힌다
node scripts/coverage.mjs s3-access-control            # 0%이므로 exit 1 (이 시점에서는 정상)
```

## 검증 절차

1. 위 AC 커맨드를 실행한다.
2. 아키텍처 체크리스트를 확인한다:
   - ARCHITECTURE.md 디렉토리 구조를 따르는가?
   - ADR 기술 스택을 벗어나지 않았는가?
   - CLAUDE.md CRITICAL 규칙을 위반하지 않았는가?
3. 결과에 따라 `phases/27-question-coverage/index.json`의 해당 step을 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"`
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

`summary`에는 **네가 쓴 문항 id 범위와 개수, 주제별 문항 수, 담당 개념을 하나도 남기지
않았다는 확인**을 반드시 적어라. 다음 step이 그 뒤 id부터 이어 쓴다.

## 금지사항

- **`src/`를 건드리지 마라.** 이 step은 기준과 도구만 만든다. 문항은 step 1~19가 쓴다.
- `scripts/topics-baseline.json`을 고치지 마라. 이유: 아직 문항이 바뀌지 않았다.
- 커버리지 목표를 낮추지 마라. "출제 가치가 있는 개념만"으로 좁히면 목적이 깨진다.
  5개 주제 44개념을 실제로 훑어 확인한 결과 **전부 출제 가능하다** — 서비스 정의,
  변별 축(`athena-vs-redshift-workload`), "이건 아니다" 유형(`s3-cors-not-authorization`)으로
  나뉘고 마지막 유형이 특히 좋은 문항이 된다.
- 기존 테스트를 깨뜨리지 마라.
