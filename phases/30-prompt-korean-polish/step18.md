## 이 phase가 세우는 기준 — 사용자가 직접 준 것이다

사용자의 요청을 그대로 옮긴다.

> 단순히 의미만 전달되는 번역체 문장이 아니라, **한국어로 자연스럽게 읽히는 문제 문장**으로
> 다듬어줬으면 해. (…) 기존 문제의 **기술적 의미와 난이도는 유지하고, 한국어 표현만**
> 자연스럽게 개선해줘.

적용할 기준 여섯이다.

1. 지나치게 직역한 표현이나 어색한 주어·조사 사용을 자연스럽게 고친다.
2. 문제의 상황을 설명하는 문장은 필요하면 `~하는 상황이다`, `~해야 하는 상황이다`처럼
   **맥락이 이어지도록** 쓴다.
3. 문장이 너무 길면 **의미 단위로 나눈다.** 단 시험 문제의 **의미와 조건은 절대 바꾸지 않는다.**
4. 조사나 어미 때문에 번역투로 느껴지는 문장을 자연스러운 한국어로 고친다.
5. **지나치게 구어체로 만들지 않는다.** 시험 문제다운 문체를 유지한다.
6. 기술 용어와 **정답을 유추할 수 있는 핵심 조건은 삭제하거나 약화하지 않는다.**

### 사용자가 보여준 예 둘 — 이것이 합격선이다

```
(이전) 규정이 데이터가 S3 버킷에 도착하기 전에 이미 암호문이어야 한다고 요구한다.
       어떤 암호화 방식을 써야 하는가?
(이후) 규정에서 데이터가 S3 버킷에 도착하기 전에 이미 암호화된 상태여야 한다고 요구한다.
       어떤 암호화 방식을 사용해야 하는가?
```

```
(이전) S3 버킷에 올리는 객체를 암호화해 두기만 하면 된다. 암호화 키를 만들거나 보관하는
       일에는 손대고 싶지 않고, 키 교체나 키 사용 기록도 필요하지 않다.
       이때 고르는 것은 무엇인가?
(이후) S3 버킷에 올리는 객체를 암호화해 두기만 하면 되는 상황이다. 암호화 키를 직접
       생성하거나 보관할 필요가 없고, 키 교체나 키 사용 기록도 필요하지 않다.
       이때 적절한 암호화 방식은 무엇인가?
```

두 예에서 읽어 낼 것 넷.

- **`요구한다` → `요구에서 … 요구한다`처럼 조사를 고쳐 주체를 바로 세운다.**
  `규정이 … 요구한다`가 아니라 `규정에서 … 요구한다`다.
- **명사형 한자어 대신 풀어 쓴다.** `암호문이어야 한다` → `암호화된 상태여야 한다`.
- **상황 문장은 `~하는 상황이다`로 닫아 다음 문장과 이어 준다.** `…하면 된다.`처럼
  단정으로 끊으면 뒤 문장이 새로 시작하는 것처럼 읽힌다.
- **묻는 문장을 온전한 물음으로 닫는다.** `이때 고르는 것은 무엇인가?`보다
  `이때 적절한 암호화 방식은 무엇인가?`가 낫다 — **무엇을 고르는 것인지**가 물음 안에 있다.
  `쓰는가` 대신 `사용해야 하는가`처럼 서술어도 온전하게 쓴다.

### 앞선 phase가 세운 기준도 그대로 지킨다 (ADR-030)

- **한 문항은 개념 하나만 묻는다.** 요구를 겹치지 마라.
- **정답 보기의 이름이나 그 일부를 프롬프트에 쓰지 마라.**
- **오답 보기는 프롬프트가 묻는 범주 안에 있어야 한다.**
- **뜻이 좁아지는 관용 표현(`돌린다`·`태운다`·`물린다`)을 쓰지 마라.**
- **`버킷`·`객체`·`접두사`처럼 서비스에 딸린 낱말을 쓰면 그 프롬프트 안에 서비스 이름을
  한 번은 넣어라.** 문항에는 주제 문맥이 없다 — ADR-011이 순서를 섞고 ADR-012·018의 랜덤
  세트는 732문항에서 일부만 뽑는다.
- **「누가 / 무엇을 / 왜」로 끊어 읽히게 쓴다.** 문장을 쪼개 문장마다 사실 하나를 담고,
  막연한 말은 이름으로 바꾸고, 주어를 앞에 세우고, 끝을 명시적 물음으로 닫는다.

이 기준들은 `docs/ADR.md`의 ADR-029·ADR-030에 있고 `scripts/content-audit.mjs`가 여섯 지표로
센다. **이 phase는 그 위에 「한국어로 자연스럽게 읽히는가」를 더한다.**

## 절대 바꾸지 말 것 — 어기면 되돌려야 한다

- **`id`·`topicId`·`conceptId`·`answerIndex`.** `answerIndex`는 `src/data/data.test.ts`가
  구간별 정답 위치 분포로 고정하고, `conceptId`는 커버리지 계산의 기준이다.
- **문항을 더하거나 지우거나 순서를 바꾸지 마라.** `data.test.ts`가
  `questions.slice(178, 187)` 같은 인덱스 구간으로 단언을 걸고 있어 하나만 더해도 뒤의 모든
  구간 단언이 다른 문항을 보게 된다. 지우면 개념 커버리지가 깨진다(ADR-026).
- **정답 논리를 바꾸지 마라.** 표현만 고친다. 어떤 보기가 정답인 이유가 달라지면 그것은
  이 phase의 범위를 넘은 것이다.
- **`src/data/topics.json`을 건드리지 마라.** 개념 본문은 phase 29가 정했다. 문항을 다듬으려고
  개념 본문을 고치지 마라.
- **모델이 아는 AWS 지식으로 조건을 지어내지 마라**(ADR-009·ADR-027). 표현을 다듬는 일이지
  사실을 더하는 일이 아니다. 상황 문장을 만들 때도 **이미 프롬프트에 있던 조건만** 쓴다.
- **`docs/source/`의 원문을 그대로 옮기지 마라**(ADR-009).

## 작업

### 1. 배치의 문항을 순서대로 다듬는다

각 문항의 `prompt`를 위 기준으로 다시 쓴다. **`choices` 중 문장형인 것도 같은 문체로 맞춘다** —
보기가 프롬프트와 한 화면에서 이어 읽히므로 한쪽만 다듬으면 이음새가 보인다. 서비스 이름만
적힌 짧은 보기(`SSE-KMS`, `S3 Bucket Key` 등)는 손댈 것이 없다.

**고칠 것이 없는 문항은 그대로 두어라.** 이미 자연스럽게 읽히는 문항을 굳이 바꾸면 diff만
커지고 검수가 어려워진다. 손대지 않은 문항 수를 `summary`에 적어라.

### 2. `explanation`은 프롬프트가 가리키는 것이 달라졌을 때만 고친다

이 phase는 해설을 다시 쓰는 일이 아니다. 다만 프롬프트의 문구를 해설이 그대로 인용하고
있으면 어긋나므로 그 자리만 맞춘다. 근거는 ADR-027의 셋뿐이다 — 그 문항 `conceptId`의 개념
본문, 오답 보기가 가리키는 개념의 본문(주제 밖이면 사양·수치 없이 성격만), 그 개념의
`docs/source/exam-gaps.md` 항목. 길이 하한 187자는 `data.test.ts`의 불변식이다.

### 3. `scripts/topics-baseline.json`의 `questionsSha256`을 갱신한다

`src/data/questions.json`이 바뀌면 `scripts/check-structure.mjs`가 막는다. 파일을 고친 뒤
sha256을 다시 계산해 넣어라. 계산 방법은 그 스크립트에 있다(파일 바이트 전체의 sha256).

### 4. `data.test.ts`가 고정한 프롬프트 문자열이 있으면 함께 갱신한다

`src/data/data.test.ts`는 일부 문항의 프롬프트를 문자열로 고정하고 있다. 다듬은 문항이 거기
걸리면 새 문구로 갱신하고, **왜 다시 썼는지 주석에 한 줄 남겨라.**

## Acceptance Criteria

```bash
npm test
npm run build
npm run lint
node scripts/check-structure.mjs
node scripts/coverage.mjs
```

전부 통과해야 한다. `check-structure.mjs`는 `questionsSha256`을 갱신한 뒤 exit 0이어야 한다.
그리고 이 배치의 주제마다 `node scripts/content-audit.mjs <topicId>`를 돌려 **③·④·⑤ 지표가
다듬기 전보다 늘지 않았는지** 확인한다(0건이 될 필요는 없다 — 이 phase의 목표가 아니다).

## 검증 절차

1. 위 AC 커맨드를 전부 실행한다.
2. **다듬은 프롬프트를 소리 내어 읽어라.** 번역투가 남았는지, 상황과 물음이 이어지는지,
   구어체로 기울지 않았는지 본다.
3. **다듬기 전후를 나란히 놓고 조건이 하나도 빠지지 않았는지 확인하라.** 이것이 이 phase의
   가장 큰 실패 방식이다 — 문장을 자연스럽게 만들려다 정답을 가르는 조건을 흘린다.
   `git diff src/data/questions.json`으로 문항마다 대조하라.
4. `phases/30-prompt-korean-polish/index.json`의 이 step을 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary"`에 **다듬은 문항 수, 손대지 않은 문항 수,
     자주 고친 번역투 패턴 두세 가지**를 적어라. 다음 step이 같은 패턴을 같은 방식으로 고쳐야
     문체가 통일된다.
   - 3회 시도 후 실패 → `"status": "error"`, `"error_message"`

## 금지사항

- **이 배치에 적힌 주제 밖의 문항을 고치지 마라.** 이유: 배치를 나눈 것은 step마다 검수
  단위를 만들기 위해서다. 남의 배치를 건드리면 어느 step이 무엇을 했는지 알 수 없게 된다.
