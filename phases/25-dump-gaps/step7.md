# Step 7: dump-gaps-301

## 읽어야 할 파일

먼저 아래 파일들을 읽고 프로젝트의 아키텍처와 설계 의도를 파악하라:

- `/CLAUDE.md` — 특히 "원본 데이터" 절
- `/docs/ADR.md` — ADR-006(출처 제한), ADR-008(덤프 해설의 지위와 오류 예외),
  ADR-009(전사 금지), **ADR-021(이 step의 근거)**
- `/docs/source/exam-gaps.md` — 항목 서술 형식의 전례. 헤더와 항목 두어 개만 훑어도 된다.
- `/docs/source/dump-gaps/README.md` — 이 phase가 쌓는 문서의 규칙
- `/docs/source/concept-index.md` — **앱이 이미 다루는 개념 182개.** 중복 판단의 기준이다.
- `/docs/source/dump-gaps/_index.md` — 앞 step들이 이미 뽑아 놓은 개념 목록. 역시 중복 판단용.
- `/docs/source/dump-slices/Q301-Q350.md` — **이번 step의 작업 대상 (50문항)**

step 0이 만든 스크립트와 슬라이스를 먼저 확인하고, 형식을 이해한 뒤 작업하라.

## 작업

`Q301`~`Q350` 50문항의 해설을 읽고, **정답 근거로 쓰였는데 앱에 없는 개념**만 추려
`docs/source/dump-gaps/Q301-Q350.md`에 쓴다.

### 무엇을 넣는가

- 정답을 고르는 데 실제로 필요한 사실. 서비스의 존재와 용도, 한계값, 전제 조건,
  헷갈리는 서비스 사이의 갈림길.
- **오답 보기에만 나오는 서비스도 대상이다.** 그 서비스가 무엇인지 몰라서 지우지 못하는 경우가 있다.

### 무엇을 넣지 않는가

- `concept-index.md`나 `_index.md`에 이미 있는 것. **중복은 적지 않는다.** 이 판단이 이 step의 핵심이다.
- 문제 상황 서술(어떤 회사가 무엇을 운영한다 같은 것). 개념이 아니다.
- 해설이 근거로 든 AWS 문서 링크나 제목.

### 항목 형식

`exam-gaps.md`와 같은 형식을 쓴다.

```markdown
### `{concept-id}` — {한 줄 제목}

**한 줄**: {요약 한 문장}

{직접 쓴 설명. 1~3문단.}

> [Q123 p456] "{덤프 원문 인용 한 문장}"
```

### 핵심 규칙

- **사실만 가져오고 문장은 직접 써라.** 원본 문장을 그대로 옮기지 마라. 근거는 ADR-009.
  `>` 인용 줄은 항목당 **한 문장까지만** 허용된다.
- 인용 표기는 `[Q{번호} p{쪽}]`. 쪽번호는 슬라이스의 `<!-- Q123 p456 -->` 주석에 있다.
- **덤프 해설이 실제 AWS 동작과 명백히 어긋나면 그대로 옮기지 마라.** 정확한 쪽으로 고쳐 싣고,
  파일 끝 "원본 수정 이력" 절에 덤프 원문과 함께 남겨라. 근거는 ADR-008의 예외 조항.
  이 예외는 **명백한 사실 오류에만** 쓴다. 네가 아는 AWS 지식으로 내용을 보강하는 데 쓰지 마라.
- `[AI 작성 해설]` 표시가 붙은 해설은 원본 덤프가 아니라 이 해설집이 새로 쓴 것이다.
  해설집 스스로 그중 6문항은 원본 정답이 AWS 기준과 어긋난다고 고지했다. 이 표시가 붙은 해설의
  사실은 다른 문항의 근거와 교차 확인되는 것만 채택하고, 아니면 "원본 수정 이력"에 남기고 넘어가라.
- 개념 id는 kebab-case로 짓는다.

### 문서 구조 — AC가 이 구조를 기계적으로 검사한다

```markdown
# 덤프 보충 개념 — Q301–Q350

## {기존 주제 id 또는 새 주제 이름}       <- 개념을 묶는 그룹. 백틱 없이 쓴다.
### `{concept-id}` — {한 줄 제목}         <- 개념 하나. 이 줄만 백틱으로 시작한다.
...
## 원본 수정 이력                         <- 파일 끝. 채택하지 않은 것을 남긴다.
### 사실 오류라 싣지 않은 것               <- 하위 절. 백틱으로 시작하지 마라.
### [AI 작성 해설]이라 채택하지 않은 것     <- 하위 절. 백틱으로 시작하지 마라.
```

**백틱으로 시작하는 `###` 줄은 개념 항목뿐이어야 한다.** 이유: AC가 `grep -c '^### \`'`로
개념 수를 세어 인용 수와 대조해 인용 누락을 잡는다. 메타 절 제목을 백틱으로 감싸면 개념으로
오인돼 AC가 깨진다. step 1이 실제로 이 이유로 실패했다.

### `_index.md` append — 잊지 마라

새로 만든 개념을 **전부** `docs/source/dump-gaps/_index.md` 끝에 한 줄씩 append하라.

```
- {concept-id} — {한 줄 제목} [Q301-Q350]
```

topicId는 적지 마라. 주제 배치는 phase 26에서 정한다. 이 파일이 비면 다음 step이 중복을
걸러낼 수 없어 phase 전체가 무너진다. AC가 줄 수 증가를 검사한다. step 1이 이걸 빠뜨려 실패했다.

## Acceptance Criteria

```bash
F=docs/source/dump-gaps/Q301-Q350.md
test -f "$F"
test "$(grep -c '^### `' "$F")" -ge 1                    # 항목이 하나 이상
test "$(grep -c '^### `' "$F")" = "$(grep -c '^> \[Q' "$F")"   # 모든 항목에 인용이 붙었다
# _index.md에 이번 범위로 등록된 줄 수 == 이번 파일의 개념 수
test "$(grep -c '\[Q301-Q350\]$' docs/source/dump-gaps/_index.md)" = "$(grep -c '^### `' "$F")"
npm run build && npm test                                # 회귀 없음
```

## 검증 절차

1. 위 AC 커맨드를 실행한다.
2. 새로 쓴 항목을 `concept-index.md`와 `_index.md`에 대조해 중복이 없는지 다시 확인한다.
3. 아키텍처 체크리스트를 확인한다:
   - ARCHITECTURE.md 디렉토리 구조를 따르는가?
   - ADR 기술 스택을 벗어나지 않았는가?
   - CLAUDE.md CRITICAL 규칙을 위반하지 않았는가?
4. 결과에 따라 `phases/25-dump-gaps/index.json`의 해당 step을 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"` (몇 개 개념을 뽑았는지 포함)
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- `src/` 아래를 건드리지 마라. 이유: 개념 데이터 반영은 phase 26이다. 이 phase는 출처 문서만 만든다.
- 이번 슬라이스 외의 `docs/source/dump-gaps/Q*.md`를 수정하지 마라.
  이유: step은 각자 자기 슬라이스만 책임진다. 남의 결과를 고치면 재실행이 불가능해진다.
- 덤프의 문제 전문이나 보기를 파일에 옮겨 적지 마라. 이유: ADR-009.
  이 phase가 만드는 것은 개념이지 문제가 아니다.
- 개념을 만들어내지 마라. 이번 슬라이스의 해설에 근거가 없으면 적지 않는다. 이유: ADR-006·008·021.
- 기존 테스트를 깨뜨리지 마라.
