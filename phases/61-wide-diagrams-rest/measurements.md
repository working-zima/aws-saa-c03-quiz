# phase 61 실측 기록 — 나머지 도식 24장의 가로형

측정일 2026-10-16. `feat-61-wide-diagrams-rest`(`22f818b`)의 `npm run build` 결과를 `vite preview`로 띄워 **Windows Chrome**에서 쟀다.
비교 대상은 develop(`68c3e56`, phase 60 병합)을 같은 방법으로 빌드해 따로 띄웠다. 폭은 같은 출처 iframe의 폭을 바꿔 쟀다(phase 60과 같다).
주제 12개(`#/topic/…`)를 차례로 열어 `svg[role=img]`가 든 `figure` 27개를 모두 쟀다.

- **표시 폭·높이**: `svg.getBoundingClientRect()`.
- **가장 빠듯한 여백**: 노드마다 `rect` 폭 − 노드 안 글줄의 `getComputedTextLength()` 가운데 가장 작은 값(`viewBox` 단위). 테스트의 기준은
  `estimateTextWidth + 12 <= 폭`이고, 실측 여백이 12 이상이면 실제 글꼴로도 들어간다.
- **가로 넘침**: iframe 문서의 `scrollWidth > clientWidth`.

## 세로형 무변경

390px iframe에서 27장의 `figure` `outerHTML`을 처음 상태와 시나리오 버튼(각 도식의 `전체` 포함)을 하나씩 누른 뒤마다 떠서 해시로 비교했다
(`useId`가 만드는 마커 id만 정규화). **156개 상태가 develop과 모두 같았다.**

## 글자 겹침

1440px에서 27장의 처음 상태와 시나리오마다(버튼을 하나씩 눌러), 보이는 `text`의 `getBBox()`끼리, 그리고 글자와 **다른** 노드의 `rect`가
0.5 이상 겹치는지, 글자가 `viewBox` 밖으로 나가는지 쟀다. **겹침 0건, 넘침 0건.** 판정이 겹침을 잡는지는 노드 위에 글자를 하나 얹어 확인했다.

## 실시간 전환 (phase 60에서 재지 못한 것)

탭이 보이는 상태(`visibilityState: visible`)에서 iframe 폭을 700 → 800 → 700px로 바꾸고, 바꿀 때마다 `requestAnimationFrame` 두 번을
기다렸다. 주제 12개의 도식 27장 모두에서 각 도식의 마지막 시나리오를 고른 채로 **`viewBox` 폭이 280 → 440 → 280으로 바뀌고, 눌린 버튼·보이는
경로·캡션이 세 시점에서 같았다.** `matchMedia('(min-width: 768px)')`의 `change`가 두 번 발생했다.

`setTimeout`만으로 기다리면 렌더링 단계가 돌기 전에 읽어 바뀌지 않은 것처럼 보인다. phase 60이 재지 못한 이유(탭이 hidden)와는 다르지만,
다시 잴 때는 프레임을 기다려야 한다.
